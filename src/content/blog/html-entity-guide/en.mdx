Every symbol in an HTML page can be written in up to four ways. The copyright sign can be typed as `©`, or written as the named reference `&copy;`, the decimal reference `&#169;` or the hexadecimal reference `&#xA9;`. All four give the same character. In a page saved as UTF-8 you can type most symbols directly, so references are needed in two cases: characters that HTML itself treats as markup, and characters that are hard to type, invisible or easy to confuse with something else.

The tables below list the symbols people look up most often. They are generated from two primary sources, not copied from other reference pages:

- the [WHATWG named character reference list](https://html.spec.whatwg.org/multipage/named-characters.html), as published in [entities.json](https://html.spec.whatwg.org/entities.json) (file last modified 12 November 2025). It has 2,231 entries: 2,125 names that end in a semicolon and 106 older names that also work without one.
- the [Unicode Character Database 18.0](https://www.unicode.org/Public/UCD/latest/ucd/), for the code points and the character names.

When a symbol has no name in the list, the table says "none". Those symbols still work, but only as numeric references or as the character itself.

## The five characters HTML needs escaped

Only five characters can change how HTML is parsed. Everything else is just text.

| Character | Why it matters | Write it as |
|---|---|---|
| `&` | Starts a character reference everywhere | `&amp;` |
| `<` | Starts a tag in text content | `&lt;` |
| `>` | Ends a tag; escaping it avoids confusion in hand-written markup | `&gt;` |
| `"` | Ends a double-quoted attribute value | `&quot;` |
| `'` | Ends a single-quoted attribute value | `&#39;` or `&apos;` |

The browser applies the same rule when it turns a DOM tree back into markup. The [HTML serialization algorithm](https://html.spec.whatwg.org/multipage/parsing.html#serialising-html-fragments) (what `innerHTML` returns) replaces `&`, `<`, `>` and the no-break space U+00A0 in text and in attribute values, and also `"` inside attribute values. It never writes any other named reference.

For text that comes from users or other systems, the [OWASP Cross Site Scripting Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html) recommends encoding all five, with `'` as `&#x27;`, so the same output is safe in text and in quoted attributes. This escaping covers HTML text and quoted attribute values only. JavaScript strings, URLs and CSS each have their own escaping rules.

Encoding the string `Tom's "Fish & Chips" <Special>` with the [HTML Entity Encoder / Decoder](/tools/html-entity/) gives:

{/* he-check: {"encode":"Tom's \"Fish & Chips\" <Special>","expect":"Tom&#39;s &quot;Fish &amp; Chips&quot; &lt;Special&gt;","count":6} */}

```text
Tom&#39;s &quot;Fish &amp; Chips&quot; &lt;Special&gt;
```

The status line reports "Encoded — 6 characters converted": one apostrophe, two double quotes, one ampersand and the two angle brackets.

## Named, decimal and hex references

A **named reference** is `&` + a name from the WHATWG list + `;`. Names are easier to read in source code than numbers, but they exist for only 1,446 single characters (plus 93 names that produce a pair of code points, covered below). Names are case-sensitive: `&Delta;` is Δ and `&delta;` is δ. `&COPY;` is a valid second name for ©, but `&Copy;` is not a name at all and stays as plain text.

A **decimal reference** is `&#` + the code point in base 10 + `;`. A **hexadecimal reference** is `&#x` + the code point in base 16 + `;`. The hex form matches the U+ notation used in character charts, so U+2713 CHECK MARK is `&#x2713;`, and the decimal form of the same character is `&#10003;`. Numeric references work for every Unicode character, including emoji: 😀 (U+1F600) is `&#128512;` or `&#x1F600;`.

Always end a reference with a semicolon. The 106 legacy names (`&copy`, `&amp`, `&lt`, `&nbsp`, `&frac12` and others) are still recognized without one, but the parser reports an error and applies the special rules shown in the parser section below.

## Symbols with several names, and names that make two characters

Most characters with names have only one, but some have many. ≈ ALMOST EQUAL TO has six: `&ap;`, `&approx;`, `&asymp;`, `&thickapprox;`, `&thkap;` and `&TildeTilde;`. → has five, and the zero-width space has five. A decoder accepts all of them. An encoder that writes names has to choose one, which is why two tools can give different output for the same input.

93 names produce two code points. They are mathematical symbols with a combining overlay. `&NotEqualTilde;` is U+2242 followed by U+0338 COMBINING LONG SOLIDUS OVERLAY (≂̸), and `&nvlt;` is `<` followed by U+20D2 COMBINING LONG VERTICAL LINE OVERLAY. If your code counts characters after decoding, these names count as two.

## Where the parser surprises you

The [HTML parser](https://html.spec.whatwg.org/multipage/parsing.html#named-character-reference-state) accepts the 106 legacy names without a semicolon, and it takes the longest name that matches. That creates a well-known bug with query strings in visible text:

{/* he-check: {"decode":"example.com/?lang=en&region=us","expect":"example.com/?lang=en®ion=us"} */}

```text
Source:  example.com/?lang=en&region=us
Shown:   example.com/?lang=en®ion=us
```

`&reg` is a legacy name for ®, so in text the parser replaces it even though no semicolon follows. Inside an attribute such as `href`, a legacy name followed by `=` or a letter or digit is left alone, so the link itself still works and only the visible text is wrong. Writing `&amp;region` fixes it in both places. The specification gives the same example: `I'm &notit; I tell you` displays as "I'm ¬it; I tell you", because `&not` is matched, while `&notin;` is a complete name for ∉.

Numeric references have their own rules ([numeric character reference end state](https://html.spec.whatwg.org/multipage/parsing.html#numeric-character-reference-end-state)):

- `&#128;` to `&#159;` do not give the C1 control characters. The parser maps them with the Windows-1252 table, because old pages written on Windows used these numbers for typographic characters. `&#150;` becomes – (en dash), `&#146;` becomes ’ and `&#128;` becomes €.
- `&#0;`, numbers above `&#x10FFFF;` and surrogates such as `&#xD83D;` become U+FFFD REPLACEMENT CHARACTER (�).
- An emoji must be written as one reference with its real code point. Encoders that loop over UTF-16 code units write two surrogate references instead, and each of them turns into �.

{/* he-check: {"decode":"&#150; &#146; &#128; &#xD83D;","expect":"– ’ € �"} */}

Double escaping is the other common fault. When text that is already escaped is escaped again, `&lt;` becomes `&amp;lt;`, and readers see the literal characters `&lt;` on the page. Escape once, at the point where the text is written into HTML, and store the raw text everywhere else.

## Checking symbols with the HTML Entity tool

The [HTML Entity Encoder / Decoder](/tools/html-entity/) runs in your browser and does two things:

- **Encode** writes the five markup characters as `&amp;`, `&lt;`, `&gt;`, `&quot;` and `&#39;`, and every character above U+007F as a decimal reference, one reference per code point. It never writes named references, so use the tables above when you want a name.
- **Decode** gives the input to the browser's own HTML parser, so it follows every rule in the previous section, including legacy names without a semicolon and the Windows-1252 mapping.

For example, the text `Early bird: 5 € — “save 20%” ✓` encodes to:

{/* he-check: {"encode":"Early bird: 5 € — “save 20%” ✓","expect":"Early bird: 5 &#8364; &#8212; &#8220;save 20%&#8221; &#10003;","count":5} */}

```text
Early bird: 5 &#8364; &#8212; &#8220;save 20%&#8221; &#10003;
```

The output is pure ASCII, which helps when a template system or mail gateway does not handle UTF-8 correctly. In a UTF-8 page you only need the first five characters escaped, and the rest can stay as typed. If you paste `example.com/?lang=en&region=us` into the input and click **Decode**, you will see the ® from the previous section appear.

## Escaping text in templates and scripts

Most template engines escape text for you. Vue's [text interpolation](https://vuejs.org/guide/essentials/template-syntax.html#text-interpolation) (`{{ }}`) inserts data as plain text, and in the browser, setting `textContent` instead of `innerHTML` never creates markup. When you write the escaping yourself, use the standard library function of your language.

Python's [`html.escape`](https://docs.python.org/3/library/html.html#html.escape) escapes the five characters by default (`quote=True`), with `'` as `&#x27;`:

```python
import html

html.escape("Tom's \"Fish & Chips\" <Special>")
# 'Tom&#x27;s &quot;Fish &amp; Chips&quot; &lt;Special&gt;'

html.unescape("&copy; 2026 &mdash; &#x2713;")
# '© 2026 — ✓'
```

In PHP, [`htmlspecialchars`](https://www.php.net/manual/en/function.htmlspecialchars.php) uses `ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML401` by default since PHP 8.1.0, so single quotes become `&#039;`. Before 8.1 the default was `ENT_COMPAT`, which left single quotes unescaped. Pass the flags explicitly if your code may run on older versions.

JavaScript has no built-in escape function. A replacement function must replace `&` first, otherwise it escapes its own output:

```javascript
const escapeHtml = (s) => s
  .replaceAll('&', '&amp;')
  .replaceAll('<', '&lt;')
  .replaceAll('>', '&gt;')
  .replaceAll('"', '&quot;')
  .replaceAll("'", '&#39;');

escapeHtml('AT&T <b>"ok"</b>'); // 'AT&amp;T &lt;b&gt;&quot;ok&quot;&lt;/b&gt;'
```

None of these functions turns © or → into names. In UTF-8 output that is correct: the character itself is valid HTML. Use the named or numeric codes from the tables when you write markup by hand, when the character is invisible, or when you need to tell look-alike characters apart in the source.
