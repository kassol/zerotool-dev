コーディングエージェントがタスクを終えた。マイグレーションを書いて実行し、`dev.db` にフィクスチャを流し込んだ。サマリーには「`orders.status` を追加しデフォルト `'pending'` を設定、3,200行をバックフィルした」とある。信じる前に自分の目で確かめたい。ORMが自分の手で書いていないマイグレーションを生成したときも、モバイルアプリがテスト端末上でローカルDBに書き込み、画面が空白になる原因を調べるためにファイルを取り出したときも、同じことが起きる。

手っ取り早いのは行データをAIチャットに貼り付けて「何が起きたか」を聞くことだ。だが実運用に近いデータベースの大半でそれはやってはいけない。ステージングからコピーした `dev.db` には顧客のメールアドレスが入っている。モバイルアプリのDBにはセッショントークンが、CLIの状態ファイルにはAPIキーが眠っている。ファイルはすでにある場所で、人間の目で読む必要がある。

[SQLiteビューアでdbファイルを開く →](/ja/tools/sqlite-viewer/)

このビューアはブラウザのタブの中でファイルを開く。テーブル、ビュー、列、インデックス、`CREATE` 文を表示し、行をページ送りで閲覧でき、入力したSQLをそのまま実行し、CSVでエクスポートできる。何もアップロードされず、ツールページはアナリティクスも広告スクリプトも読み込まない。このガイドの残りでは、SQLiteファイルの中身、ビューアがそれをどう読むか、そしてファイルが期待どおりに見えないケースを説明する。

## ブラウザのSQLiteビューアが向いている場面

| 状況 | 何を確認するか | ブラウザ版ビューアが向いている理由 |
|------|----------------|------------------------------------|
| エージェントやスクリプトがマイグレーションを実行した | 新しい列、デフォルト値、バックフィルされた値、新しいインデックス | ファイルを開いて構造パネルを読み、`SELECT` を1回実行してタブを閉じるだけで済む |
| ORMのマイグレーションレビュー | SQLiteが実際に保存した `CREATE TABLE`（モデル定義とずれることがある） | ビューアは保存されている `CREATE` 文をそのまま表示する |
| モバイルアプリのローカルDB | アプリがテスト端末に書き込んだ行 | デスクトップクライアントのインストール不要。ファイルは手元のマシンに置いたまま |
| Electronアプリ・CLIの状態管理 | 設定、キャッシュ、キューテーブル | 多くのデスクトップアプリやCLIは、状態を単一のSQLiteファイルに保持している |
| テストフィクスチャの確認 | リポジトリにコミットされたフィクスチャDB | テストが前提とする内容が、フィクスチャに実際に入っているか確認できる |
| 同僚へのデータ受け渡し | データベース全体ではなく1件のクエリ結果 | クエリを実行し、CSVをエクスポートして送るだけ |
| 本番実行前に文を試す | `UPDATE` や `DELETE` の影響範囲 | SQLはメモリ上のコピーに対して実行され、ディスク上のファイルは変わらない |
| Next.js/RailsのローカルSQLite確認 | Prisma や ActiveRecord がプロトタイプ用に書き込んだ `dev.sqlite3` の中身 | ORMのマイグレーション結果を、コマンドを叩かずその場で確認できる |

ファイルをその場で編集したい場合、非常に大きいファイル、暗号化されたデータベースの場合はローカルのツールを使う。以下のセクションで理由と、それぞれに適したツールを説明する。

## SQLiteファイルの中身

SQLiteのデータベースは、ごく普通の1つのファイルだ。フォーマットの全容は [SQLite Database File Format](https://www.sqlite.org/fileformat.html) ページに文書化されており、そこに書かれたいくつかの事実だけで、ビューアがやっていることの大半を説明できる。

### 先頭100バイトのヘッダー

すべてのデータベースファイルの先頭100バイトはファイルヘッダーだ。先頭16バイトは固定されている。

```text
53 51 4c 69 74 65 20 66 6f 72 6d 61 74 20 33 00
S  Q  L  i  t  e     f  o  r  m  a  t     3  \0
```

これはUTF-8文字列 `SQLite format 3` の後にnulバイトが続いたものだ。この16バイトで始まらないファイルは、素のSQLite 3データベースではない。拡張子は何の手がかりにもならない。`.db`、`.sqlite`、`.sqlite3`、`.db3` はどれもよく使われるし、`.db` という拡張子でも中身は別物ということは珍しくない。

ファイルの挙動がおかしいときに役立つ、その他のヘッダーフィールドは次のとおり。

| オフセット | サイズ | フィールド |
|------------|--------|-----------|
| 16 | 2 bytes | ページサイズ（ビッグエンディアン） |
| 18 | 1 byte | ファイルフォーマットの書き込みバージョン |
| 19 | 1 byte | ファイルフォーマットの読み込みバージョン |
| 40 | 4 bytes | スキーマクッキー（スキーマが変更されるたびに増加） |
| 56 | 4 bytes | テキストエンコーディング |
| 60 | 4 bytes | ユーザーバージョン（アプリがマイグレーションカウンタとして使うことが多い） |
| 68 | 4 bytes | アプリケーションID |
| 96 | 4 bytes | 最後にファイルを書き込んだSQLiteライブラリのバージョン番号 |

ページサイズは2の累乗になる。3.7.0.1までのバージョンでは512〜32,768バイトが許容されていた。SQLite 3.7.1（2010年）で65,536バイトのページが追加されたが、65,536は2バイトに収まらないため、値 `1` として格納される。ロールバックジャーナル方式のデータベースではバイト18と19が両方とも `1`、WAL方式では両方とも `2` になる。つまりファイルを開かなくても、そのジャーナルモードを見分けられる。

### スキーマテーブル

ファイルの1ページ目は `sqlite_schema` というテーブルのルートになっている。古いコードやほとんどのチュートリアルでは `sqlite_master` と呼んでおり、こちらも今なお有効なエイリアスだ。列は `type`、`name`、`tbl_name`、`rootpage`、`sql` の5つ。すべてのテーブル、インデックス、ビュー、トリガーがそれぞれ1行を持ち、`sql` 列には元の `CREATE` 文のテキストがそのまま入っている。

`sqlite_` で始まる名前は、SQLiteが内部用に自分で作成するオブジェクトだ。`AUTOINCREMENT` のカウンタ用の `sqlite_sequence` や、クエリプランナの統計情報用の `sqlite_stat1` などがそれにあたる。アプリケーション側でこのプレフィックスを持つオブジェクトを作成することはできない。

## ビューアがファイルを読み込む仕組み

ファイルをドロップしてからテーブル一覧が表示されるまでに、順を追って何が起きているかを説明する。

**1. サイズチェック。** 100MBを超えるファイルは、1バイトも読まれる前に拒否される。理由はメモリだ。ファイルはディスクから読み込んだバッファとして1つ、SQLiteエンジン内部でもう1つ、計2つ保持される。大きなデータベースを2つ抱えると、ブラウザのタブが不安定になる。

**2. ヘッダーチェック。** ビューアはFile APIで先頭100バイトだけを読み込み、先頭16バイトを `SQLite format 3\0` と比較する。ファイルが100バイト未満だったり、バイト列が一致しなかったりすると「Not a SQLite 3 database」というエラーになる。ファイルの拡張子は一切信用しない。

**3. エンジンの読み込み。** ヘッダーチェックを通過して初めて、ページはSQLiteエンジンを取得しにいく。エンジンは [sql.js](https://github.com/sql-js/sql.js) 1.14.2で、SQLite 3.49.1をWebAssemblyにコンパイルしたものだ。2つのファイルは圧縮して合計約340KBで、ブラウザは一度だけこれを取得する。誤ったファイル、PNG、CSVではこのダウンロードは発生しない。

**4. メモリ上でオープン。** ファイル全体が `Uint8Array` に読み込まれ、`new SQL.Database(bytes)` に渡される。sql.jsはそのデータベースを仮想的なメモリ上のファイルシステムに保持する。以降、すべてのクエリはこのコピーに対して実行される。

**5. オブジェクト一覧。** ビューアは `sqlite_master` に対してテーブルとビューを問い合わせる。内部の `sqlite_%` オブジェクトは一覧からは隠されるが、SQLエディタから直接クエリすることはできる。各テーブルには `COUNT(*)` が付く。ビューは件数なしで一覧に出る。

**6. 構造。** テーブルまたはビューを選択すると、ビューアはテーブル値関数形式のPRAGMAを実行する。

```sql
SELECT name, type, "notnull", dflt_value, pk FROM pragma_table_info(?);
SELECT name, "unique", origin FROM pragma_index_list(?);
SELECT name FROM pragma_index_info(?) ORDER BY seqno;
```

これらのPRAGMAのテーブル値形式は、SQLite 3.16.0（2017年）以降で利用できる。構造パネルには各列の名前、宣言された型、`NOT NULL`、デフォルト値、主キーの位置が表示される。インデックスパネルには名前、対象列、一意性、originが表示される。originは `CREATE INDEX` で作られたインデックスなら `c`、`UNIQUE` 制約由来なら `u`、`PRIMARY KEY` 制約由来なら `pk` になる。インデックスのエントリがrowidや式の場合、`pragma_index_info` は列名として `NULL` を返すが、ビューアはそうしたエントリを `(expr)` と表示する。インデックスの下には、スキーマテーブルに格納されているとおりの `CREATE` 文が表示される。

**7. 行データ。** データグリッドは `LIMIT 100 OFFSET n` で、テーブルを100行ずつページングする。範囲を示す行には「Rows 101–200 of 3,200」のように表示され、常に今どこを見ているかがわかる。

ビューアがSQLに埋め込むテーブル名・列名はすべて二重引用符で囲まれ、名前の中に二重引用符が含まれる場合は二重にエスケープされる。`order`、`user data`、`"quoted"` といった名前のテーブルや、非ラテン文字の名前も問題なく開ける。

### 「アップロードしない」の意味

ファイルはFile APIを通じて、ディスクからページのメモリへ直接渡される。このツールが発生させるネットワークリクエストは、エンジンファイルの取得のみで、しかも同じサイト内の静的ファイルだ。入力がプライベートなデータベースであることを踏まえ、このツールページはサイトのアナリティクスや広告スクリプトの読み込みもスキップするよう設定されている。タブを閉じるかリロードすれば、メモリ上のコピーは消える。

## SQLiteの値は、列の型が示すものとは限らない

SQLiteファイルを読んでいて混乱する原因の多くは、その型システムにある。詳細は [Datatypes In SQLite](https://www.sqlite.org/datatype3.html) ページに書かれているが、要点だけ言うとこうなる。

- 値は5つの**ストレージクラス**（`NULL`、`INTEGER`、`REAL`、`TEXT`、`BLOB`）のいずれかを持つ。
- SQLiteは動的型付けを採用している。**型は列ではなく値に属する。**
- 列に宣言された型が決めるのは**affinity（親和性）**（`TEXT`、`NUMERIC`、`INTEGER`、`REAL`、`BLOB`）だけで、SQLiteは可能な場合これを使って挿入時に値を変換する。

affinityは、宣言された型名に対する部分文字列マッチのルールで決まる。`INT` を含む型はINTEGER affinityになる。`CHAR`、`CLOB`、`TEXT` を含む型はTEXT affinityになるので、`VARCHAR(255)` はTEXT扱いになり255は無視される。`BLOB`、あるいは型を宣言しなければBLOB affinity。`REAL`、`FLOA`、`DOUB` はREAL。それ以外はすべてNUMERICになる。

実際には、`INTEGER` と宣言された列にも、何かがそう書き込めば文字列 `'n/a'` がそのまま入ってしまう、ということだ。`created_at DATETIME` と宣言したORMが、ある行ではISO-8601形式のテキストを、別の行ではUnixタイムスタンプを格納していることもある。SQLiteには日付型もboolean型も存在しない。日付はTEXT、REAL（ユリウス日）、INTEGER（Unix時間）のいずれかで、booleanは整数の `0` と `1` で表現される。

ビューアは宣言された列の型ではなく、実際に返ってきた値そのものからセルを描画する。

| 値 | グリッド上の表示 | CSVエクスポート |
|-----|------------------|------------------|
| `NULL` | 薄いグレーの `NULL` マーカー | 空フィールド |
| 空文字列 `''` | 空セル | 空フィールド |
| 数値（INTEGERまたはREAL） | 右揃え | 格納されている値のまま |
| テキスト | テキストとして表示。長いテキストはセル内で省略 | 必要に応じて引用符付きの全文 |
| BLOB | `BLOB · 4 B · 89504E47`（バイト長と先頭16バイトの16進表記） | 大文字16進の全内容 |

列の中身がおかしいと感じたら、SQLiteに直接何が入っているか聞いてみる。

```sql
SELECT typeof(created_at) AS storage_class, COUNT(*)
FROM orders
GROUP BY 1;
```

これで `text` と `integer` が両方返ってきたら、2つの異なるコードパスが違うフォーマットでその列に書き込んでいることになる。SQLite 3.37.0（2021年）で追加された `STRICT` テーブルは、列の型として `INT`、`INTEGER`、`REAL`、`TEXT`、`BLOB`、`ANY` のみを許可し、型が合わない値を拒否する。格納されている `CREATE` 文が `STRICT` で終わっていれば、そのテーブルで型混在の問題は起こりえない。

## メモリ上のコピーに対してSQLを実行する

データグリッドの下にあるエディタは、SQLite 3.49.1が解釈できるSQLをそのまま受け付ける。**Run SQL** を押すか、Ctrl/Cmd + Enterを使う。

- **複数文をまとめて実行できる。** エディタ内のすべての文が順番に実行される。結果グリッドには、`SELECT` や `UPDATE ... RETURNING` のように列を返す最後の文の結果が表示される。
- **エラーはSQLite自身のもの。** タイプミスをすると、`near "SELEC": syntax error` のようなSQLite本来のメッセージがステータス行に出る。前回の結果はクリアされるので、新しい結果と取り違えることはない。
- **データを変更する文** は「Done. N row(s) changed in the in-memory copy.」と報告する。件数は実行前後の `total_changes()` の差分から求めている。
- **スキーマの変更は自動的に反映される。** 実行によってデータやスキーマバージョンが変わると、テーブル一覧は再読み込みされる。直前に実行した `CREATE TABLE` は一覧に現れ、`INSERT` や `DELETE` の後は行数も更新される。
- **大きな結果セット。** ページの反応速度を保つため、グリッドは最初の1,000行だけを描画し、その旨も表示する。**Export CSV** は常に結果の全行を書き出す。

見知らぬデータベースを調べるときに役立つクエリをいくつか挙げる。

```sql
-- インデックスやトリガーも含め、すべてのオブジェクトとそのCREATE文
SELECT type, name, tbl_name, sql FROM sqlite_master ORDER BY type, name;

-- 多くのアプリがヘッダーに保持しているマイグレーションカウンタ
PRAGMA user_version;

-- テーブルに宣言された外部キー
SELECT * FROM pragma_foreign_key_list('orders');

-- ファイルの破損チェック
PRAGMA integrity_check;
```

### 書き込みはメモリ内にとどまる

ブラウザは選択したファイルへの書き込み権限を持たない。エンジンはメモリ上のコピーに対して動作するので、`INSERT`、`UPDATE`、`DELETE`、`CREATE`、`DROP` はすべて実行され、ビューアはその結果を表示するが、ディスク上のファイルは元のまま変わらない。ページをリロードしたり別のファイルを開いたりすると、変更は消える。編集後のコピーをダウンロードするオプションはツールにない。

これにより、本番で実行する前に文を試す安全な場所としてエディタを使える。例えば、クリーンアップが何行に影響するかを確認してから、残る行を見てみる。

```sql
DELETE FROM sessions WHERE expires_at < unixepoch();
SELECT COUNT(*) AS remaining FROM sessions;
```

カスケード削除をテストするなら、1つ気をつけたいことがある。新しいSQLite接続では、アプリケーションが明示的に有効化しない限り外部キー制約はオフになっており、これはビューアでも同じだ。テストで `ON DELETE CASCADE` を発火させたいなら、先に `PRAGMA foreign_keys = ON;` を実行しておく。

実際のファイルを変更したい場合は、手元のマシンで `sqlite3` コマンドラインシェルか DB Browser for SQLite を使う。

## CSVのエクスポート

**Export CSV** ボタンは2箇所にある。データグリッドの上にあるものは、選択中のテーブルまたはビューを、現在のページだけでなく全行エクスポートする。SQLエディタの下にあるものは、直前のクエリ結果を丸ごとエクスポートする。

出力はRFC 4180に準拠する。区切り文字はカンマ、改行はCRLF、先頭行に列名のヘッダー行があり、フィールドにカンマ・二重引用符・CR・LFが含まれる場合は `"` で囲まれる。フィールド内の二重引用符は二重化される。ファイル名はテーブル名から生成され、英数字と `.`、`_`、`-` 以外の文字は `_` に置き換わる。クエリ結果の場合は `query.csv` になる。

CSVという形式であることから生じる、2つの帰結がある。

- `NULL` と空文字列は、どちらも空フィールドになる。この違いが重要なら、エクスポート前にクエリで `COALESCE(col, '<null>')` や `col IS NULL AS col_is_null` を選択しておく。
- BLOBは大文字の16進表記になる。4バイトのPNGシグネチャは `89504E47` としてエクスポートされる。これによりCSVは正当なテキストのまま保たれ、たいていの言語では、Pythonの `bytes.fromhex()` のような1回の呼び出しでデコードし直せる。

同僚にデータを渡すときは、相手が必要とするクエリ結果だけをエクスポートすればいい。データベースファイル自体は手元に残る。

## 落とし穴とエッジケース

### 最近の行が見当たらない：WALファイル

これがもっともよくある驚きの原因だ。[Write-Ahead Logging](https://www.sqlite.org/wal.html) ページで説明されているWALモードでは、SQLiteはコミット済みの変更をすぐにはメインのデータベースファイルへ書き込まない。データベース名に `-wal` サフィックスを付けた別ファイルへ追記し、`-shm` というインデックスファイルも一緒に使う。**チェックポイント** によって、トランザクションはWALからメインファイルへ書き戻される。デフォルトでは、WALが1,000ページに達すると自動的にチェックポイントが走り、最後の接続が閉じられるとWALは通常削除される。

つまり、実行中のアプリから `app.db` をコピーしたり、アプリを開いたままスマホから引き抜いたりすると、最新のトランザクションがまだ `app.db-wal` の中に残っていることがある。ビューアはメインファイルしか読まないので、その行はそこには存在しない。SQLiteの公式ドキュメントも、データベースファイルをWALから切り離すと、コミット済みのトランザクションが失われたり、データベースが破損したりすると警告している。

ヘッダーのバイト18と19を見れば、そのファイルがWALを使っているかどうかがわかる（両方 `2` ならWAL）。WALをメインファイルに統合するには、書き込んでいるアプリケーションを閉じてから、次を実行する。

```bash
sqlite3 app.db "PRAGMA wal_checkpoint(TRUNCATE);"
```

`TRUNCATE` はすべてのフレームをチェックポイントしたうえで、WALファイルを0バイトに切り詰める。そのあとで改めて `app.db` を開く。ロールバックモードのデータベースに残った `-journal` ファイルについても同様だ。ビューアはメインファイルしか読まないので、まずは所有元のアプリケーションか `sqlite3` シェルにデータベースを開かせるとよい。

### データベースだとわかっているのに「Not a SQLite 3 database」と出る

このエラーが出るのは暗号化されたデータベースだ。[SQLCipher](https://www.zetetic.net/sqlcipher/design/) は先頭16バイトにランダムなソルトを格納し、残りを暗号化するため、ファイル全体がランダムなデータのように見え、`SQLite format 3` ヘッダーは消えている。SQLite Encryption Extension（SEE）もファイルを暗号化する。ビューアは暗号化されたデータベースを開けない。`sqlcipher` シェルで復号するか、SQLCipherファイルに対応した [DB Browser for SQLite](https://sqlitebrowser.org/) でファイルを開く。

同じエラーは、`.db` という名前でも中身が別物のファイルや、途中で切れたコピーでも出る。先頭バイトは `head -c 16 app.db | xxd` で確認できる。

### ファイルが100MBを超えている

この上限が固定なのは、開いている間データベースがメモリ上に2つ保持されるためだ。もっと大きいファイルを扱うなら、ローカルで `sqlite3 app.db` を実行するか、先に小さな抜粋を作る。

```bash
sqlite3 big.db "ATTACH 'small.db' AS s; CREATE TABLE s.orders AS SELECT * FROM orders WHERE created_at >= '2026-09-01';"
```

そのあと `small.db` をビューアで開く。

### テーブルが行の代わりにエラーを表示する

SQLiteのコアに含まれないコードを必要とするテーブルもある。SpatiaLiteのジオメトリテーブル、`sqlite-vec` のベクトルテーブル、FTS5の全文検索インデックス、R-Treeの空間インデックスといった仮想テーブルは、作成元のアプリケーションに組み込まれたモジュールに依存する。ビューアが使っているsql.js 1.14.2ビルドには `fts5` や `rtree` モジュールが含まれておらず、そうしたテーブルへのクエリは `no such module: fts5` のような、SQLite自身のエラーを返す。

こうしたテーブルの行数取得が失敗すると、一覧には `—` が表示され、データペインにはエラーが表示される。データベースの残りの部分は問題なく閲覧できる。FTS5は普通の「シャドウ」テーブル（例えば `notes_fts_content`）にもデータを保持しており、そちらは通常のテーブルとして読める。

### 何にも一致しないクエリ

0件しかヒットしない `SELECT` でも、列ヘッダーはちゃんと表示され、ステータス行には「0 row(s)」と出る。これはクエリ自体は実行され、列名も正しいことを意味するので、疑うべきは `WHERE` 句だ。`SELECT COUNT(*) ... WHERE ...` なら常に1行返るので、答えがはっきりする。

### 長いテキストと横に広いテーブル

セルの幅には上限があり、長いテキストは省略記号で切られる。60文字を超えるテキストは、ホバーすると先頭最大2,000文字をツールチップで確認できる。列に格納された完全なJSONドキュメントを読みたいときは、その値だけを選択してCSVとしてエクスポートするか、クエリの中で `json_extract()` を使って必要な部分だけ取り出す。

### 稼働中のデータベースを安全にコピーする

アプリケーションが書き込んでいる最中に `cp` でファイルをコピーすると、中途半端な（破損した）コピーになることがある。SQLite 3.15.0から使える `VACUUM INTO` は、トランザクション的に一貫性のあるスナップショットを新しいファイルへ書き出し、元のファイルには触れない。スナップショットは、WALのコミット済み内容も含んだ単一のファイルになる。

```bash
sqlite3 app.db "VACUUM INTO 'snapshot.db'"
```

## コード例

### Python: ヘッダーを確認してから、読み取り専用でカウントする

標準ライブラリの `sqlite3` モジュールは、URIを使ってファイルを読み取り専用で開ける。このスクリプトは、ビューアと同じ方法でヘッダーを確認し、ページサイズとジャーナルモードを表示したうえで、各テーブルの行数を一覧表示する。

```python
import sqlite3
import sys

path = sys.argv[1]
with open(path, "rb") as f:
    header = f.read(100)

if len(header) < 100 or header[:16] != b"SQLite format 3\x00":
    sys.exit(f"{path}: no SQLite 3 header (encrypted, truncated, or not a database)")

page_size = int.from_bytes(header[16:18], "big")
if page_size == 1:
    page_size = 65536                      # 1は64KiBページを表すマジックナンバー
journal = "WAL" if header[18] == 2 else "rollback"
print(f"page size: {page_size}  journal mode: {journal}")

con = sqlite3.connect(f"file:{path}?mode=ro", uri=True)   # 読み取り専用
tables = con.execute(
    "SELECT name FROM sqlite_master WHERE type = 'table' "
    "AND name NOT LIKE 'sqlite\\_%' ESCAPE '\\' ORDER BY name"
).fetchall()
for (name,) in tables:
    quoted = '"' + name.replace('"', '""') + '"'
    count = con.execute(f"SELECT COUNT(*) FROM {quoted}").fetchone()[0]
    print(f"{name:<32}{count:>10}")
con.close()
```

### JavaScript: Node.jsでも同じエンジンを使う

sql.jsはNode.js上でも動く。これはブラウザ版のツールと同じモデルだ。ファイルはメモリに読み込まれ、書き込みはそのコピーだけを変更する。

```js
import { readFileSync } from "node:fs";
import initSqlJs from "sql.js";

const bytes = readFileSync(process.argv[2]);
const SQL = await initSqlJs();
const db = new SQL.Database(bytes);          // ファイルのメモリ上コピー

const [schema] = db.exec(
  "SELECT type, name FROM sqlite_master WHERE type IN ('table', 'view') ORDER BY name"
);
for (const [type, name] of schema?.values ?? []) console.log(type.padEnd(6), name);

// 書き込みはコピーのみを変更する。ディスク上のファイルは変更されない。
db.run("DELETE FROM users WHERE email LIKE ?", ["%@example.com"]);
console.log("rows deleted in memory:", db.getRowsModified());

// 変更後のデータベースを保持したい場合、db.export() がUint8Arrayとして返す。
db.close();
```

### Bash: ビューア用にファイルを準備し、CLIからエクスポートする

```bash
# 未反映のWALトランザクションをメインファイルへ統合する（先に書き込み元のアプリを閉じる）
sqlite3 app.db "PRAGMA wal_checkpoint(TRUNCATE);"

# あるいは、一貫性のある単一ファイルのスナップショットを取り、元のファイルには触れない
sqlite3 app.db "VACUUM INTO 'snapshot.db'"

# どこかで開く前にヘッダーを確認する
head -c 16 snapshot.db | xxd

# シェルからCSVエクスポート。hex()を使うとビューアと同様、BLOBをテキストとして保持できる
sqlite3 -header -csv snapshot.db \
  "SELECT id, email, hex(avatar) AS avatar FROM users LIMIT 100" > users.csv
```

この `hex()` 呼び出しが重要だ。`sqlite3` シェルはBLOB列を生バイトのままCSVに書き出すため、たいていのCSVリーダーにとってファイルが壊れてしまう。

## 他のSQLiteツールとの比較

それぞれのツールは、異なる用途にはまる。

| ツール | 実行環境 | 読めるもの | ファイルへの書き込み | 暗号化ファイル |
|--------|----------|------------|----------------------|-----------------|
| ZeroTool SQLite Viewer | ブラウザのタブ、インストール不要 | 100MBまでの単一ファイル | しない。変更はメモリ上のコピー内にとどまる | 非対応 |
| `sqlite3` コマンドラインシェル | ローカルのターミナル | WALを含む、ローカルディスク上のファイル | する | 非対応（`sqlcipher` シェルを使う） |
| DB Browser for SQLite | Windows・macOS・Linux向けデスクトップアプリ、オープンソース | ローカルディスク上のファイル | する | 対応（SQLCipher） |

`sqlite3` シェルはリファレンス的な存在だ。ファイルをその場で開け、自身にサイズ上限はなく、WALも読め、スクリプトとの相性もいい。見るだけでいいときは `sqlite3 -readonly app.db` を使う。難点は、ドットコマンドを覚えている必要があることと、横に広いテーブルをターミナルで読まなければならないことだ。

DB Browser for SQLiteは本格的なデスクトップエディタだ。テーブルの作成・変更、グリッド上でのセル編集、SQLCipher暗号化の付け外しができる。ファイルそのものを変更したいときに使う。

ブラウザのビューアは、さっと中身を見るためのものだ。構造パネル、ページングされた行、SQLエディタ、CSVエクスポートを、インストールもアカウントもアップロードもなしで使える。仕組みとしてファイルに対して読み取り専用なので、調べている最中にデータベースを壊す心配がない。
