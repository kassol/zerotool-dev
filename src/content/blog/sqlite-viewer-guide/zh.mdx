一个写代码的 AI agent 刚完成一个任务：写了一条迁移、跑通、给 `dev.db` 灌了测试数据。它的总结里写着"给 `orders.status` 加了默认值 `'pending'`，回填了 3200 行"。在信它之前，你想亲眼确认一遍。ORM 自动生成了一条你没有手写的迁移时，会遇到同样的问题；移动端 App 在测试设备上写本地数据库、某个页面突然空白，把文件导出来排查原因，也是同一件事。

最省事的做法是把数据粘进 AI 对话框问它哪里出了问题。对大多数真实数据库来说，不能这么干。从预发环境拷贝出来的 `dev.db` 里有客户邮箱，移动 App 的数据库里有 session token，CLI 工具的状态文件里有 API key。这份文件需要留在它本来所在的机器上，由人亲自打开看。

[在 SQLite 查看器中打开文件 →](/zh/tools/sqlite-viewer/)

这个 SQLite 查看器直接在浏览器标签页里打开文件：列出表、视图、字段、索引和 `CREATE` 语句，分页翻行、执行你输入的任意 SQL，支持导出 CSV。说到底，这就是「在线打开 db 文件」看一眼——不用装桌面软件，不用担心数据外泄。全程不上传，工具页也不加载统计和广告脚本。下文讲清楚 SQLite 文件内部是什么结构、查看器怎么读它，以及哪些情况下文件不会显示你预期的内容。

## 什么时候该用浏览器端 SQLite 查看器

| 场景 | 你要检查什么 | 为什么浏览器端查看器合适 |
|------|--------------|--------------------------|
| agent 或脚本跑了一条迁移 | 新增字段、默认值、回填的数据、新索引 | 打开文件，看一眼结构面板，跑一条 `SELECT`，关掉标签页 |
| ORM 迁移复核 | SQLite 实际存下的 `CREATE TABLE` 语句，可能和模型定义不一致 | 查看器原样显示存储的 `CREATE` 语句 |
| 移动 App 本地数据库 | App 在测试设备上写入的行，比如 Android Room 生成的 `.db`，或 iOS Core Data 的 `.sqlite` 存储 | 不用装桌面客户端，文件留在你自己机器上 |
| Electron 应用或 CLI 的状态文件 | 配置项、缓存、队列表 | 很多桌面应用和 CLI 都把状态存进单个 SQLite 文件 |
| 测试夹具核对 | 提交进仓库的 fixture 数据库 | 确认夹具里的数据和测试假设的一致 |
| 把数据给同事 | 一次查询的结果，不是整个数据库 | 跑查询、导出 CSV、把 CSV 发过去 |
| 正式执行前先试一条语句 | `UPDATE` 或 `DELETE` 的影响范围 | SQL 跑在内存副本上，磁盘上的文件不会变 |

要原地编辑文件、处理超大文件或加密数据库，用本地工具。后面几节会说明原因，并给出每种场景对应的工具。

## SQLite 文件内部是什么

SQLite 数据库就是一个普通文件。格式在 [SQLite Database File Format](https://www.sqlite.org/fileformat.html) 页面里有完整记录，其中几个事实就能解释查看器大部分行为。

### 100 字节的文件头

每个数据库文件的前 100 字节是文件头，其中前 16 字节固定不变：

```text
53 51 4c 69 74 65 20 66 6f 72 6d 61 74 20 33 00
S  Q  L  i  t  e     f  o  r  m  a  t     3  \0
```

这是 UTF-8 字符串 `SQLite format 3` 加一个 nul 字节。不是以这 16 字节开头的文件，就不是纯粹的 SQLite 3 数据库。扩展名说明不了任何问题：`.db`、`.sqlite`、`.sqlite3`、`.db3` 都很常见，大量 `.db` 文件其实是别的东西。

文件行为异常时，文件头里这几个字段还有用：

| 偏移量 | 大小 | 字段 |
|--------|------|------|
| 16 | 2 字节 | 页大小（大端序） |
| 18 | 1 字节 | 文件格式写版本 |
| 19 | 1 字节 | 文件格式读版本 |
| 40 | 4 字节 | schema cookie（每次 schema 变化都会递增） |
| 56 | 4 字节 | 文本编码 |
| 60 | 4 字节 | user version（应用常用它当迁移计数器） |
| 68 | 4 字节 | application ID |
| 96 | 4 字节 | 最后写入这个文件的 SQLite 库版本号 |

页大小是 2 的幂。3.7.0.1 及之前的版本允许 512 到 32768 字节；SQLite 3.7.1（2010 年）加入了 65536 字节的页。因为 65536 放不进两个字节，就用值 `1` 表示。回滚日志（rollback-journal）模式的数据库里，第 18、19 字节都是 `1`；WAL 模式下都是 `2`。不用打开文件也能看出日志模式。

### schema 表

文件的第 1 页是一张叫 `sqlite_schema` 的表的根页。老代码和大多数教程管它叫 `sqlite_master`，这个别名现在依然有效。它有五个字段：`type`、`name`、`tbl_name`、`rootpage`、`sql`。每个表、索引、视图和触发器各占一行，`sql` 字段存的是原始 `CREATE` 语句文本。

以 `sqlite_` 开头的名字是 SQLite 给自己用的内部对象，比如给 `AUTOINCREMENT` 计数器用的 `sqlite_sequence`，或者给查询规划器统计信息用的 `sqlite_stat1`。应用层不能创建这个前缀的对象。

## 查看器怎么读你的文件

从你拖进文件到列出表清单，中间按顺序发生了这些事。

**1. 体积检查。** 超过 100 MB 的文件在读取任何字节之前就会被拒绝。原因是内存：文件会被同时持有两份——一份是从磁盘读出的 buffer，一份在 SQLite 引擎内部。大数据库存两份，浏览器标签页会变得不稳定。

**2. 文件头检查。** 查看器只用 File API 读前 100 字节，把前 16 字节和 `SQLite format 3\0` 比对。文件不足 100 字节，或者字节对不上，就会报 "Not a SQLite 3 database" 错误。扩展名从不被信任。

**3. 引擎加载。** 文件头检查通过之后，页面才会去拉取 SQLite 引擎。引擎是 [sql.js](https://github.com/sql-js/sql.js) 1.14.2，也就是编译成 WebAssembly 的 SQLite 3.49.1。两个文件压缩后大约 340 KB，浏览器只拉一次。传错文件、传 PNG 或 CSV 都不会触发这次下载。

**4. 内存中打开。** 整个文件被读进一个 `Uint8Array`，传给 `new SQL.Database(bytes)`。sql.js 把这份数据库放进一个虚拟的内存文件系统。从这一步开始，所有查询都跑在这份副本上。

**5. 对象列表。** 查看器查询 `sqlite_master` 拿到表和视图。内部的 `sqlite_%` 对象不出现在列表里，但你仍然可以在 SQL 编辑器里查询它们。每个表都会跑一次 `COUNT(*)`；视图列出来但不带计数。

**6. 结构。** 你选中一个表或视图时，查看器会跑这几个表值 pragma 函数：

```sql
SELECT name, type, "notnull", dflt_value, pk FROM pragma_table_info(?);
SELECT name, "unique", origin FROM pragma_index_list(?);
SELECT name FROM pragma_index_info(?) ORDER BY seqno;
```

这几个 pragma 的表值形式从 SQLite 3.16.0（2017 年）起就有了。结构面板显示每一列的名字、声明类型、`NOT NULL`、默认值和主键位置；索引面板显示名字、涉及的列、是否唯一以及来源。来源是 `c` 表示由 `CREATE INDEX` 创建，`u` 表示由 `UNIQUE` 约束创建，`pk` 表示由 `PRIMARY KEY` 约束创建。索引条目是 rowid 或表达式时，`pragma_index_info` 会把列名返回为 `NULL`，查看器把这种条目显示成 `(expr)`。索引下方是 schema 表里原样存储的 `CREATE` 语句。

**7. 行数据。** 数据网格用 `LIMIT 100 OFFSET n` 每次翻 100 行，范围提示会写 "Rows 101–200 of 3,200"，让你随时知道自己翻到哪了。

查看器拼进 SQL 里的每个表名和列名都用双引号包裹，名字里的双引号会被转义成两个双引号。叫 `order`、`user data`、`"quoted"` 的表，以及非拉丁字符的名字，都能正常打开。

### "不上传"具体指什么

文件通过 File API 从你的磁盘直接进到页面内存里。这个工具发出的唯一网络请求是拉取引擎文件，而且是同一个站点下的静态文件。因为输入是私有数据库，这个工具页还被配置成跳过站点的统计和广告脚本。关掉或刷新标签页，内存里的副本就没了。

## SQLite 里，值的类型不看列怎么声明

读 SQLite 文件时大多数困惑都来自它的类型系统。[Datatypes In SQLite](https://www.sqlite.org/datatype3.html) 页面有完整说明，这里是精简版：

- 一个值属于五种**存储类型**之一：`NULL`、`INTEGER`、`REAL`、`TEXT`、`BLOB`。
- SQLite 用的是动态类型：**类型属于值本身，不属于列。**
- 声明的列类型只是设置一个**亲和性（affinity）**（`TEXT`、`NUMERIC`、`INTEGER`、`REAL`、`BLOB`），SQLite 在插入时能转就转。

亲和性按子串规则从声明的类型名推出：类型名里带 `INT` 就是 INTEGER 亲和性；带 `CHAR`、`CLOB` 或 `TEXT` 是 TEXT 亲和性，所以 `VARCHAR(255)` 其实是 TEXT，`255` 这个数字会被忽略；带 `BLOB` 或不声明类型是 BLOB 亲和性；带 `REAL`、`FLOA`、`DOUB` 是 REAL 亲和性；其余的都归 NUMERIC。

这意味着一列声明成 `INTEGER`，只要有代码写过字符串 `'n/a'`，它照样存得下。某个 ORM 声明了 `created_at DATETIME`，也完全可能这一行存 ISO-8601 文本、那一行存 Unix 时间戳。SQLite 没有日期类型也没有布尔类型：日期存成 TEXT、REAL（儒略日）或 INTEGER（Unix 时间），布尔值就是整数 `0` 和 `1`。

查看器渲染每个单元格看的是拿到的实际值，不是列声明的类型：

| 值 | 网格里显示 | CSV 导出里 |
|----|------------|------------|
| `NULL` | 灰色的 `NULL` 标记 | 空字段 |
| 空字符串 `''` | 空单元格 | 空字段 |
| 数字（INTEGER 或 REAL） | 右对齐 | 按原样 |
| 文本 | 按文本显示，长文本在单元格里截断 | 完整值，需要时加引号 |
| BLOB | `BLOB · 4 B · 89504E47`（字节长度 + 前 16 字节的十六进制） | 完整内容转成大写十六进制 |

一列数据看起来不对劲时，直接问 SQLite 里面存的是什么：

```sql
SELECT typeof(created_at) AS storage_class, COUNT(*)
FROM orders
GROUP BY 1;
```

如果结果里同时出现 `text` 和 `integer`，说明有两条代码路径在用不同格式写这一列。SQLite 3.37.0（2021 年）加入了 `STRICT` 表：只允许 `INT`、`INTEGER`、`REAL`、`TEXT`、`BLOB`、`ANY` 作为列类型，类型不对的值会被拒绝写入。如果存储的 `CREATE` 语句以 `STRICT` 结尾，这张表就不会出现类型混杂的问题。

## 在内存副本上跑 SQL

数据网格下方的编辑器接受 SQLite 3.49.1 能理解的任何 SQL。按 **Run SQL** 或 Ctrl/Cmd + Enter 执行。

- **一次跑多条语句。** 编辑器里的内容按顺序全部执行。结果网格显示最后一条返回列的语句，比如 `SELECT` 或者带 `RETURNING` 的 `UPDATE`。
- **报错来自 SQLite 本身。** 写错了会在状态栏显示 SQLite 自己的报错信息，比如 `near "SELEC": syntax error`。上一次的结果会被清空，不会和新结果混在一起。
- **改数据的语句** 会报 "Done. N row(s) changed in the in-memory copy."，这个数字来自运行前后两次 `total_changes()` 的差值。
- **schema 变化会被自动识别。** 如果这次执行改了数据或 schema 版本，表清单会重新加载：刚跑的 `CREATE TABLE` 会出现在列表里，`INSERT` 或 `DELETE` 之后行数也会更新。
- **大结果集。** 网格只渲染结果的前 1000 行以保证页面流畅，并会提示这一点；**Export CSV** 始终写出结果的全部行。

几条在陌生数据库上很好用的查询：

```sql
-- 所有对象及其 CREATE 语句，包括索引和触发器
SELECT type, name, tbl_name, sql FROM sqlite_master ORDER BY type, name;

-- 很多应用存在文件头里的迁移计数器
PRAGMA user_version;

-- 一张表上声明的外键
SELECT * FROM pragma_foreign_key_list('orders');

-- 检查文件是否损坏
PRAGMA integrity_check;
```

### 写操作只停留在内存里

浏览器对你选中的文件没有写权限。引擎操作的是内存里的副本，所以 `INSERT`、`UPDATE`、`DELETE`、`CREATE`、`DROP` 都能跑，查看器也会显示它们的效果，但磁盘上的文件分毫不动。刷新页面或打开另一个文件，这些改动就消失了。这个工具没有下载编辑后副本的选项。

这让编辑器成了正式执行前的安全试验场。比如先看一次清理操作会影响多少行，再看看剩下的数据：

```sql
DELETE FROM sessions WHERE expires_at < unixepoch();
SELECT COUNT(*) AS remaining FROM sessions;
```

测试级联删除时有个细节要注意：SQLite 新建连接默认不强制外键约束，除非应用主动开启，查看器也是一样。想让测试里的 `ON DELETE CASCADE` 生效，先跑一句 `PRAGMA foreign_keys = ON;`。

要改真实文件，在自己机器上用 `sqlite3` 命令行工具或 DB Browser for SQLite。

## 导出 CSV

**Export CSV** 按钮有两个。数据网格上方那个导出整张选中的表或视图的所有行，不只是当前这一页；SQL 编辑器下方那个导出上一次查询的完整结果。

输出遵循 RFC 4180：逗号分隔、CRLF 换行、首行是列名，字段里出现逗号、双引号、CR 或 LF 时用双引号包裹，字段内部的双引号会被转义成两个双引号。文件名取自表名，字母、数字、`.`、`_`、`-` 之外的字符会替换成 `_`；查询结果导出的文件名固定是 `query.csv`。

CSV 作为格式带来两个后果：

- `NULL` 和空字符串在 CSV 里都变成空字段。如果这个区别对你有意义，导出前在查询里用 `COALESCE(col, '<null>')` 或 `col IS NULL AS col_is_null` 处理一下。
- BLOB 会变成大写十六进制。一个 4 字节的 PNG 文件头会导出成 `89504E47`，这样 CSV 依然是合法文本，绝大多数语言用一个调用就能解回二进制，比如 Python 里的 `bytes.fromhex()`。

要把数据给同事，只导出他需要的查询结果就够了，数据库文件留在你自己手里。

## 坑与边界情况

### 最近的行不见了：WAL 文件

这是最常见的意外。[Write-Ahead Logging](https://www.sqlite.org/wal.html) 页面描述的 WAL 模式下，SQLite 不会立刻把已提交的改动写进主数据库文件，而是追加到一个以数据库同名、后缀 `-wal` 的独立文件里，旁边还有一个索引文件 `-shm`。**checkpoint** 会把 WAL 里的事务搬回主文件。默认情况下，WAL 达到 1000 页时 SQLite 会自动 checkpoint，最后一个连接关闭时 WAL 通常会被删除。

所以，如果你从正在运行的 App 拷贝 `app.db`，或者在 App 开着的时候从手机上把文件拉出来，最新的事务很可能还留在 `app.db-wal` 里。查看器只读主文件，这些行自然就看不到。SQLite 官方文档也提醒过：把数据库文件和它的 WAL 分开拷贝，可能丢失已提交的事务，甚至损坏数据库。

文件头第 18、19 字节能告诉你这个文件是不是用了 WAL（都是 `2` 就是）。要把 WAL 合并回主文件，先关掉写它的那个应用，再跑：

```bash
sqlite3 app.db "PRAGMA wal_checkpoint(TRUNCATE);"
```

`TRUNCATE` 会把每一帧都 checkpoint 完，再把 WAL 文件截断到 0 字节。之后再打开 `app.db`。回滚模式数据库留下的 `-journal` 文件也是同样道理：查看器只读主文件，先让原本的应用或者 `sqlite3` shell 打开一次数据库。

### 明明是数据库，却报 "Not a SQLite 3 database"

加密数据库会触发这个错误。[SQLCipher](https://www.zetetic.net/sqlcipher/design/) 会在前 16 字节存一段随机 salt，其余部分全部加密，整个文件看起来就是随机数据，`SQLite format 3` 文件头也就没了。SQLite Encryption Extension（SEE）同样会加密文件。查看器不打开加密数据库，用 `sqlcipher` shell 解密，或者用支持 SQLCipher 的 DB Browser for SQLite 打开。

名字带 `.db` 但其实是别的东西的文件，以及被截断的拷贝，也会报同样的错误。用 `head -c 16 app.db | xxd` 看一眼前几个字节就能确认。

### 文件超过 100 MB

这个上限是固定的，因为数据库打开期间会在内存里存两份。文件更大的话，本地跑 `sqlite3 app.db`，或者先取一个小一点的子集：

```bash
sqlite3 big.db "ATTACH 'small.db' AS s; CREATE TABLE s.orders AS SELECT * FROM orders WHERE created_at >= '2026-09-01';"
```

然后把 `small.db` 丢进查看器打开。

### 某张表不显示行，只显示报错

有些表需要 SQLite 核心之外的代码支持。像 SpatiaLite 的几何表、`sqlite-vec` 向量表、FTS5 全文索引、R-Tree 空间索引这类虚表，依赖的是编译进创建它们的那个应用里的模块。查看器用的 sql.js 1.14.2 构建版本没有包含 `fts5` 或 `rtree` 模块，查询这类表会得到 SQLite 自己的报错，比如 `no such module: fts5`。

这类表的行数统计会失败，列表里显示 `—`，数据面板显示报错，数据库的其余部分照常可以浏览。FTS5 的数据本身还存在普通的 "shadow" 表里（比如 `notes_fts_content`），这些是普通表，可以正常读取。

### 查询结果一行都没有

一条匹配不到任何行的 `SELECT`，照样会显示列名，状态栏会写 "0 row(s)"。这说明查询本身跑通了、列名也对，问题出在 `WHERE` 子句上。`SELECT COUNT(*) ... WHERE ...` 永远返回一行，能把结果说清楚。

### 长文本与宽表

单元格宽度有上限，长文本会用省略号截断。超过 60 个字符的文本，悬停就能在 tooltip 里看到前 2000 个字符。要读一列里存的完整 JSON 文档，单独查出这个值再导出成 CSV，或者在查询里用 `json_extract()` 把需要的部分取出来。

### 安全地拷贝一个正在使用的数据库

应用还在写文件时用 `cp` 直接拷贝，可能拿到一份"撕裂"的坏副本。SQLite 3.15.0 起提供的 `VACUUM INTO` 会把一份事务一致的快照写进新文件，原文件不受影响。这份快照是单个文件，包含了 WAL 里已提交的内容：

```bash
sqlite3 app.db "VACUUM INTO 'snapshot.db'"
```

## 代码示例

### Python：先检查文件头，再只读统计行数

标准库的 `sqlite3` 模块可以通过 URI 以只读方式打开文件。下面这段脚本用查看器同样的方式检查文件头，打印页大小和日志模式，并列出每张表的行数。

```python
import sqlite3
import sys

path = sys.argv[1]
with open(path, "rb") as f:
    header = f.read(100)

if len(header) < 100 or header[:16] != b"SQLite format 3\x00":
    sys.exit(f"{path}: no SQLite 3 header (encrypted, truncated, or not a database)")

page_size = int.from_bytes(header[16:18], "big")
if page_size == 1:
    page_size = 65536                      # 1 是 64 KiB 页的特殊标记值
journal = "WAL" if header[18] == 2 else "rollback"
print(f"page size: {page_size}  journal mode: {journal}")

con = sqlite3.connect(f"file:{path}?mode=ro", uri=True)   # 只读打开
tables = con.execute(
    "SELECT name FROM sqlite_master WHERE type = 'table' "
    "AND name NOT LIKE 'sqlite\\_%' ESCAPE '\\' ORDER BY name"
).fetchall()
for (name,) in tables:
    quoted = '"' + name.replace('"', '""') + '"'
    count = con.execute(f"SELECT COUNT(*) FROM {quoted}").fetchone()[0]
    print(f"{name:<32}{count:>10}")
con.close()
```

### JavaScript：Node.js 里用同一个引擎

sql.js 在 Node.js 里也能跑，用的是和浏览器工具一样的模型：文件被加载进内存，写操作只改动这份副本。

```js
import { readFileSync } from "node:fs";
import initSqlJs from "sql.js";

const bytes = readFileSync(process.argv[2]);
const SQL = await initSqlJs();
const db = new SQL.Database(bytes);          // 文件的内存副本

const [schema] = db.exec(
  "SELECT type, name FROM sqlite_master WHERE type IN ('table', 'view') ORDER BY name"
);
for (const [type, name] of schema?.values ?? []) console.log(type.padEnd(6), name);

// 写操作只改动这份副本，磁盘上的文件不受影响。
db.run("DELETE FROM users WHERE email LIKE ?", ["%@example.com"]);
console.log("rows deleted in memory:", db.getRowsModified());

// 如果想保留改动，db.export() 会把改动后的数据库返回成一个 Uint8Array。
db.close();
```

### Bash：为查看准备文件，并从命令行导出

```bash
# 把待处理的 WAL 事务合并进主文件（先关掉写它的应用）
sqlite3 app.db "PRAGMA wal_checkpoint(TRUNCATE);"

# 或者取一份一致的单文件快照，不动原文件
sqlite3 app.db "VACUUM INTO 'snapshot.db'"

# 打开之前先确认文件头
head -c 16 snapshot.db | xxd

# 从 shell 导出 CSV；hex() 和查看器一样把 BLOB 转成文本
sqlite3 -header -csv snapshot.db \
  "SELECT id, email, hex(avatar) AS avatar FROM users LIMIT 100" > users.csv
```

`hex()` 这一步很关键。`sqlite3` shell 默认会把 BLOB 列原样写成字节导出到 CSV，大多数 CSV 解析器都会被这种文件搞坏。

## 和其他 SQLite 工具的对比

下面这几个工具各有各的适用场景。

| 工具 | 运行环境 | 能读什么 | 是否写入文件 | 加密文件 |
|------|----------|----------|--------------|----------|
| ZeroTool SQLite 查看器 | 浏览器标签页，无需安装 | 单个文件，最大 100 MB | 否，改动只留在内存副本里 | 不支持 |
| `sqlite3` 命令行 shell | 本地终端 | 本地磁盘上的文件，包括 WAL | 是 | 不支持（用 `sqlcipher` shell） |
| DB Browser for SQLite | Windows / macOS / Linux 桌面应用，开源 | 本地磁盘上的文件 | 是 | 支持，SQLCipher |

`sqlite3` shell 是参照系一样的工具：原地打开文件，自身没有大小限制，能读 WAL，也适合写脚本。只想看一眼的话用 `sqlite3 -readonly app.db`。它的局限是你得记住那些点命令，而且要在终端里读宽表。

DB Browser for SQLite 是一个完整的桌面编辑器，能建表改表、在网格里改单元格、添加或去掉 SQLCipher 加密。需要真的改文件时用它。

浏览器查看器就是给你快速看一眼：结构面板、分页数据、SQL 编辑器、CSV 导出，不用装软件、不用注册、不上传。它从设计上就对文件只读，所以不可能弄坏你正在检查的数据库。
