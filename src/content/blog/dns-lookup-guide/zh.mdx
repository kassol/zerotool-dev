一个常见情形：你把 `marketing.example.com` 的 CNAME 从指向 Webflow 改成指向新的自托管落地页，DNS 控制台显示变更已生效。五分钟后同事说：「我电脑上还是旧设计。」你跑 `dig +short marketing.example.com`，拿回的是新 IP。同事的电脑问的是另一个解析器，那个解析器的缓存里可能还是旧记录。谁的缓存错了？

[立刻查一下 →](/zh/tools/dns-lookup/)

诚实的答案是「谁的都没错，只是变更还没传到每一个递归解析器」——但你没办法靠对一个解析器的一次 `dig` 证明这一点。你需要快速问几个公共递归解析器并做对比。过去这意味着写 CLI 循环、买商用网络监控工具，或者去多地区查询网站。浏览器帮不上忙：网页打不开 53 端口的 UDP 或 TCP 套接字，说不了传统 DNS。RFC 8484 在 2018 年标准化了 DNS-over-HTTPS，Cloudflare 和 Google 提供了允许跨域请求的公共 DoH 端点，一次 `fetch()` 就能查任意记录类型。

这篇指南覆盖整条链路：DoH 怎样编码查询、每种记录类型回答什么问题、DNSSEC 与扩展错误怎样出现在 JSON 里、Cloudflare 和 Google 差在哪里、CORS 与 ECS 为什么会影响结果，以及哪些结论不能从浏览器查询里得出。带日期的数字都是 [DNS 查询工具](/zh/tools/dns-lookup/)发出的同一条请求的实测结果。

## DNS-over-HTTPS 改变了什么

传统 DNS 查询是走 UDP 53 端口的二进制报文，响应被截断时回退到 TCP 53（RFC 1035 §4.2）。浏览器对这两种协议都没有套接字 API。DoH 把同一条 DNS 报文装进 HTTPS 请求，查询看起来就是 443 端口上的普通网页流量，链路上是加密的（RFC 8484）。

有两种编码：

- **RFC 8484 的二进制格式。** `POST` 配 `Content-Type: application/dns-message`，或者 `GET` 把报文 base64url 编码后放进 `?dns=`。响应体是 DNS 报文。
- **JSON 格式。** `GET ?name=…&type=…`，返回 JSON。它不属于任何 RFC；Cloudflare 的文档说沿用了 Google 的结构，字段基本一致，差异见下文。

JSON 格式在网页里更好用：它就是一次普通的跨域 `GET`。2026-11-03 实测，两家端点都返回 `access-control-allow-origin: *`，页面才能读取响应。工具会带 `Accept: application/dns-json`；`Accept` 属于 CORS 安全列表请求头，带它的 `GET` 不触发预检。`POST` 配自定义 `Content-Type`，或带任何非安全列表头，都会触发预检，这也是网页里优先用 JSON 格式的原因之一。

```json
{
  "Status": 0,
  "TC": false,
  "RD": true,
  "RA": true,
  "AD": false,
  "CD": false,
  "Question": [{ "name": "zerotool.dev", "type": 1 }],
  "Answer": [
    { "name": "zerotool.dev", "type": 1, "TTL": 300, "data": "172.67.170.64" },
    { "name": "zerotool.dev", "type": 1, "TTL": 300, "data": "104.21.95.91" }
  ]
}
```

这些字段就是 DNS 报文头和四个区段。`Status` 是 RCODE（RFC 1035 §4.1.1，由 RFC 6895 扩展）：0 是 NOERROR，2 是 SERVFAIL，3 是 NXDOMAIN。`TC` 是截断标志；Cloudflare 的文档说它支持最大响应长度，DoH 下几乎总是 false。`RD` 与 `RA` 描述递归。`AD` 与 `CD` 是 DNSSEC 标志位。`Question`、`Answer`、`Authority`、`Additional` 对应 DNS 的四个区段。`Comment` 放解析器的诊断信息，Google 还提供结构化的 `extended_dns_errors`。

两家的请求参数不完全一样：

| 参数 | Cloudflare | Google | 含义 |
|---|---|---|---|
| `name` | 必填 | 必填 | 查询名；Google 接受 RFC 4343 的反斜杠转义 |
| `type` | 可选，默认 `A` | 可选，默认 `1` | 记录类型，可写名称或数字 |
| `do` | `0` / `1` | `0` / `1` | 是否返回 DNSSEC 记录（RRSIG、NSEC、NSEC3） |
| `cd` | `0` / `1` | `0` / `1` | 是否关闭 DNSSEC 验证 |
| `ct` | — | `application/dns-message` | 返回二进制 DNS 报文而不是 JSON |
| `edns_client_subnet` | — | `1.2.3.4/24` | 把客户端子网提示传给权威服务器 |
| `random_padding` | — | 任意值 | 值被忽略；把 URL 填充到固定长度，降低流量分析风险 |

两家文档都把 `do` 解释为 DNSSEC OK 位，把 `cd` 解释为关闭验证。工具发送 `do=1` 与 `cd=0`：要签名，也让解析器做验证。不带 `do=1` 时 Cloudflare 的 AD 不可靠，见下文 DNSSEC 一节。

## 十种记录类型，以及它们回答什么

每种类型回答一个特定的运维问题。挑错类型，你会花几个小时去追一个根本不存在的配置错误。

| 类型 | 编码 | 提问 | 缺失或错误时常见的运维故障 |
|---|---:|---|---|
| `A` | 1 | 哪个 IPv4 地址在服务这个域名？ | 开发者机器上能打开、别人那里 404——旧 A 与新 A 不一致。 |
| `AAAA` | 28 | 哪个 IPv6 地址在服务这个域名？ | AAAA 仍指向旧主机时，优先用 IPv6 的客户端打不开网站，只有 IPv4 的测试环境看不出问题。 |
| `CNAME` | 5 | 这个别名指向哪个规范名？ | CNAME 指向已删除的 Heroku 应用，或指向某 SaaS 的错误租户。 |
| `MX` | 15 | 哪些服务器接收这个域名的邮件？ | 入站邮件被退回，提示「no MX record found」，或迁移后投错服务商。 |
| `TXT` | 16 | 发布了哪些策略字符串？ | SPF 配成 soft-fail，DMARC 报告显示合法邮件被标垃圾，域名验证卡在「pending」。 |
| `NS` | 2 | 谁对这个区域有权威？ | 注册商转移后 NS 还指向旧服务商，更新完全不传播。 |
| `SOA` | 6 | 主服务器是谁，从服务器多久刷新一次？ | 从服务器超出 SOA 刷新窗口仍返回旧数据，或否定答案被缓存过久。 |
| `CAA` | 257 | 哪些 CA 可以为这个域名签发证书？ | 没被列出的 CA 拒绝签发，换 CA 或 CDN 后续签失败。 |
| `PTR` | 12 | 这个 IP 声称自己叫什么名字？ | 发信 IP 的 PTR 与 HELO 域名对不上，邮件被退回，声誉服务标记发件人。 |
| `SRV` | 33 | `_xmpp-client._tcp` 这类服务在哪里？ | XMPP、SIP、LDAP 或 Matrix 联邦找不到主机，因为 SRV 缺失或端口写错。 |

工具的 **ALL** 模式对前八种类型并发请求，适合「把这个区域的一切给我看看」。PTR 与 SRV 不进 ALL：PTR 要求输入 `in-addr.arpa` 形式（如 `34.216.184.93.in-addr.arpa`）而不是域名，SRV 要求带下划线前缀的服务名（`_xmpp-client._tcp.example.com`）。两者都更适合定向的单类型查询。

## A、AAAA 与 CNAME

`A` 与 `AAAA` 返回地址和 TTL。一个名字可以有多条记录，CDN 会轮换。TTL 是解析器可以缓存这组记录的秒数，不是「变更多久传到所有解析器」的承诺：每个递归解析器从自己拿到记录的那一刻开始倒计时。

`CNAME` 表示「这个名字是另一个名字的别名」。解析器通常会沿着链继续查，把目标的 `A`/`AAAA` 一起放进 `Answer`，所以一次 CNAME 查询可能返回多种类型。看每条记录的 `name` 字段，才能分清它属于链上的哪一步。

两条规则造成大部分 CNAME 意外：

- **CNAME 节点不能有别的数据。** 有 CNAME 的名字不能再持有其他记录（RFC 1034 §3.6.2、RFC 1912 §2.4）。区域根必须有 SOA 与 NS，因此不能直接是普通 CNAME。
- **展平会隐藏 CNAME。** Cloudflare 的 CNAME 展平与 Route 53 的别名记录会在查询时用 A/AAAA 回答根域名。对这类根做 DoH 查询，拿到的是地址，不是你在控制台里配的那条 CNAME。这是正确行为，但期待看到别名的人会以为记录丢了。

## MX 与 TXT

`MX` 记录带优先级和主机名。优先级数字小的先试（RFC 5321 §5.1），相同的值用于分摊负载。如果一个域名完全没有 MX，SMTP 会把它的 A/AAAA 当作优先级 0 的隐式 MX（RFC 5321 §5.1）。所以「没有 MX」不总是等于「不收邮件」。

**Null MX** 是明确表示「这个域名不收邮件」的写法：一条优先级 0、目标为 `.` 的记录（RFC 7505）。如果你以为要收邮件的域名返回 `0 .`，那是区域所有者主动发布的，要改区域，不是等传播。

`TXT` 承载域名本身的 SPF（RFC 7208）、`_dmarc.example.com` 的 DMARC（RFC 7489 §6.1），以及 `选择器._domainkey.example.com` 的 DKIM 公钥（RFC 6376 §3.6.1）。同一个类型还放着搜索引擎和 SaaS 的域名验证串，所以一次 TXT 查询可能返回十几条互不相关的值。

255 字节规则是最容易把解析器弄坏的部分。一条 TXT 记录由多个 character-string 组成，每段最多 255 字节（RFC 1035 §3.3 与 §3.3.14）。长的 SPF 或 DKIM 值会拆成多段，使用方要把它们直接相连、中间不加任何字符（SPF 见 RFC 7208 §3.3，DKIM 见 RFC 6376 §3.6.2.2）。两家 JSON 接口的呈现方式不同：2026-11-03 实测，Cloudflare 给每段加引号、段间用空格分隔，和 `dig` 的输出一样；Google 把同一把钥匙返回成一整段、没有引号。`cf2024-1._domainkey.zerotool.dev` 的 DKIM 公钥，Cloudflare 返回 425 个字符（第一段 255 个字符后有一处 `" "`），Google 返回 420 个字符。只在确有引号时去掉引号，段与段之间不要插分隔符。

Google 的文档写明 TXT 记录会编码成一个 JSON 字符串，它自己的示例里也带引号分段。实际规则是：把 `data` 当作展示文本，去掉解析器加的引号，再按无分隔符拼接。

## NS、SOA 与否定答案

`NS` 列出区域的权威服务器。它告诉你答案从哪里来，也能看出注册商转移或服务商迁移有没有把委派指错。NS 的 TTL 通常很长（86400 秒很常见），一次变更可能要一天才在所有地方可见。

`SOA` 带区域的主服务器、责任人邮箱、序列号和四个定时器：refresh、retry、expire、minimum（RFC 1035 §3.3.13）。序列号是从服务器发现变更的依据——区域传送出问题时，对比主从的序列号是最快的检查。

minimum 还决定否定缓存。名字不存在时，权威服务器返回 NXDOMAIN，并在 authority 区段带上区域的 SOA。这条否定答案可以缓存 SOA 自身 TTL 与 MINIMUM 中较小的那个秒数（RFC 2308 §5）。缓存了 NXDOMAIN 的解析器会一直返回它，直到计时结束，即使区域已经修好。这是「浏览器查询已经正确、某台笔记本却一直失败」常见的原因之一。

NXDOMAIN 与 NODATA 不同。NXDOMAIN（`Status` 3）表示名字不存在。NODATA 是 NOERROR 但零条回答：名字存在，只是没有所查类型的记录。查一个没有 CAA 的域名得到 NODATA，`Authority` 里有 SOA；查一个拼错的名字得到 NXDOMAIN。看到 NOERROR 配 0 条记录，说明类型选错了——去查你真正想要那个区域的 `NS`。

## CAA

CAA（RFC 8659）告诉公共证书颁发机构，哪些 CA 可以给这个域名签发证书。合规的 CA 在签发前必须检查 CAA。如果存在 CAA 记录、而没有任何 `issue` 属性列出该 CA，这个 CA 就不能签发（RFC 8659 §3）。如果根本不存在 CAA 记录，说明域名没有通过 CAA 限制签发。

允许 Let's Encrypt 和 Google Trust Services 签发、禁止通配符证书的区域：

```text
example.com. 0 issue "letsencrypt.org"
example.com. 0 issue "pki.goog"
example.com. 0 issuewild ";"
example.com. 0 iodef "mailto:security@example.com"
```

`issuewild ";"` 拒绝所有通配符签发。`iodef` 告诉 CA：收到未授权签发请求时把报告发到哪里。CAA 是唯一能看出这条限制的 DNS 查询；换到使用其他 CA 的 CDN 时忘了更新，下一次续签就会失败，而且看起来像 TLS 问题。

## PTR 与 SRV

`PTR` 把地址映射回名字。IPv4 的反向名在 `in-addr.arpa` 下，八位组倒过来写（RFC 1035 §3.5）；IPv6 的反向名在 `ip6.arpa` 下，半字节倒过来写（RFC 3596 §2.5）。邮件服务器常检查发信 IP 的 PTR 是否存在、是否与 HELO 名一致，所以缺 PTR 往往表现为投递问题而不是 DNS 问题。只有 PTR 不能证明归属：这个名字还应该正向解析回同一个地址。

`SRV` 在 `_服务._协议.域名` 这类名字下发布主机、端口、优先级和权重（RFC 2782）。支持 SRV 的客户端先试优先级最小的，同优先级按权重分摊。如果没有 SRV，客户端回退到域名上的服务默认端口，所以有些服务没有 SRV 也能用，有些必须要有。

## DNSSEC：AD 标志与 EDE

DNSSEC 给 DNS 数据加签名。做验证的解析器从根信任锚一路验到区域，把结果放进 `AD`（Authenticated Data）标志。RFC 4035 §3.2.3 规定什么时候可以置位；RFC 6840 §5.8 补充：只有查询带了 DO 或 AD 位时才应该置位。工具发送 `do=1` 就是这个原因。

不带 `do=1` 时 Cloudflare 的 AD 会变。2026-09-30 每种查询各发 30 次：`example.com` 的 A、AAAA、NS 每次都是 `"AD": false`，MX 每次都是 `true`；更早一轮 20 次 A 查询里 `true` 和 `false` 各 10 次。带 `do=1` 的查询、以及问 Google 的查询全部是 `true`。要靠 AD 判断，就带 `do=1`。

签名完整、链条有效的区域返回 NOERROR 与 `AD: true`。没签名的区域返回 NOERROR 与 `AD: false`，这不是错误，只说明区域没用 DNSSEC。链条坏掉的区域返回 SERVFAIL，`AD` 为 false，因为没有通过验证的回答。仅凭 SERVFAIL 分不清「DNSSEC 坏了」还是「权威服务器连不上」，要看解析器的诊断。

诊断就是扩展 DNS 错误（RFC 8914），一个数字代码加一段给人看的文字。与 DNSSEC 有关的代码：1（不支持的 DNSKEY 算法）、2（不支持的 DS 摘要类型）、5（不确定）、6（bogus）、7（签名过期）、8（签名尚未生效）、9（缺 DNSKEY）、10（缺 RRSIG）、12（缺 NSEC）。Cloudflare 把它们放在 `Comment` 数组里，形如 `EDE(9): DNSKEY Missing …`。Google 在 `Comment` 里给一句话，另加结构化的 `extended_dns_errors` 数组，含 `info_code` 与 `extra_text`。工具把两家统一显示成记录下方的 `EDE(n): 文本`。

公开的测试域名 `dnssec-failed.org` 可以看这个差别。2026-11-03 实测：Cloudflare 返回 `Status: 2`，`Comment: ["EDE(9): DNSKEY Missing no SEP matching the DS found for dnssec-failed.org."]`；Google 返回 `Status: 2`，`Comment` 以「DNSSEC validation failure」开头，另有 `extended_dns_errors: [{ "info_code": 9, "extra_text": "No DNSKEY matches DS RRs of dnssec-failed.org" }]`。两者是同一个故障：父区发布了 DS 记录，子区没有能对上的 DNSKEY。

`cd=1` 让解析器跳过验证。它适合查看坏区域的未验证数据，不适合日常查询。工具始终发送 `cd=0`；要看另一面就用 `dig +cd`。

## Cloudflare 与 Google 实际差在哪里

两家端点用同一套 JSON 结构，但它们是不同的解析器，网络位置和缓存都不同。实际会遇到的差异：

- **ECS。** Google Public DNS 默认会把大致的网络信息发给权威服务器，通常把 IPv4 地址的最后一段置零；`edns_client_subnet=0.0.0.0/0` 可以关闭。Cloudflare 的 FAQ 说 1.1.1.1 不发送 ECS。所以 CDN 域名经两家查询可能返回不同地址，Google 的结果还取决于查询从哪里发出。2026-09-30 用它查 `www.qq.com`：`114.114.114.0/24` 得到 `121.14.77.201`、`121.14.77.221`，`8.8.8.0/24` 得到 `43.159.109.55`，`139.130.4.0/24` 得到 `43.168.224.173`；Cloudflare 不理会同样的参数，返回 `43.159.109.55`。
- **TXT 呈现。** Cloudflare 给每段加引号、段间用空格；2026-11-03 实测 Google 返回的是一整段、不带引号。Google 的文档里也有带引号分段的示例，所以把引号当展示格式，不要当接口契约。
- **诊断信息。** Cloudflare 的 `Comment` 是 EDE 字符串数组；Google 的 `Comment` 是一句话，结构化数据在 `extended_dns_errors` 里。对未缓存的回答，Google 还会加 `Comment: "Response from <IP>."`，说明它问的是哪台权威服务器。
- **DNSSEC 记录的文本。** 带 `do=1` 时两家都把 RRSIG 放进 `Answer`。文本不是逐字节相同：2026-11-03 的查询里，Google 把覆盖的类型写成小写（`a 13 2 …`），Cloudflare 写成大写（`A 13 2 …`）。
- **顺序与名字。** RRset 本身无序，两家返回的顺序不同。不要按位置比较两份答案，要比较集合。
- **HTTP 缓存。** 同一次查询里，Google 的响应带 `cache-control: private, max-age=300`，Cloudflare 的没有。重复查询可能由浏览器或中间缓存直接回答，最多五分钟。

TTL 不同也是正常的：两个缓存从不同时间开始计时，不代表谁错了。

## 为什么浏览器和系统解析器结果不同

DoH 查询回答的是和笔记本上的 `dig` 不同的问题。差异不是 bug：

- **观测点。** `dig` 问的是操作系统配置的解析器（或你指定的服务器）；DoH 问的是 Cloudflare 或 Google。两者缓存独立，一个可能还是旧记录，另一个已经是新的。
- **hosts 文件与本地覆盖。** `dig`、`nslookup` 发的是 DNS 查询，通常不读 `/etc/hosts`；普通应用查询会经系统解析器读它，VPN 或本地 DNS 代理也可能改写答案。公共 DoH 解析器看不到这些。
- **分离解析（split-horizon）。** 公司网络和 VPN 对内网返回内部地址，对外返回 NXDOMAIN。DoH 看的是外网视角，所以办公室里能用的内网名字在这里是 NXDOMAIN。
- **搜索域。** 系统可能给裸主机名补上搜索后缀；DoH 端点要求完整名字。
- **浏览器的安全 DNS。** Chrome、Edge、Firefox 可以给自己的解析配置 DoH，包括解析 `cloudflare-dns.com` 或 `dns.google` 本身。它改变的是浏览器解析主机名走哪条路，不改变 DoH 请求里问的那个解析器。
- **先有鸡还是先有蛋。** 页面要先经正常网络路径解析出 `cloudflare-dns.com` 或 `dns.google`，才能发出 DoH 查询。内容过滤器或强制门户挡住这两个名字时，查询本身是加密的也没用。

这也解释了为什么 Pi-hole、NextDNS、AdGuard Home 这类过滤器会让工具既有用又误导：工具能看到公共答案（本地过滤器挡了它），但你的网络确实屏蔽了这个域名。同理，拦截 53 端口、用 fake-IP 模式的代理会让 `dig` 打出 `198.18.2.147` 这类基准测试网段地址（RFC 6890 §2.2.2），而 DoH 查询返回真实结果。

## 常见的误判

**「还在传播。」** 多半是缓存，TTL 会告诉你要等多久。看记录上的 TTL，再问第二个解析器；一个拿到新值、另一个还是旧值，你看到的是缓存过期，不是坏区域。

**「DNS 坏了，只有一台机器不行。」** 先查是不是早先配错时缓存了 NXDOMAIN。RFC 2308 §5 允许按 SOA minimum 缓存否定答案；修法是等，或者在变更前先调低 SOA minimum。

**「CDN 返回了错误的 IP。」** DoH 的答案反映解析器的网络位置，不是你的。Google 的 ECS 提示会让答案靠近你指定的子网，Cloudflare 不发。要问「圣保罗的用户看到什么」，就从那个区域查。

**「网站能打开，DNSSEC 没问题。」** 做验证的解析器可能失败，不做验证的照常成功。带 EDE 代码的 SERVFAIL 是验证失败的标志；没有 EDE 的 SERVFAIL 更像权威服务器连不上。

**「CNAME 不见了。」** 解析器沿着链查完，返回的是 A/AAAA；或者区域在根上用了展平。查别名本身，并读每条答案的 `name` 字段。

**「TXT 被截断了。」** 那是多段 255 字节的字符串。去掉引号，按无分隔符拼接。

**「没有 MX，邮件一定收不到。」** SMTP 会退回到域名 A/AAAA 上的隐式 MX（RFC 5321 §5.1）。Null MX（`0 .`）才是明确的「不收邮件」。

**「没有 CAA 记录，所以谁都签不了。」** 正好相反：没有 CAA 记录表示没有 CAA 限制。CAA 记录里漏掉某个 CA，才是挡住那个 CA。

## 自己写同样的查询

工具存在的理由是：一次性查询点几下比写脚本快。要做自动化，JSON 格式短到能塞进任何有 `fetch` 的语言。

浏览器或 Node 18+：

```js
const url = `https://cloudflare-dns.com/dns-query?name=${encodeURIComponent('zerotool.dev')}&type=MX&do=1&cd=0`;
const res = await fetch(url, { headers: { accept: 'application/dns-json' } });
const json = await res.json();
console.log(json.Answer); // [{ name, type, TTL, data }, ...]
```

要超时加 `AbortSignal.timeout(5000)`，网络可能失败就包一层 `try/catch`。两家返回的整体结构一致，换提供商主要是换 URL 和各自的参数。

Python 标准库版本：

```python
import json
import urllib.request

def doh(name: str, qtype: str, resolver: str = "cloudflare"):
    if resolver == "google":
        url = f"https://dns.google/resolve?name={name}&type={qtype}&cd=0"
        headers = {}
    else:
        url = f"https://cloudflare-dns.com/dns-query?name={name}&type={qtype}&cd=0"
        headers = {"accept": "application/dns-json"}
    req = urllib.request.Request(url, headers=headers)
    with urllib.request.urlopen(req, timeout=5) as resp:
        return json.loads(resp.read())

print(doh("zerotool.dev", "CAA"))
```

Shell 与 CI 里用 `curl` 配 `jq`：

```bash
curl -s -H 'accept: application/dns-json' \
  'https://cloudflare-dns.com/dns-query?name=cloudflare.com&type=MX' \
  | jq -r '.Answer[] | select(.type == 15) | "\(.data)"' | sort
```

带 `do=1` 时 `select(.type == 15)` 很重要：回答里还有 RRSIG 记录，直接遍历 `.[]` 会把它们也打出来。

## 在 DNS 查询工具中的位置

[DNS Checker](https://dnschecker.org/) 从自己的服务器向「分布在全球多个地区的一组 DNS 服务器」查询，并画传播地图。它回答「这次变更是不是每个地区都收到了」。

[Google Admin Toolbox Dig](https://toolbox.googleapps.com/apps/dig/) 把查询发给自己的后端（`/apps/dig/lookup`）。2026-09-29 测试时，它对 `dnssec-failed.org` 显示「Record not found!」，只有原始视图里有 `rcode SERVFAIL`；对已签名的 `example.com`，标志行是 `QR RD RA`，没有 AD。

`dig` 与 `kdig` 是 CLI 参考实现，做脚本和需要指定权威服务器的查询（`dig @ns1.example.com`）时它们是对的答案。

ZeroTool 的工具填中间那一块：想在浏览器里快速查一下，机器上装 `dig` 还得加 Homebrew 包或者上 WSL，又想看公共解析器自己的回答，而不是经查询网站服务器转手的结果。可以在 Cloudflare 和 Google 之间切换对比，看到 AD 标志和解析器备注，并复制原始 JSON。它不是做传播地图或纯权威查询的工具。
