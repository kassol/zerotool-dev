よくある例を挙げる。`marketing.example.com` の CNAME を Webflow 向けから新しいセルフホストのランディングページ向けに切り替え、DNS 管理画面で変更が反映されたのを確認する。5 分後、同僚から「私のラップトップだとまだ古いデザインのままなんだけど」と連絡が入る。`dig +short marketing.example.com` を叩くと新しい IP が返る。同僚のラップトップは別のリゾルバに問い合わせていて、そのリゾルバのキャッシュにはまだ古いレコードが残っているのかもしれない。どちらのキャッシュが間違っているのか？

[いますぐ引く →](/ja/tools/dns-lookup/)

正直に言えば「どちらも間違っていない、変更がまだすべての再帰リゾルバに届いていないだけだ」となる——しかしこれを、ひとつのリゾルバに対する一発の `dig` だけでは証明できない。複数のパブリック再帰リゾルバに速やかに問い合わせて比較する必要がある。以前なら CLI のループ、有料の監視ツール、複数地域から照会するサイトのいずれかだった。ブラウザは役に立たなかった。Web ページは 53 番ポートの UDP / TCP ソケットを開けないので、古典的な DNS を話せない。2018 年に RFC 8484 が DNS-over-HTTPS を標準化し、Cloudflare と Google がクロスオリジンのリクエストを受け付ける公開 DoH エンドポイントを提供したことで、`fetch()` 一発で任意のレコードを引けるようになった。

この記事は経路全体を扱う。DoH がクエリをどう符号化するか、各レコードタイプが何に答えるか、DNSSEC と Extended DNS Error が JSON のどこに出るか、Cloudflare と Google がどこで違うか、CORS と ECS がなぜ結果に影響するか、そしてブラウザからの照会では言えないことは何か。日付を添えた数値は、[DNS 確認ツール](/ja/tools/dns-lookup/)が送るのと同じリクエストの実測値だ。

## DNS-over-HTTPS が変えたこと

従来の DNS クエリは UDP 53 番のバイナリメッセージで、応答が切り詰められたときは TCP 53 番に切り替える（RFC 1035 §4.2）。ブラウザはどちらにもソケット API を公開していない。DoH は同じ DNS メッセージを HTTPS リクエストに包むので、クエリは 443 番の普通の Web トラフィックに見え、経路上は暗号化される（RFC 8484）。

符号化は 2 種類ある。

- **RFC 8484 のバイナリ形式。** `Content-Type: application/dns-message` を付けた `POST`、またはメッセージを base64url にして `?dns=` に入れた `GET`。応答本文は DNS メッセージになる。
- **JSON 形式。** `GET ?name=…&type=…` で JSON を受け取る。RFC はなく、Cloudflare のドキュメントは Google のスキーマに従うとしている。フィールドはほぼ共通で、違いは後述する。

Web ページでは JSON 形式が扱いやすい。通常のクロスオリジン `GET` だからだ。2026-11-03 の実測では、両エンドポイントとも `access-control-allow-origin: *` を返し、任意のオリジンのページから応答を読める。ツールは `Accept: application/dns-json` を送る。`Accept` は CORS の安全リストに入った要求ヘッダーなので、これを付けた `GET` はプリフライトを起こさない。独自の `Content-Type` を付けた `POST` や、安全リスト外のヘッダーはプリフライトを起こす。Web ページで JSON 形式が選ばれる理由のひとつだ。

```json
{
  "Status": 0,
  "TC": false,
  "RD": true,
  "RA": true,
  "AD": false,
  "CD": false,
  "Question": [{ "name": "zerotool.dev", "type": 1 }],
  "Answer": [
    { "name": "zerotool.dev", "type": 1, "TTL": 300, "data": "172.67.170.64" },
    { "name": "zerotool.dev", "type": 1, "TTL": 300, "data": "104.21.95.91" }
  ]
}
```

フィールドは DNS ヘッダーと 4 つのセクションを JSON にしたものだ。`Status` は RCODE（RFC 1035 §4.1.1、RFC 6895 で拡張）。0 が NOERROR、2 が SERVFAIL、3 が NXDOMAIN。`TC` は切り詰めフラグで、Cloudflare のドキュメントによれば最大サイズの応答に対応しているため DoH ではほぼ常に false になる。`RD` と `RA` は再帰を表す。`AD` と `CD` は DNSSEC のフラグ。`Question`、`Answer`、`Authority`、`Additional` は DNS の 4 セクションに対応する。`Comment` はリゾルバの診断で、Google は構造化された `extended_dns_errors` も返す。

要求パラメーターはほぼ同じだが完全一致ではない。

| パラメーター | Cloudflare | Google | 意味 |
|---|---|---|---|
| `name` | 必須 | 必須 | 問い合わせ名。Google は RFC 4343 のバックスラッシュエスケープを受け付ける |
| `type` | 省略可、既定 `A` | 省略可、既定 `1` | レコードタイプ。名前でも番号でもよい |
| `do` | `0` / `1` | `0` / `1` | DNSSEC レコード（RRSIG、NSEC、NSEC3）を含める |
| `cd` | `0` / `1` | `0` / `1` | DNSSEC 検証を無効にする |
| `ct` | — | `application/dns-message` | JSON ではなくバイナリの DNS メッセージを返す |
| `edns_client_subnet` | — | `1.2.3.4/24` | クライアントサブネットのヒントを権威サーバーへ渡す |
| `random_padding` | — | 任意の値 | 値は無視される。URL を固定長に埋めてトラフィック分析を難しくする |

両社とも `do` を DNSSEC OK ビット、`cd` を Checking Disabled と説明している。ツールは `do=1` と `cd=0` を送る。署名を求め、検証はリゾルバに任せる設定だ。`do=1` がないと Cloudflare の AD は当てにならない（DNSSEC の節を参照）。

## 10 種類のレコードタイプと、それが答えること

どのタイプも運用上の別の問いに答える。間違ったタイプを選ぶと、存在しない設定ミスを何時間も追いかけることになる。

| タイプ | コード | 問い | 欠落・誤設定で起きる運用障害 |
|---|---:|---|---|
| `A` | 1 | この名前を提供する IPv4 アドレスは？ | 開発者のマシンでは開けるのに他人のマシンでは 404。古い A と新しい A の食い違い。 |
| `AAAA` | 28 | この名前を提供する IPv6 アドレスは？ | AAAA が古いホストを指したままだと、IPv6 を優先するクライアントでサイトが開かない。IPv4 だけの環境では見えない。 |
| `CNAME` | 5 | この別名はどの正規名を指す？ | 削除済みの Heroku アプリや、SaaS の別テナントを指したままの CNAME。 |
| `MX` | 15 | このドメインのメールを受けるサーバーは？ | 受信メールが「no MX record found」で返る、移行後に別プロバイダーへ流れる。 |
| `TXT` | 16 | どんなポリシー文字列が公開されている？ | SPF がソフトフェイル、DMARC レポートで正規メールがスパム判定、ドメイン確認が「pending」のまま。 |
| `NS` | 2 | このゾーンの権威サーバーは？ | レジストラ移管後に NS が旧プロバイダーを指したまま。更新がまったく伝わらない。 |
| `SOA` | 6 | プライマリはどこで、セカンダリはどれくらいで更新する？ | セカンダリが SOA の refresh を過ぎても古いデータを返す。否定応答が長くキャッシュされる。 |
| `CAA` | 257 | このドメインに発行できる認証局は？ | 記載のない CA が発行を拒否し、CA や CDN の移行後に更新が失敗する。 |
| `PTR` | 12 | この IP は自分を何という名前だと主張する？ | 送信 IP の PTR が HELO 名と一致せずメールが返る。レピュテーションサービスが送信者を記録する。 |
| `SRV` | 33 | `_xmpp-client._tcp` などのサービスはどこにある？ | XMPP、SIP、LDAP、Matrix フェデレーションがホストを見つけられない。SRV 欠落かポート違い。 |

ツールの **ALL** は先頭 8 タイプを並列に問い合わせる。「このゾーンについて分かることを全部見たい」に対する既定として妥当だ。PTR と SRV が外れているのは、PTR がドメイン名ではなく `in-addr.arpa` 形式（例：`34.216.184.93.in-addr.arpa`）を要求し、SRV がアンダースコア付きのサービス名（`_xmpp-client._tcp.example.com`）を要求するためだ。どちらも単発の的を絞った照会に向いている。

## A、AAAA、CNAME

`A` と `AAAA` はアドレスと TTL を返す。1 つの名前に複数のレコードがあり、CDN はそれを回す。TTL はリゾルバがそのセットをキャッシュしてよい秒数で、「変更がすべてのリゾルバに届くまでの時間」を約束するものではない。再帰リゾルバごとに、受け取った時刻から別々に数え始める。

`CNAME` は「この名前は別の名前の別名だ」と答える。リゾルバは通常その先をたどり、対象の `A`/`AAAA` も `Answer` に追加する。だから CNAME の照会が複数のタイプを返すことがある。どのレコードがチェーンのどの段かは `name` フィールドで判断する。

CNAME で驚く原因は 2 つの規則に集約される。

- **CNAME のノードに他のデータは置けない。** CNAME を持つ名前は他のレコードを持てない（RFC 1034 §3.6.2、RFC 1912 §2.4）。ゾーン頂点には SOA と NS が必要なので、頂点を素の CNAME にはできない。
- **フラット化は CNAME を隠す。** Cloudflare の CNAME フラット化や Route 53 のエイリアスレコードは、頂点への問い合わせに A/AAAA で答える。そうした頂点を DoH で引くと、管理画面で設定した CNAME ではなくアドレスが返る。正しい挙動だが、別名があると思っている人には「レコードが消えた」ように見える。

## MX と TXT

`MX` は優先度とホスト名を持つ。数字が小さいものから試す（RFC 5321 §5.1）。同じ値は負荷分散のヒントだ。MX がまったくないドメインでは、SMTP はそのドメインの A/AAAA を優先度 0 の暗黙の MX として扱う（RFC 5321 §5.1）。「MX がない＝メールを受け取れない」とは限らない理由である。

**Null MX** は「このドメインはメールを受け取らない」と明示する書き方で、優先度 0、ターゲット `.` の 1 レコードだ（RFC 7505）。受け取るはずのドメインが `0 .` を返したら、所有者が意図して公開している。直すにはゾーンを編集する。伝播を待っても変わらない。

`TXT` はドメイン直下の SPF（RFC 7208）、`_dmarc.example.com` の DMARC（RFC 7489 §6.1）、`セレクター._domainkey.example.com` の DKIM 公開鍵（RFC 6376 §3.6.1）を運ぶ。同じタイプに検索コンソールや SaaS のドメイン確認文字列も入るので、1 回の TXT 照会が十数個の無関係な文字列を返すことがある。

255 バイトの規則がパーサーを壊す。TXT レコードは character-string の並びで、各文字列は最大 255 バイト（RFC 1035 §3.3 と §3.3.14）。長い SPF や DKIM の値は複数の文字列に分かれ、利用側は間に何も入れずにつなぐ（SPF は RFC 7208 §3.3、DKIM は RFC 6376 §3.6.2.2）。2 つの JSON API は見せ方が違う。2026-11-03 の実測では、Cloudflare は各文字列を引用符で囲み空白で区切って返し（`dig` の表示と同じ）、Google は同じ鍵を引用符なしの 1 文字列で返した。`cf2024-1._domainkey.zerotool.dev` の DKIM 公開鍵は、Cloudflare が 255 文字の後ろに `" "` を 1 つ挟んだ 425 文字、Google が 420 文字だった。引用符は付いているときだけ外し、セグメントの間に区切り文字を入れてはいけない。

Google のドキュメントは、TXT が複数の文字列を持っていても 1 つの JSON 文字列として符号化されると説明し、同社の例も引用符付きの断片を示している。実務上の規則はこうだ。`data` は表示用のテキストとして扱い、リゾルバが付けた引用符を外し、区切りなしでつなぐ。

## NS、SOA、否定応答

`NS` はゾーンの権威サーバーを列挙する。答えがどこから来るか、レジストラ移管やプロバイダー移行で委任がずれていないかが分かる。NS セットの TTL は長く（86400 秒がよくある）、変更が全員に見えるまで 1 日かかることがある。

`SOA` はゾーンのプライマリ、責任者のメールボックス、シリアル番号、4 つのタイマー（refresh、retry、expire、minimum）を持つ（RFC 1035 §3.3.13）。シリアルはセカンダリが変更に気づく仕組みで、ゾーン転送が壊れたときはプライマリとセカンダリのシリアルを比べるのが最短の確認だ。

minimum は否定キャッシュも決める。名前が存在しないとき、権威サーバーは NXDOMAIN を返し、authority セクションにゾーンの SOA を入れる。この否定応答は、SOA 自身の TTL と MINIMUM の小さい方の秒数だけキャッシュできる（RFC 2308 §5）。NXDOMAIN をキャッシュしたリゾルバは、ゾーンが直った後もタイマーが切れるまでそれを返す。「ブラウザの照会は正しいのに、1 台のラップトップだけ失敗し続ける」よくある原因のひとつだ。

NXDOMAIN と NODATA は別物だ。NXDOMAIN（`Status` 3）は名前が存在しない。NODATA は NOERROR で回答 0 件、つまり名前は存在するがそのタイプのレコードがない。CAA を持たないドメインの CAA 照会は NODATA で、`Authority` に SOA が入る。綴りを間違えた名前は NXDOMAIN になる。NOERROR で 0 件が返ったら、タイプが間違っている。本当に見たいゾーンの `NS` を確認しよう。

## CAA

CAA（RFC 8659）は、パブリック認証局のうちどれがそのドメインに発行してよいかを示す。準拠する CA は発行前に CAA を確認する。CAA レコードが存在し、どの `issue` プロパティにもその CA の名前がなければ、その CA は発行してはならない（RFC 8659 §3）。CAA レコードがまったく存在しなければ、CAA による発行制限はない。

Let's Encrypt と Google Trust Services を許可し、ワイルドカード証明書を禁止するゾーンはこうなる。

```text
example.com. 0 issue "letsencrypt.org"
example.com. 0 issue "pki.goog"
example.com. 0 issuewild ";"
example.com. 0 iodef "mailto:security@example.com"
```

`issuewild ";"` はすべてのワイルドカード発行を拒否する。`iodef` は、権限のない発行者から要求が来たときに CA が報告を送る先だ。CAA はこの制限が見える唯一の DNS 照会であり、別の CA を使う CDN へ移ったときに更新を忘れると、TLS の問題に見える更新失敗になる。

## PTR と SRV

`PTR` はアドレスから名前への逆引きだ。IPv4 の逆引き名は `in-addr.arpa` の下にオクテットを逆順で置き（RFC 1035 §3.5）、IPv6 は `ip6.arpa` の下にニブルを逆順で置く（RFC 3596 §2.5）。メールサーバーは送信 IP の PTR が存在し HELO 名と一致するかをよく確認するので、PTR の欠落は DNS の問題ではなく配信性の問題として現れる。PTR だけでは所有の証明にならない。その名前が同じアドレスへ正引きで解決することも確認する。

`SRV` はサービスのホストとポートを、優先度と重み付きで `_サービス._プロトコル.ドメイン` の下に公開する（RFC 2782）。対応するクライアントは優先度の小さいものから試し、同じ優先度では重みで負荷を分ける。SRV がない場合、クライアントはドメインの既定ポートに戻る。SRV なしでも動くサービスと、必須のサービスがあるのはこのためだ。

## DNSSEC：AD フラグと EDE

DNSSEC は DNS データに署名を付ける。検証するリゾルバはルートのトラストアンカーからゾーンまで連鎖を確認し、結果を `AD`（Authenticated Data）フラグに入れる。RFC 4035 §3.2.3 がフラグを立ててよい条件を定め、RFC 6840 §5.8 が「問い合わせに DO か AD ビットがあるときだけ立てるべき」と補足している。ツールが `do=1` を送るのはこのためだ。

`do=1` がないと Cloudflare の AD は一定しない。2026-09-30 に各クエリを 30 回ずつ送ると、`example.com` の A・AAAA・NS は毎回 `"AD": false`、MX は毎回 `true` だった。それ以前に A を 20 回送ったときは `true` と `false` が 10 回ずつだった。`do=1` 付きの照会と Google への照会はすべて `true` だった。AD で判断するなら `do=1` を付ける。

署名が揃い連鎖が有効なゾーンは NOERROR と `AD: true` を返す。署名のないゾーンは NOERROR と `AD: false` を返す。これはエラーではなく、DNSSEC を使っていないという意味だ。連鎖が壊れたゾーンは SERVFAIL を返し、検証済みの回答がないので `AD` は false になる。SERVFAIL だけでは「DNSSEC が壊れた」のか「権威サーバーに届かない」のかを区別できない。リゾルバの診断を見る。

その診断が Extended DNS Error（RFC 8914）で、数値コードと人間向けのテキストからなる。DNSSEC で重要なのは 1（未対応の DNSKEY アルゴリズム）、2（未対応の DS ダイジェスト）、5（不定）、6（bogus）、7（署名の期限切れ）、8（署名がまだ有効でない）、9（DNSKEY 欠落）、10（RRSIG 欠落）、12（NSEC 欠落）だ。Cloudflare は `Comment` 配列に `EDE(9): DNSKEY Missing …` の形で入れる。Google は `Comment` に 1 文を返し、別に `info_code` と `extra_text` を持つ `extended_dns_errors` 配列を付ける。ツールは両方を `EDE(n): テキスト` に正規化してレコードの下に表示する。

公開テストドメイン `dnssec-failed.org` で違いが見える。2026-11-03 の実測では、Cloudflare は `Status: 2` と `Comment: ["EDE(9): DNSKEY Missing no SEP matching the DS found for dnssec-failed.org."]` を返した。Google は `Status: 2`、`Comment` は「DNSSEC validation failure」で始まり、`extended_dns_errors: [{ "info_code": 9, "extra_text": "No DNSKEY matches DS RRs of dnssec-failed.org" }]` を伴った。同じ故障だ。親ゾーンが DS を公開しているのに、子ゾーンに一致する DNSKEY がない。

`cd=1` は検証を飛ばす。壊れたゾーンの未検証データを見たいときには有用で、通常の照会では選ばない。ツールは常に `cd=0` を送る。反対側を見たいときは `dig +cd` を使う。

## Cloudflare と Google の実際の違い

両エンドポイントは同じ JSON スキーマを話すが、別のリゾルバであり、ネットワークもキャッシュも違う。実務で効く違いは次のとおり。

- **ECS。** Google Public DNS は既定でおおよそのネットワーク情報を権威サーバーへ送り、通常は IPv4 アドレスの最後の部分を 0 にする。`edns_client_subnet=0.0.0.0/0` で無効にできる。Cloudflare の FAQ は 1.1.1.1 が ECS を送らないとしている。CDN はこれで別のアドレスを返すことがあり、Google の答えは照会元の位置に依存する。2026-09-30 に `www.qq.com` を引くと、`114.114.114.0/24` で `121.14.77.201` と `121.14.77.221`、`8.8.8.0/24` で `43.159.109.55`、`139.130.4.0/24` で `43.168.224.173` が返った。Cloudflare は同じパラメーターを無視し `43.159.109.55` を返した。
- **TXT の見せ方。** Cloudflare は各文字列を引用符で囲み空白で区切る。2026-11-03 の実測で Google は引用符なしの 1 文字列を返した。Google のドキュメントにも引用符付きの例があるので、引用符は表示形式とみなし、API の契約とは考えない。
- **診断。** Cloudflare の `Comment` は EDE 文字列の配列。Google の `Comment` は 1 文で、構造化データは `extended_dns_errors` に入る。キャッシュされていない回答では、Google が `Comment: "Response from <IP>."` を足し、問い合わせた権威サーバーを示す。
- **DNSSEC レコードの表記。** `do=1` では両社とも RRSIG を `Answer` に入れる。テキストは同一ではない。2026-11-03 の照会では、Google が対象タイプを小文字（`a 13 2 …`）、Cloudflare が大文字（`A 13 2 …`）で書いた。
- **順序と名前。** RRset に順序はなく、2 社は別の順で返す。回答を位置で比較せず、集合として比較する。
- **HTTP キャッシュ。** 同じ照会で、Google の応答には `cache-control: private, max-age=300` が付き、Cloudflare には付かなかった。繰り返しの照会はブラウザや中間キャッシュから最大 5 分返ることがある。

TTL が違うのも当然だ。2 つのキャッシュが別の時刻に数え始めているだけで、どちらかが間違っているわけではない。

## ブラウザとシステムリゾルバが食い違う理由

DoH の照会は、ラップトップの `dig` とは別の問いに答えている。違いは不具合ではない。

- **観測点。** `dig` は OS に設定されたリゾルバ（または指定したサーバー）に聞く。DoH は Cloudflare か Google に聞く。キャッシュは別なので、片方が古いレコードを持ち、もう片方が新しい値を持つことがある。
- **hosts ファイルとローカルの上書き。** `dig` と `nslookup` は DNS クエリを送るので、通常 `/etc/hosts` を読まない。通常のアプリケーションの名前解決は OS のリゾルバ経由で hosts を読み、VPN やローカル DNS プロキシが答えを書き換えることもある。公開 DoH リゾルバはそれらを見ない。
- **スプリットホライズン DNS。** 社内ネットワークや VPN のゾーンは、内側には内部アドレスを返し、外側には NXDOMAIN を返す。DoH は外側の見え方を見るので、会社で動く内部名はここでは NXDOMAIN になる。
- **検索ドメイン。** OS は裸のホスト名に検索サフィックスを補うことがある。DoH のエンドポイントは完全な名前を要求する。
- **ブラウザの Secure DNS。** Chrome、Edge、Firefox は、ブラウザが解決するホスト名（`cloudflare-dns.com` や `dns.google` 自身を含む）に独自の DoH を使える。これはブラウザが名前解決に使う経路を変えるが、DoH リクエストが問い合わせる先を変えるわけではない。
- **ブートストラップの問題。** ページはまず通常の経路で `cloudflare-dns.com` か `dns.google` を解決しないと、DoH クエリを送れない。コンテンツフィルターやキャプティブポータルがこの 2 つの名前を遮断すると、クエリ自体が暗号化されていても照会は失敗する。

Pi-hole、NextDNS、AdGuard Home のようなフィルターが、ツールを有用にも誤解を招くものにもするのはこのためだ。フィルターがローカルで止めている間にツールは公開側の答えを返すが、あなたのネットワークでは実際にそのドメインへ届かない。53 番を横取りして fake-IP モードで答えるプロキシが、`dig` に `198.18.2.147` のようなベンチマーク用アドレス（RFC 6890 §2.2.2）を出させ、DoH は実アドレスを返す、ということも起きる。

## よくある誤診

**「まだ伝播中。」** 多くはキャッシュで、TTL が待ち時間を教えてくれる。レコードの TTL を見て、2 つ目のリゾルバに聞く。片方が新値で片方が旧値なら、見ているのはキャッシュの期限切れであって壊れたゾーンではない。

**「DNS が壊れた。1 台だけつながらない。」** 以前の設定ミスで NXDOMAIN をキャッシュしていないか確認する。RFC 2308 §5 により、否定応答は SOA minimum の間キャッシュされる。対処は待つこと、または変更前に SOA minimum を下げることだ。

**「CDN が間違った IP を返す。」** DoH の答えはリゾルバのネットワーク位置を反映する。Google の ECS ヒントは指定したサブネットに近づけるが、Cloudflare は送らない。「サンパウロのユーザーには何が見えるか」は、その地域から引かないと分からない。

**「サイトが開くから DNSSEC は問題ない。」** 検証するリゾルバは失敗し、検証しないリゾルバは成功しうる。EDE コード付きの SERVFAIL は検証失敗の印で、EDE のない SERVFAIL は権威サーバーに届かない可能性が高い。

**「CNAME が見つからない。」** リゾルバが先をたどって A/AAAA を返したか、頂点でフラット化が使われている。別名そのものを引き、各回答の `name` を読む。

**「TXT が途中で切れている。」** 255 バイトの文字列が複数あるだけだ。引用符を外し、区切りなしでつなぐ。

**「MX がないからメールは無理。」** SMTP はドメインの A/AAAA を暗黙の MX として使う（RFC 5321 §5.1）。Null MX（`0 .`）が明示的な「受け取らない」だ。

**「CAA がないから誰も発行できない。」** 逆で、CAA レコードがないことは CAA による制限がないことを意味する。CAA レコードから特定の CA を外すことが、その CA を止める。

## 同じクエリを自分で書く

ツールがあるのは、単発の照会ではクリックの方がスクリプトより速いからだ。自動化なら、JSON 形式は `fetch` のある言語にそのまま収まる。

ブラウザ / Node 18+：

```js
const url = `https://cloudflare-dns.com/dns-query?name=${encodeURIComponent('zerotool.dev')}&type=MX&do=1&cd=0`;
const res = await fetch(url, { headers: { accept: 'application/dns-json' } });
const json = await res.json();
console.log(json.Answer); // [{ name, type, TTL, data }, ...]
```

タイムアウトには `AbortSignal.timeout(5000)`、ネットワーク障害には `try/catch` を足す。両社は同じ全体構造を返すので、プロバイダーの切り替えは URL と固有パラメーターの変更で済む。

Python 標準ライブラリ：

```python
import json
import urllib.request

def doh(name: str, qtype: str, resolver: str = "cloudflare"):
    if resolver == "google":
        url = f"https://dns.google/resolve?name={name}&type={qtype}&cd=0"
        headers = {}
    else:
        url = f"https://cloudflare-dns.com/dns-query?name={name}&type={qtype}&cd=0"
        headers = {"accept": "application/dns-json"}
    req = urllib.request.Request(url, headers=headers)
    with urllib.request.urlopen(req, timeout=5) as resp:
        return json.loads(resp.read())

print(doh("zerotool.dev", "CAA"))
```

シェルと CI では `curl` と `jq`。

```bash
curl -s -H 'accept: application/dns-json' \
  'https://cloudflare-dns.com/dns-query?name=cloudflare.com&type=MX' \
  | jq -r '.Answer[] | select(.type == 15) | "\(.data)"' | sort
```

`do=1` を付けるときは `select(.type == 15)` が重要だ。回答には RRSIG も入るので、`.[]` をそのまま回すとそれらも出力される。

## DNS 照会ツールの中での位置づけ

[DNS Checker](https://dnschecker.org/) は自社サーバーから「世界の複数地域にある選ばれた DNS サーバー」に問い合わせ、伝播マップを描く。「この変更は全リージョンに届いたか」に答える。

[Google Admin Toolbox Dig](https://toolbox.googleapps.com/apps/dig/) は照会を自社バックエンド（`/apps/dig/lookup`）へ送る。2026-09-29 のテストでは `dnssec-failed.org` に対して「Record not found!」と表示し、`rcode SERVFAIL` は Raw 表示にだけ出た。署名済みの `example.com` のフラグ行は `QR RD RA` で、AD はなかった。

`dig` と `kdig` は CLI の参照実装で、スクリプトや権威サーバー指定の照会（`dig @ns1.example.com`）に向く。

ZeroTool のツールはその中間を埋める。`dig` の導入が Homebrew パッケージや WSL ディストリビューションの追加になるようなマシンで、ブラウザから素早く引き、照会サイトのサーバーを経由しない公開リゾルバ自身の答えを見たい開発者向けだ。Cloudflare と Google を切り替えて比べ、AD フラグとリゾルバの注記を見て、生の JSON をコピーできる。伝播マップや権威サーバー限定の照会には向かない。
