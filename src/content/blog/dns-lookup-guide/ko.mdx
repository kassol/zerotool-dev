흔한 사례입니다. `marketing.example.com`이 Webflow를 가리키던 CNAME을 새로 셀프 호스팅한 랜딩 페이지로 바꾸고, DNS 콘솔에서 변경이 반영된 것까지 확인합니다. 5분 후 동료에게서 메시지가 옵니다. "내 노트북에서는 아직 예전 디자인이 보여요." `dig +short marketing.example.com`을 실행하니 새 IP가 돌아옵니다. 동료의 노트북은 다른 리졸버에 묻고 있고, 그 리졸버의 캐시에는 아직 옛 레코드가 남아 있을 수 있습니다. 누구의 캐시가 잘못된 것일까요?

[지금 조회해 보세요 →](/ko/tools/dns-lookup/)

솔직한 답은 "아무도 틀리지 않았다, 변경이 아직 모든 리커시브 리졸버에 도달하지 않았을 뿐이다"입니다. 하지만 리졸버 하나에 `dig` 한 번 친 것만으로는 이것을 증명할 수 없습니다. 여러 공용 리커시브 리졸버에 빠르게 질의해서 비교해야 합니다. 예전에는 CLI 루프, 유료 모니터링 도구, 여러 지역에서 조회해 주는 사이트 중 하나를 써야 했습니다. 브라우저는 도움이 되지 않았습니다. 웹 페이지는 53번 포트의 UDP/TCP 소켓을 열 수 없으니 클래식 DNS를 말할 수 없습니다. 2018년 RFC 8484가 DNS-over-HTTPS를 표준화하고 Cloudflare와 Google이 교차 출처 요청을 받는 공개 DoH 엔드포인트를 제공하면서 `fetch()` 한 번으로 어떤 레코드든 조회할 수 있게 되었습니다.

이 글은 전체 경로를 다룹니다. DoH가 질의를 어떻게 인코딩하는지, 각 레코드 타입이 무엇에 답하는지, DNSSEC과 Extended DNS Error가 JSON 어디에 나오는지, Cloudflare와 Google이 어디서 다른지, CORS와 ECS가 결과에 왜 영향을 주는지, 그리고 브라우저 조회로는 말할 수 없는 것이 무엇인지입니다. 날짜를 붙인 수치는 [DNS 조회 도구](/ko/tools/dns-lookup/)가 보내는 것과 같은 요청의 실측값입니다.

## DNS-over-HTTPS가 바꾼 것

전통적인 DNS 질의는 UDP 53번의 바이너리 메시지이고, 응답이 잘리면 TCP 53번으로 넘어갑니다(RFC 1035 §4.2). 브라우저는 둘 다 소켓 API를 제공하지 않습니다. DoH는 같은 DNS 메시지를 HTTPS 요청으로 감싸므로 질의는 443번의 평범한 웹 트래픽처럼 보이고 경로에서 암호화됩니다(RFC 8484).

인코딩은 두 가지입니다.

- **RFC 8484 바이너리 형식.** `Content-Type: application/dns-message`를 붙인 `POST`, 또는 메시지를 base64url로 인코딩해 `?dns=`에 넣는 `GET`. 응답 본문은 DNS 메시지입니다.
- **JSON 형식.** `GET ?name=…&type=…`으로 JSON을 받습니다. RFC는 없고, Cloudflare 문서는 Google 스키마를 따른다고 밝힙니다. 필드는 거의 같고 차이는 아래에서 다룹니다.

웹 페이지에서는 JSON 형식이 다루기 쉽습니다. 평범한 교차 출처 `GET`이기 때문입니다. 2026-11-03 실측에서 두 엔드포인트 모두 `access-control-allow-origin: *`를 반환해 어떤 출처의 페이지든 응답을 읽을 수 있었습니다. 도구는 `Accept: application/dns-json`을 보냅니다. `Accept`는 CORS 안전 목록 요청 헤더라서 이것을 붙인 `GET`은 프리플라이트를 일으키지 않습니다. 사용자 정의 `Content-Type`을 붙인 `POST`나 안전 목록 밖의 헤더는 프리플라이트를 일으킵니다. 웹 페이지에서 JSON 형식이 선택되는 이유 중 하나입니다.

```json
{
  "Status": 0,
  "TC": false,
  "RD": true,
  "RA": true,
  "AD": false,
  "CD": false,
  "Question": [{ "name": "zerotool.dev", "type": 1 }],
  "Answer": [
    { "name": "zerotool.dev", "type": 1, "TTL": 300, "data": "172.67.170.64" },
    { "name": "zerotool.dev", "type": 1, "TTL": 300, "data": "104.21.95.91" }
  ]
}
```

필드는 DNS 헤더와 네 섹션을 JSON으로 옮긴 것입니다. `Status`는 RCODE입니다(RFC 1035 §4.1.1, RFC 6895에서 확장). 0은 NOERROR, 2는 SERVFAIL, 3은 NXDOMAIN입니다. `TC`는 잘림 플래그이며, Cloudflare 문서에 따르면 최대 크기 응답을 지원하므로 DoH에서는 거의 항상 false입니다. `RD`와 `RA`는 재귀를 나타냅니다. `AD`와 `CD`는 DNSSEC 플래그입니다. `Question`, `Answer`, `Authority`, `Additional`은 DNS의 네 섹션에 대응합니다. `Comment`는 리졸버 진단을 담고, Google은 구조화된 `extended_dns_errors`도 반환합니다.

요청 파라미터는 거의 같지만 완전히 같지는 않습니다.

| 파라미터 | Cloudflare | Google | 의미 |
|---|---|---|---|
| `name` | 필수 | 필수 | 질의 이름. Google은 RFC 4343 역슬래시 이스케이프를 받음 |
| `type` | 선택, 기본 `A` | 선택, 기본 `1` | 레코드 타입. 이름 또는 숫자 |
| `do` | `0` / `1` | `0` / `1` | DNSSEC 레코드(RRSIG, NSEC, NSEC3) 포함 |
| `cd` | `0` / `1` | `0` / `1` | DNSSEC 검증 비활성화 |
| `ct` | — | `application/dns-message` | JSON 대신 바이너리 DNS 메시지 반환 |
| `edns_client_subnet` | — | `1.2.3.4/24` | 클라이언트 서브넷 힌트를 권위 서버로 전달 |
| `random_padding` | — | 임의 값 | 값은 무시됨. URL을 고정 길이로 채워 트래픽 분석을 어렵게 함 |

두 회사 모두 `do`를 DNSSEC OK 비트, `cd`를 Checking Disabled로 설명합니다. 도구는 `do=1`과 `cd=0`을 보냅니다. 서명을 요청하고 검증은 리졸버에 맡기는 설정입니다. `do=1`이 없으면 Cloudflare의 AD를 믿기 어렵습니다(DNSSEC 절 참고).

## 열 가지 레코드 타입과 그것이 답하는 것

각 타입은 운영상 다른 질문에 답합니다. 타입을 잘못 고르면 존재하지도 않는 설정 오류를 몇 시간 쫓게 됩니다.

| 타입 | 코드 | 묻는 것 | 빠지거나 틀렸을 때 흔한 운영 장애 |
|---|---:|---|---|
| `A` | 1 | 이 이름을 서비스하는 IPv4 주소는? | 개발자 머신에서는 열리는데 다른 사람 머신에서는 404. 옛 A와 새 A의 불일치. |
| `AAAA` | 28 | 이 이름을 서비스하는 IPv6 주소는? | AAAA가 옛 호스트를 가리키면 IPv6를 우선하는 클라이언트에서 사이트가 열리지 않음. IPv4만 쓰는 환경에서는 안 보임. |
| `CNAME` | 5 | 이 별칭이 가리키는 정식 이름은? | 삭제된 Heroku 앱이나 SaaS의 다른 테넌트를 가리키는 CNAME. |
| `MX` | 15 | 이 도메인의 메일을 받는 서버는? | 수신 메일이 "no MX record found"로 반송되거나 이전 후 다른 제공자로 흐름. |
| `TXT` | 16 | 어떤 정책 문자열이 게시되어 있나? | SPF가 소프트페일, DMARC 리포트에서 정상 메일이 스팸으로 분류, 도메인 확인이 "pending"에 멈춤. |
| `NS` | 2 | 이 존의 권위 서버는? | 레지스트라 이전 후 NS가 옛 제공자를 가리켜 변경이 전혀 전파되지 않음. |
| `SOA` | 6 | 프라이머리는 어디이고 세컨더리는 얼마나 자주 갱신하나? | 세컨더리가 SOA refresh를 지나도 옛 데이터를 반환. 부정 응답이 너무 오래 캐시됨. |
| `CAA` | 257 | 이 도메인에 발급할 수 있는 인증 기관은? | 목록에 없는 CA가 발급을 거부해 CA나 CDN 이전 후 갱신이 실패. |
| `PTR` | 12 | 이 IP는 자기를 어떤 이름이라고 주장하나? | 발신 IP의 PTR이 HELO 이름과 맞지 않아 메일이 반송되고 평판 서비스가 발신자를 표시. |
| `SRV` | 33 | `_xmpp-client._tcp` 같은 서비스는 어디에 있나? | XMPP, SIP, LDAP, Matrix 연합이 호스트를 찾지 못함. SRV 누락 또는 포트 오류. |

도구의 **ALL**은 앞의 여덟 타입을 병렬로 질의합니다. "이 존에 대해 아는 것을 모두 보여 달라"에 대한 합리적인 기본값입니다. PTR과 SRV가 빠지는 이유는 PTR이 도메인 이름이 아니라 `in-addr.arpa` 형식(예: `34.216.184.93.in-addr.arpa`)을 요구하고, SRV가 밑줄 접두사가 붙은 서비스 이름(`_xmpp-client._tcp.example.com`)을 요구하기 때문입니다. 둘 다 단일 타입의 표적 조회에 더 알맞습니다.

## A, AAAA, CNAME

`A`와 `AAAA`는 주소와 TTL을 반환합니다. 한 이름에 여러 레코드가 있을 수 있고 CDN은 이를 돌립니다. TTL은 리졸버가 그 레코드 집합을 캐시해도 되는 초 수이며, "변경이 모든 리졸버에 도달하는 시간"을 약속하지 않습니다. 리커시브 리졸버마다 받은 시점부터 따로 세기 시작합니다.

`CNAME`은 "이 이름은 다른 이름의 별칭"이라고 답합니다. 리졸버는 보통 그 사슬을 따라가 대상의 `A`/`AAAA`도 `Answer`에 넣습니다. 그래서 CNAME 조회가 여러 타입을 반환할 수 있습니다. 각 레코드가 사슬의 어느 단계인지는 `name` 필드로 판단합니다.

CNAME에서 놀라는 이유는 두 규칙으로 모입니다.

- **CNAME 노드에는 다른 데이터를 둘 수 없습니다.** CNAME이 있는 이름은 다른 레코드를 가질 수 없습니다(RFC 1034 §3.6.2, RFC 1912 §2.4). 존 에이펙스에는 SOA와 NS가 있어야 하므로 에이펙스가 순수 CNAME이 될 수 없습니다.
- **평탄화는 CNAME을 숨깁니다.** Cloudflare의 CNAME 평탄화와 Route 53의 별칭 레코드는 에이펙스 질의에 A/AAAA로 답합니다. 그런 에이펙스를 DoH로 조회하면 대시보드에서 설정한 CNAME이 아니라 주소가 돌아옵니다. 올바른 동작이지만 별칭이 있다고 기대한 사람에게는 레코드가 사라진 것처럼 보입니다.

## MX와 TXT

`MX`는 우선순위와 호스트 이름을 가집니다. 숫자가 작은 것부터 시도합니다(RFC 5321 §5.1). 같은 값은 부하 분산 힌트입니다. MX가 전혀 없는 도메인에서는 SMTP가 그 도메인의 A/AAAA를 우선순위 0의 암묵적 MX로 취급합니다(RFC 5321 §5.1). "MX가 없으면 메일을 못 받는다"가 항상 참은 아닌 이유입니다.

**Null MX**는 "이 도메인은 메일을 받지 않는다"를 명시하는 방법으로, 우선순위 0, 대상 `.`인 레코드 하나입니다(RFC 7505). 메일을 받아야 하는 도메인이 `0 .`을 반환하면 소유자가 의도적으로 게시한 것입니다. 고치려면 존을 편집해야 하고, 전파를 기다려도 바뀌지 않습니다.

`TXT`는 도메인 자체의 SPF(RFC 7208), `_dmarc.example.com`의 DMARC(RFC 7489 §6.1), `선택자._domainkey.example.com`의 DKIM 공개 키(RFC 6376 §3.6.1)를 담습니다. 같은 타입에 검색 콘솔과 SaaS의 도메인 확인 문자열도 들어가므로 한 번의 TXT 조회가 서로 무관한 문자열 십여 개를 반환할 수 있습니다.

255바이트 규칙이 파서를 깨뜨립니다. TXT 레코드는 character-string의 나열이고 각 문자열은 최대 255바이트입니다(RFC 1035 §3.3, §3.3.14). 긴 SPF나 DKIM 값은 여러 문자열로 나뉘고, 사용하는 쪽은 사이에 아무것도 넣지 않고 잇습니다(SPF는 RFC 7208 §3.3, DKIM은 RFC 6376 §3.6.2.2). 두 JSON API는 보여 주는 방식이 다릅니다. 2026-11-03 실측에서 Cloudflare는 각 문자열을 따옴표로 감싸고 공백으로 구분했으며(`dig` 출력과 같음), Google은 같은 키를 따옴표 없는 한 문자열로 반환했습니다. `cf2024-1._domainkey.zerotool.dev`의 DKIM 공개 키는 Cloudflare가 255자 뒤에 `" "` 하나를 넣은 425자, Google이 420자였습니다. 따옴표는 붙어 있을 때만 벗기고, 세그먼트 사이에 구분자를 넣지 마세요.

Google 문서는 TXT 레코드가 여러 문자열을 가져도 하나의 JSON 문자열로 인코딩된다고 설명하고, 자사 예시도 따옴표가 붙은 조각을 보여 줍니다. 실무 규칙은 이렇습니다. `data`를 표시용 텍스트로 보고, 리졸버가 붙인 따옴표를 제거한 뒤 구분자 없이 잇습니다.

## NS, SOA, 부정 응답

`NS`는 존의 권위 서버를 나열합니다. 답이 어디서 오는지, 레지스트라 이전이나 제공자 마이그레이션에서 위임이 잘못되지 않았는지 보여 줍니다. NS 집합의 TTL은 길어서(86400초가 흔함) 변경이 모든 곳에 보이기까지 하루가 걸릴 수 있습니다.

`SOA`는 존의 프라이머리, 책임자 메일박스, 시리얼 번호, 네 개의 타이머(refresh, retry, expire, minimum)를 가집니다(RFC 1035 §3.3.13). 시리얼은 세컨더리가 변경을 알아차리는 수단이고, 존 전송이 깨졌을 때 프라이머리와 세컨더리의 시리얼을 비교하는 것이 가장 빠른 확인입니다.

minimum은 부정 캐시도 결정합니다. 이름이 없을 때 권위 서버는 NXDOMAIN을 반환하고 authority 섹션에 존의 SOA를 넣습니다. 이 부정 응답은 SOA 자체의 TTL과 MINIMUM 중 작은 초만큼 캐시할 수 있습니다(RFC 2308 §5). NXDOMAIN을 캐시한 리졸버는 존이 고쳐진 뒤에도 타이머가 끝날 때까지 그것을 계속 반환합니다. "브라우저 조회는 맞는데 한 노트북만 계속 실패"하는 흔한 원인 중 하나입니다.

NXDOMAIN과 NODATA는 다릅니다. NXDOMAIN(`Status` 3)은 이름이 존재하지 않는다는 뜻입니다. NODATA는 NOERROR인데 답이 0건, 즉 이름은 있지만 요청한 타입의 레코드가 없다는 뜻입니다. CAA가 없는 도메인의 CAA 조회는 NODATA이고 `Authority`에 SOA가 들어갑니다. 철자를 틀린 이름은 NXDOMAIN입니다. NOERROR에 0건이 오면 타입이 잘못된 질문입니다. 실제로 보고 싶은 존의 `NS`를 확인하세요.

## CAA

CAA(RFC 8659)는 공용 인증 기관 중 어느 CA가 그 도메인에 발급할 수 있는지 알려 줍니다. 규정을 따르는 CA는 발급 전에 CAA를 확인합니다. CAA 레코드가 있고 어떤 `issue` 속성에도 해당 CA의 이름이 없으면 그 CA는 발급해서는 안 됩니다(RFC 8659 §3). CAA 레코드 자체가 없으면 CAA에 의한 발급 제한이 없다는 뜻입니다.

Let's Encrypt와 Google Trust Services를 허용하고 와일드카드 인증서를 막는 존은 이렇습니다.

```text
example.com. 0 issue "letsencrypt.org"
example.com. 0 issue "pki.goog"
example.com. 0 issuewild ";"
example.com. 0 iodef "mailto:security@example.com"
```

`issuewild ";"`는 모든 와일드카드 발급을 거부합니다. `iodef`는 권한 없는 발급자가 요청했을 때 CA가 보고를 보낼 곳입니다. CAA는 이 제한이 보이는 유일한 DNS 조회이며, 다른 CA를 쓰는 CDN으로 옮기면서 갱신을 잊으면 TLS 문제처럼 보이는 갱신 실패가 됩니다.

## PTR과 SRV

`PTR`은 주소에서 이름으로 가는 역방향 조회입니다. IPv4 역방향 이름은 `in-addr.arpa` 아래에 옥텟을 거꾸로 놓고(RFC 1035 §3.5), IPv6는 `ip6.arpa` 아래에 니블을 거꾸로 놓습니다(RFC 3596 §2.5). 메일 서버는 발신 IP의 PTR이 있는지, HELO 이름과 맞는지 자주 확인하므로 PTR 누락은 DNS 문제가 아니라 전달성 문제로 나타납니다. PTR만으로 소유를 증명할 수는 없습니다. 그 이름이 같은 주소로 정방향 조회되는지도 확인하세요.

`SRV`는 서비스의 호스트와 포트를 우선순위, 가중치와 함께 `_서비스._프로토콜.도메인` 아래에 게시합니다(RFC 2782). 지원하는 클라이언트는 우선순위가 작은 것부터 시도하고 같은 우선순위에서는 가중치로 부하를 나눕니다. SRV가 없으면 클라이언트는 도메인의 기본 포트로 돌아갑니다. SRV 없이도 되는 서비스와 반드시 필요한 서비스가 있는 이유입니다.

## DNSSEC: AD 플래그와 EDE

DNSSEC은 DNS 데이터에 서명을 붙입니다. 검증하는 리졸버는 루트 트러스트 앵커에서 존까지 사슬을 확인하고 결과를 `AD`(Authenticated Data) 플래그에 넣습니다. RFC 4035 §3.2.3이 플래그를 세울 수 있는 조건을 정하고, RFC 6840 §5.8이 "질의에 DO나 AD 비트가 있을 때만 세워야 한다"고 보탭니다. 도구가 `do=1`을 보내는 이유입니다.

`do=1`이 없으면 Cloudflare의 AD가 일정하지 않습니다. 2026-09-30에 질의마다 30번씩 보냈더니 `example.com`의 A, AAAA, NS는 매번 `"AD": false`, MX는 매번 `true`였습니다. 그 전에 A를 20번 보냈을 때는 `true`와 `false`가 10번씩 나왔습니다. `do=1`을 붙인 질의와 Google 질의는 모두 `true`였습니다. AD로 판단하려면 `do=1`을 붙이세요.

서명이 갖춰지고 사슬이 유효한 존은 NOERROR와 `AD: true`를 반환합니다. 서명이 없는 존은 NOERROR와 `AD: false`를 반환합니다. 오류가 아니라 DNSSEC을 쓰지 않는다는 뜻입니다. 사슬이 깨진 존은 SERVFAIL을 반환하고, 검증된 답이 없으므로 `AD`는 false입니다. SERVFAIL만으로는 "DNSSEC이 깨졌다"와 "권위 서버에 닿지 않는다"를 구분할 수 없습니다. 리졸버 진단을 봐야 합니다.

그 진단이 Extended DNS Error(RFC 8914)이고, 숫자 코드와 사람이 읽는 텍스트로 이루어집니다. DNSSEC에서 중요한 코드는 1(지원하지 않는 DNSKEY 알고리즘), 2(지원하지 않는 DS 다이제스트), 5(불확정), 6(bogus), 7(서명 만료), 8(서명 아직 유효하지 않음), 9(DNSKEY 누락), 10(RRSIG 누락), 12(NSEC 누락)입니다. Cloudflare는 `Comment` 배열에 `EDE(9): DNSKEY Missing …` 형태로 넣습니다. Google은 `Comment`에 한 문장을 넣고, 별도로 `info_code`와 `extra_text`를 가진 `extended_dns_errors` 배열을 붙입니다. 도구는 둘을 `EDE(n): 텍스트`로 정규화해 레코드 아래에 보여 줍니다.

공개 테스트 도메인 `dnssec-failed.org`에서 차이가 보입니다. 2026-11-03 실측에서 Cloudflare는 `Status: 2`와 `Comment: ["EDE(9): DNSKEY Missing no SEP matching the DS found for dnssec-failed.org."]`를 반환했습니다. Google은 `Status: 2`, `Comment`는 "DNSSEC validation failure"로 시작했고 `extended_dns_errors: [{ "info_code": 9, "extra_text": "No DNSKEY matches DS RRs of dnssec-failed.org" }]`를 함께 보냈습니다. 같은 고장입니다. 부모 존이 DS를 게시했는데 자식 존에 일치하는 DNSKEY가 없습니다.

`cd=1`은 검증을 건너뜁니다. 깨진 존의 미검증 데이터를 볼 때 유용하고, 일상 조회에는 맞지 않습니다. 도구는 항상 `cd=0`을 보냅니다. 반대쪽을 보려면 `dig +cd`를 쓰세요.

## Cloudflare와 Google의 실제 차이

두 엔드포인트는 같은 JSON 스키마를 쓰지만 서로 다른 리졸버이고 네트워크와 캐시가 다릅니다. 실무에서 문제가 되는 차이는 이렇습니다.

- **ECS.** Google Public DNS는 기본으로 대략적인 네트워크 정보를 권위 서버에 보내며, 보통 IPv4 주소의 마지막 부분을 0으로 만듭니다. `edns_client_subnet=0.0.0.0/0`으로 끌 수 있습니다. Cloudflare FAQ는 1.1.1.1이 ECS를 보내지 않는다고 밝힙니다. 그래서 CDN이 두 리졸버에 다른 주소를 줄 수 있고, Google의 답은 질의가 어디서 왔는지에 따라 달라집니다. 2026-09-30에 `www.qq.com`을 조회하니 `114.114.114.0/24`에서 `121.14.77.201`과 `121.14.77.221`, `8.8.8.0/24`에서 `43.159.109.55`, `139.130.4.0/24`에서 `43.168.224.173`이 나왔습니다. Cloudflare는 같은 파라미터를 무시하고 `43.159.109.55`를 반환했습니다.
- **TXT 표시.** Cloudflare는 각 문자열을 따옴표로 감싸고 공백으로 구분합니다. 2026-11-03 실측에서 Google은 따옴표 없는 한 문자열을 반환했습니다. Google 문서에도 따옴표가 붙은 예가 있으므로 따옴표는 표시 형식으로 보고 API 계약으로 보지 마세요.
- **진단.** Cloudflare의 `Comment`는 EDE 문자열 배열입니다. Google의 `Comment`는 한 문장이고 구조화 데이터는 `extended_dns_errors`에 있습니다. 캐시되지 않은 답에는 Google이 `Comment: "Response from <IP>."`를 더해 어느 권위 서버에 물었는지 보여 줍니다.
- **DNSSEC 레코드 표기.** `do=1`이면 두 회사 모두 RRSIG를 `Answer`에 넣습니다. 텍스트는 같지 않습니다. 2026-11-03 조회에서 Google은 대상 타입을 소문자(`a 13 2 …`), Cloudflare는 대문자(`A 13 2 …`)로 썼습니다.
- **순서와 이름.** RRset에는 순서가 없고 두 회사는 다른 순서로 반환합니다. 답을 위치로 비교하지 말고 집합으로 비교하세요.
- **HTTP 캐시.** 같은 조회에서 Google 응답에는 `cache-control: private, max-age=300`이 붙었고 Cloudflare에는 없었습니다. 반복 조회가 브라우저나 중간 캐시에서 최대 5분 동안 반환될 수 있습니다.

TTL이 다른 것도 당연합니다. 두 캐시가 다른 시각에 세기 시작했을 뿐이고, 어느 한쪽이 틀린 것이 아닙니다.

## 브라우저와 시스템 리졸버가 다른 이유

DoH 조회는 노트북의 `dig`와 다른 질문에 답합니다. 차이는 버그가 아닙니다.

- **관측 지점.** `dig`는 OS에 설정된 리졸버(또는 지정한 서버)에 묻습니다. DoH는 Cloudflare나 Google에 묻습니다. 캐시가 따로라서 한쪽은 옛 레코드를, 다른 쪽은 새 값을 가질 수 있습니다.
- **hosts 파일과 로컬 재정의.** `dig`와 `nslookup`은 DNS 질의를 보내므로 보통 `/etc/hosts`를 읽지 않습니다. 일반 애플리케이션의 이름 해석은 OS 리졸버를 거쳐 hosts를 읽고, VPN이나 로컬 DNS 프록시가 답을 바꿀 수 있습니다. 공용 DoH 리졸버는 이것을 보지 못합니다.
- **스플릿 호라이즌 DNS.** 사내 네트워크와 VPN 존은 안쪽에는 내부 주소를, 바깥에는 NXDOMAIN을 반환합니다. DoH는 바깥 관점을 보므로 회사에서 되는 내부 이름이 여기서는 NXDOMAIN입니다.
- **검색 도메인.** OS는 짧은 호스트 이름에 검색 접미사를 붙일 수 있습니다. DoH 엔드포인트는 완전한 이름을 요구합니다.
- **브라우저 Secure DNS.** Chrome, Edge, Firefox는 브라우저가 해석하는 호스트 이름(`cloudflare-dns.com`이나 `dns.google` 자체 포함)에 자체 DoH를 쓸 수 있습니다. 이 설정은 브라우저가 이름을 해석하는 경로를 바꾸지만, DoH 요청이 묻는 리졸버를 바꾸지는 않습니다.
- **부트스트랩 문제.** 페이지는 먼저 정상 경로로 `cloudflare-dns.com`이나 `dns.google`을 해석해야 DoH 질의를 보낼 수 있습니다. 콘텐츠 필터나 캡티브 포털이 이 두 이름을 막으면 질의 자체가 암호화되어 있어도 조회는 실패합니다.

Pi-hole, NextDNS, AdGuard Home 같은 필터가 도구를 유용하게도, 오해를 부르게도 만드는 이유입니다. 필터가 로컬에서 막는 동안 도구는 공개 측 답을 보여 주지만, 당신의 네트워크에서는 실제로 그 도메인에 닿지 않습니다. 53번을 가로채 fake-IP 모드로 답하는 프록시가 `dig`에 `198.18.2.147` 같은 벤치마크용 주소(RFC 6890 §2.2.2)를 출력하게 하고 DoH는 실제 주소를 반환하는 일도 있습니다.

## 흔한 오진

**"아직 전파 중이다."** 대개는 캐시이고 TTL이 기다릴 시간을 알려 줍니다. 레코드의 TTL을 보고 두 번째 리졸버에 물어보세요. 한쪽은 새 값, 다른 쪽은 옛 값이면 캐시 만료를 보고 있는 것이지 존이 깨진 것이 아닙니다.

**"DNS가 고장 나서 한 대만 안 된다."** 이전 설정 오류로 NXDOMAIN을 캐시했는지 확인하세요. RFC 2308 §5에 따라 부정 응답은 SOA minimum 동안 캐시됩니다. 해법은 기다리거나, 변경 전에 SOA minimum을 낮추는 것입니다.

**"CDN이 잘못된 IP를 준다."** DoH 답은 리졸버의 네트워크 위치를 반영합니다. Google의 ECS 힌트는 지정한 서브넷에 가깝게 만들지만 Cloudflare는 보내지 않습니다. "상파울루 사용자에게 무엇이 보이나"는 그 지역에서 조회해야 알 수 있습니다.

**"사이트가 열리니 DNSSEC은 문제없다."** 검증하는 리졸버는 실패하고 검증하지 않는 리졸버는 성공할 수 있습니다. EDE 코드가 붙은 SERVFAIL은 검증 실패의 표시이고, EDE가 없는 SERVFAIL은 권위 서버에 닿지 못할 가능성이 큽니다.

**"CNAME이 사라졌다."** 리졸버가 따라가서 A/AAAA를 반환했거나 에이펙스에서 평탄화를 썼습니다. 별칭 자체를 조회하고 각 답의 `name` 필드를 읽으세요.

**"TXT가 잘렸다."** 255바이트 문자열이 여러 개 있는 것입니다. 따옴표를 벗기고 구분자 없이 이으세요.

**"MX가 없으니 메일은 불가능하다."** SMTP는 도메인의 A/AAAA를 암묵적 MX로 씁니다(RFC 5321 §5.1). Null MX(`0 .`)가 명시적인 "받지 않음"입니다.

**"CAA가 없으니 아무도 발급할 수 없다."** 반대입니다. CAA 레코드가 없다는 것은 CAA 제한이 없다는 뜻입니다. CAA 레코드에서 특정 CA를 빼는 것이 그 CA를 막습니다.

## 같은 질의를 직접 작성하기

도구가 있는 이유는 일회성 조회에서 클릭이 스크립트보다 빠르기 때문입니다. 자동화에는 JSON 형식이 `fetch`가 있는 어떤 언어에도 들어갈 만큼 짧습니다.

브라우저 / Node 18+:

```js
const url = `https://cloudflare-dns.com/dns-query?name=${encodeURIComponent('zerotool.dev')}&type=MX&do=1&cd=0`;
const res = await fetch(url, { headers: { accept: 'application/dns-json' } });
const json = await res.json();
console.log(json.Answer); // [{ name, type, TTL, data }, ...]
```

타임아웃에는 `AbortSignal.timeout(5000)`, 네트워크 실패에는 `try/catch`를 더하세요. 두 회사는 같은 전체 구조를 반환하므로 제공자 전환은 URL과 고유 파라미터 변경으로 끝납니다.

Python 표준 라이브러리:

```python
import json
import urllib.request

def doh(name: str, qtype: str, resolver: str = "cloudflare"):
    if resolver == "google":
        url = f"https://dns.google/resolve?name={name}&type={qtype}&cd=0"
        headers = {}
    else:
        url = f"https://cloudflare-dns.com/dns-query?name={name}&type={qtype}&cd=0"
        headers = {"accept": "application/dns-json"}
    req = urllib.request.Request(url, headers=headers)
    with urllib.request.urlopen(req, timeout=5) as resp:
        return json.loads(resp.read())

print(doh("zerotool.dev", "CAA"))
```

셸과 CI에서는 `curl`과 `jq`.

```bash
curl -s -H 'accept: application/dns-json' \
  'https://cloudflare-dns.com/dns-query?name=cloudflare.com&type=MX' \
  | jq -r '.Answer[] | select(.type == 15) | "\(.data)"' | sort
```

`do=1`을 붙일 때는 `select(.type == 15)`가 중요합니다. 답에 RRSIG도 들어가므로 `.[]`를 그대로 돌리면 그것들도 출력됩니다.

## DNS 조회 도구 사이에서의 위치

[DNS Checker](https://dnschecker.org/)는 자사 서버에서 "전 세계 여러 지역의 선택된 DNS 서버"에 질의하고 전파 지도를 그립니다. "이 변경이 모든 지역에 도달했나"에 답합니다.

[Google Admin Toolbox Dig](https://toolbox.googleapps.com/apps/dig/)는 질의를 자사 백엔드(`/apps/dig/lookup`)로 보냅니다. 2026-09-29 테스트에서 `dnssec-failed.org`에 "Record not found!"를 표시했고 `rcode SERVFAIL`은 Raw 보기에만 나왔습니다. 서명된 `example.com`의 플래그 줄은 `QR RD RA`였고 AD는 없었습니다.

`dig`와 `kdig`는 CLI 참조 구현이며, 스크립팅과 권위 서버 지정 조회(`dig @ns1.example.com`)에 맞습니다.

ZeroTool 도구는 그 중간을 채웁니다. `dig` 설치가 Homebrew 패키지나 WSL 배포판 추가를 뜻하는 머신에서 브라우저로 빠르게 조회하고, 조회 사이트의 서버를 거치지 않은 공용 리졸버 자체의 답을 보고 싶은 개발자를 위한 것입니다. Cloudflare와 Google을 바꿔 가며 비교하고, AD 플래그와 리졸버 메모를 보고, 원본 JSON을 복사할 수 있습니다. 전파 지도나 권위 전용 조회에는 맞지 않습니다.
