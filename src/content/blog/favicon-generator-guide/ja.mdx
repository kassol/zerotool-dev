Google で技術的なことを検索し、各結果のサイト名の横にある小さなアイコンを見てください。それがサイトのファビコンです。Google は 2019 年にモバイル検索結果でファビコンの表示を始め、現在は結果のサイト名の横に表示しています（[Google 検索セントラル](https://developers.google.com/search/docs/appearance/favicon-in-search?hl=ja)）。そこで見分けのつくファビコンがないサイトは放置されているように見え、くっきりとしたブランドらしいファビコンがあれば手入れが行き届いて見えます。この小さなマークは、ユーザーがクリックするかどうか決める場所でドメインの隣に表示されます。

[Favicon ジェネレーターを開く →](/ja/tools/favicon-generator/)

その小さなマークは、ブラウザタブ・ブックマークバー・OS タスクバー・iOS ホーム画面・Android PWA インストール・RSS リーダー・ショートカットタイルを横断して生き残る、数少ないビジュアル要素の 1 つです。それぞれの場面が少しずつ違うファイルを要求します — サイズが違い、ときに形式が違い、ときに専用の manifest エントリが必要です。本稿は、モダンな favicon セットの実際の姿、なぜ単一の `favicon.ico` ではもう足りないか、ランタイムで各ファイルが何の役割を担うか、そして ZeroTool ジェネレーターがどのようにバイトをアップロードせずブラウザ内でパッケージを組み立てるかを扱います。

## モダンブラウザが実際に要求するファイル

ブラウザがどのファイルを取りに行くかは、ページの `<link>` タグとユーザーの操作で決まります。自分のサイトで DevTools を開いてリロードし、Network パネルを見てください。デスクトップブラウザは通常、タブ用に選んだアイコン 1 つだけを取得します。入り口は次の 3 つです：

| リクエスト | 用途 | 備考 |
|---|---|---|
| `/favicon.ico` | ページがアイコンを宣言していないとき、ブラウザはこのパスにフォールバックする | 複数サイズのコンテナ。ルートのパスしか試さないツールやクローラーのために残しておく |
| `<link rel="icon">` の href が指す画像 | タブ、ブックマーク、履歴 | ブラウザは `sizes` と `type` で候補から選ぶ。[HTML 標準](https://html.spec.whatwg.org/multipage/links.html#rel-icon)は選択をブラウザに任せている |
| `<link rel="apple-touch-icon">` の href が指す画像 | iOS Safari の「ホーム画面に追加」 | 標準サイズは 180×180 |

Android Chrome で PWA としてインストールすると、リクエストは増えます：

| リクエスト | 用途 |
|---|---|
| `/site.webmanifest`（または `manifest.json`） | Chrome、Edge、Brave、Samsung Internet — PWA をインストールできる場所すべて |
| manifest の `icons` 配列で宣言された 192×192 と 512×512 PNG | Android ホーム画面アイコン、起動画面、Android 共有シート |

アイコンを `purpose: "maskable"` と指定すると、Android はランチャーに応じて円形や角丸四角のマスクをかけ、ランチャーのグリッドでネイティブアプリのように見せます。maskable アイコンは見える部分をセーフゾーン（アイコンサイズの 40% を半径とする円、各辺およそ 10% の余白）に収める必要があり、はみ出すとマスクで切られます（[web.dev](https://web.dev/articles/maskable-icon)）。web.dev は 1 つのファイルに `"any maskable"` を書くことを勧めていません。マスク用に余白を取ったアイコンは、そのまま表示される場所で小さく見えるためです。`any` 用と `maskable` 用は別ファイルにしましょう。

そして長いテールがあります。Windows 8・10 のピン留めサイトのタイルは `browserconfig.xml` を読みますが、Windows 11 にはライブタイルがありません。古い Safari はピン留めタブを `<link rel="mask-icon">` で宣言した単色 SVG で描いていました。古い Android Chrome はホーム画面のショートカットに `apple-touch-icon` を使っていました。一部のジェネレーターが 20 以上のファイルを出力するのはこのためです。

## なぜ単一の `favicon.ico` では足りないか

歴史的なデフォルトは、ICO を 1 つサイトルートに置いてブラウザに任せる、でした。モニタが最大 1280×1024、タブが 16 ピクセル四方だった頃はそれで十分でした。2 つの出来事がそれを壊しました：

1. **Retina ディスプレイ。** 16×16 の ICO をブラウザが 32 論理ピクセルに拡大して 2× ディスプレイで表示すると、ぼやけます。`<link rel="icon" type="image/png" sizes="32x32">` タグはブラウザにデバイスピクセル比に合った正しいリソースを選ばせます。
2. **タブ以外の OS サーフェス。** iOS のホーム画面アイコン、Android のホーム画面アイコン、PWA のスプラッシュ画面は、それぞれセットから特定のサイズを取り、どれも 16 ピクセルの ICO は使いません。必要なのは 180、192、512 と、どれが何かを伝える manifest です。

修正策はモダンセットです：互換のための小さな ICO、モダンな `<link rel="icon">` 用のいくつかの PNG サイズ、iOS 用の apple-touch-icon、そして PWA アイコンを含む webmanifest。

## ICO 形式の仕組み

`favicon.ico` はセット中で最も奇妙なファイルです。PNG より古く、Windows 3.0 で生まれ、当初はデバイス独立ビットマップ（DIB / BMP）フレームを運んでいました。今のジェネレーターはほとんどが PNG 圧縮エントリを使い、Windows Vista 以降のシェル、IE 11、それ以降のすべてのブラウザがネイティブサポートしています。PNG 圧縮エントリは小さく、アルファを保持し、フォーマットも素直です。

ICO ファイルは次の構造です：

```text
ICONDIR (6 バイト)
├── reserved (2 バイト、ゼロ)
├── type (2 バイト、1 = ICO、2 = CUR)
└── count (2 バイト)

ICONDIRENTRY × count (各 16 バイト)
├── width (1 バイト、0 は 256 を意味)
├── height (1 バイト、0 は 256 を意味)
├── colorCount (1 バイト、32-bit ではゼロ)
├── reserved (1 バイト、ゼロ)
├── colorPlanes (2 バイト、1)
├── bitsPerPixel (2 バイト、32)
├── imageSize (4 バイト)
└── imageOffset (4 バイト — ICO ファイル内の絶対オフセット)

(画像ペイロードはディレクトリの後ろに連結)
```

PNG エントリの場合、imageSize は完全な PNG ファイル（自身の IHDR / IDAT / IEND チャンクを含む）のサイズで、imageOffset はその PNG の先頭バイトを指します。ICONDIRENTRY の幅と高さは PNG 自身の幅と高さに合わせてください。読み取り側はデコードする前にディレクトリを見てエントリを選びます。

ZeroTool ジェネレーターは 16・32・48 の PNG を ICO に詰め、それより大きいサイズは入れません。より多くのピクセルが必要なブラウザは `<link rel="icon">` の PNG、apple-touch-icon、manifest から取得します。この ICO を Windows のデスクトップアイコン（256×256 まで使われる）にも使いたいなら、そのサイズを含む ICO を別に作ってください。

## ZIP コンテナの仕組み

ブラウザは 11 ファイルを 11 回のダウンロードを発火させずに 1 クリックで届ける必要があり、ジェネレーターはそれらを ZIP にまとめます。ZIP はサードパーティツールなしにどの OS でも開けるため、長年デフォルトコンテナです。中身は層構造です：local file header と続くペイロードのシーケンス、その後すべてのエントリをリストする「central directory」、最後にリーダーへ central directory の開始位置を伝える「end-of-central-directory」レコード。

各エントリのペイロードエンコード方法は 2 つ：STORED（無圧縮）か DEFLATE。PNG はすでに圧縮済みなので、DEFLATE をかけてもほとんど縮みません。ZeroTool ジェネレーターは全エントリに STORED を使い、DEFLATE の実装をページに載せていません。

CRC-32 は ZIP 仕様で唯一スキップできない部分です。各エントリは未圧縮バイトの 32-bit CRC を必ず持つ必要があります。ジェネレーターはスクリプト起動時に 256 エントリのルックアップテーブルを事前計算し、ファイル毎にバイトを 1 回スキャンします。ファイル名は General Purpose Bit Field のビット 11 で UTF-8 として宣言され、macOS Finder、Windows Explorer、7-Zip で非 ASCII 名がそのまま読めます。

## Canvas パイプライン

各 PNG の描画は同じ 5 ステップを踏みます：

```javascript
// 1 つのターゲットサイズの擬似コード
const canvas = createCanvas(size, size);
const ctx = canvas.getContext('2d');

if (shape !== 'square') {
  drawShapePath(ctx, shape, size);
  ctx.clip();           // 角丸 / 円形のアルファマスク
}
if (bgMode === 'color') {
  ctx.fillStyle = bgColor;
  ctx.fillRect(0, 0, size, size);
}
const inner = size * (1 - padding * 2);
drawSourceCentered(ctx, source, size, inner);  // emoji / text / image / svg
const pngArrayBuffer = await canvasToPng(canvas);
```

`canvas.toBlob('image/png')` が重労働を担います — リサンプリング、アルファのエンコード。出力は `IHDR`、1 つ以上の `IDAT` チャンク、`IEND` を持つ完全な PNG です。IDAT 内の zlib 圧縮レベルはブラウザが決めるため、ファイルサイズはブラウザによって少し違います。

知っておくべき失敗モードは 3 つあります：

1. **canvas の汚染。** canvas が汚染されると `toBlob` は `SecurityError` を投げます。ジェネレーターはこれを捕まえ、先に SVG 内の外部リソースをインライン化するよう案内します。
2. **カラー絵文字フォントがない。** カラー絵文字フォントのない Linux 環境では、canvas は代替グリフ（多くは空の四角）を描き、それがすべての PNG に入ります。ジェネレーターはこれを検出しないので、プレビューを確認するか、画像 / SVG 入力に切り替えてください。
3. **大きな画像のメモリ圧迫。** ジェネレーターは 9 サイズを 1 つずつ描画し、各 `toBlob` を await します。9 つの canvas を同時に保持しません。

## SVG・絵文字・クロスプラットフォーム一貫性問題

最も微妙な出力差はカラー絵文字フォントから来ます。macOS は Apple Color Emoji、Windows は Segoe UI Emoji、Android と多くの Linux デスクトップは Noto Color Emoji を搭載し、同じコードポイント（たとえば 🚀）でもフォントごとに描き方が違います。

macOS で favicon を生成し、Windows から訪問者が来ても、訪問者は生成された favicon を見るだけです — バイトはすでに PNG に焼き込まれています。Canvas レンダラーは絵文字を開発者のマシンで描かれた通りにキャプチャし、それらのピクセルをすべての訪問者に届けます。だからマシンを 1 台選び、1 度生成すれば、その後すべての訪問者にとって結果は一貫します。一貫性が問題になるのは開発者自身の反復作業です：6 か月後に別の OS で再生成すると、わずかに異なる favicon が出力されます。

マシン横断でピクセル単位の一致が欲しければ、Image または SVG 入力に切り替えてください。SVG ベクターマークは OS フォントスタックではなく SVG 自身に基づいて決定論的にビットマップ化されます。代償は SVG が自己完結している必要があることです — リモートリソースへの `<image href>` 不可、外部 `<use>` フラグメント不可、リモート `@font-face` URL 不可。貼る前にすべてをインライン化してください。

## HTML スニペットがやってくれること

ジェネレーターはこのスニペットを出力し、`<head>` の中に置きます：

```html
<link rel="icon" type="image/x-icon" href="/favicon.ico">
<link rel="icon" type="image/png" sizes="16x16" href="/favicon-16.png">
<link rel="icon" type="image/png" sizes="32x32" href="/favicon-32.png">
<link rel="icon" type="image/png" sizes="48x48" href="/favicon-48.png">
<link rel="apple-touch-icon" sizes="180x180" href="/apple-touch-icon.png">
<link rel="manifest" href="/site.webmanifest">
<meta name="theme-color" content="#ffffff">
```

いくつかの細かい点：

- HTML 標準は、ブラウザが `sizes` と `type` を使ってすべての `<link rel="icon">` 候補から選ぶことを認めており、優先順位は定めていません。ICO を先頭に置くのは慣習で、必須ではありません。
- `<meta name="theme-color">` はモバイル Safari と Chrome のアドレスバー、インストール済み PWA のタイトルバーの色を制御します。favicon ではありませんが、同じ head 内に住み、ブランドカラーの判断を共有するため favicon セットと一緒に旅をします。
- ファイル名 `site.webmanifest` は慣習で、多くのチュートリアルは `manifest.json` を使います。どちらでも動きます。プロジェクトの他箇所が使っている方に合わせるのが楽です。
- iOS Safari はホーム画面に `apple-touch-icon` があればそれを使います。Android Chrome はインストールされた Web アプリに manifest のアイコンを使います。

[RealFaviconGenerator](https://realfavicongenerator.net/) は老舗の定番で、プラットフォーム固有の選択肢が多く、既存サイトのファビコン設定をチェックする機能もあります。そうした選択肢が必要なら使いましょう。

[favicon.io](https://favicon.io/) は考え方が ZeroTool に最も近く、入力がシンプル（絵文字、テキスト、画像）で、webmanifest を含む小さなパッケージを出力します。

ZeroTool ジェネレーターは 11 ファイル、webmanifest、コピペ用の HTML スニペットを出力し、すべてブラウザ内で描画してソース画像をアップロードしません。

## デプロイ前チェックリスト

パッケージをデプロイする前に、これらを通してください：

1. **11 ファイルをサイトルートに配置。** アイコン宣言が見つからないブラウザやクローラーはルートの `/favicon.ico` を取りに行き、HTML スニペットと manifest もルートのパスを使っています。
2. **HTML スニペットを `<head>` 内に貼る。** PNG と apple-touch-icon は、ページが `<link>` で宣言したときだけ使われます。
3. **`site.webmanifest` の `name` と `short_name` を更新。** プレースホルダ名で出荷しないよう、ジェネレーターは空のままにしています。
4. **DevTools の Application パネルでテスト。** Application → Manifest に解析済みの manifest、解決されたアイコン、エラーが表示されます。「Show only the minimum safe area for maskable icons」で maskable の切り抜きをプレビューできます。
5. **iOS の経路を確認。** 実機の iPhone（または iOS シミュレーター）で「ホーム画面に追加」を試します。iOS は角丸を自分で付け、透過は保持しないので、apple-touch-icon には不透明な背景を付けてください。
6. **Google 検索のファビコンを確認。** Google は正方形で 8×8 以上を必須とし、48×48 より大きいサイズを推奨しています（[Google 検索セントラル](https://developers.google.com/search/docs/appearance/favicon-in-search?hl=ja)）。反映されるのはトップページの再クロール後で、Search Console にファビコンのレポートはありません。
7. **ブランドが変わったら作り直す。** favicon セットを一回限りの資産ではなくビルド成果物として扱ってください。ソースファイル（ジェネレーターに与えた SVG または高解像度 PNG）をバージョン管理に入れ、マークやテーマカラーが変わったら同じソースから再生成します。

## プライバシーに関するメモ

パイプライン全体がブラウザ内で動くため、ソース画像はどのバージョンも端末を離れません。これは見かけ以上に重要です。未発表の製品のファビコンを作るとき、アップロード型のジェネレーターを使えばブランドマークをそのサービスに渡すことになります。ZeroTool は画像を手元に残します。DevTools → Network を開いて Generate を押すと、画像を運ぶリクエストはなく、計測イベントはツール名と操作だけを記録します。
