Search for almost anything technical on Google and look at the small icon next to each site name. That is the site's favicon; Google started showing favicons in mobile results in 2019 and shows them next to the site name in results today ([Google Search Central](https://developers.google.com/search/docs/appearance/favicon-in-search)). A site without a recognizable favicon there looks abandoned. A site with a sharp, on-brand favicon there looks polished. The mark is tiny and shows up next to your domain wherever a user is deciding whether to click.

That small mark is also one of the few visual elements that survives across browser tabs, bookmark bars, OS taskbars, iOS home screens, Android PWA installs, RSS readers, and shortcut tiles. Each of those surfaces wants a slightly different file — different size, sometimes a different format, sometimes its own manifest entry. This guide covers what the modern set actually looks like, why a single `favicon.ico` is no longer enough, what each file does at runtime, and how the ZeroTool generator builds the package in your browser without uploading anything.

## What modern browsers actually request

Which files a browser fetches depends on the `<link>` tags in your page and on what the user does. Open DevTools on your own site, refresh, and watch the network panel: a desktop browser usually fetches only the one tab icon it picked. The three entry points are:

| Request | Used by | Notes |
|---|---|---|
| `/favicon.ico` | Browsers fall back to this path when the page declares no icon | A multi-size container; keep it for tools and crawlers that only try the root path |
| `/<href from <link rel="icon">>` | The tab, bookmarks, and history | The browser chooses among candidates by `sizes` and `type`; the [HTML standard](https://html.spec.whatwg.org/multipage/links.html#rel-icon) leaves the choice to the browser |
| `/<href from <link rel="apple-touch-icon">>` | iOS Safari "Add to Home Screen" | Standard size is 180×180 |

Add a PWA install on Android Chrome and the picture grows:

| Request | Used by |
|---|---|
| `/site.webmanifest` (or `manifest.json`) | Chrome, Edge, Brave, Samsung Internet — anywhere PWAs install |
| 192×192 and 512×512 PNGs declared in the manifest's `icons` array | Android home-screen icon, Splash screen, Android share sheet |

Mark an icon `purpose: "maskable"` and Android applies a circular or rounded-square mask, depending on the launcher, so the icon looks native in the launcher grid. A maskable icon must keep its visible mark inside the safe zone, a circle with a radius of 40% of the icon size (about 10% padding on each side), otherwise the mask clips the edges ([web.dev](https://web.dev/articles/maskable-icon)). web.dev advises against `"any maskable"` on one file: an icon padded for masking looks too small where it is used as-is, so ship separate `any` and `maskable` files.

Then there is the long tail. Pinned-site tiles on Windows 8 and 10 read `browserconfig.xml`; Windows 11 has no live tiles. Older Safari versions drew pinned tabs from a single-color SVG declared with `<link rel="mask-icon">`. Older Chrome on Android used `apple-touch-icon` for home-screen shortcuts. These explain why some generators emit twenty-plus files.

## Why a single `favicon.ico` is not enough

The historical default was to drop one ICO at the site root and let the browser figure it out. That worked when monitors topped out at 1280×1024 and tabs were 16-pixel squares. Two things broke it:

1. **Retina displays.** A 16×16 ICO renders blurry on a 2× display when the browser scales it to 32 logical pixels. The `<link rel="icon" type="image/png" sizes="32x32">` tag lets the browser pick the right resource for the device pixel ratio.
2. **Operating system surfaces beyond the tab.** iOS home-screen icons, Android home-screen icons, and PWA splash screens each take a specific size from your set, and none of them want the 16-pixel ICO. They want 180, 192, 512, and a manifest that tells them what is what.

The fix is the modern set: a small ICO for compatibility, a few PNG sizes for the modern `<link rel="icon">` chain, an apple-touch-icon for iOS, and a webmanifest with PWA icons.

## How the ICO format works

`favicon.ico` is the strangest file in the set because it predates PNG: it was born in Windows 3.0 and originally carried Device-Independent Bitmap (DIB / BMP) frames. Many current generators emit PNG-compressed entries instead, which Windows supports since Vista and current browsers read. PNG-compressed entries are smaller, they preserve alpha, and the format is straightforward.

An ICO file is:

```text
ICONDIR (6 bytes)
├── reserved (2 bytes, zero)
├── type (2 bytes, 1 = ICO, 2 = CUR)
└── count (2 bytes)

ICONDIRENTRY × count (16 bytes each)
├── width (1 byte, 0 means 256)
├── height (1 byte, 0 means 256)
├── colorCount (1 byte, zero for 32-bit)
├── reserved (1 byte, zero)
├── colorPlanes (2 bytes, 1)
├── bitsPerPixel (2 bytes, 32)
├── imageSize (4 bytes)
└── imageOffset (4 bytes — absolute offset into the ICO file)

(image payloads concatenated after the directory)
```

For PNG entries, the imageSize is the size of a complete PNG file (including its own IHDR / IDAT / IEND chunks) and the imageOffset points at the first byte of that PNG. Set the width/height fields in the ICONDIRENTRY to match the PNG's own width and height; readers use the directory to pick an entry before they decode it.

The ZeroTool generator packs the 16, 32, and 48 PNGs into the ICO. It does not include the larger sizes: browsers that need more pixels get them from the `<link rel="icon">` PNGs, the apple-touch-icon, and the manifest. If you also want the ICO to serve as a Windows desktop icon, which can use 256×256, build a separate ICO with that size.

## How the ZIP container works

The browser needs a way to deliver eleven files in one click without firing eleven downloads, so the generator packs them into a ZIP. ZIP has been the default container for decades because every operating system can open it without third-party tooling. Inside, ZIP is layered: a sequence of local file headers each followed by a payload, then a "central directory" listing every entry, then an end-of-central-directory record telling readers where the central directory starts.

Each entry has two ways to encode payload bytes: STORED (no compression) or DEFLATE. PNG is already compressed, so re-running it through DEFLATE saves little. The ZeroTool generator uses STORED for all entries and does not ship a DEFLATE implementation.

CRC-32 is the one piece of the ZIP spec you cannot skip. Every entry must carry the 32-bit CRC of its uncompressed bytes. The generator precomputes a 256-entry lookup table at script start and walks the bytes once per file. Filenames are flagged as UTF-8 in bit 11 of the General Purpose Bit Field, which keeps non-ASCII names readable in macOS Finder, Windows Explorer, and 7-Zip.

## The Canvas pipeline

Drawing each PNG follows the same five steps:

```javascript
// Pseudocode for one target size
const canvas = createCanvas(size, size);
const ctx = canvas.getContext('2d');

if (shape !== 'square') {
  drawShapePath(ctx, shape, size);
  ctx.clip();           // alpha mask for rounded / circle
}
if (bgMode === 'color') {
  ctx.fillStyle = bgColor;
  ctx.fillRect(0, 0, size, size);
}
const inner = size * (1 - padding * 2);
drawSourceCentered(ctx, source, size, inner);  // emoji / text / image / svg
const pngArrayBuffer = await canvasToPng(canvas);
```

`canvas.toBlob('image/png')` does the heavy lifting — sizing, dithering, alpha encoding. The output is a complete PNG payload with `IHDR`, one or more `IDAT` chunks, and `IEND`. The browser chooses the zlib compression level inside the IDAT chunks, so file sizes differ slightly between browsers.

There are three failure modes worth knowing:

1. **Tainted canvas.** If the canvas becomes tainted, `toBlob` throws a `SecurityError`. The generator catches it and asks you to inline external resources in the SVG first.
2. **Missing emoji font.** Some Linux installs ship without a color emoji font. The canvas then draws a fallback glyph (often an empty box), and that box ends up in every PNG. The generator does not detect this; check the preview, or switch to Image or SVG input.
3. **Memory pressure with large images.** The generator renders the nine sizes one after another and awaits each `toBlob` instead of holding nine canvases at once.

## SVG, emoji, and the cross-platform consistency problem

The most subtle output difference is the color emoji font. macOS ships Apple Color Emoji, Windows ships Segoe UI Emoji, Android and many Linux desktops ship Noto Color Emoji. Each font draws the same code point, such as 🚀, in its own style.

If you generate your favicon on macOS and someone visits your site from Windows, they still see the favicon you generated — the bytes are baked into the PNG. The Canvas renderer captures the emoji as drawn on the developer's machine, then ships those pixels to every visitor. So pick a machine, generate once, and the result is consistent for every visitor afterward. Where consistency matters is the developer's own iteration: regenerating six months later on a different OS will produce a slightly different favicon.

For pixel-identical output across machines, switch to the Image or SVG input. A vector mark in SVG renders to bitmap deterministically based on the SVG itself, not the OS font stack. The catch is that the SVG must be self-contained — no `<image href>` to remote resources, no external `<use>` fragments, no remote `@font-face` URLs. Inline everything before pasting.

## What the HTML snippet does for you

The generator produces this snippet, which goes inside `<head>`:

```html
<link rel="icon" type="image/x-icon" href="/favicon.ico">
<link rel="icon" type="image/png" sizes="16x16" href="/favicon-16.png">
<link rel="icon" type="image/png" sizes="32x32" href="/favicon-32.png">
<link rel="icon" type="image/png" sizes="48x48" href="/favicon-48.png">
<link rel="apple-touch-icon" sizes="180x180" href="/apple-touch-icon.png">
<link rel="manifest" href="/site.webmanifest">
<meta name="theme-color" content="#ffffff">
```

A few subtleties:

- The HTML standard lets the browser choose among all `<link rel="icon">` candidates using `sizes` and `type`; it does not define an order of preference. Putting the ICO first is convention, not requirement.
- `<meta name="theme-color">` colors the address bar on mobile Safari and Chrome and the title bar on installed PWAs. It is not a favicon, but it travels with the favicon set because it lives in the same head section and shares the brand-color decision.
- `site.webmanifest` is by convention; many tutorials use `manifest.json`. Both work. Stick with whichever the rest of your project uses.
- iOS Safari uses `apple-touch-icon` for the home screen when it is present. Android Chrome uses the manifest icons for installed web apps.

## A pre-deploy checklist

Before you deploy the package, run through these:

1. **Drop the eleven files at the site root.** Browsers and crawlers that find no icon declaration request `/favicon.ico` at the root, and the HTML snippet and manifest use root paths.
2. **Paste the HTML snippet inside `<head>`.** The PNGs and apple-touch-icon are only used when the page declares them with `<link>` tags.
3. **Update `site.webmanifest`** with your site's `name` and `short_name`. The generator leaves them empty so you do not ship a placeholder name.
4. **Test in DevTools' Application panel.** Application → Manifest shows the parsed manifest, the resolved icons, and any errors. The "Show only the minimum safe area for maskable icons" option previews the maskable crop.
5. **Check the iOS path.** Add to Home Screen on a real iPhone (or in iOS Simulator). iOS rounds the corners itself and does not keep transparency, so give the apple-touch-icon an opaque background.
6. **Check the Google Search favicon.** Google requires a square icon of at least 8×8 and recommends larger than 48×48 ([Google Search Central](https://developers.google.com/search/docs/appearance/favicon-in-search)). Google picks it up when it recrawls the home page; Search Console has no favicon report.
7. **Regenerate when the brand changes.** Treat the favicon set as a build artifact, not a one-off. Keep the source file (the SVG or the high-resolution PNG you fed in) in version control, and regenerate from the same source whenever the mark or theme color changes.

## Privacy notes

Because the entire pipeline runs in your browser, no version of your source image leaves your machine. This matters more than it sounds: when you generate a favicon for an unreleased product, you are leaking the brand mark to whichever generator you use. ZeroTool keeps the image local. Open DevTools → Network and click Generate: no request carries the image; the analytics event records only the tool name and the action.
