<h2>주요 사용 사례</h2>
<ul>
  <li><strong>로컬 개발:</strong> 백엔드 없이 API 엔드포인트나 인증 흐름 테스트용 토큰을 빠르게 생성.</li>
  <li><strong>디버깅:</strong> 헤더와 페이로드 JSON이 JWT에 어떻게 인코딩되는지 확인.</li>
  <li><strong>문서화:</strong> API 문서나 README 파일용 예시 토큰 생성.</li>
  <li><strong>학습:</strong> JWT의 구조와 서명 방식 이해.</li>
</ul>

<h2>예시: jjwt(Spring 프로젝트 등)에서 Base64로 디코딩하는 키</h2>

<p>jjwt(0.13.0) <a href="https://github.com/jwtk/jjwt/blob/0.13.0/README.adoc" target="_blank" rel="noopener">README</a>는 Base64로 인코딩된 비밀 키 문자열을 <code>{"Keys.hmacShaKeyFor(Decoders.BASE64.decode(secretString))"}</code>로 키로 바꾸라고 안내합니다. 설정 파일의 키 문자열을 이렇게 읽는 서버와 같은 토큰을 만들려면 이 도구에서도 Base64 모드를 골라야 합니다. 예시용으로 만든 키 문자열 하나로 두 모드를 비교해 보겠습니다.</p>

<pre><code>{`c2VjcmV0LWtleS1mb3ItZGVtby1vbmx5`}</code></pre>

<pre><code>{`{"alg":"HS256","typ":"JWT"}`}</code></pre>

{/* jwt-time: {"iso":"2026-10-09T09:00:00+09:00","unix":1791504000} */}

<p>페이로드의 <code>{"iat"}</code>는 한국 시간 2026-10-09 오전 9시인 <code>1791504000</code>입니다. 한국 시간을 UTC로 착각해 계산하면 9시간 어긋납니다.</p>

<pre><code>{`{"sub":"user-7","name":"홍길동","iat":1791504000}`}</code></pre>

{/* jwt-check: {"algo":"HS256","fmt":"base64","secret":"c2VjcmV0LWtleS1mb3ItZGVtby1vbmx5","header":"{\"alg\":\"HS256\",\"typ\":\"JWT\"}","payload":"{\"sub\":\"user-7\",\"name\":\"홍길동\",\"iat\":1791504000}","warn":24} */}

<p>Base64 모드에서는 32자가 24바이트로 디코딩되어, 서명은 하지만 다음 경고가 나옵니다. 「키가 24바이트입니다. RFC 7518은 HS256에 32바이트 이상을 요구합니다. 서명은 하지만 이 키는 너무 짧습니다.」</p>

<pre><code>{`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyLTciLCJuYW1lIjoi7ZmN6ri464-ZIiwiaWF0IjoxNzkxNTA0MDAwfQ.YbnfzHixwRLd1N9HaIci4A8Dag2pFLwyio2gh3uHmnY`}</code></pre>

<p>jjwt도 같은 기준을 씁니다. <a href="https://github.com/jwtk/jjwt/blob/0.13.0/api/src/main/java/io/jsonwebtoken/security/Keys.java" target="_blank" rel="noopener">Keys.java</a>의 <code>{"hmacShaKeyFor"}</code>는 키가 256비트(32바이트)보다 짧으면 <code>{"WeakKeyException"}</code>을 던지도록 되어 있습니다. 이 키로 서버를 설정하면 그 호출에서 예외가 나므로 토큰을 만들 수도, 검증할 수도 없습니다.</p>

{/* jwt-check: {"algo":"HS256","fmt":"utf8","secret":"c2VjcmV0LWtleS1mb3ItZGVtby1vbmx5","header":"{\"alg\":\"HS256\",\"typ\":\"JWT\"}","payload":"{\"sub\":\"user-7\",\"name\":\"홍길동\",\"iat\":1791504000}"} */}

<p>같은 문자열을 UTF-8 모드로 두면 32바이트라 경고가 사라지지만, 서버가 쓰는 키 바이트와 달라 서명이 맞지 않습니다.</p>

<pre><code>{`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyLTciLCJuYW1lIjoi7ZmN6ri464-ZIiwiaWF0IjoxNzkxNTA0MDAwfQ.zJjAxr_JLJ9Qwy0mpu6P8_eRxOx424uZsRY_T0yvTjU`}</code></pre>

<p>경고가 없다고 모드가 맞는 것은 아닙니다. 서버가 키를 Base64로 디코딩하는지, 문자열 그대로 쓰는지 먼저 확인하세요.</p>

<h2>예시: 32바이트 키와 한글 클레임</h2>

<p>디코딩하면 32바이트가 되는 예시용 키(<code>{"MDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWY="}</code>)를 Base64 모드로 넣고, 헤더와 페이로드는 앞의 예시와 같게 둡니다.</p>

<pre><code>{`{"alg":"HS256","typ":"JWT"}`}</code></pre>

<pre><code>{`{"sub":"user-7","name":"홍길동","iat":1791504000}`}</code></pre>

{/* jwt-check: {"algo":"HS256","fmt":"base64","secret":"MDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWY=","header":"{\"alg\":\"HS256\",\"typ\":\"JWT\"}","payload":"{\"sub\":\"user-7\",\"name\":\"홍길동\",\"iat\":1791504000}"} */}

<p>경고 없이 서명된 토큰입니다.</p>

<pre><code>{`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyLTciLCJuYW1lIjoi7ZmN6ri464-ZIiwiaWF0IjoxNzkxNTA0MDAwfQ.sOnn_hJ30VRpulgHBMT4kcLd5YL6qnoJrn7ccryMmJU`}</code></pre>

<p>페이로드 부분의 <code>{"7ZmN6ri464-Z"}</code>는 「홍길동」의 UTF-8 9바이트를 Base64URL로 바꾼 것으로, URL 안전 문자 <code>{"-"}</code>가 들어 있습니다. 도구는 <code>{"iat"}</code>·<code>{"exp"}</code>·<code>{"nbf"}</code>를 자동으로 넣거나 검사하지 않으니 필요한 시각은 직접 쓰세요(Unix 초, <a href="https://www.rfc-editor.org/rfc/rfc7519#section-4.1" target="_blank" rel="noopener">RFC 7519 §4.1</a>).</p>

<p>예를 들어 HS256을 선택한 상태에서 헤더의 alg를 HS512로 바꾸면 오류를 표시하고 이전 토큰을 지웁니다.</p>

<h2>키 고르기</h2>

<p>HMAC 서명의 강도는 키에 달려 있습니다. 토큰 하나를 손에 넣은 사람은 서명이 맞을 때까지 후보 키를 오프라인으로 시험할 수 있습니다. <a href="https://www.rfc-editor.org/rfc/rfc8725#section-3.5" target="_blank" rel="noopener">RFC 8725 §3.5</a>는 사람이 기억할 수 있는 비밀번호를 HMAC 키로 쓰면 안 된다고 합니다. 난수로 만든 키를 Base64 모드로 붙여 넣으세요.</p>

<pre><code>{`openssl rand -base64 32   # HS256
openssl rand -base64 64   # HS512`}</code></pre>

<h2>제한</h2>

<ul>
  <li>HMAC 알고리즘(HS256, HS384, HS512)만 지원합니다. 개인 키가 필요한 RS256, ES256은 지원하지 않습니다.</li>
  <li><a href="https://www.rfc-editor.org/rfc/rfc7518#section-3.2" target="_blank" rel="noopener">RFC 7518 §3.2</a>는 키 길이를 해시 출력 이상으로 요구합니다(HS256은 32바이트, HS384는 48, HS512는 64). 더 짧은 시크릿으로도 서명은 하지만 바이트 수와 함께 경고를 표시합니다. 기본 예시 <code>your-256-bit-secret</code>는 19바이트라 경고가 나옵니다.</li>
  <li>Base64 모드에서는 시크릿을 먼저 디코딩합니다(표준·URL 안전 알파벳 모두 가능, 패딩 생략 가능, 공백 무시). 디코딩 결과가 0바이트(공백만 입력한 경우 등)이면 오류를 표시합니다.</li>
  <li>페이로드는 JSON 객체여야 합니다. 배열·문자열·숫자·<code>{"null"}</code>은 오류가 나고 토큰을 만들지 않습니다. <a href="https://www.rfc-editor.org/rfc/rfc7519#section-7.2" target="_blank" rel="noopener">RFC 7519 §7.2</a>가 클레임을 JSON 객체로 정하고 있고, PyJWT 같은 라이브러리도 다른 형태는 거부하기 때문입니다.</li>
  <li>헤더와 페이로드는 앞뒤 공백만 지웁니다. UTF-8 모드에서는 비밀 키를 입력한 그대로 쓰므로 앞뒤 공백 하나로도 서명이 달라집니다(Base64 모드에서는 공백을 무시합니다).</li>
  <li>헤더, 페이로드, UTF-8 모드의 비밀 키에 이모지의 반쪽(짝이 없는 UTF-16 서로게이트)이 있으면 UTF-8로 인코딩할 수 없어 위치를 알려 주고 오류로 처리합니다. Base64 모드에서는 유효하지 않은 Base64로 오류를 표시합니다.</li>
  <li>운영 환경의 서명 시크릿은 어떤 웹 페이지에도 붙여 넣지 마세요. 테스트 전용 시크릿을 쓰세요.</li>
</ul>
