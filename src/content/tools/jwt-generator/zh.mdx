<h2>常见使用场景</h2>
<ul>
  <li><strong>本地开发：</strong>无需启动后端，快速生成 Token 用于测试 API 接口或认证流程。</li>
  <li><strong>调试：</strong>了解 Header 和 Payload JSON 是如何被编码进 JWT 的。</li>
  <li><strong>文档编写：</strong>为 API 文档或 README 生成示例 Token。</li>
  <li><strong>学习：</strong>理解 JWT 的结构和签名原理。</li>
</ul>

<h2>示例：中文声明与北京时间</h2>

{/* jwt-check: {"algo":"HS256","fmt":"utf8","secret":"zerotool-demo-secret-0123456789abcdef","header":"{\n  \"alg\": \"HS256\",\n  \"typ\": \"JWT\"\n}","payload":"{\n  \"sub\": \"10086\",\n  \"name\": \"张三\",\n  \"role\": \"运营\",\n  \"iat\": 1791507600,\n  \"exp\": 1791514800\n}","inputLen":185} */}

<p>给本地后台接口造一个运营账号的测试令牌。Header 保持默认，UTF-8 密钥用演示值 <code>{"zerotool-demo-secret-0123456789abcdef"}</code>（37 字节，满足 HS256 的 32 字节下限，不会出现警告）：</p>

<pre><code>{`{
  "alg": "HS256",
  "typ": "JWT"
}`}</code></pre>

<pre><code>{`{
  "sub": "10086",
  "name": "张三",
  "role": "运营",
  "iat": 1791507600,
  "exp": 1791514800
}`}</code></pre>

<p>生成的 HS256 令牌：</p>

<pre><code>{`ewogICJhbGciOiAiSFMyNTYiLAogICJ0eXAiOiAiSldUIgp9.ewogICJzdWIiOiAiMTAwODYiLAogICJuYW1lIjogIuW8oOS4iSIsCiAgInJvbGUiOiAi6L-Q6JClIiwKICAiaWF0IjogMTc5MTUwNzYwMCwKICAiZXhwIjogMTc5MTUxNDgwMAp9.MxlA4RZOOM5N8lZ2tDYXh0jggy2PJ-wFnVw7XXxGT8g`}</code></pre>

<p>中文先按 UTF-8 编码再做 Base64URL：「运营」的 6 个字节变成 <code>{"6L-Q6JCl"}</code>，其中的 <code>-</code> 来自 URL 安全字母表（标准 Base64 在这里是 <code>+</code>）。签名前的部分有 185 个字符，因为输入框里的换行和缩进也被编码进去了。</p>

{/* jwt-time: {"iso":"2026-10-09T09:00:00+08:00","unix":1791507600} */}

<p>声明里的时间是 Unix 秒，不带时区。北京时间 2026-10-09 09:00 是 <code>1791507600</code>：</p>

{/* jwt-time: {"iso":"2026-10-09T11:00:00+08:00","unix":1791514800} */}

<p>两小时后的 11:00 是 <code>1791514800</code>，写进 <code>{"exp"}</code>。工具不会替你填 <code>{"iat"}</code>、<code>{"exp"}</code>、<code>{"nbf"}</code>，也不检查它们是否过期；按北京时间换算时别忘了时区是 UTC+8，直接把「2026-10-09 09:00」当 UTC 算会差 8 小时（<a href="https://www.rfc-editor.org/rfc/rfc7519#section-4.1" target="_blank" rel="noopener">RFC 7519 §4.1</a>）。</p>

<p>例如，所选算法仍为 HS256 时，把 Header 的 alg 改为 HS512，会显示错误并清除旧 Token。</p>

<h2>示例：jjwt 0.9 的字符串密钥要选 Base64</h2>

<p>jjwt 0.9.x 的签名可以这样写：<code>{"Jwts.builder()...signWith(SignatureAlgorithm.HS512, secret)"}</code>。按 jjwt 0.9.1 的<a href="https://github.com/jwtk/jjwt/blob/0.9.1/src/main/java/io/jsonwebtoken/JwtBuilder.java" target="_blank" rel="noopener">接口文档</a>，传入字符串的这个重载会先把字符串按 Base64 解码，再用得到的字节签名。所以配置文件里的密钥文本，在本工具里要选 Base64，签名用的才是同一组字节。下面用一个演示密钥（64 个字母和数字）对比两种模式：</p>

<pre><code>{`ZeroToolDemoKeyForJjwtBase64ModeTestOnly0123456789abcdefghijkLMN`}</code></pre>

<pre><code>{`{"alg":"HS512"}`}</code></pre>

<pre><code>{`{"sub":"admin","iat":1791507600}`}</code></pre>

{/* jwt-check: {"algo":"HS512","fmt":"base64","secret":"ZeroToolDemoKeyForJjwtBase64ModeTestOnly0123456789abcdefghijkLMN","header":"{\"alg\":\"HS512\"}","payload":"{\"sub\":\"admin\",\"iat\":1791507600}","warn":48} */}

<p>选 Base64 时，64 个字符解码成 48 字节，工具照常签名，同时提示：「密钥只有 48 字节；RFC 7518 要求 HS512 至少 64 字节。Token 照常签名，但这个密钥太短，不宜使用。」得到：</p>

<pre><code>{`eyJhbGciOiJIUzUxMiJ9.eyJzdWIiOiJhZG1pbiIsImlhdCI6MTc5MTUwNzYwMH0.69irj4xwzk9LYkoJ3CtFhePoNKAIuptKCu2H_AjCOpBWU9AKpeLVRiCkP5otl3Ml7uVKcufRVh_oxltQMHh4-Q`}</code></pre>

{/* jwt-check: {"algo":"HS512","fmt":"utf8","secret":"ZeroToolDemoKeyForJjwtBase64ModeTestOnly0123456789abcdefghijkLMN","header":"{\"alg\":\"HS512\"}","payload":"{\"sub\":\"admin\",\"iat\":1791507600}"} */}

<p>选 UTF-8 时，同一段文本是 64 字节，不再提示，但签名完全不同：</p>

<pre><code>{`eyJhbGciOiJIUzUxMiJ9.eyJzdWIiOiJhZG1pbiIsImlhdCI6MTc5MTUwNzYwMH0.vXYdQdL45dQ4z1XwnL3Su3s9weElKp908cH_-V6fbvCT54rq5s30ud6D27xzGCHrcWq-F_hLrK9hBuuVoKz1pA`}</code></pre>

<p>「没有警告」不代表选对了模式。服务端报签名不匹配时，先确认它把密钥当作文本还是当作 Base64；本例中，服务端按 Base64 解码后只有 48 字节，正好是需要换一个更长密钥的信号。</p>

<h2>选择密钥</h2>

<p>HMAC 签名的强度取决于密钥。拿到一个令牌的人可以离线尝试候选密钥，直到签名对上；<a href="https://www.rfc-editor.org/rfc/rfc8725#section-3.5" target="_blank" rel="noopener">RFC 8725 §3.5</a> 明确说人能记住的口令不能用作 HMAC 密钥。用随机字节生成密钥，再用 Base64 模式粘贴：</p>

<pre><code>{`openssl rand -base64 32   # HS256
openssl rand -base64 64   # HS512`}</code></pre>

<h2>限制</h2>

<ul>
  <li>只支持 HMAC 算法（HS256、HS384、HS512）。RS256、ES256 需要私钥，不支持。</li>
  <li><a href="https://www.rfc-editor.org/rfc/rfc7518#section-3.2" target="_blank" rel="noopener">RFC 7518 §3.2</a> 要求密钥长度不少于哈希输出：HS256 为 32 字节、HS384 为 48、HS512 为 64。密钥更短时工具照常签名，但会显示字节数并提示；默认示例密钥 <code>your-256-bit-secret</code> 只有 19 字节，会触发提示。</li>
  <li>Base64 模式下会先解码密钥（标准或 URL 安全字母表，填充可省略，空白忽略）；解码后为 0 字节（例如只填了空格）时报错。</li>
  <li>Payload 必须是 JSON 对象。数组、字符串、数字或 <code>{"null"}</code> 会报错而不生成令牌：<a href="https://www.rfc-editor.org/rfc/rfc7519#section-7.2" target="_blank" rel="noopener">RFC 7519 §7.2</a> 要求声明集是 JSON 对象，PyJWT 等库也会拒绝其他形式。</li>
  <li>Header 和 Payload 只去掉首尾空白；密钥按原样使用，末尾多一个空格或换行，签名就会不同。</li>
  <li>任何字段里如果有 emoji 的一半（落单的 UTF-16 代理项），会报出位置，因为 UTF-8 无法编码它。</li>
  <li>不要把生产环境的签名密钥粘贴到任何网页里，请用专门的测试密钥。</li>
</ul>
