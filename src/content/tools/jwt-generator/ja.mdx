<h2>主なユースケース</h2>
<ul>
  <li><strong>ローカル開発：</strong>バックエンドを起動せずに、APIエンドポイントや認証フローのテスト用トークンを素早く生成。</li>
  <li><strong>デバッグ：</strong>ヘッダーとペイロードのJSONがJWTにどのようにエンコードされるかを確認。</li>
  <li><strong>ドキュメント作成：</strong>APIドキュメントやREADMEのサンプルトークンを生成。</li>
  <li><strong>学習：</strong>JWTの構造と署名の仕組みを理解する。</li>
</ul>

<h2>例：LINE ログインの ID トークンと同じ形のテスト用トークン</h2>

<p>LINE Developers の「<a href="https://developers.line.biz/ja/docs/line-login/verify-id-token/" target="_blank" rel="noopener">IDトークンからプロフィール情報を取得する</a>」によると、ID トークンの <code>{"alg"}</code> はウェブログインでは HS256、ネイティブアプリ・LINE SDK・LIFF アプリでは ES256 で、HS256 の検証に使う鍵はチャネルシークレットです。自前の検証コードを本番の LINE につなぐ前に試したいとき、同じ形のトークンをこのツールで作れます。</p>

<p>ヘッダーはドキュメントの例と同じ並びで貼り付けます（選択は HS256 のまま）：</p>

<pre><code>{`{
  "typ": "JWT",
  "alg": "HS256"
}`}</code></pre>

{/* jwt-time: {"iso":"2026-10-09T09:00:00+09:00","unix":1791504000} */}

<p>ペイロードはドキュメントのプロパティ名に合わせ、値はすべてダミーです。<code>{"iat"}</code> は日本時間 2026-10-09 9:00 の <code>1791504000</code> です。</p>

{/* jwt-time: {"iso":"2026-10-09T10:00:00+09:00","unix":1791507600} */}

<p><code>{"exp"}</code> は 1 時間後の 10:00 で <code>1791507600</code> です。日本時間を UTC のつもりで換算すると 9 時間ずれるので注意してください。</p>

{/* jwt-check: {"algo":"HS256","fmt":"utf8","secret":"0123456789abcdef0123456789abcdef","header":"{\n  \"typ\": \"JWT\",\n  \"alg\": \"HS256\"\n}","payload":"{\n  \"iss\": \"https://access.line.me\",\n  \"sub\": \"U1234567890abcdef1234567890abcdef\",\n  \"aud\": \"1234567890\",\n  \"exp\": 1791507600,\n  \"iat\": 1791504000,\n  \"nonce\": \"0987654asdf\",\n  \"amr\": [\"pwd\"],\n  \"name\": \"テスト太郎\"\n}"} */}

<pre><code>{`{
  "iss": "https://access.line.me",
  "sub": "U1234567890abcdef1234567890abcdef",
  "aud": "1234567890",
  "exp": 1791507600,
  "iat": 1791504000,
  "nonce": "0987654asdf",
  "amr": ["pwd"],
  "name": "テスト太郎"
}`}</code></pre>

<p>鍵はダミーのチャネルシークレット <code>{"0123456789abcdef0123456789abcdef"}</code>（32 文字、UTF-8 で 32 バイトなので警告は出ません）を UTF-8 モードで使いました。生成されたトークン：</p>

<pre><code>{`ewogICJ0eXAiOiAiSldUIiwKICAiYWxnIjogIkhTMjU2Igp9.ewogICJpc3MiOiAiaHR0cHM6Ly9hY2Nlc3MubGluZS5tZSIsCiAgInN1YiI6ICJVMTIzNDU2Nzg5MGFiY2RlZjEyMzQ1Njc4OTBhYmNkZWYiLAogICJhdWQiOiAiMTIzNDU2Nzg5MCIsCiAgImV4cCI6IDE3OTE1MDc2MDAsCiAgImlhdCI6IDE3OTE1MDQwMDAsCiAgIm5vbmNlIjogIjA5ODc2NTRhc2RmIiwKICAiYW1yIjogWyJwd2QiXSwKICAibmFtZSI6ICLjg4bjgrnjg4jlpKrpg44iCn0.qRRm6F-ywB2YaOf0LQMWTVnZPkVYE3p8QnQx3MT0FbU`}</code></pre>

<p>自分の検証コードがチャネルシークレットを文字列のまま鍵に使う実装なら、このトークンで署名・<code>{"aud"}</code>・<code>{"exp"}</code>・<code>{"nonce"}</code> のチェックを順に試せます。ツールは <code>{"iat"}</code>・<code>{"exp"}</code>・<code>{"nbf"}</code> を自動で追加も確認もしません（Unix 秒、<a href="https://www.rfc-editor.org/rfc/rfc7519#section-4.1" target="_blank" rel="noopener">RFC 7519 §4.1</a>）。</p>

<p>例えば、選択を HS256 のままヘッダーの alg を HS512 に変えると、エラーを表示して以前のトークンを消します。</p>

<h2>秘密鍵の末尾に全角スペースが入ると署名が変わる</h2>

<p>鍵を手で打ち直したときに、末尾に全角スペース（U+3000）が紛れ込むことがあります。UTF-8 モードでは、このツールは秘密鍵の前後の空白を取り除かず、そのまま鍵のバイト列に含めます。詰めた JSON の同じヘッダーとペイロードで比べます。</p>

<pre><code>{`{"alg":"HS256","typ":"JWT"}`}</code></pre>

<pre><code>{`{"sub":"U1234567890abcdef1234567890abcdef","iat":1791504000}`}</code></pre>

{/* jwt-check: {"algo":"HS256","fmt":"utf8","secret":"0123456789abcdef0123456789abcdef","header":"{\"alg\":\"HS256\",\"typ\":\"JWT\"}","payload":"{\"sub\":\"U1234567890abcdef1234567890abcdef\",\"iat\":1791504000}"} */}

<p>鍵 <code>{"0123456789abcdef0123456789abcdef"}</code>（32 バイト）の場合：</p>

<pre><code>{`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJVMTIzNDU2Nzg5MGFiY2RlZjEyMzQ1Njc4OTBhYmNkZWYiLCJpYXQiOjE3OTE1MDQwMDB9.6WnM-JDnsJdssdLfWmB7d9zWW_JqXt-FdbrUUZBVnSE`}</code></pre>

{/* jwt-check: {"algo":"HS256","fmt":"utf8","secret":"0123456789abcdef0123456789abcdef\u3000","header":"{\"alg\":\"HS256\",\"typ\":\"JWT\"}","payload":"{\"sub\":\"U1234567890abcdef1234567890abcdef\",\"iat\":1791504000}","secretShown":false} */}

<p>同じ鍵の末尾に全角スペースが 1 つ付くと、UTF-8 で 3 バイト（<code>{"e3 80 80"}</code>）増えて 35 バイトになり、署名部分がまったく別になります：</p>

<pre><code>{`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJVMTIzNDU2Nzg5MGFiY2RlZjEyMzQ1Njc4OTBhYmNkZWYiLCJpYXQiOjE3OTE1MDQwMDB9.rKLMLyNqAzlWaxpj8Ns27WkqzNXVaPPStJrFhJURMyw`}</code></pre>

<p>35 バイトは HS256 の下限 32 バイトを超えているので、警告は出ません。サーバー側で「署名が一致しない」と言われ、ヘッダーとペイロードに違いが見当たらないときは、鍵の前後の空白を疑ってください。</p>

<h2>鍵の選び方</h2>

<p>HMAC 署名の強さは鍵で決まります。トークンを 1 つ手に入れた人は、署名が一致するまで候補の鍵をオフラインで試せます。<a href="https://www.rfc-editor.org/rfc/rfc8725#section-3.5" target="_blank" rel="noopener">RFC 8725 §3.5</a> は、人が覚えられるパスワードを HMAC の鍵に使ってはならないとしています。乱数で作った鍵を Base64 モードで貼り付けてください。</p>

<pre><code>{`openssl rand -base64 32   # HS256
openssl rand -base64 64   # HS512`}</code></pre>

<h2>制限</h2>

<ul>
  <li>対応するのは HMAC（HS256、HS384、HS512）だけです。署名に RSA・楕円曲線の秘密鍵（プライベートキー）が必要な RS256・ES256 には対応していません。LINE ログインの ES256 の ID トークンも作れません。</li>
  <li><a href="https://www.rfc-editor.org/rfc/rfc7518#section-3.2" target="_blank" rel="noopener">RFC 7518 §3.2</a> は、鍵の長さをハッシュの出力以上にするよう求めています（HS256 は 32 バイト、HS384 は 48、HS512 は 64）。短い秘密鍵でも署名はしますが、バイト数とともに警告を表示します。既定のサンプル <code>your-256-bit-secret</code> は 19 バイトなので警告が出ます。</li>
  <li>Base64 モードでは秘密鍵を先にデコードします（標準・URL セーフどちらのアルファベットも可、パディングは省略可、空白は無視）。デコード結果が 0 バイト（空白だけなど）のときはエラーになります。</li>
  <li>ペイロードは JSON オブジェクトにする必要があります。配列・文字列・数値・<code>{"null"}</code> はエラーになり、トークンを作りません。<a href="https://www.rfc-editor.org/rfc/rfc7519#section-7.2" target="_blank" rel="noopener">RFC 7519 §7.2</a> がクレームを JSON オブジェクトと定めており、PyJWT などのライブラリもそれ以外を拒否するためです。</li>
  <li>ヘッダーとペイロードは前後の空白だけを取り除きます。UTF-8 モードでは秘密鍵を入力どおりに使うため、前後に空白が 1 つ増えるだけで署名が変わります（Base64 モードでは空白を無視します）。</li>
  <li>絵文字の片割れ（対になっていない UTF-16 サロゲート）がヘッダー・ペイロード・UTF-8 モードの秘密鍵にあると、UTF-8 で表せないため位置を示してエラーにします。Base64 モードでは無効な Base64 としてエラーになります。</li>
  <li>本番の署名用の秘密鍵はどんな Web ページにも貼り付けないでください。テスト専用の秘密鍵を使います。</li>
</ul>
