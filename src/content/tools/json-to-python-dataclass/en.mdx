<h2>Type Mapping</h2>
<ul>
  <li><code>null</code> → <code>Optional[Any] = None</code></li>
  <li>string → <code>str</code></li>
  <li>integer → <code>int</code></li>
  <li>float → <code>float</code></li>
  <li>boolean → <code>bool</code></li>
  <li>array → <code>List[T]</code></li>
  <li>mixed array → <code>List[Union[T1, T2]]</code></li>
  <li>nested object → separate class</li>
</ul>

<h2>Example</h2>

{/* jpdc-check: {"root":"Root","mode":"dataclass"} */}

<p>Given this JSON:</p>
<pre><code>{`{"user": {"first_name": "Alice", "age": 30}, "tags": ["admin"], "note": null}`}</code></pre>
<p>The tool generates (@dataclass mode):</p>
<pre><code>{`from dataclasses import dataclass\nfrom typing import Any, List, Optional\n\n@dataclass\nclass User:\n    first_name: str\n    age: int\n\n@dataclass\nclass Root:\n    user: User\n    tags: List[str]\n    note: Optional[Any] = None`}</code></pre>

<h2>Example: Nested Objects and Missing Keys</h2>

<p>Input:</p>

<pre><code>{`{"id": 7, "title": "Release notes", "author": {"name": "Alice", "email": null}, "tags": ["python", "json"], "score": 4.5, "comments": [{"user": "bob", "text": "nice"}, {"user": "carol"}]}`}</code></pre>

<p>Output in @dataclass mode:</p>

<pre><code>{`from dataclasses import dataclass
from typing import Any, List, Optional

@dataclass
class Author:
    name: str
    email: Optional[Any] = None

@dataclass
class CommentsItem:
    user: str
    text: Optional[str] = None

@dataclass
class Root:
    id: int
    title: str
    author: Author
    tags: List[str]
    score: float
    comments: List[CommentsItem]`}</code></pre>

<p>Classes are ordered so that each one is defined before it is used. <code>{"text"}</code> is missing from the second comment, so it becomes <code>{"Optional[str] = None"}</code>.</p>

<h2>dataclass, Pydantic or TypedDict</h2>

<p>The three modes describe the same shape but behave differently at runtime (checked with Python 3.12 and Pydantic 2.13):</p>

<pre><code>{`root = Root(**json.loads(raw))
type(root.author)          # <class 'dict'>, not Author`}</code></pre>

<pre><code>{`root = Root.model_validate(json.loads(raw))   # Pydantic mode
root.comments[1]           # CommentsItem(user='carol', text=None)`}</code></pre>

<ul>
  <li><strong>@dataclass</strong> does not validate or convert. <code>{"Root(**data)"}</code> keeps nested objects as plain dicts and accepts wrong types. Use it when the data is already trusted, or convert nested fields yourself.</li>
  <li><strong>Pydantic</strong> validates types and builds nested models; use it for API responses you do not control. <code>{"model_validate_json(raw)"}</code> parses and validates in one step.</li>
  <li><strong>TypedDict</strong> only describes dict types for a type checker; nothing is checked at runtime. Every key is required by default, so the tool marks a key that is missing from some items as <code>{"NotRequired[...]"}</code> (PEP 655, <code>typing</code> in Python 3.11+, <code>typing_extensions</code> before that). <code>{"Optional[...]"}</code> only means the value may be <code>None</code>; the key would still be required.</li>
</ul>

<h2>Example: TypedDict with Missing Keys</h2>

{/* jpdc-check: {"root":"Product","mode":"typeddict"} */}

<p>Two products where <code>note</code> is null in the first and absent from the second, and <code>discount</code> only appears in the second (root class name <code>Product</code>, TypedDict mode):</p>

<pre><code>{`[{"id": 1, "sku": "PEN-01", "price": 2, "note": null}, {"id": 2, "sku": "INK-07", "price": 1.5, "discount": 0.1}]`}</code></pre>

<pre><code>{`from typing import Any, NotRequired, Optional, TypedDict

class Product(TypedDict):
    id: int
    sku: str
    price: float
    note: NotRequired[Optional[Any]]
    discount: NotRequired[float]`}</code></pre>

<p><code>price</code> is <code>2</code> in one item and <code>1.5</code> in the other; PEP 484 lets an <code>int</code> stand in for a <code>float</code>, so the field is <code>float</code>. At runtime <code>Product.__required_keys__</code> is <code>{"{'id', 'sku', 'price'}"}</code> and <code>__optional_keys__</code> is <code>{"{'note', 'discount'}"}</code> (checked with Python 3.12). A type checker then accepts a product without <code>discount</code> and rejects one without <code>sku</code> (mypy 2.3.1: Missing key "sku" for TypedDict "Product").</p>

<h2>Limits</h2>

<ul>
  <li><code>{"null"}</code> becomes <code>{"Optional[Any]"}</code>; replace <code>{"Any"}</code> with the real type.</li>
  <li>Keys that cannot be field names as they are (keywords such as <code>{"class"}</code>, keys like <code>{"user-id"}</code> or <code>2fa</code>, keys that start with <code>{"__"}</code> or name a type the annotations use, and in Pydantic keys that start with <code>{"_"}</code> or name a <code>BaseModel</code> attribute such as <code>json</code>) get a valid name. @dataclass notes the JSON key in a comment (map it yourself before <code>{"Root(**data)"}</code>), Pydantic adds <code>{"Field(alias=...)"}</code> so <code>{"model_validate()"}</code> reads the original key, and TypedDict switches to the functional form <code>{'TypedDict("Name", {...})'}</code>, which keeps every key. See the example below.</li>
  <li>Dates stay <code>{"str"}</code>; Pydantic converts ISO 8601 strings if you change the type to <code>{"datetime"}</code>.</li>
  <li>Arrays of primitives at the root generate no class. In a root array that mixes objects and other values, the objects become the root class and the whole array gets an alias at the end, <code>{"ProductArray = List[Union[...]]"}</code> (see below).</li>
  <li>A number written as <code>10.0</code> reaches the generator as the integer <code>10</code> (JavaScript's <code>JSON.parse</code> keeps no trailing zeros), so <code>{"price: int"}</code>. Pydantic then rejects a later <code>10.5</code> with <code>Input should be a valid integer, got a number with a fractional part</code>; change the field to <code>float</code> when prices can have decimals.</li>
  <li>The root class name is used as typed when it is a Python identifier; otherwise it is converted: <code>{"order-item"}</code> → <code>OrderItem</code>, <code>2fa</code> → <code>{"_2fa"}</code>, the keyword <code>class</code> → <code>{"class_"}</code>, a leading <code>{"__"}</code> becomes one <code>{"_"}</code> (nested class names start with the root name, and Python mangles names that start with two underscores inside a class body), and <code>Root</code> when no identifier character is left.</li>
</ul>

<h2>Keys That Are Not Field Names</h2>

{/* jpdc-check: {"root":"Ticket","mode":"pydantic"} */}

<p>A MongoDB-style <code>{"_id"}</code>, a keyword, a dashed key and <code>json</code>, which is a <code>BaseModel</code> method (root class name <code>Ticket</code>, Pydantic v2 mode):</p>

<pre><code>{`{"_id": "65f0c1", "class": "economy", "user-id": 7, "json": null}`}</code></pre>

<pre><code>{`from pydantic import BaseModel, Field
from typing import Any, Optional

class Ticket(BaseModel):
    id: str = Field(alias="_id")
    class_: str = Field(alias="class")
    user_id: int = Field(alias="user-id")
    json_: Optional[Any] = Field(default=None, alias="json")`}</code></pre>

<p>In @dataclass mode <code>{"_id"}</code> and <code>json</code> stay (they are valid there) and the other two get <code>{"class_"}</code> and <code>{"user_id"}</code> with a <code>{"# JSON key"}</code> comment; in TypedDict mode the output is <code>{'Ticket = TypedDict("Ticket", {"_id": str, "class": str, ...})'}</code>. The tool's test runs all three in Python 3.12 and 3.14 and reads samples back.</p>

<h2>Repeated Key Names</h2>

{/* jpdc-check: {"root":"Root","mode":"dataclass"} */}

<p>Two <code>meta</code> objects with different fields get two classes; the second takes the parent name as a prefix:</p>

<pre><code>{`{"a": {"meta": {"x": 1}}, "b": {"meta": {"y": 2}}}`}</code></pre>

<pre><code>{`from dataclasses import dataclass

@dataclass
class Meta:
    x: int

@dataclass
class BMeta:
    y: int

@dataclass
class A:
    meta: Meta

@dataclass
class B:
    meta: BMeta

@dataclass
class Root:
    a: A
    b: B`}</code></pre>

<p>A <code>meta</code> with the same fields as <code>a.meta</code> would reuse <code>Meta</code>; if <code>BMeta</code> were taken as well, the next shape would be <code>Meta2</code>. Every sample of a key counts: the objects of one key in a root array, or in arrays inside it, merge into one class, and a key missing from some of them becomes optional. A key outside ASCII keeps all its characters in the class name, and because a class never takes the name of a JSON key (a Pydantic field with a default would hide a class of the same name), <code>{"{\"收货地址\": {...}}"}</code> under root <code>Order</code> gives the class <code>Order收货地址</code>.</p>

<h2>Root Arrays With Other Values</h2>

{/* jpdc-check: {"root":"Product","mode":"pydantic"} */}

<p>A root array can hold values that are not objects. They are kept in an alias after the classes (root class name <code>Product</code>, Pydantic v2 mode):</p>

<pre><code>{`[{"sku": "PEN-01", "price": 2}, "sold out", null, {"sku": "INK-07", "price": 1.5}]`}</code></pre>

<pre><code>{`from pydantic import BaseModel
from typing import List, Union

class Product(BaseModel):
    sku: str
    price: float

ProductArray = List[Union[str, None, Product]]`}</code></pre>

<p><code>{"TypeAdapter(ProductArray).validate_python(data)"}</code> validates the whole array in Pydantic; the tool's test runs it with Pydantic 2.13.5. A <code>null</code> element becomes <code>None</code> in the union.</p>

<h2>Empty arrays and sample coverage</h2>

<p>An empty array gives the generator no evidence about its element type, so <code>{`{"tags": []}`}</code> produces <code>tags: List[Any]</code>. Include another object with <code>{`{"tags": ["admin"]}`}</code> in the same input array and the merged field becomes <code>List[str]</code>. The generator uses the samples you provide. It cannot infer a field that appears in none of them. Include representative objects with missing keys and null values before copying the classes.</p>
