faqItems:
  - question: "What is URL encoding?"
    answer: "URL encoding (percent-encoding, RFC 3986 section 2.1) writes a character as '%' followed by two hex digits for each of its UTF-8 bytes. A space becomes %20, '&' becomes %26 and 'é' becomes %C3%A9."
  - question: "What is the difference between encodeURI and encodeURIComponent?"
    answer: "encodeURI is meant for a whole URL and leaves the separators ; , / ? : @ & = + $ # unencoded. encodeURIComponent is meant for one part, such as a query value, and encodes those separators too. Both leave letters, digits and - _ . ! ~ * ' ( ) unencoded. This tool uses encodeURIComponent."
  - question: "Why does decoding leave + signs in the output?"
    answer: "decodeURIComponent only reverses %XX sequences. The + for space comes from HTML form encoding (application/x-www-form-urlencoded), not from percent-encoding, so a+b decodes to a+b. Replace + with %20 first, or decode the value with URLSearchParams in your code."
  - question: "Why do I get 'Error: URI malformed'?"
    answer: "The browser's decodeURIComponent stops at the first % that is not followed by two hex digits, or at bytes that are not valid UTF-8. Examples: 100%, %zz, a cut-off sequence such as %E4%B8, and GBK or Shift_JIS bytes such as %C4%E3."
  - question: "Is my data sent to any server?"
    answer: "No. The conversion runs in your browser with JavaScript's built-in encodeURIComponent and decodeURIComponent. The last input is kept in this browser's local storage so it is still there when you come back; Clear removes it."

<p>
  The first row shows what this tool is for: the whole address becomes one opaque value. That is what you want when a URL is itself
  a parameter, for example <code>?redirect=https%3A%2F%2Fexample.com%2Fsearch%3Fq%3D...</code>. If you encode a complete address
  that you plan to open, the <code>:</code> and <code>/</code> separators are encoded too and the result is no longer a working link.
  To clean up a full URL instead, encode each query value on its own and join them with <code>&amp;</code>, or use the
  <a href="/tools/url-parser/">URL Parser</a>, which shows every part of an address and lets you edit query values.
</p>
<p>
  Non-ASCII text is converted to UTF-8 first, so one character can become two to four <code>%XX</code> groups: <code>é</code> is
  two bytes, <code>東</code> three, and the emoji four. Encoding twice turns each <code>%</code> into <code>%25</code>
  (<code>a b</code> → <code>a%20b</code> → <code>a%2520b</code>). If you see <code>%25</code> in a link, a value was encoded one
  time too many.
</p>

<h2>Differences from Other Encoders</h2>
<ul>
  <li><strong>Characters left as they are.</strong> RFC 3986 section 2.3 lists only letters, digits and <code>- . _ ~</code> as
  unreserved. <code>encodeURIComponent</code> also leaves <code>! ' ( ) *</code> unencoded (fourth example). Most servers accept
  them, but some request-signing schemes (OAuth 1.0 signatures, AWS Signature Version 4) require them as <code>%21 %27 %28 %29 %2A</code>.
  Encode those five by hand when a signature check fails.</li>
  <li><strong>Spaces become <code>%20</code>, not <code>+</code>.</strong> HTML forms and <code>URLSearchParams</code> write a
  space as <code>+</code> (WHATWG URL Standard, application/x-www-form-urlencoded). Both forms are read as a space by form decoders,
  but this tool's decoder only reverses <code>%XX</code>, so a <code>+</code> stays a plus sign (last example).</li>
</ul>

<h2>Limitations</h2>
<ul>
  <li>Decoding fails with <code>Error: URI malformed</code> when a <code>%</code> is not followed by two hex digits
  (<code>100%</code>, <code>%zz</code>), when a UTF-8 sequence is cut short (<code>%E4%B8</code>), or when the bytes come from another
  encoding such as GBK or Shift_JIS (<code>%C4%E3</code>). The error text comes from the browser, so it is in English on every page
  and its wording differs between browsers.</li>
  <li>Encoding fails with the same error for text that contains a lone UTF-16 surrogate, which can appear when a string is cut in the
  middle of an emoji.</li>
  <li>There is no option for <code>+</code> as space, for <code>encodeURI</code> behaviour, or for legacy encodings. Only UTF-8 is
  supported, as in RFC 3986 section 2.5 for new URI schemes.</li>
</ul>
