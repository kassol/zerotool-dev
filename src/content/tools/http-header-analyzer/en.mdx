<h2>Example: Response with security headers</h2>

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
Content-Security-Policy: default-src 'self'; script-src 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Cache-Control: no-store
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict; Path=/
```

<p>The analyzer groups Strict-Transport-Security, Content-Security-Policy, X-Content-Type-Options, and Referrer-Policy under <strong>Security</strong>. Cache-Control lands in <strong>Caching</strong>, Content-Type in <strong>Content</strong>, and Set-Cookie in <strong>Cookie</strong>. Each card includes a one-line description and any hints — for example, a Set-Cookie without HttpOnly triggers a warning.</p>

<h2>Example: CORS preflight</h2>

{/* hha-check: {"view":"json"} */}
```
OPTIONS /api/v1/orders HTTP/1.1
Host: api.example.com
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Authorization, Content-Type
```

<p>This is recognized as a request, and the Access-Control-Request-* pair marks it as a preflight. Origin and both Access-Control-Request-* headers are listed under <strong>CORS</strong>; Host is under General. Copy JSON gives:</p>

```json
{
  "_status": "OPTIONS /api/v1/orders HTTP/1.1",
  "host": "api.example.com",
  "origin": "https://app.example.com",
  "access-control-request-method": "POST",
  "access-control-request-headers": "Authorization, Content-Type"
}
```

<p>Paste the server's answer to the preflight next to it to see whether the Access-Control-Allow-* values cover the requested method and headers; the tool does not compare the two messages for you.</p>

<h2>Categories at a glance</h2>
<ul>
  <li><strong>Status</strong> — the first line (status line or method line).</li>
  <li><strong>Lines not read as headers</strong> — lines that are not header field lines, for example without a colon, with the line number and the reason. They are left out of the count, the Raw view and the JSON.</li>
  <li><strong>Security</strong> — HSTS, CSP, X-Frame-Options, COOP/COEP/CORP, Permissions-Policy, fetch metadata.</li>
  <li><strong>Caching</strong> — Cache-Control, ETag, Vary, Expires, Last-Modified, conditional headers.</li>
  <li><strong>Content</strong> — Content-Type, Content-Encoding, Accept-\*, Content-Disposition.</li>
  <li><strong>CORS</strong> — Access-Control-\* and Origin.</li>
  <li><strong>Auth</strong> — Authorization, WWW-Authenticate, Proxy-Authenticate.</li>
  <li><strong>Cookie</strong> — Cookie and Set-Cookie.</li>
  <li><strong>Transport / Range / Proxy / General / Custom</strong> — the rest, with X-\* unknown headers in Custom.</li>
</ul>

<h2>Compliance hints</h2>
<p>Hints are conservative — they highlight obvious misconfiguration, not subjective style. Examples:</p>
<ul>
  <li>HSTS max-age below 1 year, or missing includeSubDomains / preload directives.</li>
  <li>CSP containing <code>'unsafe-eval'</code>, or <code>'unsafe-inline'</code> in a directive without a nonce or hash.</li>
  <li>Set-Cookie without HttpOnly or Secure flags.</li>
  <li>Access-Control-Allow-Credentials: true paired with a wildcard origin (spec-illegal).</li>
  <li>Cache-Control combining no-store with max-age (dead weight).</li>
</ul>

<h2>Example: a response with problems</h2>

<p>Pasting the following response, copied from an HTTP/2 site, produces the hints listed under it. The hint texts are quoted from the tool's output.</p>

{/* hha-check: {"view":"hints"} */}
```
HTTP/2 200
content-type: text/html; charset=utf-8
strict-transport-security: max-age=86400
content-security-policy: script-src 'self' 'unsafe-inline'
access-control-allow-origin: *
access-control-allow-credentials: true
set-cookie: sid=31d4d96e407aad42; Path=/
cache-control: no-store, max-age=600
server: nginx
```

<p>The categorized view shows these hints, card by card:</p>

```text
strict-transport-security
  Warning: max-age < 1 year (31536000s). Many preload lists require ≥ 1 year.
  Note: Add includeSubDomains for full coverage.
  Note: Add preload and submit to hstspreload.org.
content-security-policy
  Warning: 'unsafe-inline' defeats most XSS protection. Use nonces or hashes instead.
  Note: No default-src — define one as a safety net.
cache-control
  Warning: no-store and max-age together — no-store wins, max-age is dead weight.
access-control-allow-origin
  Note: Wildcard origin disables credentialed CORS by spec.
access-control-allow-credentials
  Warning: Credentialed CORS requires explicit Allow-Origin (no wildcard).
set-cookie
  Warning: Missing HttpOnly — cookie is reachable from JavaScript.
  Warning: Missing Secure — cookie can be sent over plain HTTP.
  Note: No SameSite — Chrome treats the cookie as Lax, Firefox and Safari do not. Set it explicitly.
server
  Note: Exposing server software helps attackers fingerprint the stack. Consider suppressing.
```

<ul>
  <li><strong>strict-transport-security</strong>: Warning “max-age &lt; 1 year (31536000s). Many preload lists require ≥ 1 year.”, plus notes to add includeSubDomains and preload. One day (86400 s) is far below the one year that hstspreload.org requires.</li>
  <li><strong>content-security-policy</strong>: Warning “'unsafe-inline' defeats most XSS protection. Use nonces or hashes instead.” and a note that there is no <code>default-src</code>.</li>
  <li><strong>access-control-allow-credentials</strong>: Warning “Credentialed CORS requires explicit Allow-Origin (no wildcard).” The Fetch Standard does not let a browser expose a credentialed response when the origin is <code>*</code>. The warning disappears when the pasted headers contain a specific origin such as <code>https://app.example.com</code>.</li>
  <li><strong>set-cookie</strong>: Warnings for missing HttpOnly and Secure, and a note for the missing SameSite attribute: Chrome treats such a cookie as <code>SameSite=Lax</code>, while Firefox and Safari do not (MDN browser compatibility data), so the behaviour differs between browsers.</li>
  <li><strong>cache-control</strong>: Warning that <code>no-store</code> makes <code>max-age=600</code> pointless.</li>
  <li><strong>server</strong>: A note that the software name helps fingerprinting.</li>
</ul>

<p>The summary bar shows the message type (response), the status line, the number of headers and how many fall in the Security group. A response with no security headers at all gets a warning in the summary instead.</p>

<h2>Where to copy headers from</h2>
<ul>
  <li><strong>curl</strong>: <code>curl -sS -D - -o /dev/null https://example.com/</code> prints the response headers of a normal GET. <code>curl -i</code> prints the body after them; you can paste it as it is, because the tool stops at the empty line. <code>curl -I</code> sends a HEAD request, which some servers answer with different headers.</li>
  <li><strong>Chrome or Edge DevTools</strong>: Network panel → select the request → Headers → turn on <strong>Raw</strong> next to Response Headers or Request Headers, then copy.</li>
  <li><strong>Firefox DevTools</strong>: Network panel → select the request → Headers → turn on the <strong>Raw</strong> switch.</li>
</ul>
<p>If you need the full request list with timings and bodies, export a HAR file and open it in the HAR analyzer below instead.</p>

<h2>Limitations</h2>
<ul>
  <li>The descriptions and hint texts are in English on every language version of this page. 88 headers have a description; any other header is listed under Custom / Other without one.</li>
  <li>HTTP/2 and HTTP/3 pseudo-headers such as <code>:status</code> and <code>:path</code>, which browser developer tools copy as the first lines, are listed in their own group with a short description (RFC 9113 §8.3, RFC 8441 for <code>:protocol</code>). Without a status line, <code>:status</code> marks the input as a response and <code>:method</code> as a request.</li>
  <li>The first line is read as a request line only for GET, POST, PUT, DELETE, PATCH, OPTIONS, HEAD, TRACE and CONNECT, written in uppercase. Method names are case-sensitive (RFC 9110 section 9.1), so <code>get / HTTP/1.1</code> is listed under “Lines not read as headers” with a note; other methods such as PROPFIND are listed there as lines without a colon.</li>
  <li>One message is analyzed. A header section ends at an empty line (RFC 9112 section 2.1). If the next line is a status line or request line, it starts another message: <code>curl -v</code> gives the request and then the response, <code>curl -iL</code> gives one response per redirect. The tool analyzes the last response, lists the other messages under “Other messages in the input” and says so in the status line. Any other line after an empty line ends the reading, and the status line says how many lines were not read. The tool skips the <code>*</code> lines and data lines such as <code>{'} [5 bytes data]'}</code>, and removes a leading <code>&gt; </code> or <code>&lt; </code>.</li>
  <li>A line that is not a header field line, such as one without an ASCII colon or with a full-width colon (<code>Content-Type：text/html</code>), is not counted. It is listed under “Lines not read as headers” with its line number and the reason, and the status line gives the count. A line with whitespace between the name and the colon is listed there too, because RFC 9112 section 5.1 does not allow it (a server must reject such a request with 400).</li>
  <li>The HSTS check reads <code>max-age</code> as digits or as a quoted value such as <code>max-age="31536000"</code>, which RFC 6797 section 6.1 allows. When a response has more than one Strict-Transport-Security header, only the first is checked; the others get a note that browsers ignore them (RFC 6797 section 8.1).</li>
  <li>The <code>'unsafe-inline'</code> check works per directive. When the same directive also has a nonce or hash, browsers that support CSP Level 2 or later ignore <code>'unsafe-inline'</code> (CSP Level 3 section 6.7.3.2), so the tool shows a note instead of the warning; this is the usual fallback for old browsers in a strict policy. <code>style-src 'unsafe-inline'</code> without a nonce or hash still gets the warning, whose text is about scripts. <code>'strict-dynamic'</code> on its own is not taken into account.</li>
  <li>Hints look at one header at a time, except the CORS credentials check above. The tool does not evaluate a full CSP (use the <a href="/tools/csp-header-generator/">CSP Header Generator</a>) and does not check cookie attributes beyond HttpOnly, Secure and SameSite.</li>
  <li>The JSON view uses lowercase names, because header names are case-insensitive (RFC 9110 section 5.1), and puts repeated headers into arrays.</li>
  <li>Nothing is fetched: the tool cannot see redirects or headers you did not paste. Because pasted headers often contain cookies and tokens, this page does not load Google Analytics or AdSense, and the input is not saved.</li>
</ul>
