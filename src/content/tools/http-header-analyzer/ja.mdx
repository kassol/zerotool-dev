<h2>例：LINE Messaging API の 409 レスポンス</h2>

<p>LINE Messaging API で <code>X-Line-Retry-Key</code> を付けてプッシュメッセージを再送すると、同じキーのリクエストがすでに受理されていれば <code>409 Conflict</code> が返ります（<a href="https://developers.line.biz/ja/reference/messaging-api/#status-codes">Messaging API リファレンス「ステータスコード」</a>）。そのとき元のリクエストの ID は <code>X-Line-Accepted-Request-Id</code> に入ります。</p>

<p>リファレンスでは、レスポンスヘッダーの表が <code>X-Line-Request-Id</code>、レスポンス例が <code>x-line-request-id</code> と、大文字・小文字の書き方が異なります。Webhook の説明でも、ヘッダー名の大文字・小文字は予告なく変わることがあるので区別せずに扱うよう書かれています。HTTP のフィールド名はもともと大文字・小文字を区別しない（RFC 9110 5.1 節）ので、本ツールの JSON は名前を小文字にそろえます。2 つの書き方を混ぜて貼り付けると、JSON 表示は次のとおりです。</p>

{/* hha-check: {"view":"json"} */}
```
HTTP/1.1 409 Conflict
X-Line-Request-Id: 123e4567-e89b-12d3-a456-426655440002
x-line-accepted-request-id: 123e4567-e89b-12d3-a456-426655440001
```

```json
{
  "_status": "HTTP/1.1 409 Conflict",
  "x-line-request-id": "123e4567-e89b-12d3-a456-426655440002",
  "x-line-accepted-request-id": "123e4567-e89b-12d3-a456-426655440001"
}
```

<p>リファレンスのレスポンス例は、空行のあとに JSON の本文まで続いています。これはそのまま貼っても構いません。RFC 9112 2.1 節のとおり、ヘッダーのあとの空行がヘッダー部の終わりなので、ツールはそこで読み込みを止め、本文はヘッダーとして扱いません。ボタンの下の状態表示は次のようになります。</p>

{/* hha-check: {"view":"status"} */}
```
HTTP/1.1 409 Conflict
x-line-request-id: 123e4567-e89b-12d3-a456-426655440002
x-line-accepted-request-id: 123e4567-e89b-12d3-a456-426655440001

{
  "message": "The retry key is already accepted"
}
```

```text
2 件のヘッダーを解析しました。4 行目の空行でヘッダーが終わったと判断し、その後の 3 行は読み込んでいません。
```

<p>何行目で止まり、その後に何行残っているかが表示されるので、ヘッダーを貼り漏らしていないかもここで確認できます。</p>

<h2>例：仕様書からコピーした全角コロン</h2>

<p>Excel や Word の API 仕様書では、日本語入力のまま <code>Content-Type：application/json</code> のように全角コロン（：）で書かれていることがあります。HTTP のヘッダーフィールドの区切りは半角コロンだけなので、ツールはこうした行をヘッダーとして数えず、「ヘッダーとして読まなかった行」に行番号と理由を付けて表示します。LINE のプッシュメッセージ送信のリクエストを、2 行だけ全角コロンにして貼った場合の表示です（トークンと UUID はリファレンスの書式どおりのプレースホルダーです）。</p>

{/* hha-check: {"view":"invalid"} */}
```
POST /v2/bot/message/push HTTP/1.1
Host: api.line.me
Content-Type：application/json
Authorization：Bearer {channel access token}
X-Line-Retry-Key: {UUID}
```

```text
3 行目: Content-Type：application/json
  警告: 全角コロン（：）が使われています。HTTP で区切りになるのは半角コロン（:）だけなので、この行はヘッダーフィールドとして読めません。半角で入力し直してください。
4 行目: Authorization：Bearer {channel access token}
  警告: 全角コロン（：）が使われています。HTTP で区切りになるのは半角コロン（:）だけなので、この行はヘッダーフィールドとして読めません。半角で入力し直してください。
```

<p>生データ表示と JSON には Host と X-Line-Retry-Key だけが入り、状態表示にも「ヘッダーとして読まなかった行が 2 行あります」と出ます。全角コロンの行は、半角に打ち直してから分析し直してください。</p>

<h2>カテゴリ一覧</h2>
<ul>
  <li><strong>ステータス</strong> — 1 行目（ステータス行またはメソッド行）。</li>
  <li><strong>ヘッダーとして読まなかった行</strong> — コロンのない行など、ヘッダーフィールドの形になっていない行。行番号と理由を表示し、件数・生データ・JSON には含めません。</li>
  <li><strong>セキュリティ</strong> — HSTS、CSP、X-Frame-Options、COOP/COEP/CORP、Permissions-Policy、Fetch metadata。</li>
  <li><strong>キャッシュ</strong> — Cache-Control、ETag、Vary、Expires、Last-Modified、条件付きリクエストヘッダー。</li>
  <li><strong>コンテンツ</strong> — Content-Type、Content-Encoding、Accept-\*、Content-Disposition。</li>
  <li><strong>CORS</strong> — Access-Control-\* と Origin。</li>
  <li><strong>認証</strong> — Authorization、WWW-Authenticate、Proxy-Authenticate。</li>
  <li><strong>Cookie</strong> — Cookie と Set-Cookie。</li>
  <li><strong>転送 / レンジ / プロキシ / 一般 / カスタム</strong> — 残りのヘッダー。88 種類に入っていないヘッダー（上の <code>X-Line-*</code> など）は「カスタム / その他」に入り、説明は付きません。</li>
  <li><strong>HTTP/2 · HTTP/3 疑似ヘッダー</strong> — ブラウザの開発者ツールがコピーする <code>:status</code>、<code>:method</code>、<code>:path</code> などは別のグループに説明付きで表示します（RFC 9113 §8.3）。ステータス行がなければ、<code>:status</code> でレスポンス、<code>:method</code> でリクエストと判定します。</li>
</ul>

<h2>ヒントが出る条件</h2>
<ul>
  <li>HSTS の max-age が 1 年未満、または includeSubDomains / preload がない。</li>
  <li>CSP に <code>'unsafe-eval'</code> がある、nonce やハッシュのないディレクティブに <code>'unsafe-inline'</code> がある、または <code>default-src</code> がない。</li>
  <li>Set-Cookie に HttpOnly、Secure、SameSite のどれかがない。</li>
  <li>Access-Control-Allow-Credentials: true なのに、貼り付けたヘッダーに具体的な Allow-Origin がない（<code>*</code> だけ、または Allow-Origin なし）。</li>
  <li>Cache-Control に no-store と max-age が両方ある。</li>
  <li>X-Frame-Options が DENY・SAMEORIGIN・ALLOW-FROM 以外、X-XSS-Protection が 1 で始まる。</li>
  <li>レスポンスに Server ヘッダーがある。</li>
</ul>
<p>ヘッダーの説明文とヒントは、どの言語のページでも英語で表示されます。</p>

<h2>制限事項</h2>
<ul>
  <li>リクエスト行として読むのは、大文字で書かれた GET・POST・PUT・DELETE・PATCH・OPTIONS・HEAD・TRACE・CONNECT の 9 メソッドだけです。メソッド名は大文字・小文字を区別するので（RFC 9110 9.1 節）、<code>get / HTTP/1.1</code> は説明付きで「ヘッダーとして読まなかった行」に入ります。PROPFIND など他のメソッドの行は、コロンのない行として表示されます。</li>
  <li>一度に読むのは 1 つのメッセージだけです。<code>curl -v</code> の出力はリクエスト、<code>&gt;</code> だけの行、レスポンスの順に並ぶため、まとめて貼るとリクエストしか読みません。レスポンスを見たいときはその部分だけを貼ってください。<code>*</code> で始まる行と <code>{'} [5 bytes data]'}</code> のようなデータ行は飛ばし、行頭の <code>&gt; </code>・<code>&lt; </code> は取り除きます。</li>
  <li>ヘッダー名とコロンの間に空白がある行も、RFC 9112 5.1 節が認めていないため（サーバーはこのようなリクエストを 400 で拒否します）、「ヘッダーとして読まなかった行」に入ります。</li>
  <li>HSTS の <code>max-age</code> は、数字だけの形式に加えて、RFC 6797 6.1 節が認める <code>max-age="31536000"</code> のような引用符付きの値も読みます。Strict-Transport-Security が複数あるときは最初の 1 つだけをチェックし、残りにはブラウザーが無視する旨の注意を付けます（RFC 6797 8.1 節）。</li>
  <li><code>'unsafe-inline'</code> はディレクティブごとに判定します。同じディレクティブに nonce やハッシュがあれば、CSP Level 2 以降に対応したブラウザーは <code>'unsafe-inline'</code> を無視する（CSP Level 3 6.7.3.2 節）ため、警告ではなく注意を表示します。厳格なポリシーで古いブラウザー向けに残しておく書き方がこれにあたります。nonce もハッシュもない <code>style-src 'unsafe-inline'</code> には、スクリプトについての警告文がそのまま出ます。<code>'strict-dynamic'</code> だけの場合は考慮しません。</li>
  <li>URL からは取得しないので、リダイレクトや貼り付けていないヘッダーは見えません。</li>
</ul>
