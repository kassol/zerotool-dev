<h2>예시: 네이버 개발자 문서의 curl -v 출력을 그대로 붙여넣기</h2>

<p>네이버 검색 API 문서(<a href="https://developers.naver.com/docs/serviceapi/search/blog/blog.md">블로그 검색</a>)는 요청과 응답 예를 <code>curl -v</code> 출력 형태로 보여 줍니다. 응답 헤더 줄마다 앞에 <code>&lt; </code>가 붙어 있고, 헤더가 끝나는 자리에는 <code>&lt;</code>만 있는 줄이 있으며, 그 뒤로 XML 본문이 이어집니다. 이 도구는 줄 앞의 <code>&lt; </code>를 떼어 내고, 헤더 뒤의 첫 빈 줄(여기서는 <code>&lt;</code>만 남은 줄)에서 읽기를 멈춥니다(RFC 9112 2.1절). 문서의 응답 예를 본문 첫 줄까지 그대로 붙여넣은 요약입니다.</p>

{/* hha-check: {"view":"summary"} */}
```
< HTTP/1.1 200 OK
< Server: nginx
< Date: Mon, 26 Sep 2016 01:39:37 GMT
< Content-Type: text/xml;charset=utf-8
< Transfer-Encoding: chunked
< Connection: keep-alive
< Keep-Alive: timeout=5
< Vary: Accept-Encoding
< X-Powered-By: Naver
< Cache-Control: no-cache, no-store, must-revalidate
< Pragma: no-cache
<
<?xml version="1.0" encoding="UTF-8"?>
```

```text
응답
HTTP/1.1 200 OK
10 개 헤더
보안 헤더 없음 ⚠
```

<p>응답으로 인식되고, 보안 헤더가 하나도 없다는 경고가 요약에 나타납니다. 분류별 보기에서는 Server 카드에 서버 소프트웨어 노출에 관한 참고가 붙습니다. 같은 문서의 요청 예(<code>&gt; </code>로 시작하는 줄)도 같은 방식으로 읽습니다. 다만 요청과 응답을 한꺼번에 붙여넣으면 요청 끝의 <code>&gt;</code> 줄에서 멈추므로 요청만 분석됩니다. 버튼 아래 상태 표시에는 멈춘 줄과 남은 줄 수가 나옵니다.</p>

{/* hha-check: {"view":"status"} */}
```
> GET /v1/search/blog.xml?query=%EB%A6%AC%EB%B7%B0&display=10&start=1&sort=sim HTTP/1.1
> Host: openapi.naver.com
> User-Agent: curl/7.49.1
> Accept: */*
>
< HTTP/1.1 200 OK
< Server: nginx
```

```text
3 개의 헤더를 분석했습니다. 5번째 줄의 빈 줄에서 헤더가 끝난 것으로 보고, 그 뒤의 2줄은 읽지 않았습니다.
```

<h2>예시: 클라이언트 아이디가 들어간 요청 헤더</h2>

<p>같은 문서에 따르면 검색 API를 호출할 때는 클라이언트 아이디와 시크릿을 URL이 아니라 <code>X-Naver-Client-Id</code>, <code>X-Naver-Client-Secret</code> 요청 헤더로 보내야 합니다(<a href="https://developers.naver.com/docs/common/openapiguide/errorcode.md">오류 코드</a> 문서는 이 헤더가 빠지거나 틀리면 401이 돌아온다고 설명합니다). <code>&gt; </code>를 지운 요청을 붙여넣은 분류별 보기입니다. 값은 실제 키가 아닌 자리 표시자입니다.</p>

{/* hha-check: {"view":"cards"} */}
```
GET /v1/search/blog.json?query=%EC%A0%9C%EC%A3%BC&display=10 HTTP/1.1
Host: openapi.naver.com
User-Agent: curl/7.49.1
Accept: */*
X-Naver-Client-Id: {클라이언트 아이디}
X-Naver-Client-Secret: {클라이언트 시크릿}
```

```text
상태
  GET /v1/search/blog.json?query=%EC%A0%9C%EC%A3%BC&display=10 HTTP/1.1
콘텐츠 1
  Accept
일반 2
  Host
  User-Agent
사용자 정의 / 기타 2
  X-Naver-Client-Id
  X-Naver-Client-Secret
```

<p>두 네이버 헤더는 88개 헤더 목록에 없으므로 설명 없이 ‘사용자 정의 / 기타’에 들어갑니다. 결과 화면과 ‘JSON 복사’에는 시크릿 값이 그대로 남으니, 이슈나 메신저에 붙일 때는 값을 지우세요. 요청 줄의 <code>query=%EC%A0%9C%EC%A3%BC</code>는 ‘제주’를 UTF-8로 퍼센트 인코딩한 값이며, 도구는 이를 디코딩하지 않습니다.</p>

<h2>카테고리 한눈에 보기</h2>
<ul>
  <li><strong>상태</strong> — 첫 줄(상태 줄 또는 메서드 줄).</li>
  <li><strong>헤더로 읽지 않은 줄</strong> — 콜론이 없는 줄처럼 헤더 필드 형식이 아닌 줄. 줄 번호와 이유를 보여 주며, 헤더 수·원본 보기·JSON에는 넣지 않습니다.</li>
  <li><strong>보안</strong> — HSTS, CSP, X-Frame-Options, COOP/COEP/CORP, Permissions-Policy, Fetch metadata.</li>
  <li><strong>캐싱</strong> — Cache-Control, ETag, Vary, Expires, Last-Modified, 조건부 요청 헤더.</li>
  <li><strong>콘텐츠</strong> — Content-Type, Content-Encoding, Accept-\*, Content-Disposition.</li>
  <li><strong>CORS</strong> — Access-Control-\*와 Origin.</li>
  <li><strong>인증</strong> — Authorization, WWW-Authenticate, Proxy-Authenticate.</li>
  <li><strong>쿠키</strong> — Cookie와 Set-Cookie.</li>
  <li><strong>전송 / 범위 / 프록시 / 일반 / 사용자 정의</strong> — 나머지 헤더. 88개 목록에 없는 헤더는 ‘사용자 정의 / 기타’에 들어갑니다.</li>
  <li><strong>HTTP/2 · HTTP/3 의사 헤더</strong> — 브라우저 개발자 도구가 복사하는 <code>:status</code>, <code>:method</code>, <code>:path</code> 등은 별도 그룹에 설명과 함께 표시합니다(RFC 9113 §8.3). 상태 줄이 없으면 <code>:status</code>는 응답, <code>:method</code>는 요청으로 판단합니다.</li>
</ul>

<h2>힌트가 붙는 경우</h2>
<ul>
  <li>HSTS max-age가 1년 미만이거나 includeSubDomains / preload가 없을 때.</li>
  <li>CSP에 <code>'unsafe-eval'</code>이 있거나, nonce나 해시가 없는 지시어에 <code>'unsafe-inline'</code>이 있거나, <code>default-src</code>가 없을 때.</li>
  <li>Set-Cookie에 HttpOnly, Secure, SameSite 중 하나라도 없을 때.</li>
  <li>Access-Control-Allow-Credentials: true인데 붙여넣은 헤더에 구체적인 Allow-Origin이 없을 때(<code>*</code>만 있거나 Allow-Origin이 없음).</li>
  <li>Cache-Control에 no-store와 max-age가 함께 있을 때.</li>
  <li>X-Frame-Options가 DENY, SAMEORIGIN, ALLOW-FROM이 아니거나, X-XSS-Protection이 1로 시작할 때.</li>
  <li>응답에 Server 헤더가 있을 때.</li>
</ul>
<p>헤더 설명과 힌트 문구는 모든 언어 페이지에서 영어로 표시됩니다.</p>

<h2>제한 사항</h2>
<ul>
  <li>요청 줄로 읽는 메서드는 대문자로 쓴 GET, POST, PUT, DELETE, PATCH, OPTIONS, HEAD, TRACE, CONNECT 9개뿐입니다. 메서드 이름은 대소문자를 구분하므로(RFC 9110 9.1절) <code>get / HTTP/1.1</code>은 설명과 함께 ‘헤더로 읽지 않은 줄’에 표시되고, PROPFIND 같은 다른 메서드의 줄은 콜론이 없는 줄로 표시됩니다.</li>
  <li>한 번에 메시지 하나만 읽습니다. 헤더 뒤의 첫 빈 줄에서 멈추므로 <code>curl -i</code>의 본문은 헤더로 읽지 않지만, 요청과 응답이 이어진 <code>curl -v</code> 출력은 요청만 읽습니다. <code>*</code>로 시작하는 줄과 <code>{'} [5 bytes data]'}</code> 같은 데이터 줄은 건너뜁니다.</li>
  <li>반각 콜론(:)이 없거나 전각 콜론(：)을 쓴 줄처럼 헤더 필드 형식이 아닌 줄은 헤더 수에 넣지 않고 ‘헤더로 읽지 않은 줄’에 줄 번호와 이유를 붙여 보여 주며, 상태 표시에도 그 수가 나옵니다. 헤더 이름과 콜론 사이에 공백이 있는 줄도 RFC 9112 5.1절이 허용하지 않으므로(서버는 이런 요청을 400으로 거부해야 함) 같은 곳에 표시합니다.</li>
  <li>HSTS의 <code>max-age</code>는 숫자뿐 아니라 RFC 6797 6.1절이 허용하는 <code>max-age="31536000"</code>처럼 따옴표가 붙은 값도 읽습니다. Strict-Transport-Security가 두 개면 브라우저는 첫 번째만 사용하지만(RFC 6797 8.1절) 도구는 둘 다 점검합니다.</li>
  <li><code>'unsafe-inline'</code>은 지시어별로 판단합니다. 같은 지시어에 nonce나 해시가 있으면 CSP Level 2 이상을 지원하는 브라우저는 <code>'unsafe-inline'</code>을 무시하므로(CSP Level 3 6.7.3.2절) 경고 대신 참고를 표시합니다. 엄격한 정책에서 오래된 브라우저를 위해 남겨 두는 쓰임새가 여기에 해당합니다. nonce나 해시가 없는 <code>style-src 'unsafe-inline'</code>에는 스크립트에 관한 경고 문구가 그대로 나옵니다. <code>'strict-dynamic'</code>만 있는 경우는 따지지 않습니다.</li>
  <li>URL에서 가져오지 않으므로 리다이렉트나 붙여넣지 않은 헤더는 볼 수 없습니다.</li>
</ul>
