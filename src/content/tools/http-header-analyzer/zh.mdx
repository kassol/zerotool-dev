<h2>示例：检查微信支付应答头有没有被代理去掉</h2>

<p>微信支付 APIv3 的应答把签名放在 <code>Wechatpay-Signature</code>、<code>Wechatpay-Timestamp</code>、<code>Wechatpay-Nonce</code>、<code>Wechatpay-Serial</code> 这几个头里。官方文档《<a href="https://pay.weixin.qq.com/doc/v3/merchant/4013053249">如何使用微信支付公钥验签</a>》提醒：某些代理服务器或 CDN 在转发时可能会过滤这些扩展头，导致应用层拿不到签名。验签失败时，可以把服务端实际收到的应答头贴进来，看这几个头还在不在。</p>

<p>下面的输入是该文档里 Native 下单应答的头部，签名值较长，这里截短了；第一行的状态行是为了让工具按响应处理而补上的。</p>

{/* hha-check: {"view":"cards"} */}
```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 52
Connection: keep-alive
Keep-Alive: timeout=8
Cache-Control: no-cache, must-revalidate
X-Content-Type-Options: nosniff
Request-ID: 08F5B8C2B506102C18FDDFEEA30620BE821E28EDC405-0
Content-Language: zh-CN
Wechatpay-Nonce: d824f2e086d3c1df967785d13fcd22ef
Wechatpay-Signature: mfI1CPqvBrgcXfgXMFjdNIhBf27ACE2Y
Wechatpay-Timestamp: 1722850421
Wechatpay-Serial: PUB_KEY_ID_0000000000000024101100397200000006
Wechatpay-Signature-Type: WECHATPAY2-SHA256-RSA2048
```

<p>分类视图的分组如下（每组标题后的数字是条数）：</p>

```text
状态行
  HTTP/1.1 200 OK
安全 1
  X-Content-Type-Options
缓存 1
  Cache-Control
内容 3
  Content-Type
  Content-Length
  Content-Language
通用 2
  Connection
  Keep-Alive
自定义 / 其他 6
  Request-ID
  Wechatpay-Nonce
  Wechatpay-Signature
  Wechatpay-Timestamp
  Wechatpay-Serial
  Wechatpay-Signature-Type
```

<p>5 个 <code>Wechatpay-*</code> 和 <code>Request-ID</code> 都在「自定义 / 其他」组里，没有说明文字——工具只认识 88 个常见标头，平台自己的头不在其中。工具也不做验签，只用来确认头有没有到达；验签串怎么拼、用哪把公钥，以上面的文档为准。</p>

<h2>示例：带安全头的响应</h2>

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
Content-Security-Policy: default-src 'self'; script-src 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Cache-Control: no-store
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict; Path=/
```

<p>这是工具「示例」菜单里的「响应 · 安全」。Strict-Transport-Security、Content-Security-Policy、X-Content-Type-Options、Referrer-Policy 归入<strong>安全</strong>组，Cache-Control 在<strong>缓存</strong>，Content-Type 在<strong>内容</strong>，Set-Cookie 在 <strong>Cookie</strong>。这一组配置不会触发任何警告；把 Set-Cookie 里的 HttpOnly 删掉再分析，就会出现「Missing HttpOnly」警告。</p>

<h2>示例：把 curl -i 的响应体也贴进来了</h2>

<p><code>curl -i</code> 会在头部后面接一个空行，再输出响应体。按 RFC 9112 第 2.1 节，这个空行就是头部的结尾，工具读到这里就停下，后面的响应体不当成头部。下面是一个下单接口的返回，整段贴进去后，按钮下方的状态行是：</p>

{/* hha-check: {"view":"status"} */}
```
HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8
Content-Length: 61

{"code":0,"msg":"成功","data":{"orderNo":"20261009000123"}}
```

```text
已解析 2 个标头。头部在第 4 行的空行处结束，后面的 1 行未读取。
```

<p>只算了 Content-Type 和 Content-Length 两个头部，JSON 结果里也没有响应体的内容。状态行会写明在第几行停下、后面还有几行没读，方便确认没有漏贴头部。</p>

<h2>类别一览</h2>
<ul>
  <li><strong>状态行</strong> — 首行（状态行或方法行）。</li>
  <li><strong>未作为头部读取的行</strong> — 没有冒号等不是头部字段行的行，标出行号和原因，不计入标头数，也不进原文视图和 JSON。</li>
  <li><strong>安全</strong> — HSTS、CSP、X-Frame-Options、COOP/COEP/CORP、Permissions-Policy、Fetch metadata。</li>
  <li><strong>缓存</strong> — Cache-Control、ETag、Vary、Expires、Last-Modified、条件请求头。</li>
  <li><strong>内容</strong> — Content-Type、Content-Encoding、Accept-\*、Content-Disposition。</li>
  <li><strong>CORS</strong> — Access-Control-\* 与 Origin。</li>
  <li><strong>鉴权</strong> — Authorization、WWW-Authenticate、Proxy-Authenticate。</li>
  <li><strong>Cookie</strong> — Cookie 与 Set-Cookie。</li>
  <li><strong>传输 / 范围 / 代理 / 通用 / 自定义</strong> — 其他类别；不在 88 个标头之内的头部都归入「自定义 / 其他」。</li>
  <li><strong>HTTP/2 · HTTP/3 伪首部</strong> — 浏览器开发者工具复制出的 <code>:status</code>、<code>:method</code>、<code>:path</code> 等单独成组并附说明（RFC 9113 §8.3）；没有状态行时，<code>:status</code> 表示响应，<code>:method</code> 表示请求。</li>
</ul>

<h2>提示规则</h2>
<p>提示只标出明显的配置问题：</p>
<ul>
  <li>HSTS max-age 小于 1 年，或缺少 includeSubDomains / preload。</li>
  <li>CSP 含 <code>'unsafe-eval'</code>，或某条指令有 <code>'unsafe-inline'</code> 却没有 nonce / hash，或没有 <code>default-src</code>。</li>
  <li>Set-Cookie 缺少 HttpOnly、Secure 或 SameSite。</li>
  <li>Access-Control-Allow-Credentials: true，而粘贴的头部里没有具体的 Allow-Origin（只有 <code>*</code> 或没有）。</li>
  <li>Cache-Control 同时含 no-store 与 max-age。</li>
  <li>X-Frame-Options 不是 DENY、SAMEORIGIN 或 ALLOW-FROM；X-XSS-Protection 以 1 开头。</li>
  <li>响应里有 Server 头。</li>
</ul>
<p>说明文字和提示在所有语言页面上都是英文。</p>

<h2>限制</h2>
<ul>
  <li>只有 GET、POST、PUT、DELETE、PATCH、OPTIONS、HEAD、TRACE、CONNECT 这 9 个大写方法会被识别为请求行。方法名区分大小写（RFC 9110 第 9.1 节），<code>get / HTTP/1.1</code> 会列在「未作为头部读取的行」里并附说明；PROPFIND 等其他方法的请求行会按「没有冒号」列出。</li>
  <li>一次只读一条报文：读到头部之后的第一个空行就停下。<code>curl -v</code> 的输出依次是请求、一个只有 <code>&gt;</code> 的行、响应，整段贴进去只会读到请求，要看响应请单独贴响应部分。<code>*</code> 开头的行和 <code>{'} [5 bytes data]'}</code> 这样的数据行会被跳过，行首的 <code>&gt; </code>、<code>&lt; </code> 会被去掉。</li>
  <li>不是头部字段行的行（没有半角冒号，或者像中文输入法打出的 <code>Content-Type：text/html</code> 那样用了全角冒号）不计入头部，列在「未作为头部读取的行」里，并写明行号和原因；状态行也会给出行数。名称和冒号之间有空白的行也列在这里，因为 RFC 9112 第 5.1 节不允许这样写（服务器必须以 400 拒绝这样的请求）。</li>
  <li>HSTS 的 <code>max-age</code> 既可以是纯数字，也可以按 RFC 6797 第 6.1 节写成带引号的 <code>max-age="31536000"</code>，两种都能读出。响应里有两个 Strict-Transport-Security 时，浏览器只用第一个（RFC 6797 第 8.1 节），工具两个都检查。</li>
  <li><code>'unsafe-inline'</code> 按指令逐条检查。同一指令里已有 nonce 或 hash 时，支持 CSP Level 2 及以上的浏览器会忽略 <code>'unsafe-inline'</code>（CSP Level 3 第 6.7.3.2 节），工具改为给出说明而不是警告——严格策略常这样写来照顾旧浏览器。没有 nonce 或 hash 的 <code>style-src 'unsafe-inline'</code> 仍会触发警告，而警告文字讲的是脚本。只写 <code>'strict-dynamic'</code> 的情况不在判断之内。</li>
  <li>不抓取网址，看不到重定向，也看不到你没贴进来的头部。</li>
</ul>
