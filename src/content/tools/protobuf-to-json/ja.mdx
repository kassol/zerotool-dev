<h2>使い方</h2>
<h3>Schema → サンプルJSON（デフォルトモード）</h3>
<ol>
  <li>左パネルに<code>.proto</code>スキーマを貼り付けます。</li>
  <li>ツールが全メッセージタイプを自動検出してドロップダウンに表示します。</li>
  <li>メッセージタイプを選択し、<strong>JSONを生成</strong>をクリックします。</li>
  <li>デフォルト値を持つサンプルJSONが右側に表示されます。</li>
</ol>

<h3>バイナリ → JSONモード</h3>
<ol>
  <li>トグルで<strong>バイナリ → JSON</strong>モードに切り替えます。</li>
  <li>上のテキストエリアに<code>.proto</code>スキーマを貼り付けます。</li>
  <li>2番目のテキストエリアにバイナリデータ（hexまたはbase64）を貼り付けます。</li>
  <li>メッセージタイプを選択し、<strong>バイナリをデコード</strong>をクリックします。</li>
</ol>

## Proto3構文クイックリファレンス

```proto
syntax = "proto3";

package myapp;

message User {
  string id = 1;
  string name = 2;
  int32 age = 3;
  repeated string roles = 4;
  Address address = 5;
  UserStatus status = 6;
}

message Address {
  string street = 1;
  string city = 2;
  string country_code = 3;
}

enum UserStatus {
  UNKNOWN = 0;
  ACTIVE = 1;
  INACTIVE = 2;
}
```

<h2>フィールドタイプ一覧</h2>
<ul>
  <li><strong>スカラー型：</strong><code>double</code>、<code>float</code>、<code>int32</code>、<code>int64</code>、<code>uint32</code>、<code>uint64</code>、<code>bool</code>、<code>string</code>、<code>bytes</code></li>
  <li><strong>繰り返しフィールド：</strong>フィールドの前に<code>repeated</code>を付ける — JSON配列に対応</li>
  <li><strong>ネストメッセージ：</strong>別のメッセージタイプをフィールド型として使用</li>
  <li><strong>enum：</strong><code>enum</code>で定義、最初の値は必ず0</li>
  <li><strong>oneof：</strong>グループ内の1つのフィールドのみ同時に設定可能</li>
</ul>

<h2>プライバシー</h2>
<p>処理はすべてクライアント側で行われます。スキーマとバイナリデータはアップロードも保存もされません。</p>

## 例：バイナリメッセージをデコードする

既定の `demo.Person` スキーマのまま **Binary → JSON** に切り替え、次の hex（43 バイト）を貼り付けます：

```
0a 06 e4 bd 90 e8 97 a4 10 29 1a 0f 73 61 74 6f 40 65 78 61 6d 70 6c 65 2e 6a 70 22 0c 12 06 e5 a4 a7 e9 98 aa 1a 02 4a 50 28 02
```

出力：

```json
{
  "name": "佐藤",
  "age": 41,
  "emails": [
    "sato@example.jp"
  ],
  "address": {
    "city": "大阪",
    "country": "JP"
  },
  "status": "INACTIVE"
}
```

日本語は UTF-8 で、「佐藤」は 6 バイト（`e4 bd 90 e8 97 a4`）です。Shift_JIS のバイト列を `string` フィールドに入れても正しく表示されません。`address.street` はバイナリに含まれていないため出力されません。デコード結果には実際に送られたフィールドだけが並びます。同じスキーマを **Schema → Sample JSON** モードで使うと `{"emails": [], "name": "", "age": 0, "address": null, "status": "UNKNOWN"}` になります。

## 公式 JSON マッピングとの違い

`protoc` の生成コードが出力するのは [ProtoJSON 形式](https://protobuf.dev/programming-guides/json/)です。このツール（protobuf.js 8.0.1、ページが読み込むブラウザ版で確認）は次の点が異なります：

| ケース | 公式 ProtoJSON | このツール |
|---|---|---|
| フィールド名 | lowerCamelCase（`country_code` → `countryCode`）。パーサーは両方受け付ける | `.proto` の表記のまま（`country_code`） |
| `int64` / `uint64` | 10 進文字列 | 10 進文字列。ただし 2^53 を超える値は精度が落ちる（`9007199254740993` が `"9007199254740992"` になる） |
| 列挙型 | 名前（`"ACTIVE"`） | 名前。スキーマにない数値は数値のまま（`7`） |
| `bytes` | 標準 Base64 | 標準 Base64 |
| `map<K, V>` | JSON オブジェクト | JSON オブジェクト |
| サンプルモードのネストしたメッセージ | — | `null`。ドロップダウンでその型を選ぶとフィールドが見える |

## キャプチャした gRPC ペイロードのデコード

gRPC は各メッセージの前に 5 バイト（1 バイトの圧縮フラグと 4 バイトのビッグエンディアン長）を付けます（[gRPC over HTTP/2](https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md)）。貼り付ける前にこの 5 バイトを取り除き、フラグが `01` なら先に展開してください。サーバーのリフレクションが有効なら、`grpcurl` で `.proto` なしに呼び出して JSON を表示できます。

## 制限事項

- **スキーマは単体で完結している必要があります。** `import` は取得されません。import 行だけで `google.protobuf.Timestamp` 型のフィールドを使うと `no such Type or Enum 'google.protobuf.Timestamp'` になります。参照先のメッセージも同じ欄に貼り付けてください。こうして貼った既知型は通常のメッセージとして表示され（`{"seconds": "1695427584"}`）、公式マッピングの RFC 3339 文字列にはなりません。
- **バイナリには型名がありません。** 違う型を選んでもデコードが成功し、的外れなフィールドが出ることがあります。`Customer` のバイト列 `0a 05 41 6c 69 63 65` を `Order` としてデコードすると `{"order_id": "Alice"}` になります。
- **途中で切れたデータはエラー**になります（例：`index out of range: 2 + 16 > 3`）。
- **hex か Base64 かは自動判定**：16 進文字だけで偶数長の入力は hex、それ以外は Base64 として読みます。たまたま 16 進文字だけでできた Base64 は hex と誤認されるので、先に hex に変換してください。
- **サンプルモードは既定値のみ**：空文字列、0、空の配列と map、最初の列挙値、ネストしたメッセージは `null`。`oneof` のフィールドは表示されません。
