<h2>Examples</h2>
<p><strong>The example token.</strong> <strong>Load Example</strong> fills in an HS256 token. The tool shows the header <code>{`{"alg":"HS256","typ":"JWT"}`}</code> and this payload:</p>

```json
{
  "sub": "1234567890",
  "name": "John Doe",
  "iat": 1516239022,
  "exp": 1893456000
}
```

<p>Next to <code>iat</code> it prints <code>Thu, 18 Jan 2018 01:30:22 GMT</code>, and next to <code>exp</code> it prints <code>Tue, 01 Jan 2030 00:00:00 GMT — valid</code>. The dates are in UTC; "valid" or "EXPIRED" compares <code>exp</code> with your computer's clock and nothing else.</p>
<p><strong>Non-ASCII claims.</strong> The payload segment <code>eyJuYW1lIjoiSm9zw6kiLCJyb2xlcyI6WyJhZG1pbiJdfQ</code> decodes to <code>{`{"name":"José","roles":["admin"]}`}</code>. JSON in a JWT is UTF-8 (<a href="https://www.rfc-editor.org/rfc/rfc7519#section-7.1" target="_blank" rel="noopener">RFC 7519 §7.1</a>), so the decoder turns the Base64URL bytes into UTF-8 text before parsing. A decoder that only calls <code>atob()</code> shows <code>JosÃ©</code> instead.</p>
<p>To decode a single segment without the token structure, paste it into <a href="/tools/base64/">Base64 Encode / Decode</a> with URL-safe selected. To build a test token with your own claims and secret, use the <a href="/tools/jwt-generator/">JWT Generator</a>.</p>

<h2>What the Decoder Checks</h2>
<ul>
  <li>The input must have exactly three parts separated by dots. Otherwise the status shows "Invalid JWT: expected 3 dot-separated parts, got N." An encrypted JWE has five parts and cannot be read without the key (<a href="https://www.rfc-editor.org/rfc/rfc7516#section-3" target="_blank" rel="noopener">RFC 7516 §3</a>).</li>
  <li>Header and payload must be Base64URL. Missing <code>=</code> padding is fine; other characters give "Failed to Base64URL-decode token parts."</li>
  <li>A segment that decodes but is not JSON is shown as "(unable to parse)".</li>
  <li>The signature is displayed as the raw Base64URL string and is <strong>not verified</strong>. A token with a forged payload looks exactly the same here as a genuine one. Never accept a token on the server because it decodes; verify the signature with the issuer's key, and check <code>exp</code>, <code>nbf</code>, <code>iss</code> and <code>aud</code> as <a href="https://www.rfc-editor.org/rfc/rfc8725#section-3" target="_blank" rel="noopener">RFC 8725 §3</a> recommends.</li>
</ul>

<h2>Limits</h2>
<ul>
  <li>Only <code>exp</code>, <code>iat</code> and <code>nbf</code> with numeric values in seconds get a readable UTC date. The original numeric precision is retained; the date note displays whole seconds. A millisecond value, which some libraries write by mistake, shows a date tens of thousands of years ahead.</li>
  <li>The "valid" and "EXPIRED" labels and the signature note are in English on every language version of the page.</li>
  <li>Tokens are not saved anywhere, and this page loads no analytics or ad scripts, because JWTs often carry session credentials.</li>
</ul>

<h2>What is a JWT?</h2>
<p>
  A JSON Web Token (JWT) is a compact, URL-safe token format used for authentication and
  information exchange. It consists of three Base64URL-encoded parts separated by dots:
</p>
<ul>
  <li><strong>Header:</strong> Specifies the signing algorithm (e.g., HS256, RS256) and token type.</li>
  <li><strong>Payload:</strong> Contains claims — statements about an entity (typically the user) and additional metadata.</li>
  <li><strong>Signature:</strong> Ensures the token has not been tampered with. Requires the secret or public key to verify.</li>
</ul>
<p>
  Common claims include <code>sub</code> (subject), <code>iss</code> (issuer), <code>exp</code> (expiration),
  <code>iat</code> (issued at), and <code>aud</code> (audience).
</p>
