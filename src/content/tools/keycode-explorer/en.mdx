<h2>event.key vs event.code vs keyCode</h2>
<p>
  Most front-end keyboard bugs come from mixing these three. Use this table as a reference:
</p>

| Property | Layout-aware | Recommended | Example for A on QWERTY |
|---|---|---|---|
| event.key | Yes (reflects active layout) | Yes — semantic checks | "a" or "A" with Shift |
| event.code | No (physical position) | Yes — game / shortcut bindings | "KeyA" |
| keyCode | No | No — deprecated | 65 |
| which | No | No — deprecated | 65 |
| charCode | No | No — deprecated, 0 on keydown | 0 |

<h2>Worked examples</h2>

<p>Each block below is what the pad shows for the given key: a few rows from Event properties, then the Ready-to-copy JS snippet.</p>

<h3>Ctrl+Shift+K for a command palette</h3>

<p>With Shift held, the key value of a letter is the upper-case letter. The <a href="https://www.w3.org/TR/uievents-key/" target="_blank" rel="noopener">UI Events KeyboardEvent key Values</a> spec gives the same example: the key labelled Q is <code>"q"</code>, or <code>"Q"</code> with Shift. A handler that compares with <code>'k'</code> never fires.</p>

{/* kce-check: {"event":{"key":"K","code":"KeyK","keyCode":75,"which":75,"ctrlKey":true,"shiftKey":true}} */}

```
event.key   "K"
event.code  "KeyK"
keyCode     75
```

```js
document.addEventListener('keydown', (e) => {
  if (e.key === 'K' && e.ctrlKey && e.shiftKey) {
    // your handler
  }
});
```

<h3>The letter a on a French AZERTY keyboard</h3>

<p>The key labelled a on AZERTY sits where q is on a US keyboard, so its code is <code>"KeyQ"</code> (from the code values spec). The snippet compares <code>key</code>, so it matches the letter the user typed.</p>

{/* kce-check: {"event":{"key":"a","code":"KeyQ"}} */}

```
event.key   "a"
event.code  "KeyQ"
```

```js
document.addEventListener('keydown', (e) => {
  if (e.key === 'a') {
    // your handler
  }
});
```

<h3>The space bar</h3>

<p>Recent keys and the big label on the pad show <code>Space</code>, but the key value is a single space character, and the code is <code>"Space"</code>. Copy the snippet rather than typing <code>'Space'</code> by hand.</p>

<h2>Common Use Cases</h2>
<ul>
  <li><strong>Debugging keyboard handlers</strong> — paste the exact event.key into your conditionals to fix typos.</li>
  <li><strong>Building game controls</strong> — prefer event.code so WASD works on AZERTY layouts.</li>
  <li><strong>Wiring command palettes</strong> — combine event.key with e.ctrlKey / e.metaKey checks.</li>
  <li><strong>Auditing legacy code</strong> — read keyCode / which to map old handlers to event.key.</li>
  <li><strong>Identifying composing state</strong> — e.isComposing = true means an IME is active, so single-key handlers should return early.</li>
</ul>

<h2>Preventing Default Behavior</h2>
<p>
  The capture pad calls <code>preventDefault()</code> only on Tab, Space, Backspace, Arrows, and F1-F12 — keys
  the browser would otherwise consume for navigation or page actions. System shortcuts like Ctrl+W / Cmd+Q
  are not intercepted; they continue to do their default thing.
</p>

<h2>Keyboard Layouts and Input Methods</h2>
<p>
  <code>event.code</code> names the physical key after its position on a US keyboard. The <a href="https://www.w3.org/TR/uievents-code/" target="_blank" rel="noopener">UI Events KeyboardEvent code Values</a> spec
  lists <code>"KeyQ"</code> as the key labelled q on a US keyboard and a on a French AZERTY keyboard. Use <code>code</code> for
  shortcuts that depend on where a key is (WASD movement) and <code>key</code> for shortcuts that depend on
  what the key types (Ctrl+Z for undo).
</p>
<p>
  Japanese and Korean keyboards add keys that a US keyboard does not have: <code>"IntlYen"</code>,
  <code>"IntlRo"</code>, <code>"NonConvert"</code>, <code>"Convert"</code> and <code>"KanaMode"</code> on
  a Japanese 106/109 keyboard, and <code>"Lang1"</code> (한/영) and <code>"Lang2"</code> (한자) on a Korean
  keyboard. On a Mac Japanese keyboard, the same two codes are the かな and 英数 keys. Press them on the pad to see the values your browser reports.
</p>
<p>
  While an input method is composing text, <code>isComposing</code> is <code>true</code>, and the non-normative legacy section of <a href="https://www.w3.org/TR/uievents/#determine-keydown-keyup-keyCode" target="_blank" rel="noopener">UI Events</a> says <code>keyCode</code> is 229 on keydown. Check <code>isComposing</code> before you act on Enter, or the
  key that confirms a Japanese or Chinese conversion will also submit your form. The snippet from this tool does not add that check; add it yourself:
</p>

```js
input.addEventListener('keydown', (e) => {
  if (e.isComposing || e.keyCode === 229) return;
  if (e.key === 'Enter') {
    // submit
  }
});
```

<h2>Limits</h2>
<ul>
  <li>On phones and tablets, on-screen keyboards usually send an <code>input</code> event with the typed text instead of a full keydown. The fallback field below the pad shows that text as <code>key</code> and leaves <code>code</code>, <code>keyCode</code>, <code>which</code> and <code>charCode</code> empty, because the input event does not say which key was used.</li>
  <li>The browser and operating system keep some shortcuts, such as Ctrl+W or Cmd+Q, so the page never sees them.</li>
  <li>The pad is a focusable area, not a text field. Whether an input method composes text there depends on the operating system and the input method, so the pad may not show <code>keyCode</code> 229.</li>
  <li>The snippet compares <code>event.key</code> and the held modifiers only. It does not use <code>event.code</code> and does not check <code>isComposing</code>.</li>
  <li>Only keydown is captured; keyup and keypress are not shown. Recent keys keeps the last eight captures.</li>
</ul>
