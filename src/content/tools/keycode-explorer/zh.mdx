<h2>event.key、event.code 与 keyCode 对照</h2>
<p>
  前端键盘逻辑的 bug 大多来自混用这三个属性。对照表如下：
</p>

| 属性 | 受布局影响 | 推荐使用 | QWERTY 按 A 时的取值 |
|---|---|---|---|
| event.key | 是（反映当前布局） | 推荐——语义判断 | "a" 或按 Shift 时 "A" |
| event.code | 否（物理位置） | 推荐——游戏/快捷键绑定 | "KeyA" |
| keyCode | 否 | 不推荐——已弃用 | 65 |
| which | 否 | 不推荐——已弃用 | 65 |
| charCode | 否 | 不推荐——keydown 时为 0 | 0 |

<h2>例子：评论框和聊天框里的「发送」快捷键</h2>

<p>很多评论框、工单系统和网页版聊天工具用回车换行、用 Ctrl+Enter 发送。在捕获区按下 Ctrl+Enter，工具显示的部分字段和生成的片段如下：</p>

{/* kce-check: {"event":{"key":"Enter","code":"Enter","keyCode":13,"which":13,"ctrlKey":true}} */}

```
event.key   "Enter"
event.code  "Enter"
keyCode     13
```

```js
document.addEventListener('keydown', (e) => {
  if (e.key === 'Enter' && e.ctrlKey) {
    // your handler
  }
});
```

<p>Mac 用户习惯按 ⌘+Enter。在 Mac 上按下 ⌘+Enter，Command 键对应的是 <code>metaKey</code>：</p>

{/* kce-check: {"event":{"key":"Enter","code":"Enter","keyCode":13,"which":13,"metaKey":true}} */}

```js
document.addEventListener('keydown', (e) => {
  if (e.key === 'Enter' && e.metaKey) {
    // your handler
  }
});
```

<p>两个片段合起来，写成 <code>e.key === 'Enter' &amp;&amp; (e.ctrlKey || e.metaKey)</code>，Windows 和 Mac 用户就都能用快捷键发送。</p>

<h2>输入法组字时的回车</h2>

<p><a href="https://support.microsoft.com/zh-cn/windows/hardware/input-devices/microsoft-simplified-chinese-ime" target="_blank" rel="noopener">Microsoft 简体中文输入法</a>的支持页面写明，微软拼音的候选窗口打开时按 Enter，会「关闭候选窗口而不选择任何候选项。输入的文本将保留在输入区域中。」这一下回车是给输入法用的，网页不该把它当成「发送」。组字期间 <code>isComposing</code> 为 <code>true</code>；<a href="https://www.w3.org/TR/uievents/#determine-keydown-keyup-keyCode" target="_blank" rel="noopener">UI Events</a> 中非规范性的旧版键码一节写明，输入法正在处理按键时 keydown 的 <code>keyCode</code> 为 229。上面生成的片段只比较 <code>event.key</code> 和修饰键，不检查这一点，用在输入框上时要自己加一行：</p>

```js
input.addEventListener('keydown', (e) => {
  if (e.isComposing || e.keyCode === 229) return;
  if (e.key === 'Enter' && (e.ctrlKey || e.metaKey)) {
    // 发送
  }
});
```

<p>捕获区本身不是输入框，输入法在这里是否组字取决于操作系统和输入法，所以在捕获区里不一定能看到 229。验证这一行时，请在你自己的输入框里打开拼音输入法测试。</p>

<h2>常见用途</h2>
<ul>
  <li><strong>调试键盘事件处理</strong>——把 event.key 的实际值粘到 if 条件里，排查拼写错误。</li>
  <li><strong>实现游戏控制</strong>——优先用 event.code，让 AZERTY 布局也能用 WASD 走位。</li>
  <li><strong>命令面板快捷键</strong>——组合 event.key 与 e.ctrlKey / e.metaKey。</li>
  <li><strong>审计遗留代码</strong>——读出 keyCode / which，把老代码迁移到 event.key。</li>
</ul>

<h2>关于 preventDefault</h2>
<p>
  捕获区只对 Tab、Space、Backspace、方向键、F1-F12 调用 <code>preventDefault()</code>——这些是浏览器会用于导航或页面操作的键。
  Ctrl+W / Cmd+Q 等系统级快捷键不拦截，保持浏览器默认行为。
</p>

<h2>键盘布局</h2>
<p>
  <code>event.code</code> 按美式键盘上的位置命名物理按键。<a href="https://www.w3.org/TR/uievents-code/" target="_blank" rel="noopener">UI Events KeyboardEvent code Values</a> 规范写明 <code>"KeyQ"</code> 是美式键盘上标 q、法语 AZERTY 键盘上标 a 的那个键。所以在 AZERTY 键盘上输入 a，得到 <code>key: "a"</code> 和 <code>code: "KeyQ"</code>。与按键位置有关的快捷键（WASD 移动）用 <code>code</code>，与按键输入的字符有关的快捷键（Ctrl+Z 撤销）用 <code>key</code>。
</p>

<h2>限制</h2>
<ul>
  <li>手机和平板的软键盘通常只发送带有输入文字的 <code>input</code> 事件，而不是完整的 keydown。捕获区下方的降级输入框把这段文字显示为 <code>key</code>，<code>code</code>、<code>keyCode</code>、<code>which</code>、<code>charCode</code> 留空，因为 input 事件不说明按的是哪个键。</li>
  <li>Ctrl+W、Cmd+Q 等快捷键由浏览器和操作系统处理，页面收不到。</li>
  <li>捕获区不是文本输入框，输入法是否在这里组字取决于系统，可能看不到 <code>keyCode</code> 229。</li>
  <li>生成的片段只比较 <code>event.key</code> 和按住的修饰键，不用 <code>event.code</code>，也不检查 <code>isComposing</code>。</li>
  <li>只捕获 keydown，不显示 keyup 和 keypress；「最近按键」只保留最近八次。</li>
</ul>
