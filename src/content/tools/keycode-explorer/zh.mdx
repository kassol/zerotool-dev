<h2>event.key、event.code 与 keyCode 对照</h2>
<p>
  前端键盘逻辑 bug 大多来自混用这三个属性。对照表如下：
</p>

| 属性 | 受布局影响 | 推荐使用 | QWERTY 按 A 时的取值 |
|---|---|---|---|
| event.key | 是（反映当前布局） | 推荐——语义判断 | "a" 或按 Shift 时 "A" |
| event.code | 否（物理位置） | 推荐——游戏/快捷键绑定 | "KeyA" |
| keyCode | 否 | 不推荐——已弃用 | 65 |
| which | 否 | 不推荐——已弃用 | 65 |
| charCode | 否 | 不推荐——keydown 时恒为 0 | 0 |

<h2>常见用途</h2>
<ul>
  <li><strong>调试键盘事件处理</strong>——把 event.key 实际值粘到 if 条件里，排查拼写错误。</li>
  <li><strong>实现游戏控制</strong>——优先用 event.code，让 AZERTY 布局也能用 WASD 走位。</li>
  <li><strong>命令面板快捷键</strong>——组合 event.key 与 e.ctrlKey / e.metaKey。</li>
  <li><strong>审计遗留代码</strong>——读出 keyCode / which，把老代码迁移到 event.key。</li>
  <li><strong>识别 IME 输入</strong>——e.isComposing = true 表示中文/日文输入法正在组字，单键处理器应直接返回。</li>
</ul>

<h2>关于 preventDefault</h2>
<p>
  捕获区域仅对 Tab、Space、Backspace、方向键、F1-F12 调用 <code>preventDefault()</code>——这些是浏览器会消费的导航/页面键。
  Ctrl+W / Cmd+Q 等系统级快捷键不拦截，保持浏览器默认行为。
</p>

<h2>键盘布局与输入法</h2>
<p>
  <code>event.code</code> 按美式键盘上的位置命名物理按键。<a href="https://www.w3.org/TR/uievents-code/" target="_blank" rel="noopener">UI Events KeyboardEvent code Values</a> 规范写明 <code>"KeyQ"</code> 是美式键盘上标 q、法语 AZERTY 键盘上标 a 的那个键。所以在 AZERTY 键盘上输入 a，得到 <code>key: "a"</code> 和 <code>code: "KeyQ"</code>。与按键位置有关的快捷键（WASD 移动）用 <code>code</code>，与按键输入的字符有关的快捷键（Ctrl+Z 撤销）用 <code>key</code>。
</p>
<p>
  输入法正在组字时，<a href="https://www.w3.org/TR/uievents/#determine-keydown-keyup-keyCode" target="_blank" rel="noopener">UI Events</a> 规定 keydown 的 <code>keyCode</code> 为 229，事件的 <code>isComposing</code> 为 <code>true</code>。处理 Enter 之前先检查 <code>isComposing</code>，否则用拼音输入法按回车确认候选词时也会提交表单。
</p>

<h2>限制</h2>
<ul>
  <li>手机和平板的软键盘通常只发送带有输入文字的 <code>input</code> 事件，而不是完整的 keydown。键盘区下方的降级输入框把这段文字显示为 <code>key</code>，<code>code</code>、<code>keyCode</code>、<code>which</code>、<code>charCode</code> 留空，因为 input 事件不说明按的是哪个键。</li>
  <li>Ctrl+W、Cmd+Q 等快捷键由浏览器和操作系统处理，页面收不到。</li>
</ul>
