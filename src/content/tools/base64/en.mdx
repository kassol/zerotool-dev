<p>These outputs come from the tool's own encode and decode functions.</p>

<p>Text is encoded as UTF-8 first, so <code>世界</code> takes six bytes and eight Base64 characters. The <code>{'subjects?_d'}</code> row shows the only difference between the two alphabets: Standard uses <code>+</code> and <code>/</code> (<a href="https://www.rfc-editor.org/rfc/rfc4648#section-4" target="_blank" rel="noopener">RFC 4648 §4</a>), URL-safe uses <code>-</code> and <code>{'_'}</code> and drops the <code>=</code> padding (<a href="https://www.rfc-editor.org/rfc/rfc4648#section-5" target="_blank" rel="noopener">RFC 4648 §5</a>). JWT segments use the URL-safe form without padding (<a href="https://www.rfc-editor.org/rfc/rfc7515#section-2" target="_blank" rel="noopener">RFC 7515 §2</a>), which is why the last row decodes a JWT payload in URL-safe mode. The <code>user:pass</code> row is the credential part of an HTTP Basic header (<a href="https://www.rfc-editor.org/rfc/rfc7617#section-2" target="_blank" rel="noopener">RFC 7617 §2</a>); the <a href="/tools/basic-auth-header-generator/">Basic Auth Header Generator</a> builds the whole header.</p>

<h2>What the Decoder Accepts</h2>
<ul>
  <li><strong>Missing padding.</strong> <code>SGVsbG8</code> decodes to <code>Hello</code>. The browser's <code>atob()</code> follows the WHATWG <a href="https://infra.spec.whatwg.org/#forgiving-base64-decode" target="_blank" rel="noopener">forgiving-base64 decode</a>, which does not require <code>=</code>.</li>
  <li><strong>Line breaks and spaces.</strong> MIME bodies wrap Base64 at 76 characters (<a href="https://www.rfc-editor.org/rfc/rfc2045#section-6.8" target="_blank" rel="noopener">RFC 2045 §6.8</a>). Tabs, line breaks and spaces are removed before decoding in both Standard and URL-safe mode, so wrapped text works as pasted.</li>
  <li><strong>Standard input in URL-safe mode.</strong> URL-safe mode maps <code>-</code> and <code>{'_'}</code> back to <code>+</code> and <code>/</code>, so a Standard string also decodes there. The reverse fails: {/* b64-check: {"mode":"decode","in":"c3ViamVjdHM_X2Q","error":true} */}<code>{'c3ViamVjdHM_X2Q'}</code> in Standard mode gives <code>{'Position 12: "_" is from the URL-safe alphabet. Select URL-safe to decode this string.'}</code></li>
</ul>

<h2>Limits</h2>
<ul>
  <li>Decode output is UTF-8 text only. Bytes that are not valid UTF-8 give an error. Example: <code>gqCCog==</code> is <code>あい</code> in Shift_JIS (bytes <code>82 A0 82 A2</code>) and is rejected: {/* b64-check: {"mode":"decode","in":"gqCCog==","error":true} */}<code>Byte 1 of the decoded data (82) is not valid UTF-8. Decode shows UTF-8 text only; binary data and text in GBK, Shift_JIS or EUC-KR cannot be shown here.</code> Use <a href="/tools/text-to-binary/">Text to Binary</a> to inspect raw bytes.</li>
  <li>A <code>=</code> in the middle of the string, or a length that leaves one character after the last group of four, is an error; the status line gives the position of the <code>=</code> or the number of characters.</li>
  <li>File encoding has no fixed size limit. Above 5 MiB (5,242,880 bytes) the tool shows "Large file — encoding may take a few seconds." The whole Base64 string is put into the output box, so very large files can make the page slow.</li>
  <li>Text with a lone UTF-16 surrogate (half of an emoji, left when a string is cut in the middle of one) cannot be encoded as UTF-8; the tool names its position. Switching Standard / URL-safe converts the current output to the other alphabet.</li>
  <li>Base64 is an encoding, not encryption. Anyone can decode it. For confidential data use <a href="/tools/aes-encrypt-decrypt/">AES Encryption</a>.</li>
</ul>

<h2>Common Use Cases</h2>
<ul>
  <li><strong>API authentication:</strong> Basic Auth headers use Base64-encoded credentials.</li>
  <li><strong>Data URIs:</strong> Inline images and fonts in CSS/HTML are Base64-encoded. For images, <a href="/tools/image-to-base64/">Image to Base64</a> detects the type from the file bytes and can output CSS or HTML.</li>
  <li><strong>JWT tokens:</strong> The header and payload sections are Base64url-encoded.</li>
  <li><strong>Email:</strong> MIME attachments are Base64-encoded.</li>
</ul>
