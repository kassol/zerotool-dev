<h2>阿里云虚拟主机上的 755 和 644</h2>
<p>
  网站上传到虚拟主机后出现 500 或 403，权限是常见原因之一。阿里云云虚拟主机的帮助文档
  《<a href="https://help.aliyun.com/zh/cloud-web-hosting/visit-on-cloud-hosting-website-prompt-error-internal-server-error">访问云虚拟主机上的网站提示“Internal Server Error”报错</a>》写道：“系统中目录和文件权限默认为 755，而图片、文字等 HTML 文件的权限应该为 644。”
  另一篇《<a href="https://help.aliyun.com/zh/document_detail/36490.html">解决访问子目录403报错</a>》建议：“如果没有特殊要求，建议将文件夹权限修改为755。”
</p>
<p>在工具的数字框分别输入这两个数，得到的权限串和符号命令如下：</p>
{/* chmod-page: {"numeric":"755","show":["symbolic","sym"]} */}
<pre><code>{`755  rwxr-xr-x  chmod u=rwx,g=rx,o=rx filename`}</code></pre>
{/* chmod-page: {"numeric":"644","show":["symbolic","sym","find"]} */}
<pre><code>{`644  rw-r--r--  chmod u=rw,g=r,o=r filename
find . -type f -perm 0644`}</code></pre>
<p>
  <code>find</code> 一行列出权限正好是 644 的文件，可以用来核对上传后的结果。阿里云的
  《<a href="https://help.aliyun.com/zh/cloud-web-hosting/user-guide/use-filezilla-management-files">使用FTP管理网站程序文件</a>》介绍了 FileZilla 的做法：右键文件选「文件权限」，在「数字值」框里输入新的权限值，
  填的就是这三位数；不确定某一位代表什么时，先在本工具里输入，再对照勾选框看所有者、组和其他人各自得到哪些权限。
</p>

<h2>从 ls -l 复制权限串</h2>
<p>
  在开启了 SELinux 的 Linux 上，<code>ls -l</code> 的权限后面常跟一个点，比如 <code>-rw-r--r--.</code>。
  按 <a href="https://www.gnu.org/software/coreutils/manual/html_node/What-information-is-listed.html">GNU ls 手册</a>的说明，
  点表示文件带有安全上下文、没有其他访问控制；<code>+</code> 表示还有访问控制列表（ACL）等其他方式。整段粘贴进符号框即可，工具会去掉开头的文件类型字符和末尾的标记：
</p>
{/* chmod-page: {"symbolic":"-rw-r--r--.","show":["numeric","command"]} */}
<pre><code>{`-rw-r--r--.  →  644
chmod 644 filename`}</code></pre>
<p>
  看到 <code>+</code> 时要注意：9 位权限串之外还有 ACL，实际能访问的人可能比这 9 位显示的更多或更少，工具只计算这 9 位。
</p>

<h2>部署时的三个例子</h2>
<h3>Web 服务器文件</h3>
<p>Web 服务器提供静态 HTML。服务器进程（以 <code>www-data</code> 用户运行）只需要读取文件，而你作为所有者需要编辑：</p>
<pre><code>chmod 644 index.html   # 所有者：读+写，组/其他：读</code></pre>
<p>结果为 <code>rw-r--r--</code>：你可以编辑，服务器可以读取，没有人可以执行该文件。</p>

<h3>可执行脚本</h3>
<p>你写了一个部署脚本，团队其他成员也需要运行但不能修改：</p>
{/* chmod-page: {"numeric":"755","show":["symbolic","command"]} */}
<pre><code>chmod 755 deploy.sh    # 所有者：完全权限，组/其他：读+执行</code></pre>
<p>结果为 <code>rwxr-xr-x</code>，现在可以直接执行 <code>./deploy.sh</code>。</p>

<h3>SSH 私钥</h3>
<p>SSH 会拒绝使用权限过于开放的私钥。将其锁定为仅所有者可访问：</p>
<pre><code>chmod 600 ~/.ssh/id_rsa   # 所有者：读+写，其他人无权限</code></pre>
<p>结果为 <code>rw-------</code>。只要组或其他人有任何权限，OpenSSH 就拒绝加载私钥；600、400、700 都能通过。</p>

<h2>共享目录的 setgid：2775</h2>
<p>
  多人共用的项目目录常设成 2775：组成员都能写；按 coreutils 手册的说法，在多数系统上，带 setgid 的目录里新建的文件会归目录所属的组。展开「特殊位」勾选 Setgid，或在数字框直接输入四位数：
</p>
{/* chmod-page: {"numeric":"2775","show":["symbolic","sym"]} */}
<pre><code>{`2775  rwxrwsr-x  chmod u=rwx,g=rwxs,o=rx filename`}</code></pre>
<p>
  组的执行位显示为 <code>s</code>。以后想改回普通目录时注意：GNU coreutils 手册
  《<a href="https://www.gnu.org/software/coreutils/manual/html_node/Directory-Setuid-and-Setgid.html">Directories and the Set-User-ID and Set-Group-ID Bits</a>》说明，
  用四位以内的数字（<code>755</code>、<code>0755</code>）或不提到 <code>s</code> 的符号写法设置目录权限时，chmod 不改动目录的 setuid 和 setgid，这是 GNU 的扩展行为。所以对 2775 的目录执行 <code>chmod 755</code> 后仍是 2775，工具给出的 <code>chmod u=rwx,g=rx,o=rx</code> 也一样；要清除须写 <code>chmod 00755</code> 或 <code>chmod g-s</code>。
</p>

<h2>限制</h2>
<ul>
  <li>只生成完整的权限（<code>u=…,g=…,o=…</code>），不生成 <code>chmod g+w</code>、<code>a-x</code> 这类增减写法，也不生成只对目录加执行权限的 <code>X</code>。</li>
  <li>数字框需要 3 或 4 位 0–7 的数字。首尾空格和 Python 写法的前缀 <code>0o</code>（如 <code>0o644</code>）会被忽略，全角数字按半角读取；其他字符（比如 <code>7558</code> 里的 8）或不足 3 位时显示「无效八进制」，并保留上一次的有效结果。</li>
  <li>符号框只接受 9 位权限串，或带文件类型字符与末尾 <code>+</code> <code>@</code> <code>.</code> 标记的 <code>ls -l</code> 字段。</li>
  <li><code>find -perm 0644</code> 只匹配权限正好是 644 的文件；要找至少包含这些位的文件用 <code>-perm -644</code>，包含其中任意一位的用 <code>-perm /644</code>（GNU find）。</li>
  <li>能否访问还取决于 ACL、SELinux、<code>noexec</code> 等挂载选项以及每一级父目录的权限，这些工具都算不了。</li>
</ul>
