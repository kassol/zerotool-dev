<h2>例 1：LINE Bot の .env</h2>

<p>Messaging API の Bot でよくある構成です。値はすべてダミーです。</p>

```bash
LINE_CHANNEL_SECRET=8a1f0c3e5b7d9f2a4c6e8b0d1f3a5c7e
LINE_CHANNEL_ACCESS_TOKEN=DemoOnlyNotARealLineToken0123456789abcdefGHIJKLmnopqrSTUVwxyz+/0123456789DemoOnly=
DATABASE_URL=mysql2://bot:Kintone!2026@127.0.0.1:3306/linebot
RAILS_ENV=production
```

<p>② 欄の出力（3 件）：</p>

```bash
LINE_CHANNEL_SECRET=[SECRET_1]
LINE_CHANNEL_ACCESS_TOKEN=[SECRET_2]
DATABASE_URL=mysql2://bot:[URL_PASSWORD_1]@127.0.0.1:3306/linebot
RAILS_ENV=production
```

<p>チャネルシークレットは 16 進数なので高エントロピー判定では拾えませんが、変数名が <code>SECRET</code> で終わるため置換されます。接続文字列はパスワードだけが消え、ユーザー名・ホスト・ポート・DB 名は残るので、AI は接続先を読み取れます。<code>.env</code> にどの変数があるかを先に一覧したいときは <a href="/ja/tools/env-file-parser/">.env ファイルパーサー</a>が使えます。</p>

<h2>例 2：Chatwork API の curl と、返答の復元</h2>

<p>Chatwork API のトークンは <code>X-ChatWorkToken</code> ヘッダーで送ります（<a href="https://developer.chatwork.com/reference/authentication">Chatwork API ドキュメント</a>）。</p>

```bash
$ curl -X POST -H "X-ChatWorkToken: 0f9e8d7c6b5a49382716a5b4c3d2e1f0" \
    -d "body=デプロイ完了" https://api.chatwork.com/v2/rooms/123456789/messages
```

<p>ヘッダー名が <code>Token</code> で終わるので、値が <code>[SECRET_1]</code> になります。返答のコードブロックで角括弧が Markdown エスケープされていても、③ 欄では元のトークンに戻ります。</p>

```text
トークンの前後に空白や改行が入っていないか確認してください。
curl -X POST -H "X-ChatWorkToken: \[SECRET_1\]" -d "body=テスト" https://api.chatwork.com/v2/rooms/123456789/messages
```

<p>ステータスには「1 箇所を復元しました（対応表 1 個中 1 個）」と表示されます。</p>

<p>海外サービスは形式で検出します。GitHub の <code>ghp_</code> などの接頭辞は <a href="https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/">GitHub の公式ブログ</a>、AWS の <code>AKIA</code>・<code>ASIA</code> は <a href="https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_identifiers.html">IAM のドキュメント</a>、Anthropic の <code>sk-ant-</code> は <a href="https://platform.claude.com/docs/en/get-api-key">Anthropic のドキュメント</a>に基づきます。JWT は <a href="https://www.rfc-editor.org/rfc/rfc7519">RFC 7519</a>、Bearer ヘッダーは <a href="https://www.rfc-editor.org/rfc/rfc6750">RFC 6750</a>、PEM 秘密鍵は <a href="https://www.rfc-editor.org/rfc/rfc7468">RFC 7468</a> の形式です。ログに出てきた JWT の有効期限は、<a href="/ja/tools/jwt-decoder/">JWT デコーダー</a>でローカルに確認できます。</p>

<p>変数名のない長い文字列は、base64 の文字が 32 文字以上続き、大文字・小文字・数字をすべて含み、シャノンエントロピーが 1 文字あたり 4.2 ビット以上のときだけ置換します。同じ長さのランダムな base64 は平均約 4.56 ビットです。コミット SHA、SHA-256、UUID は 16 進数か単一ケースなので対象外です。</p>

<h2>gitleaks やログのマスク処理との違い</h2>

<p><a href="https://github.com/gitleaks/gitleaks">gitleaks</a> や <a href="https://github.com/trufflesecurity/trufflehog">TruffleHog</a> は、リポジトリや git 履歴に入ってしまったシークレットを探すツールです。gitleaks の標準設定は 2026 年 9 月時点で 222 ルール（このツールは 30 ルールとエントロピー判定）。結果はレポートとして出るだけで、貼り付け用のテキストは作りません。pre-commit や CI で使うものです。GitHub Actions の <code>::add-mask::</code> は値を <code>*</code> に置き換えます（<a href="https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands">GitHub ドキュメント</a>）。どの値も同じ見た目になり、元にも戻せないので、AI には 2 つのキーが同じかどうかもわかりません。</p>

<p>このツールが担うのは、貼り付ける直前の工程です。値ごとに別の番号を振り、同じ値には同じ番号を使い、返答は元に戻せます。<strong>サンプル読込</strong>を押すと、<code>[OPENAI_KEY_1]</code> が <code>.env</code> とリトライのログ行の両方に出てきます。AI はこれを見て、リトライが設定済みのキーを使ったと判断できます。</p>

<h2>制限事項</h2>

<ul>
  <li>入力の上限は 1,000,000 文字です。超えるとステータスに「入力は N 文字です。上限は 1,000,000 文字です。分割してください。」と表示されます。</li>
  <li>秘密鍵ルール以外は行末で止まるため、ターミナルで折り返された値は検出できません。元のファイルからコピーしてください。</li>
  <li>カテゴリを切り替えると再検出され、番号が変わることがあります。復元はマスキング時と同じ設定で行ってください。</li>
  <li>メールアドレス、氏名、電話番号、IP アドレスなどの個人情報は対象外です。ホスト名は意図的に残しています。</li>
  <li>キーがまだ有効かどうかは確認しません。確認するにはキーをプロバイダーへ送る必要があるためです。</li>
</ul>
