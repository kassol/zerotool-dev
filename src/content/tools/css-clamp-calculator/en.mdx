<h2>Default example</h2>

<p>With the defaults—320px to 1440px and 16px to 32px—the result is:</p>

{/* ccc-check: {"min":320,"max":1440,"start":16,"end":32,"at":[880],"zoom":false} */}

<pre><code>font-size: clamp(1rem, 0.7143rem + 1.4286vw, 2rem);</code></pre>

<p>The preview slider starts halfway, at 880px, where the value is 24px (1.5rem).</p>

<h2>What the generated expression means</h2>

<p><code>clamp(minimum, preferred, maximum)</code> asks the browser to use the preferred value while keeping it between the two bounds. The calculator derives the preferred value from the line through your two viewport/value points:</p>

<pre><code>slope = (end value - start value) / (max viewport - min viewport)
intercept = start value - slope × min viewport
preferred = intercept + (slope × 100)vw</code></pre>

<p>Below the minimum viewport, the lower or upper bound holds the value at its endpoint. Between the endpoints, the value changes linearly. Beyond the maximum viewport, the opposite bound takes over.</p>

<h2>Fluid typography and spacing</h2>

<p>Fluid values are useful when a sudden breakpoint would create a visible jump. Typical targets include headings, section padding, grid gaps, and content widths. They are less useful for values that must align to a strict fixed system, such as one-pixel borders.</p>

<p>For font sizes, rem bounds preserve a relationship with the root font size. Still test the finished layout at 200% browser zoom and with longer translated text. A mathematically valid expression can still overflow a real component.</p>

<h2>Reverse and constant ranges</h2>

<p>The end value may be smaller than the start value. In that case the preferred expression uses a negative vw term, so the property decreases as the viewport widens. The calculator sorts only the <code>clamp()</code> bounds; it preserves the direction of the line.</p>

<p>If both endpoint values match, no fluid calculation is needed. The output becomes a single fixed length such as <code>1rem</code>. Negative values are accepted for <code>margin</code> and the custom property, where negative lengths can be meaningful, but rejected for the other presets.</p>

<h2>Two more worked examples</h2>

<p><strong>Section padding in px.</strong> Choose Padding, px output, viewports 375 and 1280, values 16 and 48:</p>

{/* ccc-check: {"property":"padding","unit":"px","min":375,"max":1280,"start":16,"end":48,"at":[768,1280],"zoom":false} */}

<pre><code>padding: clamp(16px, 2.7403px + 3.5359vw, 48px);</code></pre>

<p>In a Chrome iframe 768px wide this computed to 29.896px; the live preview shows 29.8961px with the slider at 768px, and at 1280px it reaches the 48px cap. The sampled values table lists five evenly spaced widths (375, 601.25, 827.5, 1053.75 and 1280px), so 768px is not one of its rows.</p>

<p><strong>A heading that shrinks on wide screens.</strong> Font size, rem output, 320 → 1440, values 40 and 28:</p>

{/* ccc-check: {"min":320,"max":1440,"start":40,"end":28,"at":[320,768,1440],"zoom":true} */}

<pre><code>font-size: clamp(1.75rem, 2.7143rem - 1.0714vw, 2.5rem);</code></pre>

<p>The bounds are sorted (1.75rem first), but the slope stays negative: 40px at 320px, 35.2px at 768px, 28px from 1440px on. Because 40 is less than twice 28, the calculator also shows its zoom notice for this range.</p>

<h2>Limits and things to check</h2>

<ul>
  <li><strong>Zoom.</strong> Zooming the page shrinks the viewport in CSS pixels, so the vw part grows less than the rem part. MDN's <a href="https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/clamp#accessibility">clamp() accessibility note</a> advises a maximum of at least twice the minimum so text can still reach 200% (WCAG 1.4.4). The notice appears for font-size when the maximum is under twice the minimum; with 18px → 22px, for example, it stays on.</li>
  <li><strong>vw includes the scrollbar.</strong> On desktop browsers with classic scrollbars, 100vw is the window width including the vertical scrollbar, so at a "768px" breakpoint the content area is narrower than the number the line was built on.</li>
  <li><strong>Viewport units only.</strong> The preferred value always uses <code>vw</code>. For a component that should scale with its container, replace <code>vw</code> with <code>cqi</code> by hand and add <code>container-type: inline-size</code> to the container.</li>
  <li><strong>Rounding.</strong> Numbers are written with up to four decimals, which is well under a hundredth of a pixel at common widths.</li>
  <li><strong>Inputs are pixels.</strong> Endpoint values and viewports are entered in px and converted with the root size you set; the output cannot be em, ch or %.</li>
  <li><code>clamp()</code> works in Chrome 79, Firefox 75 and Safari 13.1 and later (MDN browser compat data).</li>
</ul>
