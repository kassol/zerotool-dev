<p>
  What happens in order: the text is decomposed (NFD) and combining marks are dropped; the symbols and letters in the tables below
  are replaced; any other non-ASCII character is deleted; every remaining character that is not a letter, digit, space,
  hyphen, underscore or dot becomes a space; runs of spaces become one separator; and runs of <code>-</code>, <code>{"_"}</code> and <code>.</code>
  collapse into one separator. That last step is why <code>{"user_profile.v2"}</code> loses its underscore and dot: existing
  separators are normalised to the one you picked. With Lowercase off and the underscore separator, the first example gives
  <code>{"10_Tips_and_Tricks_for_Node_js_2026_Edition"}</code>, a common form for file names and Python identifiers.
</p>

<h2>Character Mappings</h2>
<p>Symbols become a separate word, so Rock &amp; Roll gives <code>{"rock-and-roll"}</code> and Tom&amp;Jerry gives <code>{"tom-and-jerry"}</code>. Letters that do not decompose use the second table, with values from <a href="https://github.com/sindresorhus/transliterate" rel="noopener">sindresorhus/transliterate</a>. Uppercase letters keep their case (Ø → O, Œ → OE) until Lowercase is applied.</p>

<h2>Limitations</h2>
<ul>
  <li>Marks are removed without language-specific rules: German <code>{"ä ö ü"}</code> become <code>{"a o u"}</code> (not <code>{"ae oe ue"}</code>), and Turkish <code>{"İ"}</code> becomes <code>{"I"}</code>.</li>
  <li>Non-Latin scripts are removed, so input written only in Chinese, Japanese or Korean gives an empty slug.</li>
  <li>A removed character leaves no separator behind. {/* slug-check: {"in":"Vue3入门Vite教程"} */}<code>{"Vue3入门Vite教程"}</code> gives <code>{"vue3vite"}</code>, and the full-width ideographic space U+3000 is removed rather than treated as a space: {/* slug-check: {"in":"Hello　World"} */}<code>{"Hello　World"}</code> gives <code>{"helloworld"}</code>. Put an ASCII space between words you want to keep apart.</li>
  <li>Apostrophes act as separators: <code>{"John's Guide"}</code> → <code>{"john-s-guide"}</code>.</li>
  <li>With Trim off, separators at the start and end stay: <code>{"Hello World!"}</code> → <code>{"hello-world-"}</code>.</li>
  <li>Words are never shortened and stop words (a, the, of) are kept. There is no length limit, so a long sentence gives a long slug; trim it by hand if your CMS caps slug length.</li>
  <li><code>#</code> becomes the word <code>hash</code>, so <code>{"C#"}</code> gives <code>{"c-hash"}</code> rather than <code>{"c-sharp"}</code>. Edit such names before converting.</li>
  <li>The tool converts one string at a time; each line break counts as a space, so pasting a list produces one long slug.</li>
</ul>

<p>
  The package also splits camelCase and, through <a href="https://github.com/sindresorhus/transliterate" rel="noopener">transliterate</a>,
  turns <code>Fußgängerübergänge</code> into <code>fussgaengeruebergaenge</code>; this tool gives <code>fussgangerubergange</code>. A straight
  apostrophe is a separator here (<code>{"Conway's Law"}</code> → <code>{"conway-s-law"}</code>), while the curly one is deleted
  (<code>{"Conway’s Law"}</code> → <code>{"conways-law"}</code>). If your site already has published URLs, match the generator that made them,
  and use this page for one-off slugs or to check what a title would turn into. To encode a string for a query parameter instead of a path,
  use the <a href="/tools/url-encode/">URL encoder</a>.
</p>
<h2>When to Use Slugs</h2>
<ul>
  <li><strong>Blog post URLs:</strong> <code>/blog/how-to-use-slugs</code></li>
  <li><strong>Product pages:</strong> <code>/products/red-running-shoes</code></li>
  <li><strong>File names:</strong> <code>my-important-document.pdf</code></li>
  <li><strong>Database keys:</strong> Unique, human-readable identifiers without spaces.</li>
</ul>
<p>
  Consistent slug generation ensures your URLs remain stable and SEO-friendly even when
  the original title changes formatting or punctuation.
</p>
