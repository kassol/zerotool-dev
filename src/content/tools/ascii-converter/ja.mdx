## 変換の例

以下の結果は、このツールの変換処理で求めたものです。ステータスの文言もページの表示と同じです。

{/* ac-check: {"text":"テスト","fmt":"dec","status":true} */}
### カタカナをコードにする

「テキスト」に `テスト` を入力し、10進数で「テキスト → ASCII」を押すと次の結果になります。

```text
12486 12473 12488
```

ステータスは `3 文字を変換しました。` です。片仮名は ASCII の範囲外なので、Unicode のコードポイントが出力されます。16進数を選んでもう一度押すと `0x30C6 0x30B9 0x30C8` になります。

{/* ac-check: {"codes":"0x30C6 0x30B9 0x30C8"} */}
### コードから文字に戻す

`0x30C6 0x30B9 0x30C8` を「ASCII / Unicode コード」に入れて「ASCII → テキスト」を押すと、`テスト` に戻ります。Unicode の文字表で見つけた `U+30C6` のような番号は、`0x` を付ければそのまま入力できます。

{/* ac-check: {"codes":"１２３","error":true} */}
### 全角数字はコードとして読めない

日本語入力をオンにしたまま数字を打つと、全角の `１２３` になりがちです。これを「ASCII → テキスト」に通すと、ステータスに次のエラーが出ます。

```text
Error: Invalid code: １２３
```

コードは半角数字で書く必要があります。区切りに使える空白には全角スペースも含まれますが、全角カンマ（，）は区切りになりません。

## ¥ と \（0x5C）

日本語の環境では、バックスラッシュと円記号の見分けがつきにくいことがあります。Microsoft のドキュメント「[Character Sets Used in File Names](https://learn.microsoft.com/en-us/windows/win32/intl/character-sets-used-in-file-names)」は、日本語の OS で使われる Windows コードページと OEM コードページでは、バックスラッシュの位置に円記号（¥）が入っていると説明しています。当時 Microsoft に在籍していた Michael Kaplan が MSDN ブログに書いた記事「[When is a backslash not a backslash?](http://archives.miloush.net/michkap/archive/2005/09/17/469941.html)」（アーカイブ）によると、日本語や韓国語をシステムロケールにした Windows のフォントは、U+005C を通貨記号の形で表示します。

{/* ac-check: {"text":"C:\\Users","fmt":"dec"} */}
画面に `C:¥Users` と見えるパスも、中身はバックスラッシュです。実際の文字 `C:\Users` を変換すると、3 番目のコードは 92 になります。

```text
67 58 92 85 115 101 114 115
```

{/* ac-check: {"text":"¥100","fmt":"dec"} */}
一方、本物の円記号（U+00A5）を使った `¥100` は次のとおりで、先頭は 165 です。

```text
165 49 48 48
```

見た目が同じでも、プログラムのエスケープ文字やパス区切りとして働くのは 92 だけです。コピーした文字列で `¥n` が改行にならないときなどに、どちらの文字が入っているかをこの方法で確認できます。

## 全角英数字

{/* ac-check: {"text":"ＡＢＣ１","fmt":"dec"} */}
全角の `ＡＢＣ１` を変換すると `65313 65314 65315 65297` になり、半角の `ABC1`（`65 66 67 49`）とは別の文字だとわかります。全角英数字のコードポイントは、対応する半角より 65248（16進数で FEE0）大きくなっています。フォームの入力チェックで「英数字なのに通らない」ときは、全角が混ざっていないかを確かめてください。

## 改行コード

改行やタブも数値で表示されます。Windows のテキストでは改行が `13 10`（CR LF）、macOS や Linux では `10`（LF）であることが多く、CRLF と LF の違いを確認したいときに使えます。タブは `9` です。逆方向で `10` を入れると、テキスト欄に実際の改行が入ります。

## 制限

- 「テキスト → ASCII」は Unicode のコードポイント単位で処理します。肌の色を指定した 👍🏽 のように複数のコードポイントでできた絵文字は、`128077 127997` の 2 つのコードになります。
- 出力はコードポイントで、Shift_JIS や UTF-8 のバイト列ではありません。「あ」は 12354（U+3042）と表示されますが、Shift_JIS では `82 A0` の 2 バイトです。バイト列を確認したい場合は[バイナリ変換（テキスト ⇔ 2進数）](/ja/tools/text-to-binary/)を使ってください。
- 「ASCII → テキスト」が受け付けるのは 0〜1114111（`0x10FFFF`）です。55296〜57343（`0xD800`〜`0xDFFF`）はサロゲートで文字ではないため、`Code point out of range` になります。
- `72abc`、`1.5`、`0b102` のように、その進数の数字だけでできていないコードは `Invalid code` になり、修正するまで何も変換しません。
- この 2 種類のエラーメッセージは、どの言語のページでも英語で表示されます。変換に成功したときの件数表示はページの言語で表示されます。

## ASCII とは

ASCII（American Standard Code for Information Interchange）は、英字・数字・記号・制御文字の 128 文字に 0〜127 の番号を割り当てた 7 ビットの文字コードです。UTF-8 では 0〜127 の文字を ASCII と同じ値の 1 バイトで表すため（[RFC 3629](https://www.rfc-editor.org/rfc/rfc3629#section-1)）、英数字だけの ASCII ファイルはそのまま UTF-8 として読めます。
