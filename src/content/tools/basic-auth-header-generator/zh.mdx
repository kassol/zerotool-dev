这个 Basic Auth Header 生成器用于创建许多 HTTP APIs、reverse proxies、测试 dashboards 和受保护端点需要的 `Authorization: Basic <token>` 值。

Basic auth 的 token 是 `username:password` 的 Base64 结果。工具会先用冒号连接 username 和 password，再按 UTF-8 编码成字节，最后转换为 Base64。为了获得更广泛的 Basic Auth 兼容性，ASCII 凭据最稳妥；如果使用非 ASCII 凭据，请确认目标服务器期望 UTF-8。你也可以粘贴已有的 Basic auth header，检查复制来的凭据是否和预期一致。

Basic auth 适合快速 API 联调、reverse proxy 规则、dashboard 测试，以及生成可复制的 cURL 或 Fetch snippets。但它本身不提供保密性：Base64 是编码，不是加密，可以被还原。Authorization header 经过网络传输时，HTTPS 才是保护边界。

所有生成和解码都在浏览器内完成。凭据不会上传，也不会被此页面持久保存。

<h2>示例</h2>

<p><a href="https://www.rfc-editor.org/rfc/rfc7617#section-2" target="_blank" rel="noopener">RFC 7617 §2</a> 的示例：用户名 <code>Aladdin</code>，密码 <code>open sesame</code>。工具输出：</p>

```http
Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==
```

<p>同时给出带这个请求头的 cURL 与 Fetch 片段。<code>curl -u 'Aladdin:open sesame' URL</code> 发出的请求头完全相同，只有在某个工具要求填写原始请求头时才需要这个生成值。</p>

<p>非 ASCII 凭据按 UTF-8 编码。<code>renée</code> / <code>s3cret</code> 得到 <code>cmVuw6llOnMzY3JldA==</code>，与 UTF-8 终端里 <code>curl -u</code> 发出的 token 相同。如果服务器按 ISO-8859-1 处理，它期望的是 <code>cmVu6WU6czNjcmV0</code>。RFC 7617 没有规定默认编码（只要求兼容 US-ASCII），服务器可以在质询里用 <code>charset="UTF-8"</code> 表明要 UTF-8。</p>

<p>要核对复制来的请求头，把 <code>Authorization: Basic ZGVwbG95OnBhOnNz</code> 粘贴到解码区，结果是用户名 <code>deploy</code>、密码 <code>pa:ss</code>：按第一个冒号拆分，所以密码可以含冒号，用户名不能。</p>

<h2>限制</h2>
<ul>
  <li>只解码 <code>Basic</code> 方案。<code>Bearer</code> 等其他方案会提示「仅支持 Basic 授权方案。」</li>
  <li>解码只接受标准 Base64 字母表，含 <code>-</code> 或 <code>{'_'}</code> 的 URL 安全 token 会被拒绝。</li>
  <li>不是合法 UTF-8 的字节会按 ISO-8859-1 显示，并附提示。<code>cmVu6WU6czNjcmV0</code> 按这种方式解出 <code>renée</code> / <code>s3cret</code>。工具无法区分 ISO-8859-1、Windows-1252 或其他单字节编码，ASCII 以外的字符请自行核对；GBK 编码的中文用户名会显示成乱码。</li>
  <li>用户名含冒号时拒绝生成，这是 RFC 7617 的要求。</li>
  <li>看到请求头的人都能解出密码。只通过 HTTPS 发送；真实的请求头出现在截图、工单或聊天记录里时，立即更换密码。</li>
</ul>
