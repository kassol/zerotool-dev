Use this Basic Auth Header Generator to create the exact `Authorization: Basic <token>` value required by many HTTP APIs, reverse proxies, legacy dashboards, and test endpoints.

The token is the Base64 form of `username:password`. The tool joins the username and password with a colon, encodes that pair as UTF-8, then converts the bytes to Base64. ASCII credentials are safest for broad Basic Auth compatibility; if you use non-ASCII credentials, verify that the target server expects UTF-8. It can also decode an existing Basic auth header so you can verify copied credentials before using them in a request.

Basic auth is convenient for API checks, reverse proxy rules, testing dashboards, and quick cURL or Fetch snippets. It is not secret by itself: Base64 is encoding, not encryption, and it is reversible. Treat HTTPS as the transport protection boundary whenever an Authorization header crosses the network.

All generation and decoding run in your browser. Credentials are not uploaded and are not persisted by this page.

<h2>Examples</h2>

<p>The example from <a href="https://www.rfc-editor.org/rfc/rfc7617#section-2" target="_blank" rel="noopener">RFC 7617 §2</a>: username <code>Aladdin</code>, password <code>open sesame</code>. The tool outputs:</p>

```http
Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==
```

<p>It also prints a cURL and a Fetch snippet with the same header. <code>curl -u 'Aladdin:open sesame' URL</code> sends exactly this header, so you only need the generated value when a tool asks for a raw header line.</p>

<p>Non-ASCII credentials are encoded as UTF-8. <code>renée</code> / <code>s3cret</code> becomes <code>cmVuw6llOnMzY3JldA==</code>, the same token <code>curl -u</code> sends from a UTF-8 terminal. A server that expects ISO-8859-1 would expect <code>cmVu6WU6czNjcmV0</code> instead; RFC 7617 leaves the default encoding to the server unless it announces <code>charset="UTF-8"</code> in its challenge.</p>

<p>Servers announce the encoding in their challenge. When a server answers with <code>WWW-Authenticate: Basic realm="api", charset="UTF-8"</code>, the client should send UTF-8, which is what this tool generates. Without that parameter, check the server documentation before you use non-ASCII characters.</p>

<p>To check a copied header, paste <code>Authorization: Basic ZGVwbG95OnBhOnNz</code> into the decoder. It shows username <code>deploy</code> and password <code>pa:ss</code>: the first colon splits the pair, so passwords may contain colons and usernames may not.</p>

<h2>Limits</h2>
<ul>
  <li>Only the <code>Basic</code> scheme is decoded. <code>Bearer</code> and other schemes produce "Only the Basic authorization scheme is supported."</li>
  <li>The decoder accepts the standard Base64 alphabet. URL-safe tokens with <code>-</code> or <code>{'_'}</code> are rejected.</li>
  <li>Bytes that are not valid UTF-8 are shown as ISO-8859-1 with a notice. <code>cmVu6WU6czNjcmV0</code> decodes to <code>renée</code> / <code>s3cret</code> this way. The tool cannot tell ISO-8859-1 from Windows-1252 or other single-byte encodings, so check characters outside ASCII yourself.</li>
  <li>A username that contains a colon is refused, as required by RFC 7617.</li>
  <li>Anyone who sees the header can decode the password. Send it only over HTTPS, and rotate the password if a real header ends up in a screenshot, ticket or chat log.</li>
</ul>
