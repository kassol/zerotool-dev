<h2>How to use</h2>
<ol>
  <li>Paste a prompt, a document or code into the box, or open a text file. The o200k_base count updates as you type.</li>
  <li>Press <strong>Count</strong> on the DeepSeek V4 or cl100k_base card to load that vocabulary (0.5 MB and 0.4 MB). The page remembers the choice.</li>
  <li>Set the expected output tokens. The table shows input, output and total cost per request, and how much of each model's input limit the text uses.</li>
  <li>Open <strong>Token view</strong> to see where each tokenizer splits the text. Turn on token ids to compare with what an API or a debugger prints.</li>
</ol>

<h2>Examples</h2>
<p>The sample prompt (the <strong>Sample</strong> button) is a 486-character code review request:</p>
{/* atc: {"text": "You are a senior engineer reviewing a pull request that adds a Redis read-through cache in front of a Postgres analytics database.\n\nThe cache uses a 60-second TTL on every aggregate query. The author expects p99 latency to fall from 1200 ms to under 50 ms for a dashboard that serves 12k requests per minute.\n\nList the two highest-risk failure modes, say whether 60 seconds suits a financial reporting dashboard, and name one metric to add before merging. <p>
  o200k_base gives 104 tokens, cl100k_base 104 and DeepSeek V4 105. With 1,000 output tokens, one request costs $0.03052 on gpt-5.5 and $0.001232 on deepseek-flash at peak rates (half that off-peak). For English the three tokenizers land within a few tokens of each other.
</p>

<h2>How this differs from other counters</h2>
<p>Tested on 2026-10-01 with the Chinese sentence "你是一名资深后端工程师，正在评审一个合并请求：在 PostgreSQL 分析库前面加一层 Redis 读穿缓存。" (o200k_base 35 tokens, DeepSeek V4 26):</p>
{/* atc: {"text": "你是一名资深后端工程师，正在评审一个合并请求：在 PostgreSQL 分析库前面加一层 Redis 读穿缓存。", "o200k": 35, "deepseek": 26} */}
<ul>
  <li><strong>benchlm.ai token counter</strong> shows "&#126;14 tokens" and lists 14 for every Claude, Gemini and DeepSeek model, about the character count divided by 4. The real counts are 35 and 26.</li>
  <li><strong>tokencost.app</strong> marks DeepSeek V4.1 Flash as "42&#126;" and lists GPT-6 Luna and Llama 3.3 with plain numbers, although OpenAI has published no GPT-6 tokenizer and Llama 3 uses its own vocabulary. Its DeepSeek price is the off-peak rate.</li>
  <li><strong>token-counter.dev</strong> gives the correct 35 for o200k_base through tiktoken's WebAssembly build, and has no DeepSeek tokenizer.</li>
</ul>
<p>
  This page also fixes two problems of the common JavaScript port, js-tiktoken, which it used before. js-tiktoken reads <code>\s</code> with JavaScript's rules, so text containing a byte-order mark (U+FEFF) or U+0085 can split differently from tiktoken. And its merge step slows down sharply on long runs without spaces: 20,000 Chinese characters in a row took over three minutes. Here the regex uses Unicode White_Space and the merge uses a priority queue, so the same input takes milliseconds.
</p>

<h2>Limits</h2>
<ul>
  <li>Counts are for plain text. Message wrappers, system prompts, tool schemas, images and PDFs add tokens that only the provider's counting endpoint sees.</li>
  <li>Special tokens such as <code>&lt;|endoftext|&gt;</code> count as ordinary text for OpenAI (7 tokens), the same as tiktoken's <code>encode_ordinary</code>; the page never throws on them, which the old version did. DeepSeek's <code>tokenizer.json</code> recognises its own markers such as <code>&lt;｜User｜&gt;</code> as one token, and so does this page.</li>
  <li>Claude, Gemini and GPT-6 rows are references, not counts. Use the provider's endpoint before you rely on them.</li>
  <li>Prices are a snapshot from 2026-10-01 and include no taxes, regional uplifts or negotiated discounts.</li>
  <li>DeepSeek's package says to run it with transformers. In our test, transformers 5.18.0 returned an empty list for Chinese text from this package; transformers 4.57.6 and the tokenizers library give the ids this page uses.</li>
</ul>
