<h2>Worked Examples</h2>

<h3>Simple object</h3>
<p>Input YAML:</p>

```yaml
name: Alice
age: 30
active: true
```

<p>Output JSON (indented with 2 spaces):</p>

```json
{
  "name": "Alice",
  "age": 30,
  "active": true
}
```

<p><code>30</code> stays a number and <code>true</code> a boolean, because plain YAML scalars are typed by their form.</p>

<h3>Nested structure with arrays</h3>
<p>Input YAML:</p>

```yaml
server:
  host: localhost
  port: 8080
  features:
    - auth
    - logging
    - cache
```

<p>Output JSON:</p>

```json
{
  "server": {
    "host": "localhost",
    "port": 8080,
    "features": [
      "auth",
      "logging",
      "cache"
    ]
  }
}
```

<h3>JSON to YAML</h3>
<p>Input JSON:</p>

```json
{"name":"api","version":"1.10","replicas":3,"env":{"DEBUG":"no","PORT":"8080"},"args":["--verbose","--port=8080"],"description":"line one\nline two","empty":null}
```

<p>Output YAML:</p>

```yaml
name: api
version: '1.10'
replicas: 3
env:
  DEBUG: 'no'
  PORT: '8080'
args:
  - '--verbose'
  - '--port=8080'
description: |-
  line one
  line two
empty: null
```

<p>Strings that would read back as another type (<code>'1.10'</code>, <code>'no'</code>, <code>'8080'</code>) or that start with <code>-</code> are single-quoted. A string with a line break becomes a <code>|-</code> block, and long lines are never folded. This matters for files such as Kubernetes manifests, where an environment value must stay a string.</p>

<h3>Anchors and merge keys</h3>
<p>Docker Compose files often share settings with an anchor and <code>{'<<'}</code>:</p>

```yaml
base: &base
  image: nginx
  restart: always
web:
  <<: *base
  ports: ["80:80"]
```

<p>The JSON output has no references: <code>web</code> becomes <code>{`{"image":"nginx","restart":"always","ports":["80:80"]}`}</code>, a full copy of <code>base</code> plus its own key, and the <code>base</code> entry stays in the output as well.</p>

<h3>Round-trip conversion</h3>
<p>Paste the JSON output back into the JSON panel and wait 0.3 seconds for the YAML panel to update. Note that YAML comments and formatting preferences are not preserved in round-trips.</p>

<h2>YAML vs JSON</h2>
<p>
  <strong>YAML</strong> (YAML Ain't Markup Language) is a human-friendly data serialization format popular for configuration files (Docker Compose, Kubernetes, Ansible, GitHub Actions).
  <strong>JSON</strong> (JavaScript Object Notation) is the most widely used data interchange format for APIs and web services.
  Both can represent the same data structures — this tool converts between them. Comments, anchors, and some scalar values change on the way; see "Values That Change Type" below.
</p>

## Values That Change Type

The tool uses js-yaml 4.3.2 with its default schema: the [YAML 1.2](https://yaml.org/spec/1.2.2/) core schema plus timestamps, `<<` merge keys and the `!!binary`, `!!set`, `!!omap` and `!!pairs` tags. These inputs convert as shown:

| YAML | JSON | Note |
|---|---|---|
| `country: NO` | `"NO"` | String. YAML 1.1 parsers such as PyYAML read it as `false` |
| `enabled: yes` | `"yes"` | Same as above; write `true` for a boolean |
| `version: 1.10` | `1.1` | Parsed as a number; quote version strings |
| `mode: 0755` | `755` | A leading zero is not octal in YAML 1.2; write `0o755` |
| `zip: 01234` | `1234` | The leading zero is lost; quote codes like this |
| `date: 2026-09-29` | `"2026-09-29T00:00:00.000Z"` | Dates become full UTC timestamps |
| `at: 2026-10-01T09:30:00+09:00` | `"2026-10-01T00:30:00.000Z"` | Offsets become UTC. JSON has no date type, so the text is ISO 8601 in UTC: the same instant, but the written `+09:00` is not kept |
| `zero: -0.0` | `-0.0` | Negative zero keeps its sign (`JSON.stringify` alone would write `0`) |
| `empty:` | `null` | A key with no value is null |
| `roles: !!set {admin, editor}` | `{"admin":null,"editor":null}` | js-yaml reads a set as a mapping whose values are null |
| `steps: !!pairs [run: build, run: test]` | `[["run","build"],["run","test"]]` | Pairs become [key, value] lists; a repeated key is kept |
| `2026-01-01: New Year` | `{"2026-01-01":"New Year"}` | A date used as a key keeps its text; JSON keys are strings |

## Limits

- **One document per conversion.** Input containing `---` separators fails with `expected a single document in the stream, but found more`.
- **Values JSON or YAML cannot hold stop the conversion.** YAML `.inf`, `-.inf` and `.nan`, and integers outside ±(2^53 − 1) on either side, would change on the way (`JSON.stringify` writes `null`; `JSON.parse` and js-yaml round large integers). The status line lists each field as a JSON Pointer. This YAML:

  ```yaml
  size: .inf
  id: 9007199254740993
  ```

  gives `Not converted: JSON cannot hold these values without changing them: /size: inf has no JSON form (JSON.stringify would write null); /id: integer 9007199254740993 is outside ±(2^53 − 1), so JavaScript would round it`. A JSON number too large for a double, such as `1e400`, is listed the same way. Quote large IDs. The output panel is cleared and its Copy button is disabled until the input converts.
- **Dates must be real, and times stop at milliseconds.** js-yaml builds dates with `Date.UTC`, which moves `2026-02-31` to March 3, and keeps only milliseconds. Such timestamps stop the conversion instead. This YAML:

  ```yaml
  due: 2026-02-31
  at: 2026-10-01T09:30:00.123456Z
  ```

  gives `Not converted: JSON cannot hold these values without changing them: /due: 2026-02-31 is not a valid date or time; /at: 2026-10-01T09:30:00.123456Z has more than millisecond precision`. Quote a value that is meant as text (`due: "2026-02-31"`). Valid dates and times convert to UTC as shown in the table above.
- **`!!binary` data stops the conversion too.** js-yaml reads it as bytes, and JSON has no binary type (`JSON.stringify` would write an object keyed by byte index). `photo: !!binary aGVsbG8=` gives `Not converted: JSON cannot hold these values without changing them: /photo: !!binary value — JSON has no binary type`. Without the `!!binary` tag, the Base64 text converts as a string. A `!!binary` key stops the conversion as well: js-yaml would turn the key into its byte values (`107,49` below). PyYAML 6.0.3 writes `bytes` keys this way; `yaml.dump({b'k1': 1})` gives:

  ```yaml
  ? !!binary |
    azE=
  : 1
  ```

  The tool gives `Not converted: JSON cannot hold these values without changing them: (root): !!binary key azE= — JSON keys can only be text`. A merge such as `m: {<<: !!binary aGk=}` stops with `/m: !!binary aGk= — << can only merge a mapping`.
- **js-yaml work limits.** js-yaml 4.3.2 stops a document whose collections are nested more than 100 levels deep, whose merge keys (`<<`) handle more than 10,000 mappings and keys in total, or that lists more than 100 mappings in one merge key, for example `Invalid YAML: collections are nested more than 100 levels deep (the js-yaml default limit) (1:103)`.
- **Duplicate keys are an error** (`duplicated mapping key`), not a silent overwrite.
- **Errors show line and column.** A key indented one space too far gives `Invalid YAML: bad indentation of a mapping entry (2:3)` with the offending line marked; an unclosed `[` gives `unexpected end of the stream within a flow collection`. To check a file with several `---` documents, use the [YAML Validator](/tools/yaml-validator/), which reports each document separately.
- **Comments and anchors are not kept.** Anchors and `<<` merge keys are expanded into plain copies.
- **The JSON integer `-0` becomes `0`.** `{"count":-0,"offset":-0.0}` gives `count: 0` and `offset: -0.0`: [YAML 1.2](https://yaml.org/spec/1.2.2/#1032-tag-resolution) reads `-0` as the integer zero, and `-0.0` stays the negative float zero.
- **JSON → YAML quotes ambiguous strings** such as `'1.10'`, `'yes'`, and `'NO'`, so they stay strings when read back.
