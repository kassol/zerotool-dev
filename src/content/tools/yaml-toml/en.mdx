<h2>How to Use</h2>
<ol>
  <li>To convert <strong>YAML → TOML</strong>: paste your YAML into the left panel — the TOML output updates automatically.</li>
  <li>To convert <strong>TOML → YAML</strong>: paste your TOML into the right panel — the YAML output updates automatically.</li>
  <li>Click <strong>Swap</strong> to exchange both panels and flip the conversion direction.</li>
  <li>Use <strong>Ctrl+Enter</strong> (or <strong>Cmd+Enter</strong> on Mac) as a keyboard shortcut from whichever panel you are editing.</li>
  <li>Click <strong>Copy</strong> on either panel to copy the result to your clipboard. When a conversion fails, the output panel is cleared and its Copy button is disabled.</li>
</ol>

<h2>Worked Example</h2>

<h3>YAML input</h3>

```yaml
database:
  host: localhost
  port: 5432
  enabled: true
tags:
  - web
  - backend
```

<h3>Equivalent TOML output</h3>

```toml
tags = [ "web", "backend" ]

[database]
host = "localhost"
port = 5432
enabled = true
```

<p>
  Notice that <code>tags</code> moved above <code>[database]</code>. In TOML every key after a <code>[table]</code> header belongs
  to that table, so top-level plain values must come first. The converter (<a href="https://github.com/squirrelchat/smol-toml">smol-toml</a>
  1.7.1 for TOML, <a href="https://github.com/nodeca/js-yaml">js-yaml</a> 4.3.2 for YAML) reorders keys this way: within each table, plain values keep their order and sub-tables follow them.
</p>

<h2>Example: a Cargo.toml to YAML</h2>
<p>Pasting this into the TOML panel:</p>

```toml
[package]
name = "zerotool"
version = "0.1.0"
edition = "2021"

[dependencies]
serde = { version = "1.0", features = ["derive"] }

[[bin]]
name = "cli"
path = "src/main.rs"
```

<p>gives this YAML:</p>

```yaml
package:
  name: zerotool
  version: 0.1.0
  edition: '2021'
dependencies:
  serde:
    version: '1.0'
    features:
      - derive
bin:
  - name: cli
    path: src/main.rs
```

<p>
  The inline table becomes a nested mapping and <code>[[bin]]</code> (an array of tables) becomes a list. The strings
  <code>"2021"</code> and <code>"1.0"</code> are quoted in YAML because unquoted they would be read as numbers; <code>0.1.0</code>
  is not a number, so it stays unquoted. Going the other way, a YAML list of mappings such as a <code>services:</code> list becomes
  repeated <code>[[services]]</code> blocks.
</p>

<h2>Dates and Times</h2>
<p>YAML timestamps are written as TOML dates, not as strings:</p>

```yaml
release:
  date: 2026-10-01
  at: 2026-10-01 09:30:00 +9
  utc: 2026-10-01T00:30:00Z
  label: "2026-10-01"
  ratio: .inf
```

```toml
[release]
date = 2026-10-01
at = 2026-10-01T09:30:00.000+09:00
utc = 2026-10-01T00:30:00.000Z
label = "2026-10-01"
ratio = inf
```

<p>
  A date alone becomes a TOML local date. A date-time keeps its offset, written as <code>+09:00</code>; a date-time without an offset
  is written with <code>Z</code>, because the <a href="https://yaml.org/type/timestamp.html">YAML timestamp type</a> reads it as UTC.
  The quoted <code>"2026-10-01"</code> stays a string, and <code>.inf</code> becomes TOML <code>inf</code>. TOML dates keep
  milliseconds, so a timestamp with more digits, such as <code>09:30:00.123456Z</code>, stops the conversion, and so does an impossible
  date such as <code>2026-02-31</code>.
</p>

<h2>Values TOML Cannot Hold</h2>
<p>When a value would change, nothing is converted. The status line lists each field as a JSON Pointer and says why:</p>

```yaml
service:
  id: 9007199254740993
  owner: ~
```

<p><code>Not converted: TOML cannot hold these values without changing them: /service/id: integer 9007199254740993 is outside ±(2^53 − 1), so JavaScript would round it; /service/owner: null — TOML has no null</code></p>
<p>
  The TOML panel is cleared and its Copy button is disabled, so an older result cannot be copied by mistake. Quote large IDs
  (<code>{'id: "9007199254740993"'}</code>) and replace or remove nulls, then convert again. Integers from −(2<sup>53</sup> − 1) to
  2<sup>53</sup> − 1 convert unchanged.
</p>

<h2>Limits and Error Messages</h2>
<ul>
  <li><strong>Root must be a mapping.</strong> A YAML list or scalar at the top level gives "YAML root must be a mapping (object), not a scalar or sequence."</li>
  <li><strong>One document.</strong> YAML with <code>---</code> between documents gives "expected a single document in the stream, but found more".</li>
  <li><strong>Large integers stop the conversion in both directions.</strong> TOML → YAML: <code>big = 9007199254740993</code> gives "integer value cannot be represented losslessly" with the line shown. YAML → TOML: the field is listed as above.</li>
  <li><strong>Duplicate TOML keys</strong> give "trying to redefine an already defined table or value", with the line and a caret under the problem.</li>
  <li><strong>js-yaml work limits.</strong> js-yaml 4.3.2 stops a document whose collections are nested more than 100 levels deep, whose merge keys (<code>{'<<'}</code>) handle more than 10,000 mappings and keys in total, or that lists more than 100 mappings in one merge key. The error names the limit and its line and column.</li>
  <li><strong>Comments are dropped</strong> in both directions, because both parsers return plain data. Keep a copy of a commented file before converting it.</li>
  <li><strong>Anchors are expanded.</strong> <code>{'y: *a'}</code> becomes a full copy of the anchored mapping; the TOML output has no way to share it.</li>
</ul>

<h2>YAML vs TOML</h2>
<p>
  <strong>YAML</strong> is widely used for application configuration (Docker Compose, Kubernetes, GitHub Actions) due to its human-friendly, indentation-based syntax.
  <strong>TOML</strong> is the standard for Rust projects (<code>Cargo.toml</code>), Python packaging (<code>pyproject.toml</code>), and tools like Hugo and Zola.
  This tool converts between them for data types common to both formats. To convert either one to JSON instead, use the <a href="/tools/yaml-json/">YAML ↔ JSON</a> or <a href="/tools/toml-json/">TOML ↔ JSON</a> converter.
</p>
