<h2>CSR を点検する手順</h2>

<ol>
  <li>BEGIN 行と END 行を含めて PEM 要求を貼り付けます。</li>
  <li><strong>デコード</strong>を押すか、テキストエリアで Ctrl / Cmd + Enter を押します。</li>
  <li>まず提出前チェックを読みます。却下につながりやすい順に並んでいます。</li>
  <li>Subject と要求された SAN の一覧が、取得しようとしている証明書の内容と一致するか確認します。一覧にある名前はすべて発行証明書に入り、書き忘れた名前は入りません。</li>
</ol>

<h2>CSR の中身</h2>

<p>PKCS#10 要求の実体は、DER で包まれた 3 つの要素です。要求される情報、それを署名したアルゴリズム、そして署名そのもの。情報ブロックには Subject 識別名、公開鍵、任意の属性集合が入ります。興味深い内容はほぼすべて属性集合の中にあり、<code>extensionRequest</code> 属性が SAN 一覧・key usage・extended key usage を運びます。</p>

<p>CSR に入っていないのは秘密鍵です。要求内のどの情報もなりすましには使えないため、通常の経路で CA に送っても安全です。唯一の例外が <code>challengePassword</code> で、これは一部の CA が後日の失効手続きに使う共有秘密です。本デコーダーはこの属性の有無だけを報告し、値は意図的に一切表示しません。</p>

<h2>署名検証の仕組み</h2>

<p>デコーダーは DER から <code>CertificationRequestInfo</code> のバイト範囲を正確に切り出し、埋め込まれた <code>SubjectPublicKeyInfo</code> を <code>crypto.subtle.importKey</code> で読み込み、要求に記された アルゴリズムで <code>crypto.subtle.verify</code> を呼びます。RSA PKCS#1 v1.5、RSA-PSS、および P-256 / P-384 / P-521 上の ECDSA がこの経路で検証されます。ECDSA 署名は DER の <code>SEQUENCE&#123;r,s&#125;</code> 形式から、Web Crypto が要求する固定長形式へ変換されます。</p>

<p>Ed25519 と Ed448 も同様に試行し、成否はブラウザが Web Crypto にこれらを公開しているかに依存します。ブラウザが読み込みを拒否した場合、チェックは「署名が不正」ではなく「検証できなかった」と報告します。アルゴリズム未対応と署名破損は別の問題であり、心配すべきは後者だけだからです。その場合はローカルで <code>openssl req -in req.pem -verify -noout</code> を実行してください。</p>

<h2>SPKI ピンの使いどころ</h2>

<p>要求のフィンガープリントに加えて、SubjectPublicKeyInfo から計算した <code>sha256/…</code> ピン（公開鍵ピンニング設定で使う RFC 7469 形式）も表示します。この値は鍵のみに依存するため、同じ鍵ペアで発行されたすべての証明書で同一です。<code>openssl x509 -in cert.pem -pubkey -noout | openssl pkey -pubin -outform der | openssl dgst -sha256 -binary | base64</code> の出力と突き合わせれば、受け取った証明書がこの要求から発行されたものかを確認できます。</p>

<h2>対応範囲</h2>

<p>本ツールが読むのは PEM 形式の PKCS#10 要求だけです。要求の生成は行わず、秘密鍵は読み取りも受け付けもせず、ネットワーク通信も一切しません。実行するチェックは、目の前のバイト列だけで判断できるものに限られます。証明書チェーンの検証、CT ログの確認、発行ポリシーの適用は CA の職掌であり、ローカルでの等価コマンドは <code>openssl req -in req.pem -noout -text</code> です。</p>
