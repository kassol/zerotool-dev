<h2>检查 CSR 的步骤</h2>

<ol>
  <li>粘贴 PEM 请求，保留 BEGIN 与 END 行。</li>
  <li>点击 <strong>解码</strong>，或在输入框中按 Ctrl / Cmd + Enter。</li>
  <li>先看提交前检查——这些项按「导致拒签的概率」排序。</li>
  <li>核对 Subject 与申请的 SAN 列表是否与你要买的证书一致。列表里的每个域名都会进入签发的证书，漏掉的不会。</li>
</ol>

<h2>CSR 里装了什么</h2>

<p>PKCS#10 请求本质是 DER 包裹的三件东西：被申请的信息、签名所用的算法、签名本身。信息块里是 Subject 可分辨名称、公钥，以及一个可选属性集。真正有价值的内容几乎都在属性集里——<code>extensionRequest</code> 属性承载着 SAN 列表、key usage 与 extended key usage 标志。</p>

<p>CSR 里没有的是私钥。请求中的任何内容都无法用来冒充你，所以通过常规渠道把 CSR 发给 CA 是安全的。唯一例外是 <code>challengePassword</code>——部分 CA 用它作为后续吊销的共享口令。本解码器只报告该属性是否存在，刻意不打印它的值。</p>

<h2>签名验证是怎么做的</h2>

<p>解码器从 DER 中切出 <code>CertificationRequestInfo</code> 的精确字节范围，通过 <code>crypto.subtle.importKey</code> 导入内嵌的 <code>SubjectPublicKeyInfo</code>，再用请求中声明的算法调用 <code>crypto.subtle.verify</code>。RSA PKCS#1 v1.5、RSA-PSS，以及 P-256 / P-384 / P-521 上的 ECDSA 都按此路径验证；ECDSA 签名会先从 DER 的 <code>SEQUENCE&#123;r,s&#125;</code> 形式转换为 Web Crypto 要求的定长布局。</p>

<p>Ed25519 与 Ed448 同样尝试验证，能否成功取决于浏览器是否向 Web Crypto 暴露这两种算法。浏览器拒绝导入时，检查项会报告「无法验证」而不是「签名无效」——算法不受支持与签名损坏是两个问题，只有后者值得担心。这种情况请在本地用 <code>openssl req -in req.pem -verify -noout</code> 验证。</p>

<h2>SPKI Pin 的用途</h2>

<p>除请求指纹外，工具还会输出一个基于 SubjectPublicKeyInfo 计算的 <code>sha256/…</code> pin，即公钥固定（public key pinning）配置采用的 RFC 7469 形式。由于该值只依赖密钥，同一密钥对签发的每一张证书上它都相同。把它与 <code>openssl x509 -in cert.pem -pubkey -noout | openssl pkey -pubin -outform der | openssl dgst -sha256 -binary | base64</code> 的输出比对，就能确认收到的证书确实是由这份请求签发的。</p>

<h2>能力范围</h2>

<p>本工具只读取 PEM 格式的 PKCS#10 请求。它不生成请求，不读取也不接受私钥，不发起任何网络请求——所做的检查全部能从眼前这段字节中判定。证书链校验、CT 日志检查与签发策略属于 CA 的职责，本地等价命令是 <code>openssl req -in req.pem -noout -text</code>。</p>
