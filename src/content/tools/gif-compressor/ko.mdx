## 네이버 블로그·GitHub에 올리기 전에

- **네이버 블로그**: [사진 한 장에 최대 20MB](https://help.naver.com/support/alias/blog/etc/blog16.naver)까지 올릴 수 있고 GIF도 지원합니다. 한도 안이라도 본문에 몇 MB짜리 움짤이 여러 개 있으면 모바일에서 글이 느리게 열립니다.
- **GitHub 이슈·PR**: [이미지와 GIF는 10MB까지](https://docs.github.com/ko/get-started/writing-on-github/working-with-advanced-formatting/attaching-files) 첨부할 수 있습니다. 리뷰어는 PR을 열 때마다 그 바이트를 내려받습니다.
- **사내 화면 녹화**: 출시 전 관리자 화면이나 고객 데이터가 찍힌 버그 재현 GIF는 업로드형 압축 사이트에 보내기 곤란합니다. 이 페이지는 브라우저 탭 안에서 처리하며 파일을 업로드하지 않습니다.

## 실제 GIF로 잰 결과

두 파일 모두 위키미디어 공용에 공개되어 있어 내려받아 같은 결과를 확인할 수 있습니다. 단위는 바이트입니다.

**회전하는 지구.** [Rotating earth (large).gif](https://commons.wikimedia.org/wiki/File:Rotating_earth_(large).gif)는 400 × 400px, 44프레임, 1,001,718바이트입니다. 기본값(손실 압축 40, 256색, 모든 프레임, 디더링 끔)으로 541,524바이트(54%)가 됩니다. 블로그 본문용으로 손실 압축 80, 128색, 너비 200px로 줄이면 104,387바이트(10.4%)입니다.

**뉴턴의 요람.** [Newtons cradle animation book 2.gif](https://commons.wikimedia.org/wiki/File:Newtons_cradle_animation_book_2.gif)는 480 × 360px, 36프레임, 308,156바이트입니다. 기본값으로 109,817바이트(36%), 여기에 '2프레임마다 1장'을 더하면 18프레임, 72,389바이트(23.5%)입니다. 버린 프레임의 표시 시간은 앞에 남은 프레임에 더해지므로 전체 재생 시간은 그대로이고, 움직임만 조금 끊겨 보입니다.

M1 Max 노트북의 Chrome에서 파일을 고른 뒤 결과가 나오기까지 여러 번 재 보니 지구는 0.8~2.8초, 뉴턴의 요람은 1.9~3.2초 걸렸습니다.

## 설정별 효과

| 설정 | 하는 일 | 지구 GIF에서의 결과 |
|---|---|---|
| **손실 압축** (0–100, 기본 40) | 색 차이가 '손실 압축 × 0.6' 이내면 LZW가 아는 나열을 계속 씀 | 0에서 105%, 40에서 54%, 100에서 28% |
| **색상 수** (256~4) | 색상표 크기. 1칸은 투명용 | 64색, 손실 압축 40에서 46% |
| **너비** | 비율을 유지하며 축소 (확대는 안 함) | 절반 너비, 손실 압축 40에서 18% |
| **프레임** | 2·3·4프레임마다 1장만 남김 | 2프레임마다 1장, 손실 압축 40에서 28% |
| **디더링** | Floyd–Steinberg 오차 확산 | 64색에서 46%가 58%로 늘어남 |

## gifsicle·ezgif와 비교

[ezgif](https://ezgif.com/optimize)는 파일을 업로드받아, 페이지 설명대로 gifsicle과 그 손실 LZW 인코더로 압축합니다. [gifsicle](https://www.lcdf.org/gifsicle/man.html)은 내 컴퓨터에서 도는 명령줄 도구입니다. 이 페이지는 브라우저 탭 안에서 돌며 손실 압축 기준을 두 군데에 씁니다. 하나는 LZW 안으로, gifsicle의 `--lossy`와 같은 종류입니다. 다른 하나는 프레임 사이로, 화면에 보이는 색과의 거리가 기준 이내인 픽셀은 다시 그리지 않습니다. 화면 대부분이 멈춰 있는 녹화에서는 이 두 번째 단계가 프레임마다 데이터를 크게 줄입니다. ezgif에도 fuzz 값을 지정하는 'Optimize Transparency'라는 별도 방식으로 비슷한 프레임 간 처리가 있습니다.

두 도구의 손실 압축 수치는 척도가 다릅니다(gifsicle은 감마 보정한 색 공간에서 오차를 잽니다). 그래서 SSIM(원본과의 구조 유사도, 1이면 동일)이 비슷한 지점에서 용량을 비교했습니다. SSIM은 ffmpeg 9.0으로 원본과 비교했고 gifsicle은 1.93입니다.

| 파일 | 이 도구 (기본값) | `gifsicle -O3 --lossy=80` |
|---|---|---|
| 지구 | 541,524바이트, SSIM 0.956 | 575,411바이트, SSIM 0.965 |
| 뉴턴의 요람 | 109,817바이트, SSIM 0.971 | 182,247바이트, SSIM 0.967 |
| [VisualEditor 화면 녹화](https://commons.wikimedia.org/wiki/File:Auto-citing_a_source_using_VisualEditor,_small.gif), 500 × 245, 114프레임, 698,529바이트 | 245,538바이트, SSIM 0.991 | 549,574바이트, SSIM 0.991 |

모든 픽셀이 움직이는 지구에서는 차이가 작고, 나머지 두 파일에서는 이 도구의 결과가 40%, 55% 더 작으면서 SSIM은 같거나 높았습니다. 재현 명령어입니다(`out.gif`는 이 페이지에서 내려받은 파일).

```bash
gifsicle -O3 --lossy=80 in.gif -o gifsicle.gif
ffmpeg -i in.gif -i out.gif -lavfi "[0:v]format=yuv444p[a];[1:v]format=yuv444p[b];[a][b]ssim" -f null -
```

일괄 처리, 자르기, 여러 팔레트·디더링 방식, 이 페이지 한도를 넘는 큰 파일은 gifsicle이나 ezgif를 쓰세요.

## 한도와 지원하지 않는 것

- **크기 한도**: 디코딩 후 5,000만 픽셀, 1,000프레임, 프레임당 16,777,216픽셀. 터미널 녹화는 쉽게 넘습니다. [lazygit](https://github.com/jesseduffield/lazygit) README의 `commit_and_push-compressed.gif`는 1140 × 828px, 67프레임, 6,320만 픽셀이라 이 페이지가 거절하고 gifsicle 명령어를 보여 줍니다. 이미 최적화된 파일이라 `gifsicle -O3 --lossy=80 --colors 128`로는 오히려 1% 커졌고, `--resize-width 570`을 더하자 472,611바이트에서 147,386바이트로 줄었습니다.
- **아주 짧은 지연**: Chromium과 Firefox는 0ms나 10ms 지연을 100ms로 재생합니다([Chromium 소스](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/platform/graphics/deferred_image_decoder.cc), [Firefox 소스](https://searchfox.org/mozilla-central/source/image/FrameTimeout.h)). 이 도구는 그런 프레임을 100ms로 쓰고, 나머지 지연은 10ms 단위로 반올림합니다(최소 20ms).
- **출력**: 항상 전역 색상표 하나를 쓰는 GIF입니다. 프레임 자르기·순서 바꾸기·편집은 안 됩니다. PNG 프레임으로 나누려면 [GIF 프레임 추출기](/ko/tools/gif-splitter/)를, JPEG·PNG·WebP는 [이미지 압축기](/ko/tools/image-compressor/)를 쓰세요.
- **다른 포맷**: 사진 같은 움직임은 움직이는 WebP나 MP4가 훨씬 작습니다. [WebP 변환기](/ko/tools/webp-converter/)는 GIF의 첫 프레임만 바꾸므로, 움직임을 유지하려면 컴퓨터에서 다음을 실행하세요.

```bash
gif2webp -lossy -q 75 in.gif -o out.webp
ffmpeg -i in.gif -movflags +faststart -pix_fmt yuv420p -vf "scale=trunc(iw/2)*2:trunc(ih/2)*2" out.mp4
```
