## Two Real GIFs, Before and After

Both files are public on Wikimedia Commons, so you can download them and repeat the test. Sizes are in bytes, at the default settings (Lossy 40, 256 colors, all frames, no dithering).

**A rendered animation.** [Rotating earth (large).gif](https://commons.wikimedia.org/wiki/File:Rotating_earth_(large).gif) is 400 × 400 px with 44 frames and 1,001,718 bytes. The globe turns, so most pixels change in every frame. The result is 541,524 bytes (54%) with 255 colors. Half the width (200 px) brings it to 180,441 bytes (18%).

**A screen recording.** [Auto-citing a source using VisualEditor, small.gif](https://commons.wikimedia.org/wiki/File:Auto-citing_a_source_using_VisualEditor,_small.gif) records a Wikipedia editing session at 500 × 245 px with 114 frames and 698,529 bytes. Text and a cursor move; the page around them stands still. The result is 245,538 bytes (35%). At Lossy 100 it is 75,168 bytes (11%), but the SSIM against the original falls from 0.991 to 0.932: light-gray details such as the Edit button's border disappear, and faint traces of earlier frames stay on screen, because changes that small are not redrawn.

In Chrome on an M1 Max laptop, the result appeared 0.8–2.8 s (globe) and 3.5–4.8 s (recording) after the file was picked, over several runs. The same encoder code takes 0.37 s and 0.74 s in Node.js 24 on that machine.

## What Each Setting Does to the File Size

| Setting | What it changes | Effect on the screen recording above |
|---|---|---|
| **Lossy** (0–100, default 40) | Lets LZW reuse sequences with colors up to Lossy × 0.6 away | 100% at 0, 35% at 40, 11% at 100 |
| **Colors** (256 to 4) | Size of the color table; one slot is kept for transparency | 33% at 64 colors with Lossy 40 |
| **Width** | Scales the GIF down; height follows the aspect ratio | 5.7% at half width with Lossy 40 |
| **Frames** | Keeps every 2nd, 3rd or 4th frame | 22% with every 2nd frame and Lossy 40 |
| **Dithering** | Floyd–Steinberg error diffusion | 41% instead of 33% at 64 colors |

Width only shrinks, and each output pixel is the area average of the source pixels it covers. Dropped frames add their display time to the kept frame before them, so the animation keeps its total length.

## How It Compares with gifsicle and ezgif

[ezgif](https://ezgif.com/optimize) uploads your file and runs it through gifsicle with its lossy LZW encoder. [gifsicle](https://www.lcdf.org/gifsicle/man.html) runs on your own machine. This page runs in the tab and applies its lossy threshold in two places: inside LZW, like gifsicle's `--lossy`, and between frames, where a pixel whose new color is within the lossy distance of what is already on screen is left undrawn. On footage where the picture barely moves, the second step removes most of each frame. ezgif offers a similar frame step as a separate method, "Optimize Transparency" with a fuzz factor.

The two lossy scales are different: gifsicle measures the error in a gamma-corrected color space, so equal numbers are not equal settings. The table therefore compares file size at a similar SSIM, measured against the original with ffmpeg 9.0 (1.0 means identical). gifsicle is version 1.93.

| File | This tool, default | `gifsicle -O3 --lossy=80` |
|---|---|---|
| Rotating earth | 541,524 B, SSIM 0.956 | 575,411 B, SSIM 0.965 |
| [Newton's cradle](https://commons.wikimedia.org/wiki/File:Newtons_cradle_animation_book_2.gif), 480 × 360, 36 frames, 308,156 B | 109,817 B, SSIM 0.971 | 182,247 B, SSIM 0.967 |
| VisualEditor recording | 245,538 B, SSIM 0.991 | 549,574 B, SSIM 0.991 |

On the globe, where every pixel changes, the two are close. On the other two files this page's output was 40% and 55% smaller at the same or better SSIM. Repeat the test with these commands, where `out.gif` is the file you downloaded:

```bash
gifsicle -O3 --lossy=80 in.gif -o gifsicle.gif
ffmpeg -i in.gif -i out.gif -lavfi "[0:v]format=yuv444p[a];[1:v]format=yuv444p[b];[a][b]ssim" -f null -
```

gifsicle and ezgif do more: batch jobs, cropping, several palette and dithering methods, and files far above this page's size limit. Use them for those jobs.

## How Frame Optimization Works

The first frame covers the whole canvas. For every later frame, the tool writes only the rectangle that holds changed pixels. Unchanged pixels inside it use the transparent index, which compresses into long runs. A frame with no change becomes a single transparent pixel that keeps its delay. When a visible pixel must turn transparent, the frame before it gets disposal method 2 (restore to background), as defined in the [GIF89a specification](https://www.w3.org/Graphics/GIF/spec-gif89a.txt).

The palette is built once for the whole animation: exact if the frames use few enough colors, median cut otherwise.

## Limits

- **Size.** 50 million decoded pixels, 1,000 frames and 16,777,216 pixels per frame. Terminal and app recordings often go over: the [lazygit](https://github.com/jesseduffield/lazygit) README demo `commit_and_push-compressed.gif` is 1140 × 828 px with 67 frames, 63.2 million pixels, so the page refuses it and shows a gifsicle command. That GIF is already optimized; `gifsicle -O3 --lossy=80 --colors 128` made it 1% larger, and adding `--resize-width 570` cut it from 472,611 to 147,386 bytes.
- **Short delays.** Chromium and Firefox play a delay of 0 or 10 ms as 100 ms ([Chromium source](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/platform/graphics/deferred_image_decoder.cc), [Firefox source](https://searchfox.org/mozilla-central/source/image/FrameTimeout.h)). The tool writes such frames as 100 ms, so the output plays the same in every viewer. Other delays are rounded to 10 ms steps, with a minimum of 20 ms.
- **Output.** Always a GIF with one global color table. Frames cannot be cropped, reordered or edited. To take a GIF apart into PNG frames, use the [GIF Splitter](/tools/gif-splitter/). For JPEG, PNG and WebP, use the [Image Compressor](/tools/image-compressor/).
- **Other formats.** For photographic motion, animated WebP or MP4 are far smaller. The [WebP Converter](/tools/webp-converter/) converts only the first frame of a GIF, so run these on your computer:

```bash
gif2webp -lossy -q 75 in.gif -o out.webp
ffmpeg -i in.gif -movflags +faststart -pix_fmt yuv420p -vf "scale=trunc(iw/2)*2:trunc(ih/2)*2" out.mp4
```
