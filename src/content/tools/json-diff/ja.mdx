<h2>ユースケース</h2>
<ul>
  <li>バージョン間の API レスポンスの変化を確認する。</li>
  <li>PATCH HTTP エンドポイント用のパッチ操作を生成する。</li>
  <li>設定ファイルの変更を監査する。</li>
  <li>アプリケーション内の予期しないデータの変化をデバッグする。</li>
</ul>

## 例

**変更前：**

```json
{"name":"Alice","status":"pending","legacy_id":12345,"tags":["a","b","c"],"profile":{"age":30,"city":"Paris"}}
```

**変更後**（キーの順序が変わり、`status` を変更、`legacy_id` を削除、`role` を追加、最初のタグを削除）：

```json
{"status":"active","name":"Alice","role":"admin","tags":["b","c"],"profile":{"age":31,"city":"Paris"}}
```

**JSON Patch：**

{/* diff: {"before":{"name":"Alice","status":"pending","legacy_id":12345,"tags":["a","b","c"],"profile":{"age":30,"city":"Paris"}},"after":{"status":"active","name":"Alice","role":"admin","tags":["b","c"],"profile":{"age":31,"city":"Paris"}}} */}

```json
[
  { "op": "replace", "path": "/status", "value": "active" },
  { "op": "remove", "path": "/legacy_id" },
  { "op": "replace", "path": "/tags/0", "value": "b" },
  { "op": "replace", "path": "/tags/1", "value": "c" },
  { "op": "remove", "path": "/tags/2" },
  { "op": "replace", "path": "/profile/age", "value": 31 },
  { "op": "add", "path": "/role", "value": "admin" }
]
```

キーの順序は結果に影響しません。`name` は位置が変わっても報告されません。このパッチを Python の `jsonpatch` 1.33 で適用すると、変更後のドキュメントになります。

## 例：郵便番号検索APIの正常応答とエラー応答

zipcloud「[郵便番号検索API](https://zipcloud.ibsnet.co.jp/doc/api)」のドキュメントにある 2 つのサンプル、郵便番号 0790177 の正常応答（`status` 200、住所 2 件）と、必須パラメータがないときのエラー応答（`status` 400）を比べます。

{/* diff: {"before":{"message":null,"results":[{"address1":"北海道","address2":"美唄市","address3":"上美唄町協和","kana1":"ﾎｯｶｲﾄﾞｳ","kana2":"ﾋﾞﾊﾞｲｼ","kana3":"ｶﾐﾋﾞﾊﾞｲﾁｮｳｷｮｳﾜ","prefcode":"1","zipcode":"0790177"},{"address1":"北海道","address2":"美唄市","address3":"上美唄町南","kana1":"ﾎｯｶｲﾄﾞｳ","kana2":"ﾋﾞﾊﾞｲｼ","kana3":"ｶﾐﾋﾞﾊﾞｲﾁｮｳﾐﾅﾐ","prefcode":"1","zipcode":"0790177"}],"status":200},"after":{"message":"必須パラメータが指定されていません。","results":null,"status":400}} */}

```json
[
  { "op": "replace", "path": "/message", "value": "必須パラメータが指定されていません。" },
  { "op": "replace", "path": "/results", "value": null },
  { "op": "replace", "path": "/status", "value": 400 }
]
```

`results` は配列から `null` に型が変わったので、中の 2 件を 1 件ずつ削除するのではなく、`/results` を 1 回の `replace` で置き換えます。`message` も `null` から文字列に変わるだけなので `replace` です。半角カナの値は文字列としてそのまま比べます。

## 例：同じキーが 2 回ある JSON

手で編集した設定ファイルに、同じキーが 2 回書かれていることがあります。

{/* jd-page: {"before":"{\"店舗名\":\"渋谷店\",\"営業時間\":\"10:00-20:00\",\"営業時間\":\"10:00-21:00\"}","after":"{\"店舗名\":\"渋谷店\",\"営業時間\":\"10:00-21:00\"}"} */}

```text
差異なし — JSON は同一です。次のキーは同じオブジェクト内に複数あります。JSON.parse は最後の値だけを残し、その値だけを比較します：変更前 /営業時間。
```

`JSON.parse` は 2 つ目の `"10:00-21:00"` だけを残すため、2 つの文書は同じとみなされます。ステータスに重複したキーが出たら、どちらの値が正しいか原文で確かめてください。RFC 8259 は、オブジェクト内の名前は一意であるべき（SHOULD）としています（[RFC 8259 第 4 節](https://www.rfc-editor.org/rfc/rfc8259#section-4)）。

## 配列の比較方法

配列は内容ではなくインデックスで比較されます。`["a","b","c"]` から最初のタグを外すと、`remove /tags/0` 1 件ではなく、置換 2 件と削除 1 件として表示されます。同じ配列から複数の要素を削除するときは、大きい添字から順に書き出します。例として、3 行あった注文明細が 1 行になり、数量も変わった場合：

{/* diff: {"before":{"id":7,"items":[{"sku":"A1","qty":2},{"sku":"B2","qty":1},{"sku":"C3","qty":5}]},"after":{"id":7,"items":[{"sku":"A1","qty":3}]}} */}

```json
[
  { "op": "replace", "path": "/items/0/qty", "value": 3 },
  { "op": "remove", "path": "/items/2" },
  { "op": "remove", "path": "/items/1" }
]
```

`remove /items/2` の後も配列には 2 要素あるので、`/items/1` はまだ存在します。小さい添字から書くと 2 つ目の削除が配列の末尾を越え、1 つでも操作が失敗するとパッチ全体が失敗します（[RFC 6902 第 5 節](https://www.rfc-editor.org/rfc/rfc6902#section-5)）。

## パスと JSON Pointer のエスケープ

パッチのパスは JSON Pointer（[RFC 6901](https://www.rfc-editor.org/rfc/rfc6901)）で、`~` は `~0`、`/` は `~1` と書きます。`{"a/b":1,"m~n":2,"list":[1,2,3]}` → `{"a/b":2,"list":[1,2,3,4],"x":null}` の結果：

{/* diff: {"before":{"a/b":1,"m~n":2,"list":[1,2,3]},"after":{"a/b":2,"list":[1,2,3,4],"x":null}} */}

```json
[
  { "op": "replace", "path": "/a~1b", "value": 2 },
  { "op": "remove", "path": "/m~0n" },
  { "op": "add", "path": "/list/3", "value": 4 },
  { "op": "add", "path": "/x", "value": null }
]
```

ルートの型が異なる場合（オブジェクトと配列など）、パッチはドキュメント全体を置き換え、パスは空文字列 `""` になります。ビジュアル差分はキーをドットでつないで表示します（`profile.age`、`list.3`）。

## 制限

- move と copy の操作は生成しません。キー名の変更は `remove` と `add` として表示されます。
- オブジェクトの配列を `id` フィールドで対応付けることはしません。
- 両方とも有効な JSON である必要があります。ステータス行にどちらの解析に失敗したかが表示されます（例：`変更前 JSON の解析エラー：Expected double-quoted property name in JSON at position 7`。理由の部分はブラウザーが出す英語のままです）。
- 数値は JavaScript で解析してから比べるため、`1.0` と `1` は同じとみなし、`-0` はパッチに `0` と書きます。2^53 を超え double で正確に表せない整数（`9007199254740993` など。`9007199254740994` や `1e20` は正確に表せます）と、とても長い小数は丸められ、`1e400` のように double の範囲を超える数値は Infinity になります。ステータスに一覧が出ます（最大 10 個、残りは件数）。パッチには読み取った値を書きます（`1e400` は `null`）。
- 同じオブジェクト内で重複したキーは最後の値だけが残り、ステータスに表示されます。
- 約 1,900 階層（Node.js 22 で測定。ブラウザーによって異なります）入れ子になった文書は比較できず、ステータスにその旨を表示します。
- ツールのテストでは、生成したパッチを厳密な RFC 6902 実装（インストールされていれば Python の `jsonpatch` も）で「変更前」に適用し、結果が「変更後」と一致することを確かめています。ランダムな 3,000 組の文書でも確認しています。
