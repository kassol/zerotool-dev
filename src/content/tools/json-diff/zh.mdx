<h2>使用场景</h2>
<ul>
  <li>审查不同版本之间的 API 响应变更。</li>
  <li>为 PATCH HTTP 接口生成 patch 操作。</li>
  <li>审计配置文件变更。</li>
  <li>调试应用中意外的数据变更。</li>
</ul>

<p>相关工具：<a href="/zh/tools/json-formatter/">JSON 格式化</a> — 在差异对比前格式化并验证 JSON。</p>

## 示例：一次 API 响应的变化

**输入前：**

```json
{"name":"Alice","status":"pending","legacy_id":12345,"tags":["a","b","c"],"profile":{"age":30,"city":"Paris"}}
```

**输入后**（键顺序变了，`status` 改了，删除 `legacy_id`，新增 `role`，去掉第一个标签）：

```json
{"status":"active","name":"Alice","role":"admin","tags":["b","c"],"profile":{"age":31,"city":"Paris"}}
```

**JSON Patch：**

{/* diff: {"before":{"name":"Alice","status":"pending","legacy_id":12345,"tags":["a","b","c"],"profile":{"age":30,"city":"Paris"}},"after":{"status":"active","name":"Alice","role":"admin","tags":["b","c"],"profile":{"age":31,"city":"Paris"}}} */}

```json
[
  { "op": "replace", "path": "/status", "value": "active" },
  { "op": "remove", "path": "/legacy_id" },
  { "op": "replace", "path": "/tags/0", "value": "b" },
  { "op": "replace", "path": "/tags/1", "value": "c" },
  { "op": "remove", "path": "/tags/2" },
  { "op": "replace", "path": "/profile/age", "value": 31 },
  { "op": "add", "path": "/role", "value": "admin" }
]
```

键顺序不影响结果：`name` 换了位置但不会被报告。这个 patch 用 Python 的 `jsonpatch` 1.33 应用后得到「输入后」的文档。

## 示例：雪花 ID 订单为什么显示“未发现差异”

不少 Java 后端用雪花算法生成 19 位的 Long 型主键，例如 MyBatis-Plus 的 `IdType.ASSIGN_ID` 默认用雪花算法生成 ID（[MyBatis-Plus 注解文档](https://baomidou.com/reference/annotation/)）。接口如果把它当数字输出，比较两条订单时：

{/* jd-page: {"before":"{\"orderId\":1830000000000000001,\"status\":\"待支付\"}","after":"{\"orderId\":1830000000000000002,\"status\":\"已支付\"}"} */}

```json
[
  { "op": "replace", "path": "/status", "value": "已支付" }
]
```

```text
检测到 1 处变更。JavaScript 无法精确保存以下数字，按舍入后的值比较，因此其中的差异可能漏报，Patch 也写入舍入后的值：输入前 /orderId: 1830000000000000001 → 1830000000000000000; 输入后 /orderId: 1830000000000000002 → 1830000000000000000。
```

两个订单号在 JavaScript 里都变成 `1830000000000000000`，所以 Patch 只有 `status` 一条，订单号的变化被漏掉了；状态栏把两处舍入都列了出来。RFC 8259 指出，只有 [-(2^53)+1, (2^53)-1] 范围内的整数在各实现之间能保证一致（[RFC 8259 第 6 节](https://www.rfc-editor.org/rfc/rfc8259#section-6)）。这类 ID 最好在接口里以字符串输出。

## 示例：收货地址与商品列表

键名是中文时，Patch 路径里直接写中文；按下标比较的数组，删掉第一件商品后会显示成「替换 + 删除」：

{/* diff: {"before":{"收货人":"张伟","收货地址":{"省":"广东省","市":"深圳市"},"商品":[{"sku":"A1","数量":2},{"sku":"B2","数量":1}]},"after":{"收货人":"张伟","收货地址":{"省":"广东省","市":"广州市"},"商品":[{"sku":"B2","数量":1}]}} */}

```json
[
  { "op": "replace", "path": "/收货地址/市", "value": "广州市" },
  { "op": "replace", "path": "/商品/0/sku", "value": "B2" },
  { "op": "replace", "path": "/商品/0/数量", "value": 1 },
  { "op": "remove", "path": "/商品/1" }
]
```

`A1` 那一行其实是被删除了，但工具不按 `sku` 配对，而是把第 0 项改成 `B2` 的内容，再删掉第 1 项。应用这个 Patch 后的结果与「输入后」相同，只是读起来不像“删除一件商品”。

## 数组如何比较

数组按下标比较，而不是按内容。同一个数组删除多个元素时，删除按下标从大到小写出。例如一张订单原有 3 个商品行、现在只剩 1 个且数量变了：

{/* diff: {"before":{"id":7,"items":[{"sku":"A1","qty":2},{"sku":"B2","qty":1},{"sku":"C3","qty":5}]},"after":{"id":7,"items":[{"sku":"A1","qty":3}]}} */}

```json
[
  { "op": "replace", "path": "/items/0/qty", "value": 3 },
  { "op": "remove", "path": "/items/2" },
  { "op": "remove", "path": "/items/1" }
]
```

执行 `remove /items/2` 后数组还剩两项，`/items/1` 仍然存在。若按从小到大的顺序，第二条删除会越过数组末尾；任一操作失败，整个 patch 即失败（[RFC 6902 第 5 节](https://www.rfc-editor.org/rfc/rfc6902#section-5)）。超出较短数组长度的元素写成 `remove`（大下标在前）或 `add`（小下标在前）。

## 路径与 JSON Pointer 转义

patch 里的路径是 JSON Pointer（[RFC 6901](https://www.rfc-editor.org/rfc/rfc6901)）：`~` 写成 `~0`，`/` 写成 `~1`。`{"a/b":1,"m~n":2,"list":[1,2,3]}` → `{"a/b":2,"list":[1,2,3,4],"x":null}` 的结果：

{/* diff: {"before":{"a/b":1,"m~n":2,"list":[1,2,3]},"after":{"a/b":2,"list":[1,2,3,4],"x":null}} */}

```json
[
  { "op": "replace", "path": "/a~1b", "value": 2 },
  { "op": "remove", "path": "/m~0n" },
  { "op": "add", "path": "/list/3", "value": 4 },
  { "op": "add", "path": "/x", "value": null }
]
```

两边根节点类型不同（如对象与数组）时，patch 替换整个文档，路径是空串 `""`（RFC 6901 中 `/` 指向名为空字符串的成员）。可视差异用点号连接键名（`profile.age`、`list.3`），只是方便阅读。

## 限制

- 不生成 move、copy 操作；改名的键显示为 `remove` 加 `add`。
- 对象数组不会按 `id` 或 `sku` 字段配对。
- 两边都必须是合法 JSON，状态栏会指出哪一边解析失败，例如 `前 JSON 解析错误：Expected double-quoted property name in JSON at position 7`（原因部分是浏览器给出的英文）。
- 数字按 JavaScript 解析后比较：`1.0` 与 `1` 相同，`-0` 在 Patch 里写成 `0`。超过 2^53 的整数、很长的小数和 `1e400` 这类数字会被舍入，状态栏列出它们（最多 10 个，其余写出个数），Patch 写入舍入后的值（`1e400` 写成 `null`）。
- 同一对象中重复出现的键只保留最后一个值，状态栏会列出。
- 嵌套约 1,900 层（Node.js 22 中测得，浏览器之间有差异）的文档无法比较，状态栏会给出提示。
- 工具的测试把每个生成的 patch 用严格的 RFC 6902 实现（以及已安装时的 Python `jsonpatch`）应用到「前」，结果必须等于「后」，另跑 3,000 组随机文档。
