<p>OpenAPI や Swagger の仕様書を貼り付けるか、ファイル・フォルダを開いてください。バージョンに合った公式 JSON Schema で構造を検証し、ファイルをまたいで <code>$ref</code> をたどり、スキーマだけでは表せない規則も確認します。問題には行と列が付き、クリックするとエディターのその行を選択します。</p>

<h2>実例：e-Gov 法令API Version 2 の仕様書</h2>
<p>デジタル庁の e-Gov 法令API Version 2 は、Swagger UI の画面から仕様書 <code>lawapi-v2.yaml</code>（OpenAPI 3.0.3、info.version 2.1.139、2026-10-02 取得）を読み込んでいます。このファイルを検証するとエラーは 0 件、警告は JSON のサンプル値 5 件でした。そのひとつが、法令番号の年 <code>law_num_year</code> を <code>type: integer</code> と定義しながら、サンプルでは <code>"11"</code> と文字列で書いている箇所です。該当部分を抜き出すと次のとおりです。</p>

{/* ov */}
<pre><code>{`openapi: 3.0.3
info:
  title: 法令API Version 2（抜粋）
  version: 2.1.139
paths:
  /law_data/{law_id_or_num_or_revision_id}:
    get:
      parameters:
        - name: law_id_or_num_or_revision_id
          in: path
          required: true
          schema: {type: string}
      responses:
        "200":
          description: OK
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/law_info"
              examples:
                example_law_data_json:
                  value:
                    law_id: 411AC0000000127
                    law_num_year: "11"
                    law_num_num: "127"
            application/xml:
              schema:
                $ref: "#/components/schemas/law_info"
              examples:
                example_law_data_xml:
                  value: <law_info><law_num_year>11</law_num_year></law_info>
components:
  schemas:
    law_info:
      type: object
      properties:
        law_id: {type: string}
        law_num_year:
          description: 法令番号の年
          type: integer
        law_num_num: {type: string}`}</code></pre>

{/* ov-out */}
<pre><code>{`24:21  警告  サンプル値がスキーマと一致しません（/law_num_year）：型は integer である必要があります。`}</code></pre>

<p>XML のサンプル値は文字列で書かれたシリアライズ済みの本文なので、比較しません（OpenAPI 3.x の Example Object の説明どおり）。元のファイル全体では、Spectral 6.17.0 がサンプル値の不一致を 21 件エラーにし、そのうち 16 件はこの XML 文字列への「type must be object」でした。Redocly CLI 2.57.0 も同じ 16 件を警告にしています。サンプル値の警告は仕様違反ではないため、文書自体は有効と判定されます。</p>

<h2>実例：3.0 の書き方のまま 3.1 に上げたスキーマ</h2>
<p>OpenAPI 3.1 のスキーマは JSON Schema 2020-12 そのものです。3.1 の公式スキーマはスキーマの中身をほとんど確かめないので、このツールは各スキーマを 2020-12 のメタスキーマでも検証します。プロパティに <code>required: true</code> を書く、<code>type: int</code> と書く、3.0 の <code>nullable</code> を残す、といった誤りが見つかります。</p>

{/* ov */}
<pre><code>{`openapi: 3.1.0
info:
  title: 会員 API
  version: 1.0.0
paths: {}
components:
  schemas:
    Member:
      type: object
      properties:
        name:
          type: string
          required: true
        kana:
          type: string
          nullable: true
        age:
          type: int`}</code></pre>

{/* ov-out */}
<pre><code>{`8:5  警告  スキーマ "Member" はどこからも参照されていません。
13:11  エラー  "required" の型は array である必要があります。
16:11  警告  "nullable" は OpenAPI 3.0 のキーワードで、3.1 以降では効果がありません。type に "null" を加えてください（例：type: [string, "null"]）。
18:11  エラー  "type" は次のいずれかにしてください："array", "boolean", "integer", "null", "number", "object", "string"。`}</code></pre>

<h2>実例：サーバー URL とセキュリティスキーム</h2>
<p>ステージごとに URL を切り替える書き方では、<code>variables</code> の書き漏れや、<code>enum</code> にないデフォルト値がよく起きます。3.0 の仕様ではデフォルト値は enum に含まれるべき（SHOULD）なので警告、3.1 以降は MUST なのでエラーです。セキュリティ要件の名前が宣言と違う場合はどのバージョンでもエラーです。</p>

{/* ov */}
<pre><code>{`openapi: 3.0.3
info:
  title: 予約 API
  version: 1.0.0
servers:
  - url: https://{stage}.example.jp/{version}
    variables:
      stage:
        default: prod
        enum: [dev, stg]
paths:
  /reservations:
    get:
      security:
        - api_key: []
      responses:
        "200": {description: OK}
components:
  securitySchemes:
    apiKey: {type: apiKey, in: header, name: X-API-Key}`}</code></pre>

{/* ov-out */}
<pre><code>{`6:5  警告  "https://{stage}.example.jp/{version}" の変数 {version} が variables にないため、URL を展開できません。
9:9  警告  変数 "stage" のデフォルト値 "prod" が enum にありません。
15:11  エラー  セキュリティスキーム "api_key" が components.securitySchemes に宣言されていません。
20:5  警告  セキュリティスキーム "apiKey" はどこからも参照されていません。`}</code></pre>

<p>YAML は <a href="https://yaml.org/spec/1.2.2/#1023-core-schema" target="_blank" rel="noopener">YAML 1.2 の Core Schema</a> で読みます。引用符なしの <code>version: 2026-10-02</code> は文字列のままです。同じ階層に同じキーが 2 回あると、JSON でも行番号付きの構文エラーになります。マージキー（<code>{'<<: *anchor'}</code>）も使えます。</p>

<h2>他のツールとの違い</h2>
<p>2026-10-02 に、同じテスト用の仕様書で比べました。中身は、宣言していないパスパラメーター、宣言していないセキュリティスキーム、パラメーター名だけが違う 2 つのパス、プロパティの <code>required: true</code> の 4 つのエラーと、引用符なしの日付の <code>info.version</code> です。</p>
<ul>
  <li>Redocly CLI 2.57.0 と Spectral 6.17.0 は 4 件とも検出しました。summary や 4XX レスポンスなどのスタイル規則も多数出ます。swagger-parser 13.1.0 は有効と判定しました。</li>
  <li>Swagger Editor 5.8.9（editor.swagger.io）はブラウザ内で動き、パスパラメーターと <code>required</code> は検出しましたが、同じテンプレートのパスと未宣言のスキームは出ませんでした。</li>
  <li>アサリツールズの OpenAPI（Swagger）検証ツールは通信なしで動きますが、<code>"200"</code> と <code>"204"</code> を「無効なステータスコードです」と誤って報告し、4 件のエラーはどれも出ませんでした。</li>
</ul>

<h2>制限</h2>
<ul>
  <li>命名や説明文などのスタイル規則は扱いません。チームのルールは、このツールの後で Redocly CLI や Spectral を使ってください。</li>
  <li><code>$ref</code> の URL は取得しないので、ファイルを追加してください。アンカー参照（<code>#name</code>）は確認しません。</li>
  <li>非常に大きな仕様書では、サンプル値の確認を 4 秒で打ち切り、その旨を表示します。2 MB を超える入力は「検証」を押したときに確認し、合計 50 MB を超えるファイルは読み込みません。</li>
  <li>開いたファイルが 512 K 文字を超えるときは、全文を検証しますが、編集欄には最大 300 行を読み取り専用で表示します。約 10 MB を編集欄に入れるとページが 0.5 秒ほど止まるためです。行番号を押すと表示がその行に移ります。「全文をコピー」「ダウンロード」「全文を編集（遅くなります）」で全体を扱えます。自分で大量のテキストを編集欄に貼り付けた場合は、引き続きページが止まります。</li>
  <li>YAML は js-yaml 4.3.2 で読みます。ネストが 100 階層を超える文書、マージキーで処理するマッピングとキーが合計 10,000 個を超える文書、1 つのマージキーに 100 個を超えるマッピングを並べた文書は止まり、エラーに上限と行が出ます。</li>
</ul>
