<h2>상태 코드 카테고리</h2>
<ul>
  <li><strong>1xx 정보:</strong> 임시 응답 — 요청 수신됨, 서버가 아직 처리 중.</li>
  <li><strong>2xx 성공:</strong> 요청이 수신, 이해, 수락됨.</li>
  <li><strong>3xx 리다이렉션:</strong> 요청을 완료하려면 추가 조치 필요.</li>
  <li><strong>4xx 클라이언트 오류:</strong> 요청에 잘못된 구문이 있거나 처리 불가.</li>
  <li><strong>5xx 서버 오류:</strong> 서버가 유효한 요청 처리에 실패.</li>
</ul>

## 네이버 오픈 API 오류 코드와 맞춰 보기

네이버 개발자센터의 [오류 코드](https://developers.naver.com/docs/common/openapiguide/errorcode.md) 문서는 오픈 API가 돌려주는 HTTP 상태 코드와 원인을 표로 정리해 둡니다. 같은 코드라도 일반적인 의미와 네이버에서의 원인이 다를 수 있으니, 이 도구의 영어 설명과 함께 보세요.

**403.** 이 도구의 설명은 ‘서버가 요청을 이해했지만 권한 부여를 거부했다’입니다. 네이버 문서는 HTTPS가 아닌 HTTP로 호출한 경우도 403의 원인으로 듭니다. 키를 다시 발급받기 전에 요청 URL이 `https://`인지부터 확인하세요.

{/* hsc-check: {"q":"403"} */}
```text
403 Forbidden
```

**429.** 네이버는 하루 허용량을 넘었을 때와, 검색 API의 초당 호출량을 넘었을 때 모두 429를 돌려줍니다. 하루 한도는 기다려도 그날 안에는 풀리지 않으므로, 문서는 하루 허용량 초과 시 제휴 신청을 안내합니다. 이 도구에서 영어로 `too many`를 검색하면 다음과 같습니다.

{/* hsc-check: {"q":"too many"} */}
```text
429 Too Many Requests
```

**500.** 문서에는 API 서버 오류뿐 아니라, 필수 요청 변수가 없거나 요청 변수 값을 URL 인코딩하지 않은 경우도 500의 원인으로 적혀 있습니다. 500이라고 서버 장애로 단정하지 말고 요청 변수부터 확인하세요.

설명은 영어라서 한국어로 검색하면 결과가 없습니다. 예를 들어 `한도`를 검색하면 다음과 같이 표시됩니다.

{/* hsc-check: {"q":"한도"} */}
```text
일치하는 상태 코드가 없습니다.
```

## API에서 어떤 상태 코드를 쓸까

| 상황 | 코드 |
|---|---|
| `GET`으로 리소스 반환 | 200 |
| `POST`로 리소스 생성 | 201 (`Location` 헤더 포함) |
| 성공했지만 본문 없음 (주로 `DELETE`) | 204 |
| 본문이 올바른 JSON이 아니거나 구문 오류 | 400 |
| 토큰이 없거나 유효하지 않음 | 401 |
| 토큰은 유효하지만 권한 없음 | 403 |
| 리소스가 없음 | 404 |
| 중복 (이미 가입된 이메일 등) | 409 |
| 본문은 파싱되지만 업무 규칙 위반 (종료일이 시작일보다 앞섬) | 422 |
| 요청 한도 초과 | 429 |
| 처리되지 않은 예외 | 500 |

**401과 403.** 401은 서버가 요청자를 식별하지 못한 상태이며, 401을 보내는 서버는 `WWW-Authenticate` 헤더도 반드시 보내야 합니다([RFC 9110 §15.5.2](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.2)). 403은 요청자를 알지만 이 작업을 허용하지 않는 상태입니다. 리소스가 존재한다는 사실을 숨겨야 하면 403 대신 404를 보낼 수 있습니다([§15.5.4](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.4)).

**리다이렉트와 요청 메서드.** 역사적인 이유로 브라우저는 301과 302를 따라갈 때 `POST`를 `GET`으로 바꿀 수 있습니다([§15.4.2](https://www.rfc-editor.org/rfc/rfc9110#section-15.4.2)). 307과 308은 메서드와 본문을 유지해야 합니다. 폼 `POST`를 `POST`로 유지해야 하면 307이나 308을 쓰세요.

## 코드와 함께 보내는 헤더

| 코드 | 헤더 | 규정 |
|---|---|---|
| 201 | `Location: /api/users/456` | 새 리소스를 가리킴 |
| 401 | `WWW-Authenticate: Bearer realm="api"` | 필수 |
| 405 | `Allow: GET, POST` | 필수 ([§15.5.6](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.6)) |
| 429, 503 | `Retry-After: 60` | 선택. 초 또는 HTTP 날짜 ([RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585#section-4)) |
| 304 | — | 본문 없음. 클라이언트가 캐시를 사용 |

## JavaScript에서 처리하기

`fetch()`는 4xx나 5xx에서 reject하지 않습니다. 네트워크 오류일 때만 reject하므로 `res.ok`(200–299이면 true)나 `res.status`를 확인하세요.

```javascript
const res = await fetch('/api/orders', { method: 'POST', body });
if (res.status === 401) return redirectToLogin();
if (res.status === 429) {
  const wait = Number(res.headers.get('Retry-After') ?? 60);
  return retryAfter(wait);
}
if (!res.ok) throw new Error(`HTTP ${res.status}`);
const order = await res.json();
```

## 제한 사항

{/* hsc-iana */}
- **코드 61개, IANA 레지스트리와 대조함.** [IANA HTTP Status Code Registry](https://www.iana.org/assignments/http-status-codes/)(마지막 갱신 2025-09-15)와 비교하면 목록의 코드는 모두 레지스트리에 항목이 있습니다. 레지스트리에는 104(2026-11-13에 만료되는 임시 등록), 사용 중단된 305 Use Proxy, 쓰이지 않는 306도 있지만 목록에는 넣지 않았습니다. nginx 499나 Cloudflare 520–526처럼 특정 제품만 쓰는 코드는 레지스트리에도 목록에도 없습니다.
- **네 코드는 이름이 레지스트리와 다릅니다.** 목록의 413 Payload Too Large와 422 Unprocessable Entity는 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-15.5)에서 Content Too Large와 Unprocessable Content로 이름이 바뀌었습니다. 418은 목록에서 ‘I'm a Teapot’이지만 레지스트리에는 (Unused)로 되어 있습니다. 만우절 RFC 2324에서 쓰인 탓에 RFC 9110 15.5.19절이 이 번호를 예약해 두었습니다. 510 Not Extended는 레지스트리에서 OBSOLETED(폐지)로 표시됩니다.
- **설명은 영어로만 나옵니다.** 모든 언어 페이지에서 이름과 설명이 영어입니다. 검색은 코드, 이름, 영어 설명의 단어와 일치하는 항목을 찾으므로 「리다이렉트」로는 결과가 없고 영어로 검색해야 합니다. 다만 `redirect`로는 307과 308만 나오고, 301과 302의 설명에는 `moved`라는 단어가 쓰였습니다. 전각 숫자와 영문은 검색 전에 반각으로 바꿉니다(NFKC 정규화).
