## 型の決まり方

- 文字列は `string`、数値は整数と小数を区別せず `number`、真偽値は `boolean` になります。
- オブジェクトのプロパティが `null` のときは `field?: null` になります。値があるときの型はサンプル 1 件からはわからないためです。
- 空配列は `unknown[]`、プリミティブが混ざった配列は `(string | number)[]` のようなユニオン型になります。
- オブジェクトの配列は全要素をマージして 1 つの要素インターフェース（`ResultsItem` など）にします。
- ルートのインターフェースが先頭に来て、残りは最初に見つかった順に並びます。

## 例：郵便番号検索 API のレスポンス

[zipcloud の郵便番号検索 API](https://zipcloud.ibsnet.co.jp/doc/api) は、日本郵便が公開している郵便番号データを検索する API です。ドキュメントのレスポンスサンプル（郵便番号 0790177 で 2 件ヒット）をそのまま貼り、ルートインターフェース名を `ZipcloudResponse` にします。

{/* jtt-check: {"root":"ZipcloudResponse"} */}

```json
{
  "message": null,
  "results": [
    {
      "address1": "北海道",
      "address2": "美唄市",
      "address3": "上美唄町協和",
      "kana1": "ﾎｯｶｲﾄﾞｳ",
      "kana2": "ﾋﾞﾊﾞｲｼ",
      "kana3": "ｶﾐﾋﾞﾊﾞｲﾁｮｳｷｮｳﾜ",
      "prefcode": "1",
      "zipcode": "0790177"
    },
    {
      "address1": "北海道",
      "address2": "美唄市",
      "address3": "上美唄町南",
      "kana1": "ﾎｯｶｲﾄﾞｳ",
      "kana2": "ﾋﾞﾊﾞｲｼ",
      "kana3": "ｶﾐﾋﾞﾊﾞｲﾁｮｳﾐﾅﾐ",
      "prefcode": "1",
      "zipcode": "0790177"
    }
  ],
  "status": 200
}
```

生成結果：

```typescript
interface ZipcloudResponse {
  message?: null;
  results: ResultsItem[];
  status: number;
}

interface ResultsItem {
  address1: string;
  address2: string;
  address3: string;
  kana1: string;
  kana2: string;
  kana3: string;
  prefcode: string;
  zipcode: string;
}
```

`prefcode` と `zipcode` は数字ですが、JSON では文字列なので `string` になります。郵便番号の先頭の 0 が消えないので、このまま文字列で扱うのが安全です。半角カナの `kana1` なども、ツールから見ればただの `string` です。

一方で、この型はエラー時のレスポンスに合いません。ドキュメントのエラー時サンプルでは `message` に文字列が入り、`results` は `null` です。成功時の 1 件だけから作ると、`message` は「`null` しか入らない省略可能なフィールド」、`results` は「必ず配列」になってしまいます。

## 例：成功時とエラー時をまとめて貼る

複数のパターンを 1 つの型にしたいときは、レスポンスを配列に入れて貼ります。ルートが配列の場合、各要素がマージされ、要素 1 件分の型がルート名で出力されます。成功時（results は 1 件に省略）とエラー時のサンプルを並べると：

{/* jtt-check: {"root":"ZipcloudResponse"} */}

```json
[
  {
    "message": null,
    "results": [
      {
        "address1": "北海道",
        "address2": "美唄市",
        "address3": "上美唄町協和",
        "kana1": "ﾎｯｶｲﾄﾞｳ",
        "kana2": "ﾋﾞﾊﾞｲｼ",
        "kana3": "ｶﾐﾋﾞﾊﾞｲﾁｮｳｷｮｳﾜ",
        "prefcode": "1",
        "zipcode": "0790177"
      }
    ],
    "status": 200
  },
  {
    "message": "必須パラメータが指定されていません。",
    "results": null,
    "status": 400
  }
]
```

生成結果：

```typescript
interface ZipcloudResponse {
  message: (null | string);
  results: (ResultsItem[] | null);
  status: number;
}

interface ResultsItem {
  address1: string;
  address2: string;
  address3: string;
  kana1: string;
  kana2: string;
  kana3: string;
  prefcode: string;
  zipcode: string;
}
```

`message` と `results` が `null` を含むユニオン型になり、両方のパターンを受け入れます。ここで出力された `ZipcloudResponse` は配列の要素 1 件の型なので、API の戻り値には `ZipcloudResponse` をそのまま使い、配列全体には `ZipcloudResponse[]` を使います。

## 手で直すところ

- `?: null`：API ドキュメントを確認して `string | null` のような実際の型に置き換えます。
- 空配列の `unknown[]`：要素の型を補います。
- 日付：ISO 8601 の文字列も Unix タイムスタンプも、それぞれ `string`・`number` のままです。
- `ResultsItem`、`Same_name`、`PaymentMeta` のような名前はキー名から作られます。用途に合わせて名前を変えてください。同じキー名でフィールドが違うオブジェクトが 2 つあると、2 つ目には親の名前が付き（`payment.meta` なら `PaymentMeta`）、それも使われていれば番号が付きます（`Meta2`）。
- 日本語のキー（`"氏名"` など）はプロパティ名が引用符付きになり、インターフェース名は `住所` のように日本語のままです。どちらも TypeScript として有効です。
- 有効な型名にならないキー（`2fa`、空のキー）は、インターフェース名の先頭に `T` を付けます（`T2fa`）。

## 制限

- {/* jtt-error: {"input":"{\"a\":1,}"} */}入力は有効な JSON である必要があります（コメントや末尾のカンマは不可）。無効なときは出力を消去し、ステータスに行・列と考えられる原因を表示します。行と列は入力したままのテキストで数えます。たとえば `{"a":1,}` は `無効なJSON：1 行 7 列目、閉じかっこの前に余分なカンマがあります。` です。{/* jtt-error: {"input":"{\"郵便番号\"：\"0790177\"}"} */}IME で入力した全角の `：` も位置がわかります。`{"郵便番号"："0790177"}` は `無効なJSON：1 行 8 列目、全角文字 ： があります。JSON の記号と空白は半角です。` になります。
- ルートの配列にオブジェクトとそれ以外の値が混在する場合（`[{"id": 1}, "x", null]` など）、オブジェクトはルート名のインターフェースにまとめられ、配列全体を表す型エイリアスがネストした配列と同じ書き方で追加されます：`type RootObjectArray = (string | null | RootObject)[];`。レスポンスの型には `RootObjectArray` を使います。
- ルートインターフェース名は ECMAScript の識別子のルールで整えます。各言語の文字、数字、`$`、`_` は残し、それ以外の文字は取り除いて次の文字を大文字にします（`user profile` は `userProfile`）。識別子の先頭に使えない名前には `T` を付け（`2fa` は `T2fa`）、予約語やプリミティブ型の名前には `_` を付けます（`class` は `class_`）。何も残らない場合は RootObject です。
- TypeScript の標準ライブラリ（`lib.dom.d.ts` と各 `lib.es*.d.ts`）にある 1 語のグローバル型（`Promise`、`Date`、`Map`、`Record`、`Body`、`Response`、`Event`、`JSON`、`URL` など）と同じ名前は、そのまま使いません。`import` も `export` もないファイルではその宣言がグローバル型とマージされ、モジュールではグローバル型を隠してしまうためです。ネストしたオブジェクトは親の名前を前に付け（`{"date": {"year": 2026}}` は `RootObjectDate`、キー `"URL"` は `RootObjectURL`。キー `"url"` から作られる `Url` はグローバル型ではないのでそのままです）、ルート名には `_` を付けます（`Map` は `Map_`）。ルート名 `globalThis` にも `_` を付けます（`globalThis_`）。`import` も `export` もないファイルでは、TypeScript がこの名前の宣言を受け付けないためです。`Image`、`Intl`、`Proxy` のようにグローバルな値としてだけ存在する名前は、同じ名前の interface や type とぶつからないので、そのまま使います。
- `formData` キーから作られる `FormData` のように複数の語からなるグローバル型名は、生成した名前のままです。`import` も `export` もないファイルに貼る場合や、貼り付け先のモジュールでそのグローバル型も使う場合は名前を変えてください。
- ネストが非常に深いとブラウザのコールスタックを超えることがあります。その場合はステータスにエラーを表示し、前の出力を消去します。
- 9007199254740991（`Number.MAX_SAFE_INTEGER`）を超える整数は `JSON.parse` で桁が丸められ、型も `number` になります。
- 型は貼り付けたサンプルだけから決まります。サンプルでは文字列でも本番で数値になることがあるフィールドは `string` のままです。
- 「interface の代わりに type を使用」を選ぶと、各宣言は `type Name = { ... }` になります。
