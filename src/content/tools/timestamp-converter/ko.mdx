<h2>Unix 타임스탬프에 대하여</h2>
<p>Unix 타임스탬프는 프로그래밍·데이터베이스·API에서 시각을 다루는 표준적인 방법입니다. 타임존을 신경 쓰지 않고 절대 시각을 표현할 수 있으며, 날짜·시각 계산과 비교가 간단합니다.</p>
<p>로그 분석, API 응답 디버깅, 데이터베이스 타임스탬프 확인 등에 편리합니다.</p>

## 변환 예시

단위가 ‘단위 자동 판단’이면 소수점 앞 자릿수로 판단합니다. 12자리 이하는 초, 13–15자리는 밀리초, 16–18자리는 마이크로초, 19자리 이상은 나노초입니다. 현재 시각이라면 각각 10, 13, 16, 19자리입니다. 어떤 단위로 읽었는지 상태 줄에 표시되며, 틀리면 목록에서 단위를 고를 수 있습니다.

{/* tsc-check: {"in": ["1700000000", "1700000000123", "2147483647", "1700000000123456", "1700000000123456789"]} */}

| 입력 | 판단 | ISO 8601(UTC) |
|---|---|---|
| `1700000000` | 초 | `2023-11-14T22:13:20.000Z` |
| `1700000000123` | 밀리초 | `2023-11-14T22:13:20.123Z` |
| `2147483647` | 초 | `2038-01-19T03:14:07.000Z` |
| `1700000000123456` | 마이크로초 | `2023-11-14T22:13:20.123Z` |
| `1700000000123456789` | 나노초 | `2023-11-14T22:13:20.123Z` |

`2147483647`은 부호 있는 32비트 정수의 최댓값이며, 2038년 문제는 이 시점에 시작됩니다. 마지막 두 행은 마이크로초(Python `time.time_ns() // 1000` 등)와 나노초(Go `time.Now().UnixNano()`, `date +%s%N`) 타임스탬프입니다. JavaScript 날짜는 밀리초 단위이므로 밀리초 미만 자릿수는 버립니다. 나노초 값은 2<sup>53</sup>을 넘기 때문에 큰 정수로 읽어 정밀도를 잃지 않습니다.

## 업비트 시세 API로 확인하기

아래 결과는 컴퓨터 타임존이 한국(Asia/Seoul)일 때의 값이며, 로컬 행이 곧 한국 시간입니다.

{/* tsc-check: {"in": "1751606040365", "tz": "Asia/Seoul", "show": ["iso", "local"], "label": true, "status": true} */}

업비트 [페어 단위 현재가 조회](https://docs.upbit.com/kr/reference/list-tickers) 응답에는 최근 체결 시각이 세 가지 형태로 들어 있습니다. `trade_timestamp`는 밀리초 단위 타임스탬프이고, `trade_date`·`trade_time`은 UTC 기준, `trade_date_kst`·`trade_time_kst`는 KST 기준 날짜와 시각입니다. 문서 응답 예시의 KRW-BTC `trade_timestamp` 값 `1751606040365`를 붙여 넣으면 13자리라서 상태 줄에 ‘밀리초(으)로 읽었습니다(13자리). 틀리면 단위를 고르세요.’가 표시되고, ISO 8601 행은 `2025-07-04T05:14:00.365Z`가 됩니다. 같은 응답의 `trade_time` 값 `051400`(UTC)과 맞습니다. ‘Local (UTC+09:00)’ 행은 `2025-07-04 14:14:00`으로, `trade_date_kst` 값 `20250704`, `trade_time_kst` 값 `141400`과 일치합니다.

네이버 클라우드 플랫폼 API의 요청 헤더 `x-ncp-apigw-timestamp`도 밀리초 단위입니다. [Ncloud API 공통 가이드](https://api.ncloud-docs.com/docs/common-ncpapi)는 API Gateway 서버와 5분 이상 시간 차가 나면 유효하지 않은 요청으로 본다고 설명합니다. 서명 오류가 나면 보낸 헤더 값을 붙여 넣어 실제로 어느 시각인지 확인해 보세요.

### 1987–1988년 서머타임

{/* tsc-check: {"in": "583718400", "tz": "Asia/Seoul", "show": ["iso", "local"], "label": true} */}

브라우저의 타임존 데이터는 [IANA tz](https://github.com/eggert/tz/blob/main/asia)를 바탕으로 하며, Asia/Seoul의 Rule ROK에 1987–1988년 서머타임이 들어 있습니다. 컴퓨터 타임존이 한국이면 `583718400`(`1988-07-01T00:00:00.000Z`)은 ‘Local (UTC+10:00)’ 행에서 `1988-07-01 10:00:00`으로 표시됩니다. 평소처럼 UTC+09:00이었다면 09:00:00입니다. 오래된 기록을 대조할 때는 ISO 8601 행을 기준으로 삼으세요.

## 코드로 변환하기

```bash
date +%s                      # current timestamp (Linux, macOS)
date -u -d @1700000000        # GNU date (Linux)
date -u -r 1700000000         # BSD date (macOS)
```

```javascript
Math.floor(Date.now() / 1000)          // current timestamp in seconds
new Date(1700000000 * 1000).toISOString()  // "2023-11-14T22:13:20.000Z"
```

```python
import time, datetime
int(time.time())                                                  # current timestamp
datetime.datetime.fromtimestamp(1700000000, datetime.timezone.utc)  # 2023-11-14 22:13:20+00:00
```

## 제한 사항

{/* tsc-check: {"cases": [{"in": "1e10", "error": true}, {"in": "8640000000000000", "unit": "ms"}, {"in": "8640000000000001", "unit": "ms", "error": true}]} */}

- **자동 판단은 자릿수만 봅니다.** 2001-09-09 이전의 밀리초 값은 12자리라 초로, 13자리 이상의 초 값(서기 33658년 이후)은 밀리초로 읽습니다. 이럴 때는 단위를 고르세요.
- **숫자만 받습니다.** 지수(`1e10`), 16진수, 천 단위 구분 기호는 오류가 나며 상태 줄에 `잘못된 타임스탬프입니다. 숫자를 입력하세요(부호와 소수점 사용 가능). 날짜는 ‘날짜 → 타임스탬프’에서 고르세요.`가 표시됩니다. 소수 부분은 입력할 수 있고, 전각 숫자는 반각으로 읽습니다.
- **‘날짜 → 타임스탬프’는 로컬 타임존을 씁니다.** 날짜 선택기 값은 브라우저의 타임존으로 해석되므로, 같은 값이라도 타임존 설정이 다른 컴퓨터에서는 다른 타임스탬프가 나옵니다.
- **윤초를 세지 않습니다.** Unix 시간은 윤초를 무시하며 JavaScript의 `Date`도 마찬가지입니다.
- **표현 범위가 있습니다.** JavaScript 날짜는 에포크 전후 ±8,640,000,000,000,000밀리초까지만 나타냅니다. 단위를 밀리초로 고르면 `8640000000000000`은 `+275760-09-13T00:00:00.000Z`가 되고, 1밀리초를 더하면 ‘타임스탬프가 범위를 벗어났습니다.’가 표시됩니다.
