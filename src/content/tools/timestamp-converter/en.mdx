<h2>About Unix Timestamps</h2>
<p>
  The Unix epoch began at 1970-01-01 00:00:00 UTC. Every moment in time is stored
  as an integer offset from that point. Most systems use seconds; JavaScript uses milliseconds.
</p>
<p>
  The 32-bit signed timestamp will overflow (the <em>Year 2038 problem</em>) on
  January 19, 2038. Modern 64-bit systems are not affected.
</p>

## Examples

With the unit set to <strong>Auto unit</strong>, the converter counts the digits before any decimal point: up to 12 digits are seconds, 13–15 milliseconds, 16–18 microseconds, and 19 or more nanoseconds. Present-day values have 10, 13, 16 and 19 digits. The status line says which unit it used; choose a unit from the list to override it.

{/* tsc-check: {"in": ["1700000000", "1700000000123", "2147483647", "1700000000123456", "1700000000123456789"]} */}

| Input | Read as | ISO 8601 (UTC) |
|---|---|---|
| `1700000000` | seconds | `2023-11-14T22:13:20.000Z` |
| `1700000000123` | milliseconds | `2023-11-14T22:13:20.123Z` |
| `2147483647` | seconds | `2038-01-19T03:14:07.000Z` |
| `1700000000123456` | microseconds | `2023-11-14T22:13:20.123Z` |
| `1700000000123456789` | nanoseconds | `2023-11-14T22:13:20.123Z` |

`2147483647` is the largest value a signed 32-bit integer can hold, which is where the Year 2038 problem starts. The last two rows are a microsecond timestamp (Python `time.time_ns() // 1000`, PostgreSQL internals) and a nanosecond one (Go `time.Now().UnixNano()`, `date +%s%N`); digits below the millisecond are dropped, because a JavaScript date holds whole milliseconds. Nanosecond values are larger than 2<sup>53</sup>, so the tool reads them as big integers instead of floating-point numbers.

### What each result row means

{/* tsc-check: {"in": "1700000000", "tz": "Asia/Tokyo", "show": ["s", "ms", "iso", "utc", "local"], "label": true} */}

Converting `1700000000` gives five rows:

| Row | Value | Notes |
|---|---|---|
| Unix (s) | `1700000000` | Whole seconds, rounded down |
| Unix (ms) | `1700000000000` | What `Date.now()` and Java `System.currentTimeMillis()` return |
| ISO 8601 | `2023-11-14T22:13:20.000Z` | Always UTC (`Z`) with milliseconds, from `Date.prototype.toISOString` |
| UTC | `Tue, 14 Nov 2023 22:13:20 GMT` | The HTTP date format of [RFC 9110 §5.6.7](https://www.rfc-editor.org/rfc/rfc9110#section-5.6.7), used in `Date`, `Expires` and `Last-Modified` headers |
| Local (UTC+09:00) | `2023-11-15 07:13:20` | Your computer's time zone; the label shows its offset on that date (here Tokyo) |

### Date to Timestamp across time zones

{/* tsc-check: {"date": "2026-01-01T09:00:00", "tz": ["Asia/Tokyo", "America/New_York"], "show": ["s", "iso"]} */}

The date picker has no time zone field, so the same wall-clock time gives different timestamps on different computers. Picking 2026-01-01 09:00:00 returns `1767225600` (`2026-01-01T00:00:00.000Z`) on a computer set to Asia/Tokyo, and `1767276000` (`2026-01-01T14:00:00.000Z`) on one set to America/New_York. The ISO 8601 row shows which instant you actually selected. To work with a zone other than your own, use the [Timezone Converter](/tools/timezone-converter/).

{/* tsc-check: {"date": "2026-03-08T02:30:00", "tz": "America/New_York", "show": ["s", "iso", "local"], "label": true} */}

Daylight saving time skips an hour in some zones. In America/New_York, clocks jump from 02:00 to 03:00 on the second Sunday in March (`Rule US 2007 max Mar Sun>=8 2:00` in the [tz database](https://github.com/eggert/tz/blob/main/northamerica)), so 02:30 on 2026-03-08 does not exist there. Picking 2026-03-08 02:30:00 on a computer set to that zone still converts, using the offset from before the jump: the result is `1772955000` (`2026-03-08T07:30:00.000Z`), and the Local (UTC-04:00) row shows `2026-03-08 03:30:00`, not the time you picked. That reading follows the UTC(t) operation in [ECMA-262 §21.4.1.26](https://tc39.es/ecma262/#sec-utc-t).

### Accepted input

The timestamp field takes decimal digits with an optional `+` or `-` sign and an optional decimal part. Spaces around the value are ignored, and full-width digits, signs and decimal points typed with a Chinese, Japanese or Korean input method are read as ASCII; the field keeps what you typed.

{/* tsc-check: {"cases": [{"in": "-86400"}, {"in": "1700000000.5", "show": ["ms"]}, {"in": "１７００００００００"}, {"in": "1e9", "error": true}, {"in": "2024-05-01", "error": true}]} */}

- Negative values are dates before 1970: `-86400` is `1969-12-31T00:00:00.000Z`.
- A decimal part adds milliseconds: `1700000000.5` gives `1700000000500`.
- The full-width `１７００００００００` gives the same `2023-11-14T22:13:20.000Z` as `1700000000`.
- Exponent notation is rejected: `1e9` gives “Invalid timestamp. Enter digits with an optional sign and decimal point. For a date, use Date → Timestamp.”
- Dates as text, such as `2024-05-01`, get the same message. Use the date picker for those.

## Do It in Code

```bash
date +%s                      # current timestamp (Linux, macOS)
date -u -d @1700000000        # GNU date (Linux)
date -u -r 1700000000         # BSD date (macOS)
```

```javascript
Math.floor(Date.now() / 1000)          // current timestamp in seconds
new Date(1700000000 * 1000).toISOString()  // "2023-11-14T22:13:20.000Z"
```

```python
import time, datetime
int(time.time())                                                  # current timestamp
datetime.datetime.fromtimestamp(1700000000, datetime.timezone.utc)  # 2023-11-14 22:13:20+00:00
```

## Limits

{/* tsc-check: {"cases": [{"in": "8640000000000000", "unit": "ms"}, {"in": "8640000000000001", "unit": "ms", "error": true}]} */}

- **Automatic unit by length only.** A millisecond value from before 2001-09-09 has 12 digits and is read as seconds, and a seconds value of 13 digits or more (after year 33658) is read as milliseconds. Choose the unit in those cases.
- **Digits only.** Exponents (`1e10`), hexadecimal and thousands separators are rejected; a decimal part is accepted. Full-width digits are read as ASCII, but other digit sets, such as Arabic-Indic digits, are rejected.
- **Date to Timestamp uses your local time zone.** The date picker value is read in your browser's time zone, so the same picker value gives different timestamps on computers set to different zones.
- **No leap seconds.** Unix time ignores leap seconds, as does JavaScript's `Date`.
- **Range.** JavaScript dates cover ±8,640,000,000,000,000 ms from the epoch, about 273,790 years each way ([ECMA-262 §21.4.1.1](https://tc39.es/ecma262/#sec-time-values-and-time-range)). With the unit set to milliseconds, `8640000000000000` converts to `+275760-09-13T00:00:00.000Z`; one more millisecond gives "Timestamp out of range."
