## 실제 예: www.kakao.com 인증서 체인

**예시**를 누르면 2026-10-01에 `openssl s_client -showcerts`로 `www.kakao.com`에서 받은 인증서 3개를 불러옵니다. {/* scd-check: {"chain":"www.kakao.com","field":"count","expect":"3"} */}

| # | 주체 CN | 역할 | 다음 인증서의 서명 |
|---|---|---|---|
| 1 | kakao.com | 서버 인증서 | 서명 검증됨 |
| 2 | Thawte TLS RSA CA G1 | 중간 CA | 서명 검증됨 |
| 3 | DigiCert Global Root G2 | 루트 CA (자체 서명) | 자체 서명 검증됨 |

카카오 서버는 루트 인증서까지 보냅니다. 도구는 "체인이 자체 서명 루트 인증서로 끝납니다"라고 알려 줍니다. 클라이언트는 루트를 이미 갖고 있으므로 보내지 않아도 되고([RFC 8446 §4.4.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.2)), 보내도 오류는 아닙니다.

서버 인증서에서 볼 만한 값:

- 유효 기간 `2026-09-01 00:00:00 UTC` ~ `2027-03-18 23:59:59 UTC`, 길이 **199일**. {/* scd-check: {"chain":"www.kakao.com","field":"days","expect":"199"} */}{/* scd-check: {"chain":"www.kakao.com","field":"notAfter","expect":"2027-03-18 23:59:59 UTC"} */}2026년 3월 15일부터 발급되는 공개 신뢰 TLS 인증서는 최대 200일입니다([CA/B 포럼 BR §6.3.2](https://github.com/cabforum/servercert/blob/main/docs/BR.md), SC-081 투표). 2027년 3월 15일부터는 100일, 2029년 3월 15일부터는 47일로 줄어듭니다.
- SAN 2개. `www.kakao.com`을 입력하면 SAN 항목과 일치한다고 나옵니다. {/* scd-check: {"chain":"www.kakao.com","field":"sanCount","expect":"2"} */}{/* scd-check: {"chain":"www.kakao.com","field":"host","host":"www.kakao.com","expect":"match"} */}
- 인증서 투명성 SCT 3개와 각 로그 ID, 타임스탬프. {/* scd-check: {"chain":"www.kakao.com","field":"sct","expect":"3"} */}

## 중간 인증서가 빠진 서버

같은 날 `www.kisa.or.kr`은 서버 인증서 1개만 보냈습니다. {/* scd-check: {"chain":"www.kisa.or.kr","field":"count","expect":"1"} */}이 인증서를 붙여넣으면 도구는 발급자 GeoTrust TLS RSA CA G1이 입력에 없다고 알리고, AIA에 적힌 `http://cacerts.geotrust.com/GeoTrustTLSRSACAG1.crt`를 보여 줍니다. {/* scd-check: {"chain":"www.kisa.or.kr","field":"caIssuers","expect":"http://cacerts.geotrust.com/GeoTrustTLSRSACAG1.crt"} */}

브라우저는 이 주소로 중간 인증서를 받아 와 화면이 정상으로 보이는 경우가 많습니다. 하지만 [Java](https://docs.oracle.com/en/java/javase/21/security/java-pki-programmers-guide.html)는 이 기능이 기본으로 꺼져 있고, Go의 TLS도 받아 오지 않습니다([golang/go#31773](https://go.dev/issue/31773)). API 서버나 앱에서만 연결 오류가 나면 먼저 중간 인증서 누락을 의심하세요. nginx는 서버 인증서 뒤에 중간 인증서를 이어 붙인 파일을 쓰도록 안내합니다([Configuring HTTPS servers](https://nginx.org/en/docs/http/configuring_https_servers.html)).

체인을 거꾸로 붙여넣으면 "순서가 틀렸거나 다른 체인이 섞였습니다. 서버 인증서부터의 경로: #3 → #2 → #1."처럼 올바른 순서를 알려 주고, **올바른 순서로 복사**로 바로잡은 파일을 얻을 수 있습니다. {/* scd-check: {"chain":"www.kakao.com","field":"reversedPath","expect":"#3 → #2 → #1"} */}

## 검사 항목

- 바깥 서명 알고리즘과 tbsCertificate 안의 알고리즘 일치([RFC 5280 §4.1.1.2](https://www.rfc-editor.org/rfc/rfc5280#section-4.1.1.2)), 일련번호가 양수이고 20옥텟 이하인지(§4.1.2.2), 시각에 초와 `Z`가 있는지(§4.1.2.5).
- 인식할 수 없는 중요 확장, 중복 확장(§4.2).
- SAN이 없는 인증서: Chrome은 [58 버전](https://chromestatus.com/feature/4981025180483584)부터 CN으로 호스트 이름을 비교하지 않습니다.
- SHA-1·MD5 서명, 2048비트 미만 RSA 키, 발급자가 CA가 아니거나 keyCertSign이 없거나 경로 길이를 넘는 경우.

공개 키 길이는 키 자체에서 계산합니다(P-521은 521비트). 지문 카드에는 DER의 SHA-256·SHA-1·MD5와 공개 키(SPKI)의 SHA-256 Base64 값이 있습니다. [RFC 7469](https://www.rfc-editor.org/rfc/rfc7469#section-2.4)의 pin-sha256 형식으로, Android 네트워크 보안 구성과 OkHttp 인증서 고정에 그대로 쓸 수 있습니다.

## 입력 형식

- PEM `CERTIFICATE`, 예전 표기 `X509 CERTIFICATE`, OpenSSL의 `TRUSTED CERTIFICATE`([RFC 7468](https://www.rfc-editor.org/rfc/rfc7468)). 앞뒤 문장, CRLF, 여분의 공백은 무시합니다.
- BEGIN / END 줄 없는 Base64.
- 바이너리 DER 파일과 PKCS #7(`.p7b`). 불러오면 PEM으로 바꿔 입력란에 보여 줍니다.
- CSR, 공개 키, CRL은 종류만 알려 주고 분석하지 않습니다. CSR은 [CSR 디코더](/ko/tools/csr-decoder/)를 쓰세요.

오류는 위치를 알려 줍니다. 위 서버 인증서를 복사하다 Base64 한 줄이 빠지면 "0번째 바이트의 Certificate는 1618바이트가 필요하지만 1570바이트만 남았습니다"라고 나옵니다. {/* scd-check: {"chain":"www.kakao.com","field":"cutNeed","expect":"1618"} */}{/* scd-check: {"chain":"www.kakao.com","field":"cutHave","expect":"1570"} */}

## 제한 사항

- 신뢰 저장소가 없고, OCSP / CRL 폐기 확인과 서버 연결도 하지 않습니다. 체인은 `openssl s_client -connect 도메인:443 -showcerts`로 받고, DNS는 [DNS Lookup](/ko/tools/dns-lookup/), 응답 헤더는 [HTTP Header 분석기](/ko/tools/http-header-analyzer/)로 확인하세요.
- 서명 검증은 Web Crypto로 합니다. RSA(PKCS #1 v1.5, PSS), P-256 / P-384 / P-521 ECDSA, 브라우저가 지원하면 Ed25519까지입니다. ML-DSA, Ed448, DSA, SM2는 분석하지만 "미검증"으로 표시합니다.
- 이름 제약은 표시만 하고 서버 인증서 이름에 적용하지 않습니다.
- 파일은 1MB까지, 한 번에 인증서 200개까지 처리합니다.
