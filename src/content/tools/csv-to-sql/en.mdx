<h2>How Values Are Written</h2>
<ul>
  <li>Empty CSV fields produce <code>NULL</code>.</li>
  <li>A column whose non-empty cells are all plain numbers (<code>42</code>, <code>-7</code>, <code>19.90</code>) is written without quotes. A plain number has no leading zero, no <code>+</code>, no exponent and at most 15 digits.</li>
  <li>Every other column is written as quoted strings, including its numbers, so <code>02134</code>, <code>1e5</code> and a 20-digit card number keep their exact text. MySQL, PostgreSQL and SQLite all convert a quoted number when the target column is numeric.</li>
  <li>Single quotes are doubled (<code>O''Brien</code>) in every dialect. In MySQL, backslashes are doubled too: MySQL's default SQL mode reads <code>\n</code> inside a string as a newline (<a href="https://dev.mysql.com/doc/refman/8.4/en/string-literals.html" target="_blank" rel="noopener">MySQL 8.4 Reference Manual, String Literals</a>, Table 11.1). PostgreSQL with <code>standard_conforming_strings</code> on (the default since 9.1, <a href="https://www.postgresql.org/docs/current/sql-syntax-lexical.html#SQL-SYNTAX-STRINGS" target="_blank" rel="noopener">PostgreSQL 4.1.2.1</a>) and SQLite store backslashes as written.</li>
  <li>Cells beyond the header get extra columns named <code>column_3</code>, <code>column_4</code> and so on, and the status line lists them. Short rows are padded with <code>NULL</code>.</li>
</ul>

<h2>Example: Quotes, Leading Zeros and Empty Fields</h2>

<p>Input (SQLite, batch mode, table <code>customers</code>):</p>

{/* sql: {"dialect":"sqlite","table":"customers","mode":"batch"} */}

<pre><code>{`id,name,zip,note
1,"O'Brien, Pat",02134,
2,Lee,10001,"path C:\\new"`}</code></pre>

<pre><code>{`INSERT INTO "customers" ("id", "name", "zip", "note") VALUES
  (1, 'O''Brien, Pat', '02134', NULL),
  (2, 'Lee', '10001', 'path C:\\new');`}</code></pre>

<p>The quoted field <code>"O'Brien, Pat"</code> keeps its comma. The empty <code>note</code> becomes <code>NULL</code>. <code>02134</code> makes the zip column a text column, so <code>10001</code> is quoted as well. Run against SQLite 3, <code>SELECT zip FROM customers</code> returns <code>02134</code> and <code>10001</code>.</p>

<p>The same input in MySQL doubles the backslash, so the stored value is still <code>path C:\new</code>:</p>

{/* sql: {"dialect":"mysql","table":"customers","mode":"batch"} */}

<pre><code>{`id,name,zip,note
1,"O'Brien, Pat",02134,
2,Lee,10001,"path C:\\new"`}</code></pre>

<pre><code>{`INSERT INTO \`customers\` (\`id\`, \`name\`, \`zip\`, \`note\`) VALUES
  (1, 'O''Brien, Pat', '02134', NULL),
  (2, 'Lee', '10001', 'path C:\\\\new');`}</code></pre>

<p>If your server runs with <code>NO_BACKSLASH_ESCAPES</code> in <code>sql_mode</code>, backslashes are ordinary characters; use the PostgreSQL or SQLite output for that server instead.</p>

<h2>Example: CREATE TABLE</h2>

<p>With <strong>Add CREATE TABLE</strong> ticked, column types are chosen from the values: whole numbers become <code>INTEGER</code> (<code>INT</code> in MySQL, <code>BIGINT</code> beyond 2,147,483,647), numbers with a decimal point become <code>DOUBLE PRECISION</code> (<code>DOUBLE</code> in MySQL, <code>REAL</code> in SQLite), everything else <code>TEXT</code>. PostgreSQL:</p>

{/* sql: {"dialect":"postgresql","table":"orders","mode":"batch","createTable":true} */}

<pre><code>{`order_id,amount,paid_at
1001,19.90,2026-09-30
1002,5,`}</code></pre>

<pre><code>{`CREATE TABLE "orders" ("order_id" INTEGER, "amount" DOUBLE PRECISION, "paid_at" TEXT);
INSERT INTO "orders" ("order_id", "amount", "paid_at") VALUES
  (1001, 19.90, '2026-09-30'),
  (1002, 5, NULL);`}</code></pre>

<p>Change the types before running it when they matter: money belongs in <code>NUMERIC</code> / <code>DECIMAL</code>, and dates such as <code>paid_at</code> in <code>DATE</code> or <code>TIMESTAMP</code>. No primary key or constraints are added.</p>

<h2>Example: More Cells Than Headers</h2>

{/* sql: {"dialect":"sqlite","table":"stock","mode":"individual"} */}

<pre><code>{`sku,qty
A-1,3,fragile
B-2,5`}</code></pre>

<pre><code>{`INSERT INTO "stock" ("sku", "qty", "column_3") VALUES ('A-1', 3, 'fragile');
INSERT INTO "stock" ("sku", "qty", "column_3") VALUES ('B-2', 5, NULL);`}</code></pre>

<p>The status line reports the added column <code>column_3</code>. Rename it in the header row if you want a real name.</p>

<h2>Example: Repeated Header Names and Stray Quotes</h2>

<p>A header row from a spreadsheet can repeat a name or leave the last cell empty. Every column still gets its own name (SQLite, Add CREATE TABLE, table <code>stock</code>):</p>

{/* sql: {"dialect":"sqlite","table":"stock","mode":"batch","createTable":true} */}

<pre><code>{`sku,qty,qty,
A-1,3,4,boxed
B-2,5,,`}</code></pre>

<pre><code>{`CREATE TABLE "stock" ("sku" TEXT, "qty" INTEGER, "qty_2" INTEGER, "column_4" TEXT);
INSERT INTO "stock" ("sku", "qty", "qty_2", "column_4") VALUES
  ('A-1', 3, 4, 'boxed'),
  ('B-2', 5, NULL, NULL);`}</code></pre>

{/* cts-status: {"csv":"sku,qty,qty,\nA-1,3,4,boxed\nB-2,5,,"} */}

<p>The status line lists the new names:</p>

<pre><code>{`Duplicate or empty header names were renamed: qty → qty_2, "" → column_4.`}</code></pre>

<p>The second <code>qty</code> becomes <code>qty_2</code>, and the empty fourth header becomes <code>column_4</code> (its position). Names are compared without case, so <code>Name</code> and <code>name</code> also count as the same name: MySQL column names are not case-sensitive (<a href="https://dev.mysql.com/doc/refman/8.4/en/identifier-case-sensitivity.html" target="_blank" rel="noopener">MySQL 8.4, Identifier Case Sensitivity</a>), and SQLite rejects <code>"Name"</code> and <code>"name"</code> in one table. Quoted names are case-sensitive in PostgreSQL, but the tool renames them in the same way, so the three dialects get the same column names. A new name never takes a name that is already in the header: <code>a,a,a_2</code> gives <code>a</code>, <code>a_3</code>, <code>a_2</code>.</p>

{/* sql: {"dialect":"sqlite","table":"stock","mode":"batch","createTable":true} */}

<pre><code>{`item,size
monitor,27" wide`}</code></pre>

<pre><code>{`CREATE TABLE "stock" ("item" TEXT, "size" TEXT);
INSERT INTO "stock" ("item", "size") VALUES
  ('monitor', '27" wide');`}</code></pre>

<p>Only a double quote at the start of a field opens a quoted field. A quote inside an unquoted field, like the inch mark in <code>{'27" wide'}</code>, is an ordinary character. A quoted field that is never closed stops the conversion:</p>

{/* cts-status: {"csv":"sku,note\nA-1,\"fragile\nB-2,ok"} */}

<pre><code>{`sku,note
A-1,"fragile
B-2,ok`}</code></pre>

<pre><code>{`A quoted field that starts on line 2 is never closed. Add the closing " or remove the opening one.`}</code></pre>

<p>The line number counts the lines in CSV Input, blank lines at the top included. The SQL output stays empty until the quote is fixed.</p>

<h2>Limits</h2>
<ul>
  <li>The delimiter is a comma, and the first row is always the header. Semicolon or tab separated files need converting first.</li>
  <li>Types are guessed from the text only. Dates, booleans and <code>1e5</code> are strings.</li>
  <li>Table and column names are quoted as single identifiers, so <code>public.users</code> becomes one name with a dot in it.</li>
  <li>Large files are converted in the browser tab in one pass; for millions of rows use the database's bulk loader (<code>LOAD DATA</code>, <code>COPY</code>, <code>.import</code>).</li>
  <li>Upload CSV reads UTF-8 files only. A file in another encoding is not loaded, and the status line gives the first byte that is not UTF-8 (counting from 0); a UTF-16 file is reported as UTF-16, and a binary file by its first NUL byte.</li>
  <li>A quoted field that is never closed stops the conversion with its line number; a quote inside an unquoted field is kept as text.</li>
  <li>Repeated header names (compared without case) get <code>_2</code>, <code>_3</code>, and empty header cells get <code>column_N</code>; the status line lists them. Other names are used as written, spaces included: in MySQL a column name cannot end with a space, and characters outside the Basic Multilingual Plane, such as emoji, are not allowed in names (<a href="https://dev.mysql.com/doc/refman/8.4/en/identifiers.html" target="_blank" rel="noopener">MySQL 8.4 Reference Manual, Schema Object Names</a>).</li>
  <li>Only a byte order mark, blank lines at the top and line breaks at the end are removed from the input. Spaces at the start or end of a header or a cell are kept as they are.</li>
</ul>
